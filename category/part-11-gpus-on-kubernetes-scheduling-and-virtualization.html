Part 11: GPUs on Kubernetes, scheduling and virtualization

30 chapters. Default priority tier 1.

📄️11.1 Why Kubernetes needs a GPU platform layer

Why standard CPU-era Kubernetes cannot operate GPUs natively: the Two-Path Agreement Model, the six-layer false-positive matrix, 32-GPU pool fragmentation math, whole-GPU underutilization, the GPU software lifecycle dependency graph, combinatorial vs profile-based qualification, GPU Operator ownership models, and the five-gate node acceptance protocol.

📄️11.2 Device plugin, container toolkit, CDI and runtime classes

How the Kubernetes device plugin gRPC contract, NVIDIA Container Toolkit, Container Device Interface, and RuntimeClass turn a scheduled extended resource into a working CUDA container.

📄️11.3 Node Feature Discovery and GPU Feature Discovery

How Node Feature Discovery (NFD) and GPU Feature Discovery (GFD) transform raw PCIe, CPU, and NVML hardware signals into governed Kubernetes scheduling metadata and portable service classes.

📄️11.4 GPU Operator architecture and operands

How the NVIDIA GPU Operator reconciles ClusterPolicy desired state into privileged node DaemonSets, init-container validation chains, driver containers, and bounded canary rollouts.

📄️11.5 GPU Operator installation, configuration and upgrades

Production installation boundaries, GitOps Helm values governance, seven-gate pool acceptance, staged canary upgrades across hardware batches, and coherent host-plus-chart rollback.

📄️11.6 Scheduling GPUs: requests, Topology Manager, CPU and NUMA alignment

How Kubernetes schedules GPU workloads across capacity, eligibility, locality, and coordination boundaries using CPU Manager, Topology Manager, NUMA pinning, and PCIe/NVLink data-path alignment.

📄️11.7 Multi-node jobs: why a pod cannot span nodes, and gang scheduling concepts

Why a Kubernetes Pod is bounded to a single node, how partial Pod placement deadlocks PyTorch rendezvous barriers, and how gang scheduling, bin packing, descheduling, and backfill queues solve multi-node GPU orchestration.

📄️11.8 Kueue, Volcano and scheduler plugins

Deep dive into the Kubernetes Scheduling Framework (Reserve and Permit gates), the Coscheduling PodGroup plugin, Kueue (ResourceFlavor, ClusterQueue, LocalQueue, Cohorts, and Flavor Fungibility), and Volcano batch scheduling.

📄️11.9 JobSet, LeaderWorkerSet, PyTorchJob and the MPI Operator

How Kubernetes workload APIs and operators—JobSet, LeaderWorkerSet, Kubeflow PyTorchJob, Kubeflow Trainer v2, and the MPI Operator—orchestrate multi-node training and sharded inference.

📄️11.10 Secondary networks: Multus, SR-IOV device plugin and RDMA device plugin

How Kubernetes primary CNIs (Calico, Cilium eBPF), Multus CNI, Whereabouts IPAM, the RDMA Shared Device Plugin, and the SR-IOV Network Device Plugin expose GPUDirect RDMA over InfiniBand and RoCEv2 into multi-homed GPU Pods.

📄️11.11 NVIDIA Network Operator

How the NVIDIA Network Operator (NicClusterPolicy) reconciles MOFED/DOCA-OFED drivers, nvidia-peermem, RDMA and SR-IOV device plugins, and Multus secondary networks across InfiniBand, RoCEv2, and GPUDirect Storage fabrics.

📄️11.12 Dynamic Resource Allocation (DRA)

How Kubernetes Dynamic Resource Allocation (DRA, resource.k8s.io/v1 in Kubernetes 1.34) replaces opaque integer device plugins with structured ResourceSlices, DeviceClasses, and ResourceClaimTemplates, alongside Kubelet PLEG, CSI, and control-plane OCC mechanics.

📄️11.13 KAI Scheduler: why default scheduling is not enough

Why the default Kubernetes scheduler fails on multi-tenant, bimodal AI clusters, and how NVIDIA KAI Scheduler (open-sourced from Run:ai) unifies Project fair-share quotas, gang scheduling, fractional GPUs, and NVLink/InfiniBand topology placement.

📄️11.14 KAI Scheduler architecture and resources

Inside the NVIDIA KAI Scheduler control-plane microservices (pod-grouper, queue-controller, kai-scheduler, binder, and admission webhooks), Custom Resource Definitions (Project, Queue, PodGroup, Topology, BindRequest), and the session-based batch scheduling pipeline.

📄️11.15 KAI queues, quotas and fair sharing

How NVIDIA KAI Scheduler structures hierarchical Department-to-Project queues, computes proportional over-quota borrowing, reclaims lent GPUs, and ties fair sharing to capacity planning and showback/chargeback.

📄️11.16 KAI gang scheduling and topology-aware placement

How NVIDIA KAI Scheduler unifies atomic PodGroup gang scheduling with multi-level hardware topology placement across NUMA islands, NVSwitch nodes, NVL72 racks, and InfiniBand leaf switches.

📄️11.17 KAI GPU sharing and fractions

How NVIDIA KAI Scheduler implements fractional GPU allocation (gpu-fraction and gpu-memory), reservation pods, and dynamic bin-packing alongside Kubernetes time-slicing and Multi-Instance GPU (MIG).

📄️11.18 KAI operations and troubleshooting

Operating, monitoring, and troubleshooting NVIDIA KAI Scheduler and shared GPU clusters across hardware, MIG/time-slicing state, registration, scheduling policy, runtime binding, and service SLOs.

📄️11.19 The Run:ai platform view

How the enterprise NVIDIA Run:ai platform layers multi-cluster governance, department/project hierarchies, workload portals, and multi-tenant security above the KAI Scheduler engine.

📄️11.20 Scheduler comparison guide: KAI, Kueue, Volcano, YuniKorn and Slurm

Architectural comparison and decision guide across NVIDIA KAI Scheduler, Kueue, Volcano, Apache YuniKorn, Scheduler-Plugins Coscheduling, and bare-metal Slurm.

📄️11.21 PCIe, IOMMU, VFIO and device passthrough

How PCIe root complexes, switches, NUMA boundaries, IOMMU DMA remapping, and Linux VFIO enable secure bare-metal-speed GPU and NIC passthrough across hardware VMs, containers, and lightweight microVMs.

📄️11.22 SR-IOV for NICs and GPUs

How Single-Root I/O Virtualization slices ConnectX RDMA NICs and NVIDIA GPUs into hardware-isolated Virtual Functions, and how to secure and forensically operate SR-IOV AI clusters.

📄️11.23 NVIDIA vGPU: architecture, profiles and licensing

Designing, licensing, and operating NVIDIA vGPU across VMware ESXi, KVM, and KubeVirt: the two-path driver architecture, time-sliced vs MIG-backed vGPU profiles, NLS entitlement, and the validation suite.

📄️11.24 MIG in depth

Deep dive into NVIDIA Multi-Instance GPU (MIG): GPU Instances (GIs) vs Compute Instances (CIs), silicon memory-path partitioning, profile placement geometry, 24-node H100 fleet sizing, DCGM telemetry, and node lifecycle runbooks.

📄️11.25 Time-slicing, MPS and oversubscription

Deep dive into software GPU sharing on Kubernetes: device-plugin time-slicing, CUDA Multi-Process Service (MPS), replica-ratio benchmarking, and oversubscription governance.

📄️11.26 Choosing a GPU sharing model

How to choose among Dedicated Whole GPUs, Multi-Instance GPU, NVIDIA vGPU, Time-Slicing, and CUDA MPS, and how to build the capacity, reserve, and chargeback model around your choice.

📄️11.27 Virtual machines on Kubernetes: KubeVirt, Kata and GPU passthrough

Running GPU-accelerated Virtual Machines and MicroVMs on Kubernetes using KubeVirt, Kata Containers, NVIDIA GPU Operator VFIO/vGPU operands, and Confidential Computing.

📄️11.28 DPUs, BlueField and DOCA

Evaluating, securing, and operating NVIDIA BlueField Data Processing Units (DPUs) and the DOCA software framework across AI Ethernet and Kubernetes clusters.

📄️11.29 Multi-tenancy, quotas, fault tolerance and health on GPU clusters

Production Day-2 operations for multi-tenant GPU clusters: compute/network/storage isolation, IRSA workload identity, FinOps zombie reapers, rolling driver upgrades, Thanos observability, WORM disaster recovery, and the Universal AI SRE Diagnostic Matrix.

📄️11.30 Lab: multi-node GPU Kubernetes on GKE and Nebius

Capstone hands-on lab for Part 11: provisioning, validating, networking, and autoscaling multi-node GPU Kubernetes clusters on Nebius GPU, Google Kubernetes Engine (GKE), and Amazon EKS.

📄️11.31 NVIDIA's open-source AI factory stack (NVKE and more)

Which NVIDIA Kubernetes projects are open source in November 2026, what each one does, how NVKE, NVKR, AICR, NVCRE, GPU Operator, Run:ai and KAI, Grove, Dynamo and NVSentinel fit together, and how mature each one is.

📄️11.32 NVKE part 1: architecture, API, cluster spec

NVIDIA Kubernetes Engine (NVKE) in November 2026: the problem it solves, the management plane architecture, how a cluster request becomes work, the REST API catalog with real responses from a locally run controller, and the cluster and node pool specification field by field.

📄️11.33 NVKE part 2: install, NVKR, NICo, lifecycle

How to install the NVKE management plane step by step, how NVKR builds the artifacts, how NICo and CAPNICo provision bare metal, and runbooks to create a cluster, add a pool, upgrade Kubernetes and replace a failed GPU node, with validated examples.
