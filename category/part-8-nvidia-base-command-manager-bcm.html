Part 8: NVIDIA Base Command Manager (BCM)

16 chapters. Default priority tier 1b.

📄️8.1 BCM architecture and concepts

What NVIDIA Base Command Manager is and why a cluster needs one: head node, regular nodes, CMDaemon, the front ends Base View and cmsh, and the object model of devices, software images, categories, node groups, roles and configuration overlays, with the exact inheritance and priority rules from the manual, tested in a small model

📄️8.2 Planning and installing BCM

How to plan a BCM install before touching a server: hardware and head-node sizing, the three network topologies, node naming and IP offsets, disk layout, licensing, the install path (ISO or Ansible), first boot and adding nodes, then burn-in testing and the SELinux warning, with the manual's numbers reproduced in a small tested planner

📄️8.3 Cluster configuration: networks, nodes and categories

How a BCM cluster is configured after install: cluster-wide settings, the network objects and who overrides whom, interfaces, bridges, VLANs and bonds, disk layouts, NFS exports and mounts, services, racks, GPU settings, and the safe ways to go beyond what CMDaemon does, with the manual's rules reproduced in a tested model

📄️8.4 Node provisioning: images, kernels, categories and the PXE flow

How a blank node becomes a working cluster member in BCM: PXE and the boot menu, the 13 steps of the node installer, install modes and why NOSYNC is not data protection, how new nodes are identified, provisioning nodes at scale, software images and kernels, live image updates and exclude lists, node states, and a troubleshooting checklist, with the manual's rules reproduced in a tested model

📄️8.5 cmsh and Base View: administering the cluster

How to drive a BCM cluster day to day: the Base View web GUI, the cmsh shell, its modes and objects, the commit model with asterisks, node list syntax, foreach and range, cloning and renaming, scripting and output formats, and the CMDaemon behind both, with the manual's sessions reproduced in a tested cmsh simulator

📄️8.6 Users, authentication and security in BCM

Who can do what on a BCM cluster: cluster users and groups in BCM's LDAP, passwords, SSH, the certificates and profiles that control cmsh and Base View, external LDAP and Keycloak, audit logging, and a security checklist that gathers the settings from chapters 8.2 to 8.5, with the manual's rules reproduced in a tested model

📄️8.7 Power, BMC and hardware management in BCM

How BCM turns servers on and off and looks after the hardware under the operating system: power control methods and scheduling, BMC networks and credentials, identifying nodes, BIOS settings with their four states, firmware flashing with AC-power-cycle activation, serial over LAN, hardware inventory and leak detection, with the manual's rules reproduced in a tested model

📄️8.8 Workload managers under BCM: Slurm setup

How BCM installs and runs Slurm: forcing jobs through the scheduler, cm-wlm-setup, the server, client, submit and accounting roles as configuration overlays, the GPU client overlay priority trap, GPU autodetection, nodesets and queues, high availability, Pyxis and Enroot containers, cgroups, draining and upgrades, with the manual's rules reproduced in a tested model

📄️8.9 Kubernetes under BCM: deployment and GPU enablement

How BCM deploys and manages Kubernetes: the reference architecture, cm-kubernetes-setup, node roles and overlays, networking and add-ons, operators including the NVIDIA GPU and Network operators, kubelet GPU defaults, users and Kyverno policies, Gateway access, and upgrades, with the manual's rules reproduced in a tested model

📄️8.10 Containerization in BCM: Docker, Apptainer and Enroot

How containers fit into a BCM cluster: the cluster's container tools side by side, Docker via cm-docker-setup and the DockerHost role, container registries (Docker Registry as a Docker Hub cache, and Harbor), the Enroot and Pyxis setup that BCM integrates with Slurm, and Apptainer, which the BCM manuals do not cover, with a decision guide and a tested checklist model

📄️8.11 Monitoring, health checks and alerts in BCM

How BCM watches a cluster: measurables and data producers, metrics, enummetrics and health checks, triggers with enter, leave, during and flapping actions, severities and AlertLevel, built-in actions, GPU and DCGM health checks, consolidation and scale, and a safe design for automatic remediation, with the manual's trigger rules reproduced in a tested model

📄️8.12 High availability and head node failover

How BCM keeps a cluster running when a head node fails: the active and passive pair, shared IPs and storage, what runs on both heads and what migrates, fencing, quorum and STONITH, automatic and manual failover, building the pair with cmha-setup, testing safely, keeping the heads in sync, and HA for regular nodes, with the manual's decision rules reproduced in a tested model

📄️8.13 Day-2 operations: updates, scaling, hardware replacement, disaster recovery

Running a BCM cluster after it is built: version numbers and update rules, running commands on many nodes safely, getting support with cm-diagnose, backups and database recovery, image revision control, checking new hardware, replacing nodes, scaling out, Ansible, and change runbooks, with the manual's rules reproduced in a tested model

📄️8.14 Air-gapped installation and upgrades

How to build and upgrade BCM and Kubernetes on a cluster with no internet: what you prepare on a connected host, the bundle of packages, images, charts and CRDs, the ordered steps on the active head node, the local registry, Run:ai, version skew rules for upgrades, and offline options for the rest of BCM, with the manuals' rules reproduced in a tested checker

📄️8.15 BCM in an AI factory: DGX SuperPOD integration

Where BCM sits in a DGX SuperPOD: scalable units, the four networks, the software stack with Mission Control, and the power and cooling arithmetic that decides how many systems a rack can take, with the numbers from NVIDIA's GB300 reference architecture and B200 data center deck reproduced and checked in a small calculator

📄️8.16 Mission Control, DGX Cloud and autonomous recovery concepts

How NVIDIA Mission Control, the Run:ai Operator, autonomous recovery profiles, head-node HA database replication, and DGX Cloud fit into a BCM-managed AI factory, with a tested checker for the configuration and prerequisite rules.
