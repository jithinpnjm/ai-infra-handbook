Why this matters for AI infrastructure​

Picture a Monday morning when a marketing email doubles the traffic to your chat API within minutes. On a normal web service, the autoscaler sees the CPU climb, adds a few containers, and the page loads again before most people notice. Stateless web microservices scale predictably on CPU and memory utilization, because a stateless service keeps no data between requests. When incoming HTTP traffic doubles, processor usage rises proportionally. A Kubernetes HorizontalPodAutoscaler then launches lightweight containers that become ready in a few seconds. The same reflex fails for a language model, and the rest of this chapter explains why. Large language model serving breaks every assumption behind that traditional control loop.

Start with what a serving engine does on a GPU node. In a modern serving engine such as vLLM, SGLang, or TensorRT-LLM, the host CPU only parses HTTP requests, runs fast tokenization, and dispatches asynchronous GPU kernels. Meanwhile, the engine pre-allocates nearly all GPU High-Bandwidth Memory at startup to store model weights and the PagedAttention KV cache pool. PagedAttention is the scheme that stores the Key-Value cache in fixed-size blocks, so the memory can be shared and reused. A single active user streaming tokens in a continuous batching loop keeps the GPU kernel engine active nearly 100 percent of the time. So the two signals that a normal autoscaler reads, CPU and memory, stop telling you much about how busy the model really is.

Wiring standard CPU, memory, or raw GPU utilization metrics into an untuned autoscaler triggers three severe production failures. Each one looks reasonable on paper, which is why they keep showing up in real clusters.

  • Single-request thrashing and premature scale-out: One request drives GPU activity near 100 percent, so an autoscaler watching raw GPU utilization scales the deployment to its maximum replica ceiling during light traffic. Conversely, a tiny queue threshold of 5 on a fast 8B model causes a brief burst of 50 requests to trigger eight new GPU pods. Those pods take 60 seconds to boot, long after the original two pods cleared the burst in under two seconds. The autoscaler reacted to a burst that was already over, and the new pods arrived to an empty queue.
  • Scale-down amputation during micro-lulls: By default, the Kubernetes HorizontalPodAutoscaler can remove 100 percent of excess replicas every 15 seconds after a 300-second window. Terminating a multi-GPU pod takes seconds, but replacing it when traffic returns requires minutes of weight loading. Brief traffic dips therefore turn into prolonged latency outages. A lull that lasts a few seconds costs you a pod that takes minutes to get back.
  • Shared-storage probe cascades: When an autoscaler launches eight new Llama-3-70B pods at once and each pod pulls 140 GB of weights from a shared NFS volume, storage bandwidth saturates. NFS is a network file share that many machines mount at the same time. If existing pods use a tight one-second readiness probe on the main engine thread, transient I/O stalls cause Kubernetes to mark all healthy pods unready. A readiness probe is the health check that tells Kubernetes whether a pod should receive traffic. The cluster then drops 100 percent of user traffic. The scale-out meant to help is what took the service down.

Autoscaling LLM inference requires replacing hardware utilization signals with queue depth, KV cache saturation, and token latency metrics, while pairing asymmetric scale-down policies with sub-minute weight streaming.

1. Why Legacy Autoscaling Signals Fail for LLM Serving​

1.1 The Decoupling of CPU, Memory, and GPU Activity​

Think about a normal web application first. Every incoming HTTP request allocates heap memory and consumes CPU cycles in proportion to the work it does. The heap is the memory a program uses for data that lives beyond a single function call. When concurrency rises, both CPU and memory climb in a straight line, so a graph of either one tells you how loaded the service is. LLM inference engines invert this relationship. They isolate token generation inside pre-allocated GPU memory pools, so the memory graph goes flat even when the service is very busy. That flat line is the first thing that confuses people who try to scale a model the way they scale a web app.

Here is what the flat line looks like at startup. When vLLM starts on an 80 GB GPU with --gpu-memory-utilization 0.90, it profiles the model and reserves 90 percent of physical VRAM before serving a single user request. Profiling here means running a test pass so the engine can measure how much memory the model really needs. On an H100 reporting 79.14 GiB of usable device memory, vLLM claims 71.22 GiB at startup. For an 8B parameter model in 16-bit precision, the weights consume 14.99 GiB, peak PyTorch activations take 1.19 GiB, and the remaining 54.93 GiB is locked into the PagedAttention KV cache pool. The engine has claimed that memory on purpose, so an empty server and a full server look identical from the outside.

Because those KV blocks remain reserved by the process for its entire lifetime, container memory metrics and DCGM_FI_DEV_FB_USED report a flat 90 percent utilization whether the pod is idle or serving 64 concurrent streams. Host CPU utilization is equally flat when sized properly. Once a Rust tokenizer and asynchronous API server are in place, host CPU usage stays below 35 percent even when the GPU KV cache is full. Ironically, if an engineer under-provisions host CPU cores for the HTTP layer, the pod throttles on CPU before requests ever reach the GPU, preventing a GPU-based autoscaler from ever firing. The bottleneck then sits in a place your GPU metrics cannot see, which is why the CPU limits of the pod deserve a look too.

1.2 Why DCGM_FI_DEV_GPU_UTIL Misleads Under Continuous Batching​

When teams realize CPU and memory remain flat, their first instinct is to scale on DCGM_FI_DEV_GPU_UTIL exported by NVIDIA DCGM Exporter. DCGM is NVIDIA's data center GPU manager, and the exporter turns its readings into Prometheus metrics. The number looks like a good signal, since it climbs when the GPU is busy. In production LLM serving, raw GPU utilization is a trap.

DCGM_FI_DEV_GPU_UTIL measures the percentage of time over a sampling interval during which at least one CUDA kernel was executing on any Streaming Multiprocessor. A kernel is one unit of GPU work, and a Streaming Multiprocessor is one of the GPU's internal compute blocks. The metric does not measure how many Streaming Multiprocessors are occupied or how full the matrix multiplication tiles are. Under iteration-level continuous batching, a single user generating a 500-token response forces the GPU to run 500 consecutive decode steps back to back. During those several seconds, a CUDA kernel runs on the GPU nearly 100 percent of the time, even though 98 percent of the GPU compute units sit idle waiting for HBM weight reads. So the graph reads as full while the chip is mostly waiting on memory. An autoscaler that trusts this line will add pods to a model that is nowhere near capacity.

To distinguish between a lightly loaded GPU running a single decode stream and a truly saturated GPU, operators must separate engine-level queue and cache metrics from low-level DCGM hardware counters. Engine-level metrics describe what the serving software is holding, such as who is waiting and how full the cache is. Hardware counters describe what the silicon is doing at a given instant. Each kind answers a different question, and a scaler needs the first kind to decide when users are waiting. The table below lists the metrics side by side, with the value you should expect at a single request and at a full batch, so you can recognize the pattern on your own dashboard.

Pipeline parallelism adds a second trap for hardware utilization metrics. When a model is partitioned across nodes using pipeline parallelism, the model is cut into stages, and each stage lives on a different group of GPUs. Sequential stage dependencies introduce pipeline bubbles where downstream GPUs briefly wait for upstream activations. A bubble is an idle gap, and it is the price of passing work along a chain. Consequently, average GPU utilization across a pipeline-parallel group never reaches 100 percent even when the admission queue is overflowing. The gauge stays below full, and a team reading only that gauge would conclude the service has room to spare when the queue says otherwise.

Before you configure any autoscaler for an LLM service, remove CPU, memory, and DCGM_FI_DEV_GPU_UTIL from its scaling triggers and expose the serving engine metrics endpoint to Prometheus. Prometheus is the system that will store and query those numbers, so the engine has to publish them there first. The table earlier in this section works well as a checklist for which signal to keep and which one to drop. Before you trust a new trigger, open the engine's metrics endpoint in a browser or with curl, find the metric by name, and watch it move during a small test. A metric you have never seen change is a metric you cannot yet trust to scale a fleet.

2. Custom Prometheus Metrics: Queue Depth, KV Cache, and Latency SLIs​

2.1 Scaling on Scheduler Queue Depth (vllm:num_requests_waiting)​

Every production LLM serving engine maintains two internal scheduling queues. The RUNNING queue holds sequences actively using PagedAttention KV blocks in the current continuous batch. The WAITING queue holds newly arrived requests waiting for either token budget or free KV cache blocks. In vLLM, these queues are exported on /metrics as vllm:num_requests_running and vllm:num_requests_waiting.

Picture a scale-out rule that says "add a replica as soon as one request waits." It sounds careful, and it is quietly expensive. A GPU replica gets faster per token when it has a full batch to work on. If your autoscaler adds a new GPU replica the moment a single request waits, each replica runs with a realized batch size near 1, and the GPUs barely share their work. A golden rule of LLM cost engineering is therefore to never scale up at a queue depth of 1. That configuration ruins GPU throughput and inflates cost per million tokens by an order of magnitude. Instead, each GPU replica should fill its active batch first and accumulate a modest admission queue before spawning additional replicas. The queue is the buffer that tells you the batch is full.

In a multi-replica deployment, querying the raw sum of waiting requests is insufficient. A raw total of waiting requests means very different things for a small deployment and for a large one, so you must normalize the backlog by the number of active replicas. Dividing by the replica count turns the total into a per-replica backlog that you can compare with a fixed threshold. The standard PromQL trigger query divides total waiting requests by the count of running instances. PromQL is the query language Prometheus uses, and sum and count are its functions for adding up a set of series and counting them. Read the query from the inside out. The first part adds all the waiting requests across the model's pods, the second part counts how many replicas are running, and the division gives the average backlog each replica is carrying. That average is the number you compare with the target.

PromQL Queue-Depth Trigger for vLLM (Volume 5, Chapter 3):
  Query:
    sum(vllm:num_requests_waiting{model_name="llama3-70b"})
    /
    count(vllm:num_requests_running{model_name="llama3-70b"})
  Target Threshold: 20 waiting requests per active replica

PromQL Bottleneck Queue Delay Trigger for NVIDIA Triton Inference Server (Volume 5, Chapter 3 Appendix):
  Query:
    sum(nv_inference_queue_duration_us{model="vision-trt"})
    /
    sum(nv_inference_request_success{model="vision-trt"}) > 500000
  Target Threshold: 500,000 microseconds (0.5 seconds average queue wait)
  Engine Context: Paired with dynamic_batching { preferred_batch_size: [32, 64, 128], max_queue_delay_microseconds: 50000 }

Triton is more subtle than vLLM, because a Triton deployment can chain several models together in one ensemble. Do not scale the deployment on the front-end ensemble wrapper, since the wrapper does not show which model is actually slow. Instead, target the bottleneck model. Its average queue wait time is the total time requests spent waiting, divided by the number of successful requests, and that is what the query above computes from nv_inference_queue_duration_us and nv_inference_request_success. When the dynamic batcher uses a 50-millisecond delay window, an average queue wait exceeding 500,000 microseconds shows that the GPU instance groups are saturated. Keep in mind that the batcher's own delay is part of the wait, so a long window can make the number look worse even when the GPU is fine.

2.2 Scaling on KV Cache Saturation (vllm:gpu_cache_usage_perc)​

Queue depth alone can miss silent memory exhaustion during long-context workloads. Suppose a Llama-3-70B replica configured with a 64-sequence limit receives 25 RAG requests, each carrying an 8,192-token document context. RAG means retrieval-augmented generation, where the app pastes retrieved documents into the prompt. Because 25 is well below the 64-sequence concurrency limit, vllm:num_requests_waiting remains 0. Nobody is in line, so a queue-based scaler stays quiet. However, those 25 long-context sequences consume nearly 100 percent of the physical PagedAttention KV blocks. The replica looks idle by one measure and is full by another.

When the next token generation step requires a new KV block and none are free, the vLLM scheduler must preempt running sequences. Preemption means the scheduler pauses a running request and frees its cache blocks, so another request can move forward. It logs swap or recompute warnings and increments vllm:num_preemptions_total. Once preemption starts, Inter-Token Latency spikes from 18 ms to over 850 ms, and throughput collapses. A preempted request has to rebuild its cache later, which costs work it had already done.

To prevent preemption storms, production clusters scale proactively on KV cache block utilization via vllm:gpu_cache_usage_perc, exported as a ratio from 0.0 to 1.0. Proactively means the scaler acts while there is still free memory, so the new pod is ready before the old one runs out. The zones in the table below give that ratio a meaning. Think of them as traffic lights. The safe zone is green, and you can afford to scale down there, but only after the stabilization window has passed. The warning zone is amber, so the scaler should act now while new pods still have time to warm up. The emergency zone is red, where preemption has already begun and the right move is to shed load at the gateway. Keeping the amber light on purpose is what separates a calm service from one that fights fires every evening.

2.3 Scaling on Token Latency SLIs (TTFT and ITL) and llm-d WVA​

Imagine the queue looks calm and the cache has plenty of room, yet a product manager says the chat feels sluggish. Queue depth and KV cache utilization measure internal engine pressure, which is useful but indirect. Time to First Token and Inter-Token Latency measure the actual user experience, so they catch problems the internal gauges miss. In OpenMetrics and Prometheus, vLLM exports vllm:time_to_first_token_seconds_bucket and vllm:time_per_output_token_seconds_bucket, while OpenTelemetry semantic conventions standardize on gen_ai.server.time_to_first_token and gen_ai.server.time_per_output_token.

PromQL Latency SLI Queries and Production Targets (Volume 5 Ch. 3, Volume 12 Ch. 10, GAK Ch. 5):
1. p95 Time to First Token (Prefill + Queueing SLI):
   histogram_quantile(0.95, sum(rate(vllm:time_to_first_token_seconds_bucket[5m])) by (le))
   Target SLO: < 0.200 s (200 ms) for interactive chat; < 1.0 s (1,000 ms) for long-context RAG.
2. p95 Inter-Token Latency / TPOT (Decode Bandwidth SLI):
   histogram_quantile(0.95, sum(rate(vllm:time_per_output_token_seconds_bucket[5m])) by (le))
   Target SLO: < 0.025 s (25 ms/token, or 40 tok/s) for real-time assistants; alert at > 0.040 s (40 ms).
   Human reading baseline: ~180 words/min (~3 words/s, or 4-5 tok/s minimum in GAK Ch. 5; 11 tok/s comfortable stream in LLP Ch. 6).
3. Pod Output Token Throughput (GTPS):
   sum(rate(vllm:generation_tokens_total[1m])) by (pod)

Some services mix very short prompts with very long ones, and that mix breaks a simple scaler. For heterogeneous workloads where prompt lengths vary from 64 tokens to 32,000 tokens, the llm-d project introduces the Workload Variant Autoscaler (WVA). A workload variant here is one kind of request with its own size profile. Instead of treating every request as an identical unit, WVA inspects each replica token processing capacity and accounts for variable input and output token distributions. It then scales replica pools directly against p95 TTFT and TPOT latency targets. In disaggregated serving architectures, which split prefill and decode onto separate pools, WVA independently scales compute-bound prefill replicas when TTFT rises and memory-bandwidth-bound decode replicas when KV cache usage or ITL rises. Each pool is then scaled on the signal that actually limits it.

Always combine a fast leading indicator such as queue depth or KV cache usage at 80 percent with a lagging latency SLI so your cluster scales out before users feel latency degradation. The leading indicator warns you early, and the latency SLI confirms that the warning was real. Using only one of them either reacts too late or reacts to noise.

3. Kubernetes HPA Mechanics, Stabilization Windows, and Scaling Policies​

3.1 The HPA Control Loop Equation and Deadband Tolerance​

Suppose the deployment already runs a few pods, the queue per pod is well above the target, and you want to know exactly how many pods the scaler will ask for. The answer comes from one formula, and it is worth working through by hand once. Whether you configure a native Kubernetes HorizontalPodAutoscaler with Prometheus Adapter or let KEDA manage the HPA object on your behalf, the Kubernetes HPA controller executes the underlying replica calculation. Every 15 seconds by default, the controller queries the registered metrics API and evaluates the ratio between current metric values and the target value. The ratio is the heart of the loop, because it turns a metric value into a replica count.

Kubernetes HPA Replica Calculation Equation (LLP Ch. 6, K8GS Ch. 6):
  desiredReplicas = ceil[ currentReplicas * ( currentMetricValue / desiredMetricValue ) ]

Deadband Tolerance Rule:
  Default --horizontal-pod-autoscaler-tolerance = 0.10 (10%)
  If 0.90 <= (currentMetricValue / desiredMetricValue) <= 1.10, HPA makes no change.

Worked Example (code/part15/autoscaling_inference_keda.py):
  - Current state: currentReplicas = 3, desiredMetricValue = 20.0 waiting requests/pod
  - Case A (Small fluctuation): currentMetricValue = 21.5 -> ratio = 1.075 (within 10% tolerance) -> desiredReplicas = 3
  - Case B (Traffic surge): currentMetricValue = 50.0 -> ratio = 2.50 -> raw desiredReplicas = ceil(3 * 2.50) = 8 replicas

When multiple metrics are specified in a single HPA or KEDA configuration, the HPA controller evaluates the formula for each metric independently. It then selects the maximum desired replica count across all triggers. That rule is conservative in a useful way. If the queue trigger asks for a smaller count and the cache trigger asks for a larger one, the scaler follows the larger request, because that constraint must be satisfied. Adding a second trigger therefore never makes the scaler lazier, which is a good reason to add one when a single metric has blind spots.

3.2 Tuning Stabilization Windows and Asymmetric Scaling Policies​

Picture a quiet afternoon. Traffic drops for a moment, the scaler sees low numbers, and it starts removing pods. Later that day a wave of users arrives, and the pods that were removed are still loading. Relying on default HPA scaling behavior is one of the most destructive mistakes in production LLM operations. The default scale-up stabilization window of 0 seconds reacts quickly to traffic surges. A stabilization window is the time the controller looks back over before it acts on a new recommendation. However, the default scale-down policy allows Kubernetes to terminate 100 percent of excess pods every 15 seconds once the 300-second stabilization window elapses.

For a stateless Go microservice that boots in 800 milliseconds, dropping from 10 pods to 2 pods in 15 seconds is harmless. Replacing a pod costs almost nothing. For a Llama-3-70B deployment where each pod claims four or eight H100 GPUs and takes two to five minutes to initialize, terminating pods is a semi-irreversible action. If a brief two-minute lull triggers an aggressive scale-down, the next traffic wave hits the surviving replicas while replacement pods are stuck loading 140 GB of weights. The cost of a wrong scale-down is paid later, by the users who arrive during the reload.

The fix is to write the scale-up and scale-down rules as two different policies. The block below shows one way to do it, and the three bullets after it explain what each part guards against.

# Production HPA v2 Behavior Block for LLM Serving (VL5 Ch. 3, K8GS Ch. 6, LLP Ch. 6)
behavior:
  scaleUp:
    stabilizationWindowSeconds: 0
    selectPolicy: Max
    policies:
      - type: Percent
        value: 100
        periodSeconds: 15
      - type: Pods
        value: 2
        periodSeconds: 15
  scaleDown:
    stabilizationWindowSeconds: 300
    selectPolicy: Min
    policies:
      - type: Pods
        value: 1
        periodSeconds: 60
      - type: Percent
        value: 10
        periodSeconds: 300

This asymmetric behavior configuration enforces three critical invariants. Read each one as a rule about a specific mistake, because that is what each line is there to prevent.

  • Immediate, bounded scale-up: With a 0-second stabilization window and selectPolicy: Max, the cluster responds immediately to queue or KV cache spikes. It doubles replicas or adds at least 2 pods every 15 seconds. For our 3-replica cluster needing 8 raw replicas, the 100 percent policy caps the single-step jump to 6 replicas in the first 15-second tick. That cap prevents a single telemetry spike from exhausting cluster quota. Without a cap, one bad reading could ask for far more GPU nodes than the budget allows.
  • Lookback peak tracking: During scale-down, the HPA controller inspects all desired replica recommendations computed over the past 300 to 600 seconds and scales to the highest recommendation in that window. In other words, the controller remembers the recent peak and refuses to drop below it too fast. This stabilization window must always exceed your pod end-to-end deployment and warmup time, or the controller will scale down before a replacement could ever finish loading.
  • Gradual scale-down: Even after traffic remains low for 5 full minutes, selectPolicy: Min drains at most 1 pod per minute. That pacing gives the load balancer time to finish active streaming connections gracefully. A streaming reply can run for many seconds, and cutting it off in the middle is the failure users remember.

3.3 Why VPA Conflicts with HPA and How to Size Rolling Updates​

Kubernetes also offers the VerticalPodAutoscaler, which adjusts container CPU and memory requests and limits across four operating modes. The VerticalPodAutoscaler, or VPA, changes the size of a pod rather than the number of pods. The Off mode only generates sizing recommendations, which tools like Fairwinds Goldilocks display. The Initial mode applies recommendations only at pod creation. The Recreate and Auto modes evict and restart running pods to apply new resource sizes. A pod restart is exactly what an LLM replica cannot afford, because the reload takes minutes.

Never run VPA in Auto or Recreate mode alongside HPA on the same LLM deployment. First, Kubernetes GPUs cannot be vertically resized in place. Second, when VPA mutates a pod CPU or memory request and evicts the pod, it fights the HPA utilization ratio calculation and destroys the pod in-memory GPU KV cache. The two controllers end up pulling in opposite directions, and the cache that took minutes to fill is thrown away. Use VPA strictly in Off mode with Goldilocks in staging to right-size the host CPU and RAM requests of your vLLM container. Staging is the test environment that mirrors production, so you can read the recommendations without risking a live pod.

A related capacity trap occurs during Deployment rolling updates. Picture a rollout on a cluster that has no spare hardware. Suppose your cluster runs a 5-replica deployment where each replica requests an entire 8-GPU node, consuming 40 GPUs total, and your cluster has zero idle 8-GPU nodes. Under standard web defaults where maxSurge is 1 and maxUnavailable is 0, Kubernetes attempts to schedule a sixth 8-GPU pod before terminating any old pod. Because no spare 8-GPU node exists, the new pod sits in Pending and the rollout deadlocks forever. In GPU-constrained clusters without dedicated surge capacity, you must either provision temporary burst capacity via Karpenter or set maxSurge: 1 and maxUnavailable: 3. That setting allows three replicas to terminate first, freeing 24 GPUs while two replicas remain online so replacement pods can schedule. The rollout then finishes, but for a while the service runs with fewer replicas than usual, so plan the window for it.

Always set your HPA scale-down stabilization window longer than your worst-case model cold-start time, and restrict scale-down policies to a single pod per minute. Those two rules together keep the scaler from giving away capacity faster than it can get it back.

4. KEDA Architecture, ScaledObject, Scale-to-Zero, and KServe Concurrency​

4.1 Why KEDA Replaces prometheus-adapter for AI Factories​

Picture a platform team with many model teams, each wanting its own scaling rule for its own model. The old way to feed custom Prometheus metrics into a standard Kubernetes HPA was to deploy prometheus-adapter, and that setup gets messy fast. However, prometheus-adapter has two severe limitations in multi-tenant AI clusters. First, every new PromQL scaling query must be written into a global cluster ConfigMap using complex regex discovery rules, requiring cluster-admin privileges for every model team. A ConfigMap is a Kubernetes object that holds configuration, and a cluster-admin is the account with full control of the whole cluster. Second, native Kubernetes HPA enforces a hard lower bound of 1 replica. It cannot scale a deployment down to zero or wake it from zero. A lower bound of 1 means one expensive pod must keep running even when nobody is using the model. For a small internal model that is a reasonable cost. For a large model on several GPUs, it is a fixed bill that buys nothing during quiet hours, and that is the cost KEDA lets you remove.

Kubernetes Event-Driven Autoscaling (KEDA) solves both problems. KEDA runs three control-plane components inside the cluster. The control plane is the set of components that make decisions, as opposed to the pods that do the serving. Each component below has one job, and together they let each model team keep its own scaler without touching the global config.

  • The KEDA Operator (keda-operator). Polls external event sources such as Prometheus, Kafka, RabbitMQ, AWS SQS, or OpenTelemetry at a configurable polling interval of 15 seconds. Crucially, the operator directly controls the 0-to-1 and 1-to-0 replica transitions on the target Deployment or StatefulSet.
  • The KEDA Metrics Server (keda-operator-metrics-apiserver). Registers as the cluster external.metrics.k8s.io provider and feeds evaluated trigger metrics to the native Kubernetes HPA controller, which manages scaling between 1 and N replicas.
  • The KEDA Admission Webhooks (keda-admission-webhooks). Validates ScaledObject manifests to prevent conflicting scalers from targeting the same workload.

4.2 Production KEDA ScaledObject and KServe Integration​

Here is the object you actually write. A KEDA ScaledObject encapsulates the target workload, replica bounds, polling and cooldown intervals, HPA behavior overrides, failure fallback replicas, and Prometheus triggers in a single namespace-scoped manifest. A manifest is the YAML file you apply to the cluster, and namespace-scoped means the object lives inside one team's namespace, so that team can own it without global rights. Read it from the top down. The target tells KEDA what to scale, the bounds say how far it may go, and the triggers say why.

Notice two production safeguards in this ScaledObject. First, the fallback block guarantees that if Prometheus becomes unreachable for 3 consecutive polls, KEDA pins the deployment at 4 safe replicas instead of scaling down or crashing. This matters because a scaler that goes blind has no idea what load it is facing, and the safest guess is a steady, known size. Second, wrapping count(vllm:num_requests_running) in clamp_min with a lower bound of 1 prevents PromQL from returning NaN when all pods are temporarily restarting or scaled to zero. NaN means not a number, and a NaN in a scaling formula can quietly break the decision.

KServe is the model-serving layer that sits on top of Kubernetes, and it lets you choose between three deployment modes depending on your scaling and traffic architecture. Each mode trades simplicity against features, so pick the one that matches the traffic pattern you actually have.

  • Standard mode (serving.kserve.io/deploymentMode: Standard). Creates a standard Kubernetes Deployment without Knative or Istio sidecars. By adding serving.kserve.io/autoscalerClass: "keda", KServe automatically generates the KEDA ScaledObject from the InferenceService specification. It supports either PodMetric scraping via a local OpenTelemetry sidecar or External queries against cluster Prometheus. KServe 0.16 further introduces LLMInferenceService and LLMInferenceServiceConfig on top of Standard mode to wire KV-cache-aware routing and multi-node parallelism.
  • Knative mode (serving.kserve.io/deploymentMode: Knative). Wraps each predictor in a Knative Service using the Knative Pod Autoscaler. Every pod receives a queue-proxy sidecar that enforces containerConcurrency and reports active request concurrency to the autoscaler. KPA evaluates a 60-second stable window during normal operation, but automatically switches to a 6-second panic window whenever short-term concurrency reaches 200 percent of the target. Because Knative injects both queue-proxy and Istio sidecars, KServe provides the qpext metric aggregator via serving.kserve.io/enable-metric-aggregation: "true" so Prometheus can scrape both vLLM and sidecar metrics from a single port.
  • ModelMesh mode. Designed for high-density packing of thousands of small predictive ML models. It is unsuitable for large foundation models.

4.3 The Mechanics of Scale-to-Zero (minReplicaCount: 0)​

Setting minReplicaCount: 0 in KEDA or Knative eliminates GPU spend during idle nights, weekends, or low-volume LoRA endpoints. A LoRA endpoint is a small adapter served on top of a shared base model, and many of them see very little traffic. However, you cannot wake a deployment from 0 replicas using pod-internal metrics alone. Think about it for a moment. The metrics live inside the pods, and the pods are what you are trying to create. When replicas equals 0, no vLLM pods are running, so vllm:num_requests_waiting, vllm:gpu_cache_usage_perc, and DCGM_FI_DEV_GPU_UTIL do not exist.

To wake a model from zero, the architecture must include an external request buffer that remains in the data path even when zero GPU pods exist. The buffer is the thing that sees the request first, so it can count demand while the model is asleep.

  • Asynchronous Queue Broker. For batch, document-ingestion, or asynchronous agent tasks, requests land in a durable queue such as Amazon SQS, Kafka, or RabbitMQ. When queue depth exceeds the activation threshold, KEDA scales the deployment from 0 to 1, and HPA scales from 1 to N.
  • KEDA HTTP Add-on Interceptor. For synchronous HTTP APIs in Standard mode, client traffic routes to the KEDA HTTP interceptor proxy service. When the backend deployment has 0 endpoints, the interceptor holds the incoming HTTP connection open in an in-memory pending queue and signals KEDA to wake the deployment from 0 to 1. Once the new pod passes its /health readiness probe, the interceptor forwards the held request.
  • Knative Activator. In KServe Knative mode, when a revision scales to zero after its idle window, Knative swaps the Activator into the network data path. When a request arrives, the Activator buffers the HTTP request, triggers KPA to launch a pod, and proxies the request once queue-proxy reports ready. The user experiences this as one slow first reply rather than an error. That is acceptable for an internal tool, but for a customer-facing chat it is the reason a warm fallback still matters.

Use scale-to-zero only for bursty, non-critical, or small-to-medium models where cold starts can be engineered below 30 seconds, or pair it with a gateway fallback to a warm shared endpoint. A fallback is a second, always-on route that answers while the cold model is still loading, so the user gets a slower but working answer instead of a timeout.

5. Cold-Start Anatomy: Image Pulls, Node Provisioning, and Weight Streaming​

5.1 Deconstructing the Five Phases of an LLM Cold Start​

Picture the on-call engineer watching the scaler add pods during a spike, and the new pods still not answering after a long wait. Dynamic autoscaling fails if a newly requested replica takes seven minutes to serve its first token. The scaler did its job, but the user waited anyway. To engineer sub-minute scale-out, you must decompose cold-start latency into its five sequential physical stages. Decomposing it means timing each stage separately, so you know which one to attack first. The stages run one after another, so their times add up.

End-to-End LLM Cold-Start Equation (GAK Ch. 2 & 4, VL5 Ch. 3, HLS Ch. 5, K8GS Ch. 6):
  T_cold = T_node_provision + T_image_pull + T_init + T_weight_load + T_cuda_graph_warmup

Stage Breakdown for Llama-3-70B (140 GB FP16 weights):
1. T_node_provision (Cluster Autoscaler vs Karpenter):
   - Legacy Cluster Autoscaler (ASG node groups): 180 to 480 seconds
   - Karpenter (NodePool + EC2NodeClass): ~33.66 ms pod match + ~117 seconds VM boot & driver init
   - Pre-warmed Standby Node / Warm Pool: 0 seconds (node already Ready)
2. T_image_pull (vLLM + CUDA runtime image ~5 GB):
   - Uncached pull (imagePullPolicy: Always @ 0.25 GB/s): ~20 to 60 seconds
   - Pre-pulled image (imagePullPolicy: IfNotPresent): 0 seconds
3. T_init (Python interpreter + Uvicorn + CUDA context init): ~1.0 second
4. T_weight_load (140 GB FP16 weights from storage -> Host DRAM -> PCIe Gen5 -> GPU HBM):
   - Remote S3 / Hugging Face Hub download (0.5 GB/s): 280.0 seconds
   - Shared NFS PVC (10 Gbps = 1.25 GB/s single pod): 112.0 seconds (or ~900 s when 8 pods contend)
   - Local NVMe SSD single-thread safetensors (7.0 GB/s): 20.0 seconds
   - Local NVMe / PVC + Run:ai Model Streamer (16 threads @ 11.2 GB/s): 12.5 seconds
   - Local NVMe RAID + NVIDIA GPUDirect Storage (GDS cuFile DMA @ 28.0 GB/s): 5.0 seconds
5. T_cuda_graph_warmup (KV pool profiling + CUDA Graph capture): 8.0 seconds

5.2 Node Autoscaling: Cluster Autoscaler vs. Karpenter and Pre-Warmed Standby Nodes​

When HPA or KEDA increases a deployment replica count and existing GPU nodes are full, the new pods enter Pending with Insufficient nvidia.com/gpu. Pending means the pod exists but has no node yet. At that point, node-level autoscaling takes over. Picture the node layer as a second scaler that works one level below the pods, and it has its own, slower clock.

Traditional Cluster Autoscaler polls predefined cloud Auto Scaling Groups or GKE Node Auto-Provisioning limits and provisions fixed-template nodes. A fixed template means every new node looks the same, whether or not the pending pod needs that shape. By contrast, Karpenter watches unschedulable pods directly via the Kubernetes API server, solves bin-packing constraints in 33.66 milliseconds, and provisions optimal GPU instances using NodePool and EC2NodeClass resources. Bin-packing is the job of fitting pods onto nodes so that as little hardware as possible sits empty. When jobs finish or KEDA scales pods down, Karpenter WhenEmptyOrUnderutilized consolidation automatically applies the karpenter.sh/disrupted:NoSchedule taint, drains empty nodes, and terminates the cloud instance within minutes. A taint with NoSchedule tells new pods to stay away from that node, which lets the node empty out safely.

However, even Karpenter requires roughly 90 to 120 seconds for the cloud hypervisor to boot the VM, load the NVIDIA kernel driver, and register the device plugin. A hypervisor is the layer that runs virtual machines, and the device plugin is what tells Kubernetes that the node has GPUs to hand out. To eliminate node provisioning time completely for latency-critical services, AI factories maintain Pre-Warmed Standby Nodes. In this pattern, GPU nodes stay booted and joined to the cluster running low-priority, preemptible batch jobs assigned a low Kubernetes PriorityClass. A PriorityClass ranks pods so the scheduler knows which ones may be evicted to make room. When KEDA scales up a high-priority vLLM pod, the Kubernetes scheduler immediately preempts the batch pod in 0 seconds of node boot time and schedules the inference pod on the warm GPU. The cost is that you pay for the standby capacity even while it is idle, so this pattern makes sense only for services that cannot wait.

5.3 Storage Packaging and Weight Streaming (modelcar, OCI Volumes, runai_streamer, GDS)​

Once the pod is scheduled on a node, two rules govern container image startup. Picture a deploy on a Friday afternoon that ships a one-line code fix, and the image takes ages to pull because the weights are inside it. The rules below prevent that.

  • Never bake 140 GB model weights into the application container image: Baking weights into the Docker image creates a monolithic 145 GB artifact that bloats registry pulls on every code change. Every small code change now means pushing and pulling the whole model again. It also doubles disk usage during extraction and exposes proprietary weights inside standard container registries. Keep the code in the image and the weights somewhere else.
  • Set imagePullPolicy: IfNotPresent and pin immutable image digests: The vLLM runtime container image is roughly 5 GB because it bundles CUDA user-space libraries. A digest is a fixed fingerprint of an image, so pinning it means the pod always gets the exact bytes you tested. Pre-pulling that 5 GB runtime image via a DaemonSet or cloud VPC endpoint reduces T_image_pull to 0 seconds. A DaemonSet runs one copy of a pod on every node, which is how the image gets onto each node before it is needed.

Let us examine why Run:ai Model Streamer and NVIDIA GPUDirect Storage achieve such dramatic speedups. The answer is about how many lanes the data travels through and whether it has to stop at the CPU on the way. Safetensors is a file format for storing model weights, and the rows in the table above are only as fast as the path they take. In standard PyTorch and vLLM loading, a single CPU thread reads .safetensors files sequentially into host page cache. The page cache is the memory where Linux keeps recently read file data. It then copies tensors into pinned DRAM at 50 to 200 GB/s and transfers them across PCIe to GPU HBM. By passing --load-format runai_streamer with 16 threads, vLLM streams tensor chunks in parallel directly from local NVMe or object storage into GPU memory without repackaging the model. When paired with GPUDirect Storage over local NVMe drives, the cuFile DMA engine transfers weight blocks directly from NVMe controllers across the local PCIe Gen5 switch into GPU HBM. That path bypasses CPU bounce buffers entirely and loads a 140 GB model in 5 seconds, achieving 14.0 seconds total pod readiness. A bounce buffer is a staging copy in CPU memory, and skipping it removes one full copy of every byte. The remaining time goes to the stages that do not touch the weights, such as starting the process and capturing CUDA graphs, so the weight load is no longer the only thing to tune.

Eliminate network downloads from the scaling path by caching weights on local NVMe or OCI image volumes and enabling --load-format runai_streamer with 16 concurrent threads. A download on the scaling path is the step that blocks a new pod from starting, so moving it off that path is the single biggest cold-start win. Test the change on one node first, and measure the time to first token before rolling it out to the rest of the fleet.

6. Production Failure Modes, Probe Design, and FinOps Cost Engineering​

6.1 Failure Mode 1: Queue-Depth Thrashing on Fast Models​

  • Symptom: A Llama-3-8B deployment configured with KEDA scales violently from 2 replicas to 10 replicas every few minutes, sits idle for 5 minutes, and drops back to 2 replicas. User tail latency degrades during every scale-up wave despite low average utilization. The average looks calm, which is why the dashboard did not raise an alarm. The tail tells the real story, because it is the users who arrive during each wave who feel the delay.
  • Root Cause: The KEDA trigger was configured with a naive queue threshold of 5 on vllm:num_requests_waiting. Because Llama-3-8B processes batches rapidly at roughly 15 requests per second per replica, a micro-burst of 50 requests creates a momentary queue of 25 requests per pod. KEDA computes 10 desired replicas and launches 8 new pods. However, the 2 existing pods drain all 50 requests in 1.67 seconds, whereas the 8 new pods take 60 seconds to cold-start. By the time the 8 new pods become ready, the queue is 0, wasting 2,400 GPU-pod-seconds during the 300-second cooldown window. The mismatch is the whole story. The scaler reacted to a burst that was already draining, and the new pods arrived after the queue was empty. The fix is to make the trigger tolerant of short bursts, not to make it faster.
  • Fix: Raise the queue threshold to 100 to match the GPU batch capacity of 128 so micro-bursts are absorbed by continuous batching without spawning unneeded pods. Smooth the metric in PromQL with avg_over_time(vllm:num_requests_waiting[1m]) or scale on queue wait time exceeding 2 seconds. The smoothing step matters because a one-sample spike is exactly the kind of signal that caused the thrashing in the first place. A smoothed value follows the trend, and it ignores the single bad reading.

6.2 Failure Mode 2: Readiness Probe Cascading Outage During HPA Scale-Out​

  • Symptom: During a traffic surge, HPA scales a Llama-3-70B deployment from 4 replicas to 12 replicas. Within 90 seconds of scaling starting, all 4 original healthy pods are marked unready with HTTP 504 probe timeouts, causing a 100 percent cluster-wide HTTP 503 outage. The outage started with a scale-out, which is the reverse of what anyone expects from adding capacity.
  • Root Cause: All pods loaded 140 GB weights from a shared 10 Gbps NFS volume providing 1.25 GB/s aggregate bandwidth. When 8 new pods started pulling weights simultaneously at 156.25 MB/s per pod, shared storage I/O saturated completely. Because the deployment used an aggressive readiness probe hitting /v1/models with a 1-second timeout, the storage stall delayed the Python event loop on the 4 existing pods to 1.2 seconds. Kubelet timed out at 1.0 second and removed all 4 healthy pods from the Service endpoints. The kubelet is the node agent that runs the probes, and when it removes a pod from the endpoints, the Service stops sending it traffic. Those healthy pods were fine the whole time. They were simply too busy waiting on storage to answer a health check in time.
  • Fix: Move weights off uncached shared NFS to local NVMe or OCI volumes, and decouple Kubernetes health probes into three distinct endpoints. Configure startupProbe on /health with periodSeconds: 10 and failureThreshold: 60 to allow 600 seconds for initial weight loading. Configure readinessProbe on /health with timeoutSeconds: 5 to tolerate transient jitter. Configure livenessProbe on /ping with timeoutSeconds: 3 and never execute a GPU forward pass inside a liveness check. A liveness check decides whether to restart the pod, so it should be cheap and must not depend on the GPU being free. Splitting the three probes lets each one answer only the question it is meant to answer.

6.3 Failure Mode 3: Multi-Turn Prefix Cache Miss Storm Across Autoscaled Replicas​

  • Symptom: As KEDA scales a conversational RAG deployment from 2 pods to 10 pods behind a standard Round-Robin Kubernetes Service, p95 TTFT degrades by 3x to 5x even though per-pod request rate is low. The scale-out looked healthy on the autoscaler dashboard, and only the latency graph showed the damage.
  • Root Cause: Under Round-Robin routing across 10 pods, Turn 1 of a user conversation lands on Pod A, which computes and caches the 4,096-token system and RAG prefix in PagedAttention blocks. However, Turn 2 has a 90 percent probability of landing on Pods B through J. The receiving pod suffers a prefix cache miss and must recompute the entire prefill from scratch, dropping the cluster prefix-cache hit rate from over 85 percent to roughly 10 percent.
  • Fix: Deploy the Kubernetes Gateway API Inference Extension using an InferencePool backed by an Envoy External Processing Endpoint Picker service on port 9002, or configure Chat-Session-ID sticky session affinity at the Ingress gateway. The Endpoint Picker routes matching prefixes or session IDs to the warm replica. That routing preserves over 85 percent cache hit rates and cuts TTFT by up to 90 percent until that replica KV cache exceeds 95 percent saturation. Sticky routing is the trade. Each user keeps landing on the replica that already holds their history, so the cache stays warm, and the scaler has to take care not to pile every busy session onto one replica.

Key takeaways​

  • Never scale LLM pods on CPU, memory, or raw GPU utilization: PagedAttention pre-allocates 90 percent of GPU VRAM at startup. Furthermore, a single active decode request drives DCGM_FI_DEV_GPU_UTIL to 98 to 100 percent while true SM occupancy sits below 2 percent.
  • Scale on queue backlog, KV cache saturation, and token latency SLIs: Trigger scale-up when normalized waiting requests exceed 20 per pod or when vllm:gpu_cache_usage_perc reaches 0.80. Combine those leading signals with p95 TTFT and p95 ITL histogram thresholds.
  • Enforce asymmetric HPA stabilization and rate limits: Scale up immediately with a 0-second window and a 100 percent or 2-pod step limit. Hold scale-down behind a 300-to-600-second stabilization window and drain at most 1 pod per 60 seconds.
  • Use KEDA or Knative for scale-to-zero backed by an external request buffer: Because pod metrics vanish at 0 replicas, waking from zero requires an external queue, KEDA HTTP Add-on interceptor, or Knative Activator.
  • Attack weight loading to conquer cold starts: Combine pre-pulled runtime images, local NVMe or OCI image volume mounts, and --load-format runai_streamer or GPUDirect Storage. Together they shrink 140 GB model loads from minutes to 14 to 22 seconds.
  • Protect healthy pods during scale-out and route with KV affinity: Isolate slow initialization behind a 600-second startup probe, use a 5-second readiness probe and lightweight liveness probe, and deploy the Gateway API Inference Extension to preserve multi-turn prefix cache hit rates.

Checkpoint questions​

1. Why does container memory utilization remain flat at 90% on a vLLM pod regardless of whether 0 or 64 users are active?

At startup, vLLM profiles the model and statically pre-allocates gpu_memory_utilization of physical HBM. On an 80 GB GPU reporting 79.14 GiB, it reserves 71.22 GiB total and locks 54.93 GiB into the PagedAttention KV cache pool. Because those HBM blocks remain held by the CUDA process for its entire lifetime, OS and container memory counters never fluctuate with request traffic.

2. Why does DCGM_FI_DEV_GPU_UTIL jump to nearly 100% when only a single user is generating tokens?

DCGM_FI_DEV_GPU_UTIL measures the percentage of sampling intervals during which at least one CUDA kernel is executing on any SM, not how many SMs are occupied. A single autoregressive decode stream executes a forward pass every 18 to 42 milliseconds continuously, keeping DCGM_FI_DEV_GPU_UTIL at 98 to 100 percent while DCGM_FI_PROF_SM_ACTIVE sits below 2 percent.

3. Which DCGM metrics distinguish compute-bound prefill saturation from memory-bandwidth-bound decode saturation?

DCGM_FI_PROF_SM_ACTIVE measures the fraction of Streaming Multiprocessors actively executing warps, which spikes during compute-bound prefill. By contrast, DCGM_FI_DEV_MEM_COPY_UTIL measures HBM memory controller bandwidth utilization, which dominates during memory-bandwidth-bound decode.

4. Why is scaling on vllm:num_requests_waiting alone insufficient for long-context RAG workloads?

A small number of long-context RAG requests, such as 25 requests with 8,192-token prompts on a replica with a 64-sequence limit, stays below the sequence concurrency cap so vllm:num_requests_waiting remains 0. However, those long sequences can still exhaust 100 percent of physical PagedAttention KV cache blocks and trigger swap or recompute preemption storms.

5. What are the three operating zones for vllm:gpu_cache_usage_perc, and at what threshold should KEDA trigger scale-up?

The three zones are the Safe Zone from 0 to 80 percent, the Warning Zone from 80 to 90 percent, and the Emergency Zone above 90 percent where sequence preemptions occur. KEDA should trigger scale-up at 0.80 so new replicas finish warming up before KV cache usage enters the preemption zone, while the API gateway trips a circuit breaker at 0.95.

6. How do you write a PromQL trigger for NVIDIA Triton Inference Server when serving a multi-model ensemble?

Instead of scaling on the front-end ensemble wrapper, query the bottleneck model average queue delay by dividing nv_inference_queue_duration_us by nv_inference_request_success. Trigger scale-up when that ratio exceeds 500,000 microseconds, which equals 0.5 seconds of average wait time in the dynamic batcher queue.

7. How does the Kubernetes HPA v2 replica equation handle small metric fluctuations around the target value?

HPA multiplies current replicas by the ratio of current metric value to desired metric value and rounds up to the next integer, but it applies a default 10 percent deadband tolerance. If the metric ratio lies between 0.90 and 1.10, such as 21.5 divided by 20.0 equaling 1.075, HPA makes no scaling change.

8. Why is the default Kubernetes HPA scaleDown policy dangerous for 70B LLM deployments?

By default, the HPA scale-down policy allows terminating 100 percent of excess pods every 15 seconds after a 300-second window. Because terminating a GPU pod takes seconds while loading 140 GB of weights takes minutes, a brief traffic dip wipes out warm capacity and causes severe latency spikes when traffic resumes.

9. Why must you never enable VerticalPodAutoscaler in Auto or Recreate mode alongside HPA on an LLM deployment?

First, Kubernetes cannot vertically resize GPU counts in place. Second, VPA in Auto or Recreate mode evicts and restarts pods to change their CPU or memory requests, which conflicts with the HPA replica loop and destroys the pod in-memory GPU KV cache. VPA should only be used in Off mode with Goldilocks to generate right-sizing recommendations.

10. Why does a rolling update of a 5-replica, 8-GPU-per-pod deployment deadlock under default maxSurge settings when the cluster has 40 GPUs total, and how do you fix it?

With 5 replicas using all 40 GPUs, setting maxSurge: 1 and maxUnavailable: 0 tries to schedule a sixth 8-GPU pod before terminating any existing pod, leaving the new pod stuck in Pending. Setting maxUnavailable: 3 allows Kubernetes to terminate up to three old replicas first, freeing 24 GPUs while two replicas remain active so new pods can schedule.

11. How do keda-operator and keda-operator-metrics-apiserver divide responsibility between 0-to-1 scaling and 1-to-N scaling?

Because the native Kubernetes HPA controller cannot scale to or from 0 replicas, keda-operator directly polls triggers and transitions the target Deployment between 0 and 1 replica. Once at least 1 replica is active, keda-operator-metrics-apiserver exposes the metric via external.metrics.k8s.io so the Kubernetes HPA controller drives scaling between 1 and maxReplicaCount.

12. Why does a PromQL query dividing vllm:num_requests_waiting by count(vllm:num_requests_running) fail at 0 replicas, and how do you prevent it?

When 0 pods are running, count(vllm:num_requests_running) evaluates to 0, producing division by zero, and no pod exists to emit vllm:num_requests_waiting. You prevent division by zero using clamp_min with a lower bound of 1, and you drive 0-to-1 activation from an external queue, API gateway counter, or KEDA HTTP Add-on interceptor.

13. How does the Knative Pod Autoscaler switch between its stable window and panic window in KServe Knative mode?

KPA normally averages request concurrency reported by each pod queue-proxy sidecar over a 60-second stable window. If the 6-second panic window average concurrency reaches or exceeds 200 percent of containerConcurrency, KPA enters panic mode and scales immediately on the 6-second average.

14. How does the llm-d Workload Variant Autoscaler improve upon simple request-count autoscalers?

Simple request-count autoscalers treat a 32-token prompt and a 32,000-token prompt as identical work. The Workload Variant Autoscaler models the token capacity of each replica and accounts for variable input and output token lengths across workload variants. It then scales pods directly to maintain TTFT and TPOT latency targets at higher cluster utilization.

15. How does Karpenter differ from the legacy Kubernetes Cluster Autoscaler when provisioning GPU nodes?

Cluster Autoscaler relies on pre-configured cloud node groups and polling loops, taking 3 to 8 minutes. Karpenter watches unschedulable pods directly on the API server and solves bin-packing constraints in 33.66 milliseconds. It dynamically selects optimal instance types via NodePool and EC2NodeClass in roughly 117 seconds, and consolidates underutilized nodes via WhenEmptyOrUnderutilized.

16. How do KServe OCI modelcars and Kubernetes 1.31/1.35 OCI image volume mounts avoid copying 140 GB of weights at pod startup?

Init-container storage initializers copy gigabytes of weights into an emptyDir on every pod restart. A KServe modelcar runs a lightweight sidecar using under 10 MB of RAM with shareProcessNamespace: true that creates a symbolic link from /proc/$$$$/root/models to /mnt/models with zero file copying. Kubernetes native OCI image volume mounts attach the read-only OCI image layers directly via kubelet without needing shared process namespaces.

17. How do Run:ai Model Streamer and NVIDIA GPUDirect Storage accelerate model weight loading into GPU HBM?

Run:ai Model Streamer replaces single-threaded sequential file reads with 16 concurrent streaming threads from NVMe or S3 without repackaging .safetensors files, cutting a 140 GB load to 12.5 seconds. NVIDIA GPUDirect Storage uses cuFile DMA to transfer weights directly from local NVMe drives across the PCIe switch into GPU HBM without CPU bounce buffers, loading 140 GB in 5.0 seconds.

18. What causes a 50-request burst on a Llama-3-8B service with KEDA threshold=5 to waste 2,400 GPU-pod-seconds, and what fixes it?

With a threshold of 5, a burst of 50 requests across 2 pods scales the deployment from 2 to 10 pods. However, Llama-3-8B clears the 50 requests in 1.67 seconds while the 8 new pods take 60 seconds to cold-start and then sit idle for the 300-second cooldown, wasting 2,400 GPU-pod-seconds. Raising the threshold to 100 to match GPU batch capacity or smoothing with avg_over_time over 1 minute prevents the false scale-up.

19. How must Kubernetes startupProbe, readinessProbe, and livenessProbe be configured on a 70B LLM container to prevent cascading 503 outages?

Use a generous startupProbe on /health with periodSeconds: 10 and failureThreshold: 60 to allow 600 seconds for initial weight loading. Point readinessProbe to /health with timeoutSeconds: 5 so storage I/O jitter does not drop healthy pods. Point livenessProbe to a lightweight /ping check that never runs a GPU forward pass.

20. How does premature scale-out at queue_depth=1 impact Cost per 1M Tokens on an 8x H100 node ($49.60/hr), and how does 4-bit AWQ quantization change autoscaling capacity on an L40S ($2.25/hr)?

On an 8x H100 node costing 49.60 dollars per hour, full continuous batching at 2,658.76 tokens per second yields 5.18 dollars per 1M output tokens. Scaling prematurely at a batch size of 1 and 24.0 tokens per second inflates cost to 574.07 dollars per 1M tokens, a 110.82x penalty. On an L40S costing 2.25 dollars per hour, quantizing Qwen3-14B from BF16 to 4-bit AWQ expands the KV cache pool 2.65x and raises throughput 2.70x, cutting total token cost from 1.32 to 0.49 dollars per 1M tokens.
