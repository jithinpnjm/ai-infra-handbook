Why this matters for AI infrastructure​

Picture the first week after your team opens an LLM endpoint to real customers and to autonomous agents. In testing the model answered well. In production, some requests hang for minutes at peak hours, the autoscaler adds pods that never become useful, and the dashboards still show green. That gap between a green dashboard and a broken experience is what this chapter is about.

Getting a model to answer a prompt on a single GPU is only the start of inference engineering. Once you expose that model to real users and autonomous agents, the failure modes change completely. A stateless web microservice either returns a fast response or crashes cleanly, and both outcomes are easy to see. A large language model serving stack can fail partially and silently across several infrastructure layers at once, so the failure can look like success from the outside.

When a serving platform relies on standard microservice defaults instead of AI-native reliability controls, four operational disasters happen regularly. Each one starts with a default that looked reasonable for a web service and turned out to be wrong for a GPU.

  • How can a broken pod still look healthy? An uncorrectable hardware memory fault on one GPU inside an eight-GPU Tensor Parallel group deadlocks the collective ring forever. The Python HTTP web server on the host CPU stays alive and returns HTTP 200 to naive Kubernetes health checks. The broken pod then drops one-eighth of all cluster traffic into a black hole.
  • Why does a scale-up make things worse? When an autoscaler launches new replicas that pull seventy-gigabyte weight files over shared storage, transient I/O contention delays responses on existing pods. If a readiness probe checks an inference thread with a one-second timeout, Kubernetes marks every healthy pod unready at once. That single probe mistake takes down the entire cluster.
  • Why do long prompts crowd out short ones? Counting only requests per second treats a ten-token greeting the same as a ten-thousand-token document analysis. Admitting unbounded long-context prompts exhausts the PagedAttention block pool and forces the scheduler to preempt running requests. On current vLLM a preempted request is recomputed, which burns GPU time. On engines before v0.18 that swapped KV blocks to host memory over PCIe, one reported incident inflated inter-token latency by over forty times.
  • What breaks during a rollout? Terminating a pod or unloading a model without draining active Server-Sent Events streams cuts off long-running generations mid-sentence. Rolling out a quantized model without automated latency and accuracy gates silently degrades production answers.

Production reliability is not a single feature inside the model runner. It is a coordinated contract across the API gateway, the Kubernetes scheduler, the GPU driver telemetry pipeline, and the observability stack. Before you expose an inference cluster to production traffic, engineer every layer to bound incoming work, isolate hardware faults within seconds, and degrade gracefully under overload.

A useful way to hold this in your head is to ask, at every layer, what happens when this layer is slow or broken. The gateway needs an answer for a full pool. The scheduler needs an answer for a full KV cache. The probes need an answer for a hung GPU. When every layer has a written answer, an incident becomes a known sequence of steps instead of a surprise.

1. End-to-End Production Serving Architecture and AI Gateways​

1.1 The Nine-Stage Request Lifecycle and Non-GPU Latency​

Suppose the latency dashboard shows a slow API, and the first instinct on the team is to blame the GPU kernels. In production clusters that instinct is often wrong. Up to 60 percent of total end-to-end request latency can occur outside the GPU. A request must cross network proxies, admission queues, CPU tokenizers, host memory allocators, PCIe buses, and streaming socket buffers before a single token reaches the user.

Tracing one streaming chat request from the client to the GPU and back reveals nine distinct stages. Think of them as a relay race in which the baton is the prompt, and every runner can drop it. First, the API gateway terminates TLS 1.3 and parses the JSON payload. Second, the admission controller verifies tenant quotas and queues the request if all GPU workers are busy. Third, a CPU thread pool tokenizes the raw UTF-8 prompt into 64-bit integer vocabulary IDs. Fourth, the continuous batch scheduler queries the PagedAttention block manager to reserve physical KV cache pages in GPU memory. Fifth, the CUDA driver copies the input token tensor across the PCIe Gen5 bus into GPU High Bandwidth Memory.

Once the prompt reaches the GPU, the sixth stage runs compute-bound prefill matrix multiplications to emit the first token. Prefill is the phase where the model reads the whole prompt at once. Memory-bandwidth-bound autoregressive decode iterations then generate the remaining tokens one step at a time. Decode is slower per token because each step has to read the model weights and the stored history again. In the seventh stage, GPU sampling kernels apply temperature scaling, repetition penalties, and nucleus filtering over the vocabulary logits. Logits are the raw scores the model gives every possible next token. In the eighth stage, the selected 32-bit integer token ID copies back over PCIe to pinned host memory and detokenizes into UTF-8 text. Finally, the ninth stage wraps each text chunk into a Server-Sent Events frame and flushes the TCP socket.

Every stage outside the GPU can become a silent bottleneck. Consider the host side first. If the inference server allocates input tensors in standard pageable host memory via malloc, the operating system can page that memory out. The CUDA driver must then copy the tensor into a temporary page-locked staging buffer before starting a PCIe Direct Memory Access transfer. Direct Memory Access, or DMA, lets a device move data without the CPU copying each byte. That extra copy caps PCIe Gen5 transfer throughput at 10 to 14 GB/s. Allocating host staging buffers in pinned memory via cudaHostAlloc lets the GPU DMA engine read directly from physical RAM at 55 to 62 GB/s. Using pinned memory delivers a 5.0x transfer speedup.

It helps to picture the copy path as a loading dock. A pageable buffer is like a crate that a warehouse worker can move out of the way at any moment. Before the truck can take it, the worker has to carry it to a fixed dock first, and that extra carry is the staging copy. A pinned buffer is a crate already sitting on the dock, so the truck loads straight from it. Nothing about the truck changes. The only difference is whether the crate is allowed to move.

This is also why the fix is so cheap. Allocating a pinned buffer once at server start costs a little memory up front. After that, each request reuses the same dock space instead of paying the carry on every transfer. Teams who skip this step often blame the GPU when the real delay is sitting in the host copy.

1.2 Layered Enterprise Architecture and Multi-Model Routing​

Imagine a platform team that hosts a small chat model, a code model, and a domain classifier, and every product team wants one URL to call. The team does not want clients to know which pod holds which weights. Cloud-scale providers such as OpenAI, Anthropic, and Together AI organize production inference into a seven-layer enterprise architecture. The upper layers are the Public API Layer, the Resource Management Layer, and the Model Selection and Orchestration Layer. The lower layers are the Distributed Serving Layer, the Core Inference Layer, the Model Optimization Layer, and the Model Layer. Separating these layers lets platform engineers update routing rules, swap quantization formats, or scale GPU node pools without breaking client applications.

In a Kubernetes deployment, a request enters through an API gateway on port 8000 and optionally calls a CPU tokenizer on port 8001. The gateway then dispatches the request to stateful GPU model runners on port 8002. Stateful here means each runner keeps memory about the work in flight, such as its KV cache, so a request that lands on the wrong runner loses that memory and must pay for it again.

Think of the three ports as three desks in one office. The gateway desk checks identity and quotas, the tokenizer desk turns words into numbers when billing needs a count, and the model desk does the heavy GPU work. Each desk can be staffed, measured, and replaced on its own. That separation is the reason a team can change the tokenizer or swap the model runner without rewriting the client. A model runner is the process that holds the weights and runs the forward pass. Modern inference engines like vLLM and SGLang handle text tokenization internally. Even so, running a standalone CPU tokenizer service on port 8001 remains useful when counting tokens ahead of billing and rate limiting. A separate tokenizer service also helps when serving diffusion models that require CLIP tokenization alongside standard language model tokenizers.

When an organization hosts several models and inference engines behind one unified endpoint, the gateway routes requests by inspecting the OpenAI-compatible JSON body. The body is the part of the request that names the model, so the gateway can read it before choosing a backend.

  • How does the gateway know where a request goes? It reads the requested model name and maps it to its internal Kubernetes service DNS address in the multi-models namespace. Clients send all requests to port 8080 without needing to know which pod hosts which weights.
  • What happens when a team benchmarks two runtimes? In a multi-engines namespace, the gateway inspects both the model field and the inference server field. Specifying SGLang routes the request to the SGLang service, while leaving the engine field empty defaults to vLLM. The gateway also aggregates /v1/models across all backends.
  • Can routing depend on what the prompt says? A feature-based router inspects prompt keywords or a classifier to send coding tasks to a code model. An A/B router hashes the user ID so a user consistently lands on the same model variant. A dynamic router selects among candidate models in real time based on active load, latency budgets, and per-token cost.
  • Why not give each rare model its own pod? Dedicating an entire GPU pod to each rarely used domain classifier wastes memory. Ray Serve provides @serve.multiplexed paired with the ray_serve_multiplexed_model_id HTTP header. Each replica lazily loads and caches up to a configured number of models and evicts the Least Recently Used model when a new model arrives. Least Recently Used means the model nobody has asked for the longest time is the one that gets dropped.

1.3 Kubernetes Gateway API Inference Extension and llm-d​

Picture a support queue in which one agent gets a long, complicated ticket and the next agent gets a one-line question. If a manager hands out tickets in strict turn order, the first agent may be buried while the second sits idle. Standard Kubernetes Service and Ingress objects balance traffic in much the same way, using round-robin or active connection counts. Round-robin fails for LLM serving because prompt lengths vary widely and GPU replicas maintain stateful PagedAttention and RadixAttention prefix caches. Sending a ten-thousand-token prompt to a replica whose KV cache is already 90 percent full causes queueing delays. Sending a multi-turn follow-up to a replica that lacks the conversation's cached prefix wastes hundreds of milliseconds recomputing prefill.

To make Kubernetes routing natively aware of LLM state, the Kubernetes WG-Serving community developed the Gateway API Inference Extension. This extension forms the routing core of both the Envoy AI Gateway and the llm-d production stack.

Gateway API Inference Extension & Endpoint Picker (EPP) Architecture (GAK Ch. 4, DAI Ch. 9):
1. Custom Resources:
   - InferencePool (inference.networking.k8s.io/v1): Groups homogeneous model pods (targetPorts: [8000])
     and binds an Endpoint Picker service (endpointPickerRef: port 9002, failureMode: FailClose).
   - InferenceObjective (inference.networking.x-k8s.io/v1alpha2, evolved from InferenceModel):
     Declares workload priorities (e.g., priority: 1 for high-priority-inference vs priority: 2 for standard)
     and maps virtual model or LoRA adapter names to the underlying InferencePool.
2. Envoy External Processing (ext_proc) + Endpoint Picker (EPP) Scoring:
   - Envoy intercepts the HTTP request and calls the EPP gRPC service on port 9002 via ext_proc.
   - EPP scrapes live vLLM telemetry (vllm:num_requests_waiting, vllm:gpu_cache_usage_perc,
     prefix cache block hashes, and loaded --lora-modules).
   - Composite EPP Routing Score (lower is better; pods with KV >= 95% or queue >= 50 are filtered out):
     Score(pod) = 2.0 * waiting_reqs + 100.0 * kv_usage - 30.0 * prefix_hit_ratio - 15.0 * int(lora_loaded)
   - Lab Verification: pod-2 (55 waiting, 96% KV) is filtered out; pod-1 (3 waiting, 65% KV, 85% prefix hit,
     finance-lora loaded) scores 30.5 vs pod-0 (8 waiting, 72% KV, 10% prefix hit) at 85.0 -> pod-1 selected.

In our verification model, three pods compete for a request that needs the finance LoRA adapter. A LoRA adapter is a small add-on file that changes how a base model behaves, and it has to be loaded into GPU memory before a pod can use it. The Endpoint Picker immediately eliminates the third pod because its KV cache is at 96 percent with 55 waiting requests. Between the remaining two candidates, the second pod has 3 waiting requests, 65 percent KV usage, an 85 percent prefix match, and the finance adapter already loaded in GPU memory. That pod achieves a composite score of 30.5 compared to 85.0 for the first pod, so Envoy routes the request to the second pod. Lower scores win, so the second pod is the better choice.

It is worth walking through the arithmetic once, because the same pattern shows up in every scoring decision. The picker first throws away any pod that is nearly full, using a hard limit on KV usage and on the waiting queue. Only the survivors get a score. For each survivor, waiting requests and KV usage add cost, while a prefix hit and an already-loaded adapter subtract cost. The weights make queue depth and KV usage the big terms, and they make cache reuse a strong reason to prefer a pod. A pod that has the adapter in memory skips a load that could take seconds, which is why the adapter bonus matters so much for a request that needs it.

Notice what the picker does not do. It does not look at the text of the prompt, and it does not know whether the answer will be long. It only sees the live signals that the pods report, and it scores them every time a request arrives. If those signals are stale, the decision is stale too, which is one reason the chapter insists on fresh telemetry from every pod.

1.4 Local k3d Development vs Production Stack Options​

Engineering teams often prototype manifests locally on k3d before deploying to a production Kubernetes stack such as llm-d, KServe, KubeAI, or the vLLM Production Stack. k3d runs a small Kubernetes cluster inside Docker on a laptop, so it is a good place to check that manifests parse, but it is not a place to measure real GPU behavior. On public clouds, teams also evaluate a six-option build-versus-buy spectrum. That spectrum spans from fully managed APIs like Amazon Bedrock at $0.10 per million input tokens to self-hosted instances at $1.172 per hour. Running open-source models on reserved cloud instances cuts serving costs by 30 to 70 percent and avoids the 50 percent managed surcharge on fine-tuned models. A managed surcharge is the extra fee a provider adds on top of the raw compute price.

2. Admission Control, Token-Based Rate Limiting, Caching, and Guardrails​

2.1 Dual Token-Bucket Rate Limiting (RPM and TPM) and Tenant Quotas​

Imagine two customers sharing one API key on a busy afternoon. The first sends fifty tiny classification prompts in a minute, and each one is quick to answer. The second sends a handful of huge document analyses, and each one keeps the GPU busy for a long time. A gateway that counts only calls sees the first customer as the heavy user, which is backwards. The second sends a handful of huge document analyses. A simple limit of requests per minute treats them the same, even though the second customer is consuming far more of the GPU. In a traditional REST API, limiting each client to a fixed number of requests per second protects the backend because every request performs similar work. In an LLM serving stack, request-based rate limiting alone is dangerous. One client might send fifty short classification prompts of ten tokens each, consuming 500 tokens total. Another client might send ten requests that each contain an 8,000-token context window and generate 2,000 output tokens, consuming 100,000 tokens of GPU time. Furthermore, generating a single output token during memory-bound decoding has roughly the same latency impact as processing 100 input tokens during parallel prefill.

To enforce fair multi-tenant access in Model-as-a-Service platforms, gateways such as the Envoy AI Gateway, Kuadrant, and FastAPI middleware enforce dual Token Bucket rate limits per tenant. A tenant is one customer or one internal team that shares the platform. A token bucket is a counter that fills at a steady rate up to a maximum size, and each request takes some amount from it. The gateway extracts the tenant ID from a verified JWT claim or API key header and checks two independent buckets before admitting any request. JWT is a signed token that carries the tenant's identity.

  • What does the request-count bucket protect? The Requests Per Minute (RPM) bucket protects the gateway, tokenizer thread pool, and continuous batch scheduler from connection floods. A limit of 60 RPM refills at 1.0 request per second up to the burst cap.
  • What does the token bucket protect? The Tokens Per Minute (TPM) bucket protects GPU Tensor Cores and PagedAttention KV cache blocks from long-context exhaustion. A limit of 60,000 TPM refills at 1,000.0 tokens per second up to the token burst cap. On arrival, the gateway pre-deducts the prompt tokens plus the requested maximum output tokens, or reconciles actual generated tokens when streaming finishes. If either bucket is empty, the gateway rejects the request with HTTP 429 and returns the remaining quota and reset timer in response headers.
Dual Token Bucket Rate Limiting Equations (DAI Ch. 9, GAK Ch. 4, HLS Ch. 4):
  Refill update after elapsed time dt = t_now - t_last:
    Avail_req(t_now) = min(B_req, Avail_req(t_last) + dt * (RPM / 60))
    Avail_tok(t_now) = min(B_tok, Avail_tok(t_last) + dt * (TPM / 60))

  Admission condition for request demanding T_req = prompt_tokens + max_tokens:
    Allowed = (Avail_req(t_now) >= 1) AND (Avail_tok(t_now) >= T_req)

  Reset wait time (X-RateLimit-Reset) when rejected (HTTP 429):
    Wait_seconds = max( max(0, 1 - Avail_req) / (RPM / 60),
                        max(0, T_req - Avail_tok) / (TPM / 60) )

  Worked Example (RPM = 10 -> 0.1667 req/s, B_req = 5; TPM = 6,000 -> 100 tok/s, B_tok = 3,000):
    - At t = 0.0 s: 5 burst requests of 500 tokens each (2,500 tokens total) are all ALLOWED.
      Remaining state: Avail_req = 0, Avail_tok = 500 tokens.
    - A 6th request of 500 tokens at t = 0.0 s is REJECTED (HTTP 429) because Avail_req = 0 < 1.
      Wait_seconds = (1 - 0) / (10 / 60) = 6.00 seconds.
    - At t = 6.0 s: Avail_req refills to 1.0, and Avail_tok refills by 6 * 100 = 600 to 1,100 tokens.
      A new request asking for 1,200 tokens is REJECTED by the TPM bucket (deficit = 100 tokens),
      returning X-RateLimit-Reset = 100 / 100 = 1.00 second.

To prevent memory leaks in long-running gateway processes, the rate limiter also runs a periodic cleanup sweep. Without it, every tenant that ever called the gateway would keep a bucket in memory forever. The sweep removes tenant entries that have been idle longer than a configured staleness window such as 3,600 seconds.

2.2 Semantic Caching, Prefix Caching, and Prompt Compression​

Picture a help desk that gets the same question from many customers every hour. Answering it once and reusing the answer is far cheaper than answering it fresh each time. The fastest and most reliable inference request is one whose work you never have to compute on the GPU. Production serving stacks eliminate redundant GPU work at three distinct layers.

First, at the gateway layer, an Endpoint Semantic Cache intercepts incoming prompts before they reach any model runner. A semantic cache matches on meaning rather than on exact text, so "reset my password" and "how do I change my password" can share one answer. The gateway first runs a Named Entity Recognition pass that masks Personal Identifiable Information so tenant secrets never pollute the shared cache. Named Entity Recognition finds names, emails, and similar items in text. It then encodes the sanitized query into a 768-dimensional embedding vector and searches an in-memory vector index. An embedding is a list of numbers that places the text at a point in a meaning space, so similar questions land close together. When cosine similarity exceeds a strict threshold such as 0.95, the gateway returns the cached answer in 3 milliseconds at zero GPU cost. Gateways also apply a 2 to 5 ms request debouncing window to coalesce duplicate submissions when frustrated users double-click submit.

Second, at the application preprocessing layer, Prompt Cleansing and Compression shrinks the input token count. Because prefill self-attention scales quadratically with sequence length, trimming older context saves massive compute. Quadratic scaling means that doubling the prompt length roughly quadruples the attention work. Production chatbots automatically summarize the oldest 25 percent of a conversation whenever the history exceeds 75 percent of the model's maximum context window. On a 32,768-token window, crossing the 24,576-token trigger compresses a 26,000-token history down to 20,800 tokens and cuts quadratic prefill work by 36.0 percent. Similarly, replacing a 200-token natural-language system prompt with 10 learned configuration tokens achieves a 20.0x prefix reduction.

Semantic Cache, Prompt Compression, and Prefix Caching Math (ASP Ch. 16, HLS Ch. 10, AIE Ch. 9):
- NER PII Redaction: PERSON ("John Doe", 0.97) -> <NAME_1>; EMAIL ("john@abc.com", 0.95) -> <Email_1> before 768-dim lookup.
- Quadratic Prefill Work: W(N) = N * (N + 1) / 2.
  Compressing 26,000 tokens -> 20,800 tokens (oldest 6,500 tokens compressed 5x to 1,300 tokens) reduces W(N) by 36.0%.
- System Prompt Prefix Reuse: 1,000-token system prompt x 1,000,000 daily calls = 1,000,000,000 (1B) input tokens saved/day.

A quick way to see why the first two layers matter is to picture a cache hit as a shortcut. If the gateway has already answered a near-identical question, the request never reaches a GPU, and the only cost is a lookup. Each shortcut removes work from the expensive layer below it. The risk is that a shortcut can return a wrong answer if the matching rule is too loose, so the similarity threshold deserves the same care as any other production setting.

Third, at the inference engine layer, Prefix Caching reuses the physical KV cache tensors of shared system prompts, RAG documents, and multi-turn chat histories. A RAG document is a passage pulled from your own knowledge base and pasted into the prompt. You enable it with --enable-prefix-caching in vLLM or RadixAttention in SGLang. Asking 10 separate questions against the same long document processes roughly 10x faster because the document's KV blocks are computed only once. If an application uses a 1,000-token system prompt across one million daily API calls, prefix caching avoids reprocessing one billion input tokens every day.

Prefix caching pays off most when the same long text sits at the start of many prompts. A shared system prompt is the classic example, because every user on the product gets the same instructions before their own question. Once the engine has computed that shared start once, later requests only pay for their own new tokens. The benefit shrinks when every prompt is unique, so measure your real traffic before you count on the gain.

2.3 Runtime Safety Shields: NVIDIA NeMo Guardrails​

Picture a support bot that a customer tricks into printing an internal API key, or an agent that a user talks into calling a payroll database. A well-tuned model can still be talked into this, because a model is a statistical engine, not a security boundary. Even when a model server is fast and well-cached, an unguarded LLM remains a statistical engine. Attackers can trick it with prompt injection, extract secrets, invoke unapproved database tools, or trigger policy hallucinations. Prompt injection means hiding instructions inside the user text so the model follows them. NVIDIA NeMo Guardrails places a programmable policy shield written in Colang around the model without requiring weight retraining. Colang is the small scripting language NeMo Guardrails uses to describe allowed conversation flows.

NeMo Guardrails intercepts execution across five distinct rail stages. A rail is a checkpoint that a request or a response must pass through.

  • What checks the prompt first? Input rails validate prompt length up to 2,048 tokens, redact PII via Presidio, and block jailbreaks or prompt injections before the core LLM sees the text. Presidio is an open-source PII detection library.
  • What keeps the bot on topic? Dialog rails classify user intent with a zero-shot classifier and enforce canonical Colang conversation flows so a banking assistant never gives medical advice. A zero-shot classifier labels text it was never explicitly trained to label.
  • What checks retrieved documents? Retrieval rails filter and validate chunks returned from RAG vector databases before they enter the model context.
  • What guards tool calls? Execution rails enforce strict allowlists and timeouts when an agent invokes external tools or Model Context Protocol servers. For example, a policy can allow queries against production metrics while blocking payroll databases.
  • What checks the answer? Output rails scan generated answers for leaked credentials and run a fact-checking or guardian model such as Llama Guard or Granite Guardian. Output rails also enforce a 0.85 minimum confidence threshold and write an immutable S3 compliance log with seven-year retention.

3. Safe Model Rollouts, Traffic Governance, and SSE Streaming Drain​

3.1 Canary, A/B Testing, Shadow, and Blue-Green Model Rollouts​

A useful habit is to treat every rollout as an experiment with a stop rule written down before it starts. The stop rule names the metrics, the comparison, and the action. Without it, people argue about a dashboard during an incident, and the argument takes longer than the rollback would have.

Consider what a rollback actually costs. Shifting traffic back to the stable version is quick when the old version is still warm and running. It is slow when the old version was already scaled to zero, because its weights must load again before it can answer. That is why blue-green keeps the old environment warm for a while after the cutover, even though it costs extra memory during that window.

When you read a canary report, look at both the error rate and the tail, not only the average. A canary can match the stable version on average and still be worse for the slowest few percent of users. That is exactly the kind of regression that an average hides, and it is the reason the gate uses percentiles.

Picture a Thursday deployment. The team swaps in a new checkpoint that was quantized to a smaller number format to save memory. The unit tests pass and the first few requests look fine. Two hours later, support tickets arrive about answers that sound confident and are wrong. Swapping model weights, upgrading vLLM or TensorRT-LLM versions, or switching a checkpoint from BF16 to FP8 or INT4 quantization can silently break accuracy or spike tail latency. Tail latency means the slowest few percent of requests, which averages hide. Production serving platforms never replace 100 percent of traffic in a single cutover. Instead, they use four complementary rollout patterns.

  • How does a canary limit damage? The gateway shifts a small percentage of live traffic to the new model version while comparing its error rate and latency percentiles against the stable baseline. A standard traffic shifter progresses through 10, 25, 50, 75, and 100 percent. At each step, the controller promotes the canary only if its error rate stays within 10 percent and mean latency stays within 20 percent of the stable version. It rolls back to zero percent if the canary error rate exceeds twice the stable rate or exceeds stable by 5 percent. It also rolls back immediately if p95 latency crosses the 300 ms critical gate.
  • Why compare two models with hashing? While canaries manage rollout risk, A/B tests compare two models, prompt templates, or quantization schemes for product quality. In multi-turn chat, a user must never bounce between Model A on turn one and Model B on turn two. The gateway hashes the test name and user ID with SHA-256 so the same user deterministically lands on the exact same variant across every turn. SHA-256 is a standard hash function, and hashing turns the user ID into a stable bucket.
  • Can you test a candidate without users noticing? Envoy duplicates a fraction of live requests asynchronously to a shadow candidate pool. It then discards the shadow response after logging its latency, token count, and quality score. Shadow testing validates GPU memory stability and kernel throughput under real production prompt distributions with zero user-facing risk.
  • What if you need a fast way back? Two complete environments run concurrently with pre-warmed weights and CUDA Graphs. CUDA Graphs record a sequence of GPU work once so it can be replayed quickly. Once the Green environment passes synthetic smoke checks, the gateway shifts traffic from 1 percent to 10 percent to 100 percent while keeping Blue warm for instant one-second rollback.
Canary Promotion and Rollback Gate Thresholds (DAI Ch. 9, V14 Ch. 4 & Lab 01):
- Traffic shift steps: 10% -> 25% -> 50% -> 75% -> 100% (or 1% -> 10% -> 100% Blue-Green).
- Promotion gate: Canary_Err <= 1.10 * Stable_Err AND Canary_Latency <= 1.20 * Stable_Latency AND p95 < 200 ms.
- Rollback gate: (Canary_Err - Stable_Err) > 0.05 (5%) OR Canary_Err > 2.0 * Stable_Err OR p95 >= 300 ms
  (180 ms baseline: < 200 ms pass, 250 ms [+40%] warning circuit breaker, 300 ms [+67%] critical rollback).

3.2 Server-Sent Events (SSE) Streaming and Graceful Connection Draining​

Picture a user who asks a question and then stares at a blank box while the server works. Even if the answer is correct, the app feels broken. Waiting for the full answer to finish for a 100-token answer to finish before displaying a single word makes an application feel broken. Streaming fixes that feeling by showing each token as it arrives. Humans read 180 to 300 words per minute, which equals roughly 4 to 7 tokens per second for average readers and up to 13 tokens per second for fast readers. Suppose an inference engine generates 20 tokens per second and flushes batches of 5 tokens over Server-Sent Events. Server-Sent Events, or SSE, is a one-way stream in which the server pushes text chunks to the browser over a single open HTTP response. The user sees the first 5-token chunk in just 0.25 seconds instead of waiting 5.0 seconds. That streaming cadence delivers a 20.0x improvement in perceived responsiveness.

When you debug a stream, start from the client and walk backward. Check whether the first chunk arrived, then whether the chunks keep coming, then whether the proxy is holding them. Each step rules out one layer, and the order keeps you from chasing a GPU problem that is really a buffering problem.

Think of a token stream as a conveyor belt that carries words from the GPU to the reader. If the belt jams at the end, the belt backs up all the way to the machine, unless something buffers the parts in between. The safeguards below are the parts that keep the belt moving when one reader is slow. Operating SSE streaming reliably at scale requires four transport and flow-control safeguards. Each one protects a different part of the path between the GPU and the browser.

  1. Why do tokens sometimes arrive in bursts? Nagle's algorithm and proxy buffering can hold small packets back. Interaction between TCP Nagle batching and delayed acknowledgments can stall small token packets for tens of milliseconds (the Linux delayed-ACK timer is about 40 ms, and some stacks use up to 200 ms). Enable TCP_NODELAY on the server socket and pass X-Accel-Buffering: no so proxies flush SSE chunks immediately.
  2. What if one slow phone blocks the GPU? Decouple egress I/O from the GPU loop with bounded buffers. Slow mobile clients must never block the GPU continuous batching loop. A separate async I/O thread buffers outgoing tokens up to a hard cap of 50 to 100 unacknowledged tokens per client. If a stalled client exceeds 100 buffered tokens or clicks a Stop button, the server aborts that sequence and frees its PagedAttention KV blocks immediately.
  3. Can streaming feel steadier? Optional typewriter token pooling helps here. Speculative decoding can burst 20 tokens in 0.5 seconds. Speculative decoding has a smaller draft model guess ahead and the main model check the guesses, so several tokens can appear at once. Inserting a configurable 50 ms smoothing delay creates a steady reading cadence for free-tier users while streaming at full speed for paid tiers.
  4. What stops a runaway answer? Hard generation ceilings do. Enforce a maximum output limit of 4,096 tokens and a server-side generation timeout of 30 seconds so runaway loops never monopolize GPU slots.
Zero-Drop Graceful SSE Connection Draining Sequence (V12 Ch. 3 & 11, DAI Ch. 9):
1. Kubernetes initiates Pod termination (or rolling upgrade) -> Pod enters Terminating state.
2. Container preStop hook executes `sleep 15` (while simultaneously marking /health readiness = 503).
3. Kubernetes Endpoints / EndpointSlice controller and Envoy EPP remove the pod within 5–15 seconds;
   zero new requests are routed to the draining pod.
4. The inference engine receives SIGTERM, stops admitting new requests, and drains active SSE streams:
   For 24 active streams with up to 60 remaining tokens at 20 tok/s:
   Stream_Drain_Time = 60 tokens / 20 tok/s = 3.0 seconds (or up to 60–90 s for long 1,500-token streams).

   All 24 streaming responses finish with `data: [DONE]` and 0% dropped connections before SIGKILL.

Here is what a clean drain looks like from the user's side. The stream keeps flowing, the sentence finishes, and the stream closes with its normal end marker. Nobody sees a cut-off reply. The server gets there by changing the order of events. First it stops being offered new work. Then it finishes the work already in flight. Only at the very end does the process exit. Each of those steps waits for the previous one, so the order matters as much as the time limits.

Streaming creates a severe reliability hazard during pod scale-downs, rolling upgrades, or Triton model reloads. Triton is NVIDIA's model server, and reloading a model means unloading the old copy and loading the new one. Issuing an uncoordinated model unload while traffic is in flight drops 15 percent of active requests immediately with HTTP 503 MODEL_UNAVAILABLE. The fix is to tell the load balancer to stop sending traffic first, and only then let the engine finish what it already started. The sequence below shows that order for a single pod.

Always pair a 120-second termination grace period and a 15-second preStop hook with a Kubernetes PodDisruptionBudget so voluntary node drains never evict more replicas than your spare capacity can absorb. A PodDisruptionBudget is a rule that limits how many replicas a planned drain may take down at once.

4. Kubernetes Health Probes, Silent GPU Deaths, and Hardware Fault Remediation​

4.1 The Zombie Pod Problem and Three-Probe Architecture​

A simple habit helps here. Before you change any probe, write down what question each probe answers and what action Kubernetes takes when it fails. If you cannot name the action in one sentence, the probe is probably measuring the wrong thing.

Often the first clue comes from a teammate's chat message rather than a graph. Someone says the pod looks fine, yet a single client keeps timing out. Trust that report, then go and look at the per-pod queue depth and the per-GPU utilization side by side, because the mismatch between them is where the problem hides.

Picture a Monday morning when the on-call engineer sees that one pod reports healthy, yet its request queue never moves. In a traditional web application, a process crash kills the HTTP server immediately, causing Kubernetes to restart the container and reroute traffic. In an AI inference cluster, the HTTP server runs on the host CPU while the mathematical work executes asynchronously on physical GPUs. If a GPU suffers an uncorrectable hardware ECC memory error or a CUDA stream deadlock, the GPU halts completely. ECC means error-correcting memory, which can detect bad bits on the GPU. A CUDA stream is an ordered queue of GPU work, and a deadlock means the queue waits forever. Meanwhile, the Python or C++ HTTP server on the CPU stays healthy and keeps returning HTTP 200 to naive health checks.

The zombie pod is hard to catch because nothing crashes. Logs look quiet, the restart count stays at zero, and the pod's status reads Running. The only sign is that some requests never finish, and those requests often belong to one unlucky client who retries until the failure is obvious. A team that trusts the pod status alone will not see the problem until users complain.

Kubernetes continues routing live customer prompts to this zombie pod, where every request enters an infinite wait loop. Conversely, if an engineer tries to prevent zombie pods by making the liveness probe run an actual model forward pass, any long prefill batch will delay the probe response. Kubelet then kills healthy, busy containers in a cascading restart storm. Kubelet is the agent on each node that starts, watches, and restarts containers.

Think of a new pod as a restaurant on its first night. The kitchen needs time to set up before it can take orders, and it should not be judged on the first few minutes. Once it is open, the host should seat guests only when the kitchen is ready, and the manager should close the restaurant only when the kitchen has truly stalled. Production LLM containers must strictly decouple initialization, traffic readiness, and process liveness across three distinct Kubernetes probes. A probe is a periodic check that Kubernetes runs against a container. Each probe answers a different question, and mixing the questions causes trouble.

  • Startup probe. Protects slow model initialization while 70 to 140 GB of weights load and CUDA Graphs compile, which takes 2 to 8 minutes. Configure startupProbe on /health with a 30-second initial delay, a 10-second period, and a failure threshold of 60. That grants a 600-second polling window before liveness checks even begin. To shrink cold-start weight loading from minutes to tens of seconds, pair IfNotPresent image policies with local NVMe PVC caching. You can also stream weights in parallel using the Run:ai Model Streamer with 16 concurrent threads.
  • Readiness probe. Controls whether the pod stays in the Kubernetes Service and Envoy InferencePool endpoints. Point readinessProbe to /health with a 5-second period, a 5-second timeout, and a failure threshold of 3. Never set a readiness timeout below 3 seconds. The handler must not submit a dummy inference request into the GPU batch queue. Be aware that the vLLM /health route in v0.32.0 only reports that the engine has not crashed. A hung but live engine still answers 200, so chapter 20.18 section 6 adds a real check: a one-token request, or a watch on the token counter.
  • Liveness probe. Verifies only that the API server process is not deadlocked by querying /ping every 15 seconds with a 3-second timeout and a failure threshold of 5. Never execute model inference inside a liveness probe. Liveness answers whether the process should be killed, readiness answers whether it should receive traffic, and mixing them causes both restart storms and silent pool shrink, as chapter 20.18 section 8 describes. Raise the liveness timeout and failure threshold, move load checks to readiness, and alert when ready replicas fall below desired replicas.

- startupProbe: httpGet /health:8000 | initialDelaySeconds: 30, periodSeconds: 10, failureThreshold: 60 (600 s window / 630 s total).
- readinessProbe: httpGet /health:8000 (or /v2/health/ready, /v1/health/ready) | periodSeconds: 5, timeoutSeconds: 5 (>= 3 s), failureThreshold: 3.
- livenessProbe: httpGet /ping:8000 (or /v2/health/live, /v1/health/live) | periodSeconds: 15, timeoutSeconds: 3, failureThreshold: 5.

4.2 Automated Hardware Fault Remediation (XID 62 + DCGM + NPD)​

Suppose a GPU inside an eight-GPU Tensor Parallel replica hits an uncorrectable Double-Bit ECC memory error or falls off the PCIe bus. Tensor Parallel means one model is split across several GPUs that must talk to each other at every layer. The CUDA context on that GPU deadlocks permanently. A CUDA context is the per-GPU state that holds the work in progress. Because eight-way Tensor Parallelism executes two synchronous AllReduce operations per Transformer layer, the remaining seven healthy GPUs hang forever waiting for the faulted GPU to complete the collective ring. An AllReduce is an operation in which every GPU shares its partial result and receives the combined total, so one missing GPU stalls all the others.

Think of the fault path as a smoke alarm wired to a fire door. The GPU driver senses the fault, the exporter reports it as a number, the node problem detector turns that number into a node condition, and remediation closes the door on new traffic. Each hop is simple, and the chain only works when every hop is wired. Because a lightweight /ping liveness probe only checks the CPU web server, hardware faults must be remediated out-of-band by pairing NVIDIA DCGM Exporter with Kubernetes Node Problem Detector. Out-of-band here means the fix runs beside the serving path rather than through it. DCGM Exporter is the agent that publishes GPU health numbers, and Node Problem Detector is a Kubernetes add-on that reports node faults.

  1. DCGM Exporter monitors kernel driver events and increments dcgm_xid_error the instant a fatal hardware fault such as XID 62 appears in dmesg. It also tracks rising rates of precursor single-bit ECC warnings such as XID 63 and XID 92.
  2. Node Problem Detector matches the fatal XID pattern and immediately marks the node condition unhealthy.
  3. Automated remediation cordons the node via kubectl cordon so no new pods land there. Cordoning only blocks new scheduling. It then drains active pods via kubectl drain so the Deployment or LeaderWorkerSet respawns the replica on a healthy server, and sends the faulted node for nvidia-smi --gpu-reset or hardware replacement.
XID Triage Tiers & Automated Node Remediation Reference (V12 Ch. 11, V19 Ch. 2, V26 Ch. 2):
- Tier 1 (User / App Error): XID 13, 31, 32, 43, 94 (Segfault / OOM) -> Debug application code; run DCGM diag if recurring across apps.
- Tier 2 (Precursor Warning): XID 45, 63, 92 (High single-bit ECC rate) -> Log and monitor trend; schedule preventive maintenance if accelerating.
- Tier 3 (Fatal Hardware Fault): XID 48, 61, 62, 64, 79, 95 (62 is a micro-controller halt, 48 a double-bit ECC error on page 0x0001f4a0, 79 a GPU that fell off the bus; PCI:0000:0f:00.0)
  -> NPD rule on DCGM_FI_DEV_XID_ERRORS ("Xid 62|Xid 79|Xid 92") triggers immediate CordonAndDrainNode.

For example DCGM_FI_DEV_GPU_UTIL (percent) became DCGM_FI_DEV_GPU_UTIL_RATIO (0 to 1), and DCGM_FI_DEV_FB_USED (MiB) became DCGM_FI_DEV_FB_USED_BYTES. 5. Overload Protection: Circuit Breakers, Fallback Cascades, and Cost Resilience​

5.1 Admission Operating Zones and Hysteretic Circuit Breaking​

Picture a product launch that suddenly brings a crowd of new users to the chat box. Every GPU is healthy, yet the queue grows and latency climbs. Even when every GPU is healthy, an unexpected traffic surge can push an inference cluster past its capacity knee. The capacity knee is the point where adding load makes latency rise sharply. An inference engine operates across three distinct capacity zones based on GPU KV cache utilization and waiting queue depth.

Operating ZoneKV Cache UsageQueue Depth & WaitOperational Action
Safe Zone (0%–80%)< 80%< 10 waiting (< 20 ms wait, < 25 ms p99 ITL)Route normally to primary 70B or 700B pool.
Warning Zone (80%–90%)80%–90%10–50 waiting (20–50 ms wait)Trigger KEDA or WVA scale-out at 120% target RPS; throttle batch jobs.

Why must the gateway start shedding load before KV cache usage hits 100 percent? Once the block pool is full, the scheduler preempts running requests. On current vLLM, which preempts by recompute, each victim is put back in the queue and its prefill is repeated, so extra load turns into repeated work and latency for everyone. Chapter 20.18 section 3 describes this and gives the signals: vllm:kv_cache_usage_perc near 1 and vllm:num_preemptions_total rising. Any preemption above zero means you are over-admitting, so reduce admission before adding anything else.

An older incident shows the worst case. On a pre-v0.18 engine, a platform team enabled 32 GB of host swap with --swap-space 32. GPU cache usage reached 99.8 percent and swap usage 88.4 percent. The scheduler preempted 4.2 sequences per second and copied KV blocks back and forth over PCIe, GPU utilisation fell to 18 percent and inter-token latency went from 20 ms to 850 ms. That flag no longer exists, so the case is history, not a setting to tune. Cap --gpu-memory-utilization between 0.85 and 0.92 and keep headroom instead. Chapter 15.3 explains the swap versus recompute arithmetic. Recompute means throwing away the cached state and recalculating it later, while swap means copying it to host memory and back.

Here is the difference in one picture. A full pool is a parking lot with no spaces left. Shedding means the attendant tells new cars at the gate that the lot is full, and each car can go elsewhere. A circuit breaker is a different tool, closer to closing one lane that has a broken car stuck in it, so traffic keeps moving in the other lanes.

Two terms need separating. Shedding load at the gateway means refusing new requests when the pool is nearly full: a 429 says this tenant is over its limit, a 503 with a Retry-After header says this server cannot take the request now, as chapter 20.21 explains. A circuit breaker per replica is a different tool. It ejects a replica that is failing. Chapter 20.21 section 7 notes that a hung replica returns nothing, so the breaker should watch time-to-first-token timeouts and zero tokens while work is queued, not only status codes. Retries must also stay inside a retry budget, or clients amplify the overload. A retry budget caps how many retries the fleet may send as a share of normal traffic.

Before you trust any threshold, run a short drill. Push a synthetic burst at the pool, watch the KV usage and the waiting queue climb, and note the exact moment the breaker opens. Then let the load fall and note the moment it closes. If the breaker closes too early, the gap between the marks is too narrow. If it stays open long after the pool has recovered, the gap is too wide and capacity is being wasted.

Picture a dimmer switch with two marks. Without hysteresis, a single switch point makes the lights flicker every time the load sits right on that point. With two marks, the lights turn off at the high mark and stay off until the load falls well below it. The gap between the marks is what keeps the system calm during a long, noisy peak. The gateway rule used here is: when GPU KV cache usage exceeds 95 percent or waiting requests exceed 50 for 5 seconds, start shedding. To prevent rapid flapping between shedding and normal on every completed request, add hysteresis: keep shedding until KV cache usage drops below 80 percent and the waiting queue drops below 20. Hysteresis means the switch-off point is lower than the switch-on point, so the breaker does not bounce open and closed. Treat these thresholds as starting values to tune against your own traffic.

1. Readiness Probe Cascading Outage During Autoscaling​

During a scheduled traffic promotion, Horizontal Pod Autoscaler scaled the LLM deployment from 4 to 12 replicas. Horizontal Pod Autoscaler is the Kubernetes controller that adds or removes pods based on a metric. Within 90 seconds, all 4 original healthy pods flipped to unready, the ingress controller reported zero healthy endpoints, and cluster-wide HTTP 503 errors hit 100 percent. Inspecting pod events revealed readiness probe timeouts against /v1/models after 1 second. When 8 new pods pulled 70 GB weights simultaneously from shared NFS storage, I/O contention slowed the main Python thread on the 4 existing pods to 1.2 seconds. The readiness probe gave up before the answer came back, so Kubernetes removed the healthy pods too. Pointing the readiness probe to a fast /health status endpoint with a 5-second timeout and caching weights on local NVMe drives eliminates the cascade.

2. Silent GPU Halt (XID 62) and Tensor-Parallel Traffic Blackhole​

Consider an eight-replica cluster where each replica runs Llama-3-70B with eight-way Tensor Parallelism on an eight-GPU HGX node. HGX is NVIDIA's reference eight-GPU server design. During the incident, exactly 12.5 percent of client requests hung until timeout while all pods reported Running. Checking nvidia-smi on the suspect node showed GPU 3 pinned at 100 percent utilization while the other seven GPUs sat at 0 percent. Host dmesg logs revealed an Xid 62 micro-controller halt on GPU 3 that deadlocked ncclAllReduce. That single fault trapped the seven peer GPUs while the CPU HTTP server kept accepting one-eighth of cluster traffic. Deploying DCGM Exporter and Node Problem Detector cordons and drains any node reporting XID 48, 62, 79, or 92 within seconds.

3. PCIe Host-Memory Swap Thrashing (Before v0.18) and Prefill-Starved Decode Stalls​

On vLLM before v0.18, enabling host CPU swapping via --swap-space 32 made the scheduler copy KV pages back and forth across PCIe on every step. That loop dropped GPU utilization to 18 percent and inflated Inter-Token Latency from 20 ms to 850 ms per token. vLLM V1 has no swap, so on a current engine the same pressure shows up as a rising preemption rate and repeated prefills. Shed excess load at the gateway and keep preemptions at zero. Similarly, when unchunked 16,000-token RAG prompts share a GPU with interactive chat, prefill kernels monopolize Tensor Cores and freeze active streams for 3,850 ms. Enabling --enable-chunked-prefill with a 512-token budget restores p99 ITL from 4,500 ms to 22.8 ms. Chunked prefill splits a long prompt into pieces, so decode steps for other users can run between the pieces.

4. Single-Threaded CPU Tokenization Starvation and Silent FP8 NaN Spikes​

When client p99 latency exceeds 1,400 ms while GPU utilization sits below 20 percent, check per-core CPU usage with mpstat. A single Python process locked on the Global Interpreter Lock pins one core at 100 percent while starving the GPU. The Global Interpreter Lock, or GIL, lets only one Python thread run Python code at a time. Switching to a multi-process tokenizer pool raises throughput 7.73x and cuts p99 latency 31.48x. Finally, monitor long-running pods for PyTorch allocator fragmentation over 24 to 48 hours and enable expandable_segments:True. Also scan output rails for non-printable or NaN token spikes above 0.01 percent caused by corrupted FP8 scaling factors, and pass --disable-custom-all-reduce when needed. NaN means not-a-number, a broken value that can spread through the rest of a computation.

Checkpoint questions​

1. Why can up to 60 percent of end-to-end inference latency occur outside the GPU, and how does pinned host memory accelerate Stage 5 and Stage 8 transfers?

An inference request traverses nine stages: TLS ingress, admission queueing, CPU tokenization, batch scheduling, PCIe host-to-device transfer, GPU prefill and decode, logit sampling, device-to-host detokenization, and SSE socket flushing. Standard pageable memory allocated via malloc forces the CUDA driver to copy tensors into a temporary page-locked staging buffer before DMA transfer, capping PCIe Gen5 speed at 10 to 14 GB/s. Allocating pinned memory via cudaHostAlloc allows direct GPU DMA at 55 to 62 GB/s, a 5.0x transfer speedup.

2. How does an AI Gateway route requests across multiple models and multiple engines behind a single endpoint?

The gateway parses the OpenAI-compatible JSON request body. For multi-model routing, it maps the model field to the corresponding Kubernetes ClusterIP service DNS name in the multi-models namespace. For multi-engine routing, it inspects both the model field and the inference server field, routing requests to vLLM or SGLang accordingly while aggregating /v1/models across all backends.

3. How do InferencePool, InferenceObjective, and the Endpoint Picker interact in the Kubernetes Gateway API Inference Extension?

InferencePool groups homogeneous model-serving pods on port 8000 and references an Endpoint Picker service on gRPC port 9002 with FailClose mode. InferenceObjective, which evolved from InferenceModel, defines workload priorities and adapter targets. Envoy Proxy invokes the Endpoint Picker via the External Processing protocol, and the picker scrapes live queue depth, KV cache usage, prefix cache hashes, and loaded LoRA modules to select the optimal pod.

4. How does Ray Serve model multiplexing reduce GPU waste when hosting many domain models?

Instead of dedicating a separate GPU pod to every rarely used model, @serve.multiplexed reads the model ID from the HTTP header and routes matching requests to replicas that already hold that model in memory. When a replica must load a new model beyond its per-replica limit, Ray Serve uses a Least Recently Used policy to evict the oldest cached model.

5. Why is request-based rate limiting insufficient for multi-tenant LLM APIs, and how does dual Token Bucket rate limiting work?

A single request can process 10 tokens or 10,000 tokens, and generating 1 output token costs roughly as much latency as processing 100 input tokens. Dual Token Bucket rate limiting maintains both an RPM bucket and a TPM bucket per tenant. A request is admitted only if at least one request token and enough LLM tokens are available. Otherwise, the gateway returns HTTP 429 with a reset header equal to the longer refill wait of the two buckets.

6. Why must an endpoint-level semantic cache run Named Entity Recognition PII masking before computing embedding vectors?

A user prompt often contains personal identifiers such as a name or email address. Embedding and caching raw text risks leaking one user's PII to another user whose query matches the similarity threshold. Raw identifiers also perturb the embedding vector away from canonical queries. Masking entities to placeholders before computing the 768-dimensional embedding preserves privacy and raises semantic cache hit rates.

7. How does conversation prompt compression at the 75 percent context threshold reduce prefill compute?

Self-attention prefill work scales quadratically with sequence length. On a 32,768-token window, the 75 percent trigger fires at 24,576 tokens. Summarizing the oldest 25 percent of a 26,000-token history by 5x reduces the prompt to 20,800 tokens and cuts quadratic prefill work by 36.0 percent.

8. What are the five rail stages in NVIDIA NeMo Guardrails, and how much latency do they add in the Volume 14 reference budget?

The five Colang rail stages are Input rails, Dialog rails, Retrieval rails, Execution rails, and Output rails. The pipeline adds 15.0 ms for input checks, 30.0 ms for intent classification, 100.0 ms for RAG retrieval, 50.0 ms for output fact-checking, and 10.0 ms for S3 audit logging. On a 45.0 ms base model, total latency reaches 250.0 ms, which is a 5.56x increase.

9. What quantitative criteria govern promotion and automated rollback during a progressive canary rollout?

Traffic shifts in steps from 10 to 25, 50, 75, and 100 percent. Promotion requires the canary error rate to stay within 1.10x of stable, mean latency within 1.20x of stable, and p95 latency below the 200 ms gate. Automated rollback triggers immediately if the canary error rate exceeds stable by 5 percent or exceeds 2.0x the stable rate. Rollback also triggers if p95 latency reaches the 300 ms critical threshold.

10. Why must A/B tests on conversational LLMs use consistent hashing on the user ID instead of per-request random routing?

If a multi-turn user is routed randomly on each request, turn one goes to Model A while turn two goes to Model B. Switching models mid-conversation contaminates user satisfaction metrics and destroys replica prefix-cache locality. Hashing the test name and user ID with SHA-256 guarantees deterministic stickiness across the entire session.

11. How does SSE token chunking improve perceived responsiveness, and why are TCP_NODELAY and a bounded 50–100 token client buffer required?

At 20 tokens per second, a 100-token response takes 5.0 seconds total, but flushing 5-token SSE chunks delivers the first text in 0.25 seconds, which is 20.0x faster perceived responsiveness. Setting TCP_NODELAY prevents Nagle's algorithm and delayed ACKs from adding tens of milliseconds of packet stall (about 40 ms with the Linux delayed-ACK timer). A bounded 50 to 100 token buffer ensures a slow or disconnected client is aborted cleanly without blocking the GPU decode loop.

12. How do you prevent the 15 percent HTTP 503 drop rate during Kubernetes pod termination or model reload?

Configure a PodDisruptionBudget and a container preStop hook that sleeps 15 seconds while failing the /health readiness endpoint first. Kubernetes and Envoy then remove the pod from active endpoints before SIGTERM arrives. Setting a 120-second termination grace period gives the engine ample time to finish streaming all in-flight SSE connections before SIGKILL.

13. Why must Kubernetes startup, readiness, and liveness probes be strictly separated for a 70B LLM container?

Loading 70 to 140 GB of weights and capturing CUDA Graphs takes 2 to 8 minutes, so startupProbe grants a 600-second polling window to prevent restart loops. The readinessProbe checks internal engine status and free KV blocks on /health with a 5-second timeout without queueing a dummy inference pass. The livenessProbe checks only the HTTP process on /ping so a heavy prefill batch never triggers a false container kill.

14. Why does Docker's default shared memory size break multi-GPU vLLM or Triton pods on Kubernetes, and what is the fix?

Docker defaults /dev/shm to 64 MB, whereas multi-GPU Tensor Parallel workers allocate large POSIX shared-memory buffers for NCCL intra-node communication and Python IPC. Exhausting /dev/shm causes NCCL collectives to hang or crash with exit code 139. Mount an in-memory emptyDir volume sized at 8 to 16 GiB at /dev/shm.

15. Walk through the root cause of Worked Failure Scenario 1, where scaling from 4 to 12 replicas caused a 100 percent cluster-wide HTTP 503 outage.

The deployment used a 1-second readiness timeout against /v1/models. When HPA launched 8 new pods that pulled model weights simultaneously over shared NFS storage, I/O contention caused the existing 4 healthy pods to take 1.2 seconds to respond. Kubelet marked all 4 healthy pods unready at once and removed them from the load balancer while the 8 new pods were still initializing.

16. What is an NVIDIA XID 62 error, why did it cause exactly 12.5 percent of cluster requests to hang in Worked Failure Scenario 2, and how is it remediated automatically?

XID 62 is PMU_HALT_ERROR, an internal micro-controller halt logged by the NVIDIA driver in dmesg. The double-bit ECC error is Xid 48. On one eight-GPU Tensor Parallel replica out of eight cluster replicas, GPU 3 deadlocked at 100 percent utilization while the other seven GPUs sat at 0 percent waiting in ncclAllReduce. Because the CPU HTTP server stayed alive, one-eighth of cluster traffic entered a black hole. Pairing DCGM Exporter with Node Problem Detector automatically cordons and drains the node upon detecting XID 48, 62, 79, or 92.

17. Why does current vLLM not swap KV blocks to host memory, and how does gateway load shedding with hysteresis protect the cluster instead?

On an engine before v0.18, a full GPU cache with host swap enabled triggered 4.2 preemptions per second over the 64 GB/s PCIe bus. GPU utilization fell to 18 percent and inter-token latency rose 4,150 percent, from 20 ms to 850 ms per token. vLLM V1 removed swap and preempts by recompute, so that failure cannot be configured any more, but a full cache still forces repeated prefills. The gateway therefore starts shedding when KV usage exceeds 95 percent or waiting requests exceed 50 for 5 seconds, and keeps shedding until KV usage drops below 80 percent.

18. How does OpenTelemetry tracing distinguish a prefill-starved decode stall from a frontend CPU tokenization bottleneck?

The six-span trace isolates exact stage durations across the gateway, tokenizer, and model runner. In a prefill-starved decode stall totaling 4,820 ms, tokenization takes 4 ms while model inference shows a 3,850 ms gap between decode tokens. Enabling --enable-chunked-prefill reduces that p99 ITL to 22.8 ms. In a CPU GIL bottleneck with 1,410.20 ms p99 latency at 13.47 RPS, CPU preprocessing takes 1,395.80 ms while GPU inference takes 18.10 ms. Switching to ProcessPoolExecutor improves throughput to 104.17 RPS and cuts p99 latency to 44.80 ms.

19. How many minutes of downtime per 30-day month are permitted under 99.9%, 99.95%, 99.99%, and 99.999% availability targets?

Over a 30-day month of 43,200 minutes, 99.9% permits 43.20 minutes of downtime, and 99.95% permits 21.60 minutes. A 99.99% target permits 4.32 minutes or 259.2 seconds, while 99.999% permits 0.432 minutes or 25.92 seconds.

20. How do you compute Mean Average Precision and F1 Relevance for a RAG retrieval pipeline, and why is LLM-as-a-Judge run asynchronously on a 1 to 10 percent sample?

For a three-result query where positions 1 and 2 are relevant, average precision is 67%. When positions 1 and 3 are relevant on a second query, average precision is 56%, giving a Mean Average Precision of 61%. The F1 harmonic mean penalizes extreme imbalance, scoring 60.0% for 60% precision and 60% recall versus 45.0% for 90% precision and 30% recall. Running an LLM judge synchronously on all traffic doubles inference cost and adds hundreds of milliseconds to user latency, so production stacks evaluate a 1 to 10 percent sample asynchronously.

Key takeaways​

  1. Up to 60 percent of end-to-end latency happens outside the GPU. Use pinned host memory at 60 GB/s instead of 12 GB/s pageable memory, and move tokenization into a multi-process pool or a Rust tokenizer. Enable TCP_NODELAY SSE streaming so the first five-token chunk reaches the user in 0.25 seconds.
  2. Route on LLM state rather than round-robin. Pair Envoy Proxy with the Kubernetes Gateway API Inference Extension. Let the Endpoint Picker choose by prefix-cache hit ratio, free KV blocks, queue depth, and loaded LoRA adapters.
  3. Protect multi-tenant capacity with dual Token Buckets and layered caching. Enforce both RPM and TPM quotas per tenant, and mask PII before 768-dimensional semantic caching. Compress chat histories above 75 percent context to save 36.0 percent quadratic prefill work, and budget NeMo Guardrails latency explicitly.
  4. Never cut over model versions or kill streaming pods abruptly. Shift canary traffic progressively from 10 to 100 percent with automated error and latency rollback gates. Drain SSE streams using a 15-second preStop hook and a 120-second termination grace period.
  5. Isolate Kubernetes probes and automate XID hardware remediation. Keep startup, readiness, and liveness probes separate. Shed load at the gateway above 95 percent KV usage with hysteresis, because vLLM V1 recomputes preempted requests and has no swap. Wire DCGM Exporter to Node Problem Detector so that XID 62 zombie nodes are cordoned and drained automatically.
