## 4. One-Line Expected Exercise Solutions

1. **Exercise 1 (Counters vs. Profiling vs. Tracing, Observability Sources, and Event-Rate Overhead):** (a) Counters (`vmstat`, `iostat`, `sar`) are always-on kernel integers (nearly zero cost), Profiling (`perf record -F 99`, `49`/`99` Hz to avoid `100` Hz timer lockstep) samples at a fixed rate with predictable low overhead, and Tracing (`perf trace`, Ftrace, eBPF) runs on every event with overhead proportional to event frequency; (b) tracepoints (`~100 ns`/hit) are static/stable and negligible below `10,000` events/s but measurable above `100,000` events/s, kprobes (`50,000+` functions) are dynamic/unstable in-kernel, uprobes trap to the kernel (`~1 µs+`/hit, dangerous on hot `malloc` loops), and `ptrace` (`strace`) stops the target twice per syscall (`> 70%` core cost at `50,000` syscalls/s).
2. **Exercise 2 (`perf stat`, `perf record`, Stack Unwinding `fp`/`dwarf`/`lbr`, and Flame Graphs):** (a) Always run `perf stat` first to check IPC and measure an event's per-second rate before recording/tracing it; `perf record -F 99` uses frequency sampling whereas `-c N` samples every `N`th event; (b) if binaries lack frame pointers (`-fomit-frame-pointer`), `--call-graph fp` produces broken stacks—fix by rebuilding with `-fno-omit-frame-pointer`, using `--call-graph dwarf` (with `-dbgsym`), or `--call-graph lbr` (and `python -X perf` for Python 3.12+).
3. **Exercise 3 (Ftrace via `tracefs`, `trace` vs. `trace_pipe`, `function_graph` Marks, and `hwlat`):** (a) `trace` is a non-consuming snapshot of the ring buffer while `trace_pipe` is a blocking stream that consumes events as read; in `function_graph`, `+` > `10 µs`, `!` > `100 µs`, `#` > `1 ms`, `*` > `10 ms`, `@` > `100 ms`, and `$` > `1 s`; (b) the `hwlat` tracer spins with interrupts disabled to detect external hardware/firmware/SMI or hypervisor steal gaps exceeding `tracing_thresh` (default `10 µs`).
4. **Exercise 4 (eBPF Safety, BCC Canned Tools, and `bpftrace` Latency Histograms):** (a) The kernel eBPF verifier enforces bounded execution and safe memory access before JIT compilation, and BPF maps aggregate counts and histograms (`hist()`) in kernel memory so user space reads only summaries; (b) in the `bpftrace` timing pattern (`kprobe:vfs_read { @start[tid] = nsecs; } kretprobe:vfs_read /@start[tid]/ { @us = hist((nsecs - @start[tid]) / 1000); delete(@start[tid]); }`), the `/@start[tid]/` filter ignores calls that were already in flight before tracing started.
5. **Exercise 5 (BCC vs. `bpftrace` and Choosing the Right Tool for Host Bottlenecks):** Use BCC's canned tools first (`offcputime` for blocked threads, `runqlat` for scheduler latency, `biolatency`/`biosnoop` for disk I/O, `opensnoop`/`nfsslower` for file/NFS latency, `tcplife`/`tcpretrans` for TCP retransmits, `execsnoop` for short-lived process storms like repeated `nvidia-smi` forks) and write ad hoc `bpftrace` one-liners (~30 lines vs ~230 lines in BCC) for custom questions.
6. **Exercise 6 (Correlating Linux Host Tracers with GPU Profilers `DCGM`, `Nsight Systems`, `Nsight Compute`):** Use `DCGM` (`dcgmi dmon`) for always-on fleet GPU counters, **Nsight Systems** (`nsys profile -t cuda,nvtx,osrt,cudnn,cublas`) to view the combined CPU-thread + CUDA kernel + NCCL timeline and locate GPU idle bubbles, `perf record -F 99 -g` / `offcputime` / `biolatency` to explain what the host CPU or storage was doing during those bubbles, and **Nsight Compute** (`ncu`) to analyze individual slow GPU kernels.
