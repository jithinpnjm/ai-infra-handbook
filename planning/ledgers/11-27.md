## 4. One-Line Expected Exercise Solutions

1. **Exercise 1:** The `4` OCI lifecycle stages are `creating -> created -> running -> stopped`; the `5` CRI gRPC methods are `RunPodSandbox -> ImageStatus -> PullImage -> CreateContainer -> StartContainer`; and Kubernetes uses the `containerd` `k8s.io` namespace whereas Docker uses `moby`.
2. **Exercise 2:** Standard `runc` containers run `Pod` objects directly on the shared host Linux kernel with CDI `/dev/nvidia*` bind mounts; **Kata Containers** runs standard `Pod` objects (`runtimeClassName: kata-containers`) inside a lightweight guest-kernel MicroVM (`containerd-shim-kata-v2`) with VFIO GPU passthrough; and **KubeVirt** runs `VirtualMachine` / `VirtualMachineInstance` CRDs inside a `virt-launcher` Pod (`libvirtd` + `qemu-kvm`) supporting persistent Linux/Windows guest OS lifecycles and `vfio-pci` / `vGPU` attachment.
3. **Exercise 3:** Switching a node label from `container` to `vm-passthrough` stops `nvidia-driver-daemonset` and starts `nvidia-vfio-manager` + `nvidia-kubevirt-gpu-device-plugin` (binding physical GPUs to `vfio-pci`), whereas `vm-vgpu` starts `nvidia-vgpu-manager` + `nvidia-vgpu-device-plugin` to expose mediated/SR-IOV vGPU profiles to KubeVirt VMs.
4. **Exercise 4:** Kubernetes `Namespaces` only isolate API objects in etcd while software time-slicing shares one unprotected VRAM pool; **MIG** isolates GPU crossbar ports, L2 cache banks, memory controllers, and DRAM address buses in hardware, but all MIG containers still share the **Host Linux Kernel** (where a root container escape can run `nvidia-smi mig`), which **KubeVirt / Kata / vGPU** closes by placing each tenant in a dedicated guest OS kernel behind a hypervisor.
5. **Exercise 5:** Disk encryption (`AES-256`) only protects Data at Rest, leaving decrypted weights and prompts exposed in plaintext RAM and VRAM (**Data in Use**) to a rogue hypervisor admin; pairing an **AMD SEV-SNP** or **Intel TDX** CPU TEE with **NVIDIA Hopper (`H100`) Confidential Computing** encrypts system RAM, places GPU VRAM in a hardware-protected region, and encrypts CPU-to-GPU PCIe transfers via encrypted bounce buffers.
6. **Exercise 6:** `1.` VM boots and requests hardware quote from CPU TEE & H100 GPU -> `2.` Hardware generates quote with firmware hashes, boot state, and active enclave proof -> `3.` Hardware signs quote using an **unextractable private key fused into the silicon during manufacturing** -> `4.` Client/KMS verifies the signature against the independent **NVIDIA Remote Attestation Service** -> `5.` Only after verification passes does the KMS release decryption keys into the enclave.
