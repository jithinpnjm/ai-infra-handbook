## 4. One-Line Expected Exercise Solutions

1. **Exercise 1 (Cloud Service/Deployment Models, CAPEX vs. OPEX, Operational/Business Trade-Offs, and Technical Challenges, `CN` Chapter 28):** (a) Contrast `IaaS`, `PaaS`, `FaaS`, and `SaaS` across public, private, hybrid, and multicloud deployments; (b) moving to the cloud shifts `CAPEX -> OPEX` and provides elasticity, but **does not remove the need for network design or expert engineers**, introduces **data gravity** (petabyte datasets attract compute because WAN transfer is slow and egress fees are expensive), and requires redesign rather than naive \"lift and shift\".
2. **Exercise 2 (Comparing AWS, Azure, and GCP VPC Models, `NK` Chapter 6):** In **AWS** and **Azure**, a `VPC`/`VNet` is **regional** and each subnet lives inside a single **Availability Zone (`AZ`)** (with stateful `Security Groups`/`NSG`s and stateless subnet `NACL`s), whereas in **GCP**, a **VPC network is global** and **subnets are regional** (spanning all zones in the region, so VMs in `us-central1` and `europe-west1` in the same VPC route over Google's backbone using private IPs without peering).
3. **Exercise 3 (GCP Outbound Access, Peering Non-Transitivity, Shared VPC, and Hybrid Interconnect):** Using `evaluate_vpc_peering_reachability()`: private VMs use **Cloud NAT** for Internet egress and **Private Google Access / Private Service Connect (`PSC`)** for Google APIs; **VPC Network Peering** is **non-transitive** (if VPC A peers with B and B peers with C, A cannot reach C without direct peering or **Network Connectivity Center `NCC`**) and forbids overlapping CIDRs; **Shared VPC** shares subnets from a host project to service projects; and **99.99% HA VPN / Dedicated Interconnect** uses redundant tunnels/metros with **Cloud Router (`eBGP` + `BFD`)**.
4. **Exercise 4 (GCP Load Balancer Taxonomy, Health-Check Firewall Ranges, and `GKE` Container-Native `NEG`s):** Using `check_gcp_lb_health_check_firewall()`: GCP load balancers split along Global vs Regional, External vs Internal, and **Proxy** (`Global/Regional Application LB` L7 Envoy, `TCP/SSL Proxy`) vs **Passthrough** (`Passthrough Network LB` L4 Maglev DSR, preserving client IP), all requiring ingress firewall rules permitting Google's health-check ranges **`35.191.0.0/16` and `130.211.0.0/22`**; in GKE, **Container-Native Load Balancing (`NEG`s)** routes directly from the Google LB to Pod IPs without `NodePort` double-NAT hops.
5. **Exercise 5 (`GKE` VPC-Native Alias IP Sizing and `Dataplane V2`):** Using `plan_gke_vpc_native_capacity("10.100.0.0/20", "10.104.0.0/14", "10.108.0.0/20", 24)`: a `/20` primary subnet (`4,092` usable node IPs), a `/14` Pod secondary range (`1,024` `/24` node slices of `256` Pod IPs each), and a `/20` Service secondary range (`4,096` `ClusterIP`s) cap the cluster at **`1,024` nodes**, while **GKE Dataplane V2 (`Cilium` eBPF)** provides native routing, eBPF service load balancing, and `NetworkPolicy` enforcement.
6. **Exercise 6 (Designing Multi-NIC GPU Cluster Networking in the Cloud: GCP `GPUDirect-TCPX`/`TCPXO`/`RDMA`, AWS `EFA`, and Azure InfiniBand):** On GCP (`A3`/`A3 Mega`/`A3 Ultra`/`A4`), attach `1` management VPC (`eth0`) plus `4` or `8` dedicated GPU data VPCs (`MTU 8244`/`8896`) with **compact placement policies**, **GKE multi-network pods (`GKENetworkParamSet`)**, and the **`GPUDirect-TCPX` / `TCPXO` (`fastrak`) or RoCE RDMA** `NCCL` plugin (analogous to **AWS EFA `SRD` + `aws-ofi-nccl`** on `P5` at `3.2 Tbps` and **Azure NDR InfiniBand** on `ND H100 v5`).
