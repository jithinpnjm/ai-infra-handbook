## 4. One-Line Expected Exercise Solutions

1. **Exercise 1 (End-to-End `curl` Sequence and `strace` Verification):** Narrate the 9 stages of `curl https://example.com/`: (1) URL parsing (`https`, `example.com`, port `443`, `/`), (2) `getaddrinfo()` checking `/etc/nsswitch.conf` and `/etc/hosts`, (3) UDP/53 DNS query for `A` and `AAAA` records, (4) `socket(AF_INET, SOCK_STREAM)` and `connect()` route lookup (`ip route get`) + ephemeral source port (`32768–60999`), (5) ARP (`ff:ff:ff:ff:ff:ff`) or IPv6 NDP for the next-hop gateway's MAC (`ip neigh`), (6) TCP 3-way handshake (`SYN`, `SYN-ACK`, `ACK`), (7) TLS 1.3 1-RTT handshake (`ClientHello` with SNI + ALPN -> `ServerHello` + X.509 cert chain + `Finished`), (8) encrypted `GET /` request and HTTP response, and (9) `FIN`/`ACK` teardown (`TIME_WAIT` `~60 s`).
2. **Exercise 2 (Name Resolution: `nsswitch.conf`, `systemd-resolved`, and Kubernetes `ndots:5`):** `/etc/nsswitch.conf` (`hosts: files resolve dns`) checks `/etc/hosts` before querying `127.0.0.53` (`systemd-resolved`) or upstream DNS servers in `/etc/resolv.conf`; in Kubernetes Pods (`ndots:5`), a name like `example.com` (1 dot < 5) is appended to every `search` domain (`default.svc.cluster.local`, `svc.cluster.local`, `cluster.local`) for both `A` and `AAAA` queries before trying `example.com.` directly.
3. **Exercise 3 (Routing Lookup, ARP vs. Off-Subnet Gateway MAC, and Hop-by-Hop Rewrites):** For off-subnet destination `93.184.216.34`, `ip route get 93.184.216.34` selects the default gateway `10.0.0.1` (`dev ens4 src 10.0.0.15`), so the outgoing Ethernet frame's destination MAC is the **gateway's MAC**, not the final server's MAC; across router hops (`simulate_router_hop_headers()`), source and destination MACs are rewritten and IP `TTL` is decremented at every router hop, while source and destination IP addresses remain unchanged (except where rewritten by edge NAT/PAT).
4. **Exercise 4 (TCP 3-Way Handshake, `Connection refused` vs. `Connection timed out`, and PMTUD):** A closed TCP port where no process is listening elicits an immediate `RST` packet from the server kernel (`Connection refused`), whereas a firewall `DROP` rule or blackhole produces silence and exponential `SYN` retransmissions (`1 s, 2 s, 4 s...` -> `Connection timed out`); if ICMP `Fragmentation Needed` / `Packet Too Big` is blocked along the path, Path MTU Discovery breaks, so small handshakes succeed while full-MTU (`1500` B, `MSS 1460`) bulk transfers stall (`ping -M do -s 1472`).
5. **Exercise 5 (Decomposing `curl -w` Timings and Diagnosing `curl` Exit Codes):** Because `curl -w` timestamps are cumulative from start (`decompose_curl_timings()`), `dns = time_namelookup`, `tcp_connect = time_connect - time_namelookup`, `tls_handshake = time_appconnect - time_connect`, `server_wait = time_starttransfer - time_pretransfer`, and `body_transfer = time_total - time_starttransfer`; exit code `6` is DNS failure, `7` is connect failure, `22` is HTTP 4xx/5xx (`-f`), `28` is timeout, `35` is TLS handshake failure, and `60` is X.509 certificate verification failure.
6. **Exercise 6 (TCP/IP vs. Kernel-Bypass RDMA in AI Clusters):** Distributed training jobs (`torchrun`, `MPI`, `NCCL`) use the standard Linux kernel TCP/IP stack (`getaddrinfo`, routing table, ARP, `qdisc`, sockets) for **control-plane rendezvous and bootstrap**, then switch to **RDMA verbs** (`InfiniBand` or `RoCEv2` with `GPUDirect RDMA`) for bulk collective tensors—bypassing the kernel socket layer, routing table, and `qdisc` so the NIC DMAs directly from GPU `HBM` (making bulk training traffic invisible to `tcpdump` and `iptables`).
