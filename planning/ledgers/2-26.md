## 4. One-Line Expected Exercise Solutions

1. **Exercise 1 (How Linux Packet Capture Works: `libpcap`, `AF_PACKET`, Kernel BPF, Snaplen, and Offload Artefacts):** `libpcap` opens an `AF_PACKET` socket (`PACKET_MMAP` ring buffer) and attaches compiled **BPF bytecode** (`tcpdump -d`) in the kernel so non-matching packets are dropped before copying to user space; because `AF_PACKET` taps outgoing packets **before** the NIC hardware, **TX checksum offload** causes false `[bad tcp cksum]` warnings and **`TSO`/`GSO` (and `GRO` on RX)** causes `64 KiB` super-packets to appear in captures.
2. **Exercise 2 (Writing `pcap-filter` Capture Filters and Byte-Offset Expressions):** Using `evaluate_pcap_byte_offset_filters()`: exclude your own SSH session with `not port 22`; match pure TCP `SYN`s (without `SYN-ACK`) using `'tcp[tcpflags] & (tcp-syn|tcp-ack) == tcp-syn'`; match `RST`/`FIN` with `'tcp[tcpflags] & (tcp-rst|tcp-fin) != 0'`; match IPv4 More-Fragments with `'ip[6:2] & 0x2000 != 0'`; match DSCP `EF` (`46`) with `'ip[1] & 0xfc == 0xb8'`; match ECN `CE` with `'ip[1] & 0x3 == 3'`; and match PFC (`ether proto 0x8808`), LACP (`0x8809`), LLDP (`0x88cc`), and RoCEv2 (`udp dst port 4791`).
3. **Exercise 3 (`tcpdump` vs. `tshark` vs. Wireshark, Capture Filters `-f` vs. Display Filters `-Y`, and Lab TLS Decryption):** Capture filters (`tcpdump` / `tshark -f`) run in kernel BPF at capture time with limited header syntax, whereas display filters (`tshark -Y` / Wireshark) run in user space across 3,000+ protocol dissectors (`tcp.analysis.retransmission`, `tcp.analysis.zero_window`, `vxlan.vni == 10100`, `ib.bth.opcode`); to decrypt TLS 1.3 in a lab, set **`SSLKEYLOGFILE=/tmp/keys.log`** in the client and pass `-o tls.keylog_file:/tmp/keys.log` to `tshark`/Wireshark.
4. **Exercise 4 (Capturing on `100G`–`400G` Links, Ring Buffers, Containers, and `RDMA` Fabrics):** Using `compute_capture_rate_and_ring_storage()`, a `100 Gb/s` link at `1500` B carries **`~8.13 million` packets/s**; avoid kernel buffer drops by filtering tightly in BPF, truncating to headers (`-s 96`), raising `-B 65536`, using rolling ring buffers (`-C 100 -W 10`), capturing inside containers via `sudo nsenter -t <pid> -n tcpdump`, and using **`ibdump` / `tcpdump -i mlx5_0` (RDMA sniffer) or switch `SPAN`/`ERSPAN`/optical `TAP`s** for kernel-bypassed RoCEv2/GPUDirect traffic.
5. **Exercise 5 (Two-Endpoint Capture Correlation and Reading TCP Failure Signatures):** Using `diagnose_two_side_tcp_capture()` on time-synchronized (`PTP`/`NTP`) client + server captures: `SYN` arriving at the server with no `SYN-ACK` proves a server firewall or listen-backlog drop; `SYN-ACK` leaving the server but never reaching the client proves a return-path or asymmetric-NAT drop; repeated full-MTU retransmissions with no ICMP `3/4` prove a **PMTU black hole**; `win 0` proves a slow receiving app; and a `RST` whose IP `TTL` differs from the peer's normal segments proves a **middlebox-injected reset**.
6. **Exercise 6 (Complementing `pcap` with `BCC` and `bpftrace` Kernel Tracing, `SP` Chapter 15):** While `tcpdump` shows wire headers, `BCC` (`tcplife`, `tcpretrans`, `tcpconnlat`, `tcpdrop`) and `bpftrace` (`tracepoint:tcp:tcp_retransmit_skb`, `tracepoint:skb:kfree_skb`, `kprobe:tcp_sendmsg`, `uprobe:libssl.so.3:SSL_write`) run verified eBPF programs in the kernel and aggregate into in-kernel maps (`count()`, `hist()`) to reveal *which PID/process* sent the traffic, *what plaintext passed into TLS*, and *which exact kernel function dropped the `sk_buff`*.
