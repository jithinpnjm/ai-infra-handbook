## 4. One-Line Expected Exercise Solutions

1. **Exercise 1 (Comparing `Ansible`, `Nornir`, `Terraform`, and Controllers Across the 10 Automation Axes, `NPA` Chapter 12):** **Terraform** is declarative infrastructure provisioning with explicit state (`terraform.tfstate`, `plan`/`apply`) for cloud VPCs and controllers; **Ansible** is stateless, agentless YAML configuration management running on the control node via connection plugins (`network_cli`, `netconf`, `httpapi`, `grpc`); and **Nornir** is a pure-Python threaded automation framework (`num_workers: 20`) for fast, unit-testable custom workflows.
2. **Exercise 2 (Ansible for Networks: Connection Plugins, Variable Precedence, Vault, `serial` Batching, and Resource Modules):** Network switches lack on-box Python, so Ansible executes modules on the control node over `ansible.netcommon.network_cli`/`netconf`/`httpapi`; using `simulate_serial_batch_rollout()`, `serial: "25%"` with `max_fail_percentage: 0` rolls through 8 leaves in 4 batches of 2 and halts immediately if a single switch fails BGP post-validation (`until: ... Established`), while `compute_idempotent_config_diff()` and resource modules (`state: merged|replaced|overridden`) ensure idempotency (`--check --diff`).
3. **Exercise 3 (Nornir Tasks, Threaded Execution, and `dry_run` Diffs):** Nornir loads `hosts.yaml`, `groups.yaml`, and `defaults.yaml`, filters targets (`nr.filter(role="leaf")`), and runs Python task functions (`build` -> `deploy(dry_run=True)` -> `verify`) concurrently across a thread pool while returning structured `AggregatedResult` objects testable with `pytest`.
4. **Exercise 4 (The Five Components of a Network CI/CD Pipeline and Deployment Strategies, `NPA` Chapter 13):** Using `evaluate_network_ci_pipeline()`: a network CI pipeline combines (1) **Peer review** (PR + rendered config diff), (2) **Build automation** (`yamllint`, `ansible-lint`, `pytest` schema + golden files, `Batfish` offline analysis), (3) **Test/emulation environment** (`containerlab`), (4) **Deployment validation** (operational state, connectivity, performance), and (5) **Deployment strategy** (*in-place*, *rolling*, *canary*, or *blue/green*).
5. **Exercise 5 (The Six Components of Network Automation Architecture and Source-of-Truth Design, `NPA` Chapter 14):** The 6 architectural blocks are **User Interactions** (GUI/ITSM/ChatOps), **Orchestration** (thin cross-domain workflow coordinator), **Source of Truth (`SoT`)** (`NetBox`/`Nautobot` relational DB + Git YAML for templates/intent, enforcing the 6 data-quality dimensions), **Automation Engine** (backup, render, compliance, deploy, and 5-step NOS upgrades), **Network Infrastructure**, and **Telemetry & Observability** (closed-loop gNMI/Prometheus/Alertmanager).
6. **Exercise 6 (On-Box Automation, Controllers, `VNF`s / Service Chaining, Intent-Based Networking, and the Complexity Lens, `CN` Chapters 26 & 27):** Contrast **on-box automation** (local event scripts/SONiC services) with **off-box controllers** (`Apstra`, `CloudVision`, `NVIDIA UFM`/`NetQ`); explain **Virtual Network Functions (`VNF`s / `CNF`s)**, **service chaining**, and **DPU/SR-IOV/DPDK** acceleration; and analyze automation trade-offs using `CN` Chapter 26's **state / optimization / interaction-surface** triangle.
