## 4. One-Line Expected Exercise Solutions

1. **Exercise 1 (`<cuda/pipeline>` & 3-role `SMEM` sizing):** (a) `gemm_tiled_pipeline` at `TILE_SIZE = 32` uses `4 * 1,024 * 4 = 16,384 B` (`16 KiB`, `STAGES = 2`) and `6 * 1,024 * 4 = 24,576 B` (`24 KiB`, `STAGES = 3`); (b) `warp_specialized_pipeline_kernel` uses `3 * 112^2 * 4 = 150,528 B` (`< 227,328 B` Blackwell limit, fits) at `TILE_SIZE = 112`, whereas `TILE_SIZE = 160` requires `3 * 160^2 * 4 = 307,200 B` (`> 227,328 B`, fails); (c) `warp_specialized_cluster_pipeline` at `TILE_SIZE = 128` uses `3 * 16,384 * 4 = 196,608 B` (`192 KiB`) per CTA and assigns `64` rows/CTA (`2` CTAs) or `32` rows/CTA (`4` CTAs).
2. **Exercise 2 (Table 10-5 4-stage progression):** Time drops `41.3 -> 20.5 (2.01x) -> 18.4 (+10.2%) -> 17.2 ms (+6.5%, 2.40x total)`; warp efficiency climbs `68% -> 92% -> 96% -> 97%`; L2 throughput rises `80 -> 155 (+94%) -> 165 (+6.45%) -> 170 GB/s (+3%)`; instructions drop `1.7 B -> 1.05 B (-38%) -> ~1.00 B (-4.76%) -> ~0.98 B (-2%)`; warp scalability grows from `2–3` warps/SM (naive) and `~6` warps/SM (2-stage) to `64` warps/SM (warp-specialized and cluster pipeline).
3. **Exercise 3 (Persistent kernel math & occupancy):** (a) `1,000` separate launches add `1,000 * 0.02 = 20.0 ms` overhead (`120.0 ms` total at `~35%` GPU utilization) vs `0.02 ms` (`100.02 ms` total, saving `19.98 ms ~ 20 ms`) for `1` persistent launch; (b) `132 * 256 = 33,792` persistent threads; (c) `1` block of `256` threads on each of the `132` SMs gives `256 / 2,048 = 12.5%` (`~12%`) per-SM thread occupancy while keeping `100%` of the `132` SMs continuously active.
4. **Exercise 4 (Cooperative Grid sizing & `combinedKernel`):** (a) Replaces `2 * 1,000 = 2,000` launches with `1` launch (`1,999` launches eliminated); (b) unclamped `(1,000,000 + 255) // 256 = 3,907` blocks vs `maxCoopGrid = 4 * 132 = 528` co-resident blocks; (c) launching `3,907 > 528` blocks with `cudaLaunchCooperativeKernel` fails immediately (`cudaErrorCooperativeLaunchTooLarge`) because all blocks must co-reside for `grid.sync()`.
5. **Exercise 5 (Table 10-4 DSMEM pair & TMA multicast vs DSMEM rule):** Table 10-4 shows global loads drop `2x -> 1x`, L2 hit rate jumps `50% -> 85%`, DRAM BW/CTA drops `300 -> 150 GB/s` (`-50%`), and kernel time drops `1.0x -> 0.6x` (`40%` speedup); use **TMA Multicast (`cp.async.bulk.tensor` to `shared::cluster`)** when per-block tile reuse is high or cluster size is large (`8–16` CTAs), and use **DSMEM `map_shared_rank()`** when SMEM is tight or cluster size is small (`2–4` CTAs) with single-touch follower reads.
6. **Exercise 6 (Broken pipeline sync snippets):** (a) A unified CTA pipeline (`cuda::make_pipeline(cta, &pipe_state)`) requires all threads in `cta` to call `producer_acquire`, `producer_commit`, `consumer_wait`, and `consumer_release` collectively outside divergent `warp_id` branches; (b) `cuda::pipeline` (`thread_scope_block`) is scoped only to its creating CTA, so rank 0's `producer_commit()` never synchronizes follower CTAs—followers must wait on `cluster.sync()` before reading rank 0's SMEM via `map_shared_rank()`.
