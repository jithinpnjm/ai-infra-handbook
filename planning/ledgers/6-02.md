## 4. One-Line Expected Exercise Solutions

1. **Exercise 1 (32-Node GPU Cluster Port and Power Sizing):** Using `plan_cluster_power_and_ports(32, 8, 10.0, 2, 2, 0.10)`, the cluster needs `256` compute-fabric ports, `36` in-band Ethernet ports, `36` out-of-band BMC ports, `320.0 kW` raw compute power, and `352.0 kW` with `10%` headroom, while multiplying server power by `1.5–2.0` estimates total facility power including cooling, storage, switches, and UPS losses.
2. **Exercise 2 (Network Latencies `Table 4-1` and 3D Torus vs. Hypercube Topologies):** MPI latency drops from `50 us` (`1 GbE`) and `25–30 us` (`10 GbE`) to `1–3 us` (`100 GbE` and `InfiniBand`, `4–5 us` on `SlingShot`), and `torus_3d_max_hops()` gives `[8/2]+[8/2]+[8/2] = 12` hops for an `8x8x8` 3D torus and `2+3+4 = 9` hops for a `5x7x9` 3D torus (compared to `N` hops in an `N`-D hypercube).
3. **Exercise 3 (BIOS HyperThreading vs. Scheduler Core Declaration and NUMA Pinning):** `scheduler_declared_cores(2, 64, 2)` leaves BIOS HyperThreading enabled (`256` OS logical CPUs) while declaring `128` physical cores to Slurm so compute tasks get 1 physical core each and OS daemons use the `128` sibling threads, while CPU and memory `NUMA` pinning (`numactl`/MPI) prevent millisecond OS core migration and slow cross-socket memory reads.
4. **Exercise 4 (Node Role Rules: Local Disks, License Server MACs, `VSCode` Traps, and Pre-/Postprocessing Nodes):** Local disks add cost, heat, power, and failure points but provide local OS boot, swap, and `/tmp`; `VSCode remote` plugins spawn heavy language servers that can paralyze shared login nodes without per-user cgroup limits; pre-/postprocessing nodes require `256 GB+` RAM; and recording a `FlexLM` license server's MAC address lets a replacement server spoof the old MAC for immediate recovery.
5. **Exercise 5 (The 5 Verification Check Types, 8-Column Runbook Schema, and Node Hardening):** The 5 checks are full cluster, performance verification, node performance, node readiness, and periodic node health; `validate_runbook_schema()` checks `phase`, `action`, `start`, `duration`, `dependency`, `owner`, `status`, and `info`; and `molly-guard` prevents accidental service-node reboots while `ssmtp`/`nail` and local `systemd` timers replace `postfix` and central SSH cron storms.
6. **Exercise 6 (The Job Life Cycle and Invisible Cluster Services):** A job moves through `ssh` login -> queueing (`sbatch`) -> scheduling & `prolog` -> parallel startup (`mpirun`/`srun`) -> `epilog` cleanup & accounting, backed invisibly by account sync, parallel storage, quotas, node/facility monitoring, UPS shutdown, and backups (which is why a 2-laptop `ssh`+`NFS` setup collapses at 20 nodes).
