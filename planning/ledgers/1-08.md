## 4. One-Line Expected Exercise Solutions

1. **Exercise 1 (Signal Delivery Across States & `PID 1`):** (a) `SIGKILL` (`9`) to a `D`-state process is deferred (`delivered_immediately = False`) until the kernel I/O call finishes; (b) `SIGKILL` to a `Z`-state zombie does nothing (`ignored_already_dead_zombie`); (c) `SIGTERM` (`15`) to a container `PID 1` with no custom handler is ignored by kernel `PID 1` protection; (d) `SIGKILL` (`9`) to container `PID 1` terminates it immediately (`137`).
2. **Exercise 2 (Load Average & `vmstat` Diagnosis):** (a) `load = 60.0` on `16` CPUs with `b = 48` and `id = 90%` is `uninterruptible_io_wait_D_state` (processes stuck in `D` state on storage/NFS); (b) `so = 500` is `memory_swapping_thrashing`; line 1 of `vmstat 2` must be ignored because it reports the average since boot rather than current activity.
3. **Exercise 3 (`time` & Page Faults):** (a) `real = 0.442s` vs `user + sys = 0.143s` is `io_network_or_lock_wait`; (b) `real = 10.0s` vs `user + sys = 78.0s` is `multithreaded_parallel_cpu` (~7.8 cores); (c) the `254` minor page faults require zero disk I/O because the pages (such as shared `libc.so.6` code or zero-filled heap pages) are already in RAM and only need page-table entries wired up.
4. **Exercise 4 (`cgroup v2` `cpu.max`, `memory.max`, & Leaf Rule):** (a) `"50000 100000"` allows `50,000 / 100,000 = 0.5` CPU cores; exceeding `cpu.max` throttles the cgroup (`nr_throttled`), whereas exceeding `memory.max` (`200M`) invokes the cgroup OOM killer (`oom_kill`, exit `137`); (b) under `cgroup v2`'s no-internal-process constraint, non-root cgroups that have child cgroups (`sub1`) cannot hold processes directly—processes may reside only in leaf cgroups.
5. **Exercise 5 (`nice`, `ionice`, & `limits.conf` vs `systemd`):** (a) `nice` runs from `-20` (highest priority) to `+19` (lowest priority), so `ionice -c 3 nice -n 19` runs `rsync` at lowest CPU priority and idle disk I/O class; (b) `/etc/security/limits.conf` is enforced by `pam_limits.so` during interactive logins, whereas `systemd` spawns service daemons directly without PAM login sessions and uses unit directives like `LimitMEMLOCK=infinity`.
6. **Exercise 6 (Graceful Shutdown in Containers & Slurm):** (a) Without `exec`, `/bin/sh` remains `PID 1` and does not forward `SIGTERM` to `python train.py`, so Kubernetes waits `30 s` and sends `SIGKILL` (`137`); (b) in `#SBATCH --signal=B:USR1@180`, `bash` defers `trap` handlers while waiting on a foreground command, so running `python train.py &` and `wait "$pid"` lets `bash` catch `SIGUSR1` immediately and forward it to `$pid`.
