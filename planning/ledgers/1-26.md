## 4. One-Line Expected Exercise Solutions

1. **Exercise 1 (Emulators vs. Hardware-Assisted Virtualization, Config A vs. Config B, and VM Exits):** (a) An emulator (`QEMU` TCG) translates every guest instruction in software, whereas hardware-assisted virtualization (`KVM` + `VT-x`/`AMD-V`) executes guest instructions natively on the CPU in VMX non-root mode and traps to the hypervisor (**VM exit**) only on privileged events (`HLT`, `MSR_WRITE`, `IO_INSTRUCTION`/`MMIO`, `EPT_VIOLATION`, `EXTERNAL_INTERRUPT`); (b) Config A (Xen) runs a bare-metal hypervisor with a privileged `dom0`, while Config B (KVM) loads `kvm.ko`/`kvm_intel.ko` into the Linux host kernel so each VM is an ordinary `qemu-system-x86_64` process and each vCPU is a `CPU n/KVM` Linux thread; exits handled in `kvm.ko` are fast, whereas exits returning from `KVM_RUN` to user-space QEMU (`IO_INSTRUCTION`/`MMIO`) are much more expensive.
2. **Exercise 2 (Nested Paging `EPT`/`NPT`, 2D Page Walks, and Huge Pages):** A guest has Guest Virtual (GVA), Guest Physical (GPA), and Host Physical (HPA) addresses; under hardware nested paging (`EPT`/`NPT`), a TLB miss on 4-level guest + 4-level host page tables requires up to `4 * (4 + 1) + 4 = 24` memory reads (`compute_2d_page_walk_max_reads()`), which is why backing both host (`<hugepages/>`) and guest with `2 MiB` or `1 GiB` huge pages drastically reduces page-walk depth and boosts TLB reach.
3. **Exercise 3 (I/O Virtualization Spectrum: Full Emulation, `virtio`, `vhost`, `SR-IOV`, and `VFIO`):** Full emulation (`e1000`, `IDE`) traps to QEMU on every register access; `virtio` (`virtio-net`, `virtio-blk`, `virtio-scsi`) uses shared-memory `virtqueues` between guest and host; `vhost` (`vhost-net` in-kernel or `vhost-user` DPDK/SPDK) moves the `virtio` data plane out of the QEMU process; `SR-IOV` splits one physical NIC/GPU (`PF`) into hardware Virtual Functions (`VF`s) passed directly to guests; and `VFIO` passes an entire physical PCIe device exclusively to a guest using the hardware **IOMMU** (`VT-d`/`AMD-Vi`) to translate and isolate DMA.
4. **Exercise 4 (Storage Formats `raw` vs. `qcow2`, `cache=none`, and Networking Modes):** `raw` has zero metadata overhead, while `qcow2` supports thin provisioning, backing-file copy-on-write overlays (`qemu-img create -f qcow2 -F qcow2 -b base.img vm1.qcow2`), and snapshots; always set `cache='none'` (`O_DIRECT`) on `virtio` disks to avoid **double caching** in both the guest page cache and host page cache.
5. **Exercise 5 (Observing VMs from Host and Guest: `pidstat -tp`, `perf kvm stat`, and `%steal`):** On the host, `pidstat -tp <qemu-pid> 1` shows `%guest` (time executing guest code) vs `%system`/`%usr` (hypervisor/QEMU exit overhead) per `CPU n/KVM` thread, and `sudo perf kvm stat report` (or `bpftrace` on `t:kvm:kvm_exit` / `t:kvm:kvm_entry`) breaks down exit counts and durations (remembering that long `HLT` durations simply mean the vCPU was idle). Inside the guest, `%steal` (`st` in `vmstat`/`mpstat`) measures time a runnable vCPU waited because the host scheduled another thread or throttled the VM's cgroup.
6. **Exercise 6 (VFIO GPU Passthrough, IOMMU Groups, OVMF 64-Bit BARs, and Guest Topology):** To pass a GPU (`0000:3b:00.0`, `10de:2330`) to a KVM guest: enable `intel_iommu=on` / `amd_iommu=on`, verify all functions in the GPU's **IOMMU group** (`validate_iommu_group_passthrough()`) are bound to `vfio-pci`, configure the guest with `q35` + `OVMF` (with a 64-bit MMIO window `X-PciMmio64Mb=262144` for large GPU BARs), lock guest huge-page memory (`<hugepages/><locked/>`), pin vCPUs and memory to the GPU's physical NUMA node, and expose accurate PCIe/NUMA/NVSwitch topology (`nvidia-smi topo -m`) so GPUDirect RDMA and NCCL do not degrade.
