## 4. One-Line Expected Exercise Solutions

1. **Exercise 1 (Real, Effective, and Saved UIDs, Setuid Risks, and Safe Account Editing):** (a) The kernel checks the **effective UID (`euid`)** for file and privilege permissions, the **real UID (`ruid`)** for who started the process and may signal it, and the **saved set-user-ID (`suid`)** so a setuid program can drop and re-acquire privileges; (b) always edit `/etc/passwd` with `sudo vipw` and `/etc/shadow` with `sudo vipw -s` (and `/etc/sudoers` with `sudo visudo`), mount user-writable filesystems `nosuid,nodev`, and use `sudoedit` rather than `sudo vim` (which allows shell escapes).
2. **Exercise 2 (PAM Function Types, Control Flags, and Tracing the `chsh` Stack):** (a) The 4 PAM types are `auth` (identity verification), `account` (account validity/access policy), `session` (setup/teardown such as `pam_limits`, `pam_systemd`, `pam_slurm_adopt`), and `password` (updating credentials); (b) in the `chsh` stack (`sufficient pam_rootok.so`, `requisite pam_shells.so`, `sufficient pam_unix.so`, `required pam_deny.so`), `requisite` stops immediately on failure without running `pam_unix.so`, whereas an earlier `required` failure remembers the failure so a later `sufficient` success still fails overall.
3. **Exercise 3 (Linux Capabilities, the 5 Capability Sets, and `no_new_privs`):** (a) The 5 thread capability sets are `Permitted`, `Effective`, `Inheritable`, `Bounding`, and `Ambient`; a GPU container needs `/dev/nvidia*` device nodes + device-cgroup access (not `--privileged`), and an RDMA job needs `CAP_IPC_LOCK` (`ulimit -l unlimited`); (b) setting `no_new_privs` (`PR_SET_NO_NEW_PRIVS`) prevents `execve()` from granting any new privileges via setuid bits or file capabilities (`security.capability`), which is why unprivileged processes must set `no_new_privs` before installing a `seccomp-bpf` filter.
4. **Exercise 4 (DAC vs. MAC, Diagnosing SELinux Denials Without `setenforce 0`, and AppArmor):** (a) DAC (`chmod`/`chown`/ACLs) is controlled by the file owner and bypassed by root, whereas MAC (`SELinux` type enforcement `user:role:type:level` or `AppArmor` path profiles) enforces system-wide policy even on root; (b) diagnose SELinux denials via `sudo ausearch -m avc -ts recent` and `sealert`, then fix the boolean (`setsebool -P container_use_devices on`), persistent file context (`semanage fcontext -a -t container_file_t ... && restorecon -Rv`), or port (`semanage port`), never by leaving `setenforce 0`.
5. **Exercise 5 (SSH Certificates, `pam_slurm_adopt`, and Hardening GPU/HPC Nodes Without Breaking Workloads):** (a) SSH certificates (`TrustedUserCAKeys`, short TTLs, `ProxyJump` bastions) eliminate copying `authorized_keys` across thousands of nodes, while `pam_slurm_adopt` restricts compute-node SSH logins to users with an active Slurm job on that node and places their SSH session inside the job's cgroup; (b) on GPU/HPC nodes, adjust CIS rules to write core dumps to a root-protected `/var/crash` directory, keep `kernel.yama.ptrace_scope=1` (not `2`/`3`, which break `gdb` and MPI CMA), permit RoCEv2 UDP `4791` (and use IB `PKeys` since host firewalls do not see native InfiniBand RDMA), and sign `nvidia.ko` with a MOK under UEFI Secure Boot.
6. **Exercise 6 (Kubernetes Admission Chain, Pod Security Standards, and Webhook Failure Policies):** Every Kubernetes API request traverses Authentication -> RBAC Authorization -> **Mutating Admission** -> Schema Validation -> **Validating Admission** -> `etcd`; Pod Security Admission enforces `privileged`, `baseline`, and `restricted` standards via namespace labels, while dynamic webhooks (`failurePolicy: Fail`) must exclude `kube-system` and their own namespace via `namespaceSelector` so a dead webhook cannot deadlock the cluster.
