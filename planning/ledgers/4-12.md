## 4. One-Line Expected Exercise Solutions

1. **Exercise 1 (Ansible Vault Mechanics, Header Format, and `vault_` Indirection Pattern, `AUR` Ch. 10):** Using `parse_ansible_vault_header()`, Ansible Vault encrypts files/strings with AES-256 (`$ANSIBLE_VAULT;1.1;AES256` or `1.2;AES256;<label>`); pairing plaintext `vars.yml` (`db_password: "{{ vault_db_password }}"`) with encrypted `vault.yml` keeps secret references greppable and PR-reviewable while encrypting values at rest.
2. **Exercise 2 (Multi-Environment Vault IDs `--vault-id`/`vault_identity_list` and Client Scripts, `AUR` Ch. 10):** `can_decrypt_vault_blob()` shows that labeling encrypted files with `dev` and `prod` prevents developers holding only the `dev` password from decrypting `prod` secrets, and an executable `*-client` password script fetches the vault password dynamically from a secret manager or OS keychain at runtime.
3. **Exercise 3 (Preventing Secret Leakage Across Nine Execution Paths):** Combine `no_log: true` and `diff: false` on tasks, pass secrets via `0600`/`0640` `EnvironmentFile`s rather than CLI arguments or unit `Environment=` lines, keep `cacheable: false` on `set_fact`, and use `--stdin-name` with `encrypt_string`.
4. **Exercise 4 (Comparing Ansible Vault, SOPS `community.sops`, and HashiCorp Vault / Cloud Secret Managers):** Ansible Vault uses a shared password over files, SOPS encrypts only YAML/JSON values using KMS/`age` per-recipient keys with readable diffs, and HashiCorp Vault / Cloud Secret Managers provide centralized RBAC, audit logs, and dynamic short-lived credentials fetched via OIDC/JWT.
5. **Exercise 5 (Managing High-Privilege Fleet Credentials: SSH CA, Sudo, Redfish BMCs, and Munge Keys):** Replace static SSH keys with short-lived SSH CA certificates (`TrustedUserCAKeys`), fetch unique per-BMC Redfish credentials from a secret manager at runtime, and distribute `/etc/munge/munge.key` (`mode: "0400"`, `no_log: true`) idempotently without overwriting active keys.
6. **Exercise 6 (Two-Phase Zero-Downtime Rotation `TwoPhaseSecretRotator`, Pre-Commit Guards, and Incident Response):** `TwoPhaseSecretRotator` adds `key_v2` alongside `key_v1`, rolls all consumers to `key_v2`, and only then revokes `key_v1`; when an engineer leaves or a secret leaks, `ansible-vault rekey` must be paired with rotating the underlying secrets because Git history still holds old ciphertexts.
