## 4. One-Line Expected Exercise Solutions

1. **Exercise 1 (Vector Pipelining and Hardware Parallelism):** Using `vector_pipeline_cycles(100, 1, 5)`, a 5-stage pipeline (`S=5`, `K=1`) processes `100` elements in `1*(100-1)+5 = 104` clock cycles (`4.81x` faster than `500` unpipelined cycles), and four `8 GB` DIMMs across four independent memory banks allow overlapping writes across channels whereas one `32 GB` DIMM serializes all accesses on a single bank.
2. **Exercise 2 (The Nine Levels of Cluster Parallelism and Slow-Job Triage):** The nine levels are `[HW]` memory banks, CPU caches, CPUs, CPU cores, core execution units, accelerators (`GPUs`/`FPGAs`), and `DMA`/offload NICs plus `[SW]` UNIX processes/threads (`OpenMP`) and multi-server programs (`MPI`/`CUDA`/`OpenACC`); parallel programs slow down when threads thrash cache or when `MPI` is misconfigured to use slow management Ethernet instead of InfiniBand.
3. **Exercise 3 (CPU and GPU `Rpeak`, `Rmax`, `HPL` Efficiency, and `MFU`):** For `100` nodes (`2` sockets, `64` cores, `2.4 GHz`), `rpeak_cpu()` gives `983.0 TFLOP/s` at `32` FLOPs/cycle (`AVX-512` dual FMA) and `491.5 TFLOP/s` at `16` FLOPs/cycle; for `800` GPUs (`100 x 8`), `48.0 PFLOP/s` `FP64` `Rpeak` with `Rmax = 38 PFLOP/s` gives `79%` `HPL` efficiency, while `800 PFLOP/s` illustrative `BF16` peak at `40%` `MFU` yields `320 PFLOP/s`.
4. **Exercise 4 (Cluster Taxonomy: `HA` vs. `HTC` vs. `HPC`, `COTS` vs. `Blue Gene`, and Cloud/Fog/Edge):** `HA` clusters fail over transparently and `HTC`/Grid clusters (`SETI@home`, `Folding@home`) retry only the dead node's task slice, whereas one dead node aborts a tightly coupled `HPC`/`NCCL` job; `COTS` and `Beowulf` clusters use retail parts unlike proprietary single-vendor supercomputers (`IBM Blue Gene`, `NEC Tsubasa`); and Cloud handles heavy training while Fog and Edge (`cloudlets`) filter streams and serve low-latency local inference.
5. **Exercise 5 (Physical Operations and Power-On Surge Sequencing):** Compute racks often occupy `< 25%` of floor area (with `> 75%` for power and cooling) and run at `80–100%` utilization 24/7; powering on requires pacing node boots to avoid kilowatt power spikes and request storms, spinning up multi-rack disk shelves sequentially before storage controllers (avoiding starting currents, rack sway from disk torque, and false array rebuilds), and staggering face-to-face hot-corridor racks.
6. **Exercise 6 (Command-Line Fleet Verification vs. Monolithic GUI Consoles):** Running `pdsh -w node[001-100] "grep MemTotal /proc/meminfo | awk '{print \$2}'"` and filtering via `filter_nodes_missing_ram()` flags any node whose `MemTotal` drops more than `2%` below benchmark in seconds, whereas enterprise GUI consoles (`HP OpenView`, `Zenoss`) require costly, fragile customization that breaks whenever cluster hardware changes.
