# Claim Ledger: 7.5 Redfish actions, tasks, events and subscriptions

## DMTF Redfish Specification (DSP0266 v1.21.0) & Resource Guide (DSP2046) Claims
- **Actions & `ResetType` (§7.11, §7.12, §9.6.14, DSP2046 `ComputerSystem`):** Actions are invoked via `POST` to the `target` URI inside `Actions.#<ResourceType>.<ActionName>`. Valid `2xx` responses (Table 10) are `200 OK` (including `NoOperation` when already in target state), `201 Created`, `202 Accepted` (with `Location` Task Monitor URI and `Retry-After`), and `204 No Content`. Missing or unallowed parameters return `400 Bad Request`. `PowerState` is read-only (`PATCH` returns `400`).
- **Asynchronous Tasks & Task Monitors (§12.2, §13.6, DSP2046 `Task`):** While running, `GET` on a Task Monitor URI returns `202 Accepted` with `TaskState: "Running"` and `PercentComplete`. When finished, `GET` on the Task Monitor returns the final HTTP status code and body of the original operation. `DELETE` cancels a running task (`204 No Content`; subsequent `GET` returns `410 Gone`; cancelling an already completed task returns `409 Conflict`).
- **Push Events, Subscriptions & SSE (§12.1, §12.5, §13.7, DSP2046 `EventDestination`):** `POST /redfish/v1/EventService/Subscriptions` returns `201 Created` + `Location`. Subscriptions filter on `RegistryPrefixes`, `MessageIds`, `ExcludeMessageIds`, `ExcludeRegistryPrefixes`, `ResourceTypes`, `OriginResources`, and `SubordinateResources`, with `DeliveryRetryPolicy` (`RetryForever`, `RetryForeverWithBackoff`, `SuspendRetries`, `TerminateAfterRetries`). Pushed payloads are at most `1 MiB` (metric reports excluded) and have no historical replay. SSE (`ServerSentEventUri`) streams `Content-Type: text/event-stream` (`id:` and `data:` lines), supports `Last-Event-ID` and `$filter`, and automatically creates/deletes a subscription resource on connect/disconnect (§12.5.2).
