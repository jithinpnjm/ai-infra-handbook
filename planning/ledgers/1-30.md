## 4. One-Line Expected Exercise Solutions

1. **Exercise 1 (Choosing the Right File-Sharing Tool and Network Latency vs. Bandwidth):** (a) Use `python3 -m http.server --bind <IP>` for a quick one-off LAN copy, `rsync` over SSH for repeated/automated directory syncs, Samba (`SMB`) to export Linux directories to Windows, `mount -t cifs` to mount Windows shares on Linux, `SSHFS` for zero-setup small Linux mounts over SSH, `NFS` for local-network multi-host mounts, and object-store CLIs/`FUSE` for cloud buckets; (b) network filesystems perform well on large sequential streams (read-ahead) but poorly on workloads touching thousands of small files because per-request **network and metadata lookup latency** dominates every open/stat/read.
2. **Exercise 2 (`rsync` Trailing Slash, `--delete`, and Quick-Check vs. `--checksum`):** (a) `rsync -a dir host:dest_dir` creates `dest_dir/dir/...`, whereas `rsync -a dir/ host:dest_dir` (trailing slash) dumps the contents of `dir` directly into `dest_dir/...`—combining a wrong trailing slash or an unmounted empty source with `--delete` wipes unrelated files at the destination (always preview with `-nva --delete` first); (b) `rsync`'s default quick check compares only file **size and modification time (`mtime`)**, so a corrupted file with preserved size and timestamp is skipped unless `-c` (`--checksum`) is passed.
3. **Exercise 3 (`rsync` Filter Ordering `--include` / `--exclude`, `-z`, and `--bwlimit`):** Because `rsync` evaluates filter rules on a **first-match-wins** basis, you must place `--include='keep.log'` *before* `--exclude='*.log'` (`evaluate_rsync_filter_rules()`); `-z` compression speeds up compressible text over slow WAN links but slows down transfers on fast LANs or already-compressed data (checkpoints/archives), while `--bwlimit` prevents saturating an uplink and starving TCP ACK/control traffic.
4. **Exercise 4 (Samba `smb.conf`, `smbpasswd`, `unix password sync`, and CIFS Credentials):** Samba requires its own password database (`tdbsam`, managed with `sudo smbpasswd -a user`) because SMB password hashes differ from `/etc/shadow`; enabling `unix password sync = yes` is a classic trap because changing a user's SMB password silently overwrites their Linux login password; on the client, mount `//SERVER/sharename` with `-t cifs -o credentials=/root/.smbcreds` (`0600`) so passwords never appear in `ps aux` or `/etc/fstab`.
5. **Exercise 5 (`SSHFS` vs. `NFS` Security Flavors `sec=`, Automounting, and Why `AFS`/FUSE Evolved):** `SSHFS` runs in user space over SFTP (`fusermount -u` to unmount) with zero server setup, whereas `NFS` (`sec=sys` trusts client UIDs by default; `sec=krb5`/`krb5i`/`krb5p` adds Kerberos auth/integrity/encryption) requires matching UIDs across machines and `x-systemd.automount` so dead NFS servers do not hang boot; AFS never became universal because it required Kerberos and complex kernel clients, whereas modern cloud storage uses TLS/API tokens and user-space `FUSE` clients.
6. **Exercise 6 (X11 Client/Server Role Inversion, Wayland/D-Bus/CUPS, `xauth` vs. `xhost`, and `VNC` / `x2go` / SSH Tunnels):** In X11 (`X.Org`), the **X server** runs on the user's local laptop (`XQuartz`, `VcXsrv` / `Xming -clipboard -multiwindow`) owning the display/mouse/keyboard, while the remote cluster application (`xclock`) is the **X client**; `ssh -X` sets `DISPLAY` and an `xauth` cookie (never use `xhost +`), and when X11's chatty drawing protocol is too slow over a WAN, use **`x2go`** (which tunnels compressed screen updates over SSH with no persistent daemon) or tunnel Jupyter/TensorBoard ports directly with `ssh -L`.
