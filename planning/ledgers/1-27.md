## 4. One-Line Expected Exercise Solutions

1. **Exercise 1 (The Three Virtualization Models: Hardware VMs, OS Containers, and MicroVMs):** Hardware VMs (`KVM`, `Xen`, `Nitro`) run a full guest kernel per VM with strong hardware isolation (`VT-x`/EPT/IOMMU) and high guest-side observability; OS containers (`runc`) share one host kernel via namespaces and cgroups with millisecond startup, zero guest-kernel memory, and full host-operator visibility; and lightweight MicroVMs (`Firecracker` `< 5 MB`, `~100 ms` boot, `Kata`) combine hardware VM isolation with container-like startup and density.
2. **Exercise 2 (CPU Shares vs. Bandwidth Quotas and the 10x \"Bait-and-Switch\" Burst Trap):** Given `100` total shares where Container A has `10` shares: when tested alone on an idle host, A bursts to `100%` of the CPUs; when a sibling with `30` shares is also busy, A gets `10 / (10 + 30) = 25.0%`; and when all `100` shares on the host are busy, A drops to its guaranteed minimum of `10.0%` (`10.0x` slower than the idle test).
3. **Exercise 3 (The 5-Fact Container CPU Throttling Decision Flow):** Using `diagnose_container_cpu_limit_cause()`: (a) rising `throttled_usec` (`nr_throttled`) proves a CFS bandwidth quota cap (`cpu.max`) is binding even when the host is idle; (b) zero quota throttling with `100%` busy `cpuset` cores while other host CPUs are idle proves the `cpuset` is saturated; and (c) zero quota throttling with rising involuntary context switches (`nonvoluntary_ctxt_switches`) and busy neighbors proves CPU shares (`cpu.weight`) contention.
4. **Exercise 4 (Observing Containers from Host and Guest: `NSpid`, `/proc/PID/root`, and Which Tools Lie):** (a) On the host, `grep NSpid /proc/4915/status` (`NSpid: 4915 753`) maps host PID `4915` to container PID `753` (`parse_proc_status_nspid()`), `/proc/4915/root/` accesses the container's filesystem, and BPF scripts can group by `$task->nsproxy->uts_ns->name.nodename` or `cgroupid()`; (b) inside a container, `ps` and `pidstat` show only container processes and `sar -n DEV,TCP` / `tcpdump` show only the container's network namespace, whereas `uptime`, `mpstat`, `vmstat`, `free`, and `iostat` report **host-wide** CPU, RAM, and disk activity.
5. **Exercise 5 (AI/HPC Cloud Realities: `5–15%` VM Overhead, Compact Placement, and 5-Minute Checkpoint Testing):** (a) Cloud HPC/GPU VMs typically incur a `5–15%` performance drop versus bare metal (`SCL` Ch. 17) unless network/storage/interrupts are hardware-offloaded (e.g., AWS Nitro + EFA or InfiniBand VFIO) and all instances are scheduled inside a single compact placement group / performance subnet; (b) before committing to a cloud shared filesystem, rent cheap instances and simulate your job's periodic checkpoint burst (e.g., writing compute-node RAM size every `5 minutes`).
6. **Exercise 6 (Cloud GPU Cost Modeling, Goodput vs. Nominal Price, and Spot Preemption):** Using `compute_cloud_gpu_effective_cost()`, a job needing `640` useful GPU-hours on `64` GPUs at `$3.00`/GPU-hour with `80%` goodput (`0.80`) requires `640 / 0.80 = 800` paid GPU-hours (`12.5` wall-clock hours) = `$2,400` compute + `$200` storage/egress = `$2,600` total; running on spot/preemptible instances requires frequent asynchronous checkpointing, metadata-server preemption polling (`/computeMetadata/v1/instance/preempted`), and automatic elastic requeuing.
