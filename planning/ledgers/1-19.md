## 4. One-Line Expected Exercise Solutions

1. **Exercise 1 (What a Container Is, the 8 Namespaces, and `clone`/`unshare`/`setns`):** (a) The Linux kernel has no "container" object (`struct nsproxy` is the closest pointer); a container is an ordinary process tree combining 8 namespaces (`mnt` `CLONE_NEWNS`, `pid` `CLONE_NEWPID`, `net` `CLONE_NEWNET`, `uts` `CLONE_NEWUTS`, `ipc` `CLONE_NEWIPC`, `user` `CLONE_NEWUSER`, `cgroup` `CLONE_NEWCGROUP`, `time` `CLONE_NEWTIME`), cgroups, an OverlayFS/`pivot_root` rootfs, and capabilities/seccomp/LSM filters on a shared host kernel; (b) `clone()` creates a new child process in new namespaces, `unshare()` moves the calling process (or its future children for `pid`) into new namespaces, and `setns()` (`nsenter` / `docker exec`) attaches to an existing `/proc/PID/ns/*` descriptor.
2. **Exercise 2 (PID Namespace Semantics, PID 1 Signal Rules, and Zombie Reaping):** In a PID namespace, PID 1 has no default signal handlers for unhandled signals (so `SIGTERM` from `docker stop` / `kubectl delete pod` is ignored unless PID 1 explicitly installs a `SIGTERM` handler, and `SIGKILL` from inside the namespace is ignored while `SIGKILL` from the parent namespace kills it), reaps orphaned descendants, and causes the kernel to `SIGKILL` the entire namespace when PID 1 exits; use `exec python train.py` or `tini`/`--init` so a shell wrapper does not swallow `SIGTERM`.
3. **Exercise 3 (Mount Propagation, `chroot` vs. `pivot_root`, and OverlayFS Copy-Up / Whiteouts):** (a) `chroot` only changes a process's root path pointer and can be escaped by root, whereas `pivot_root` inside a private/slave mount namespace swaps the root mount and unmounts the old host root completely; (b) in OverlayFS (`lowerdir=lower2:lower1,upperdir=upper,workdir=work`), modifying a `4 GiB` file in `lowerdir` triggers a synchronous `4 GiB` **copy-up** into `upperdir`, and deleting a lower file creates a `0, 0` character-device **whiteout** in `upperdir` without freeing bytes in the lower image layer.
4. **Exercise 4 (Network Namespaces, `veth` Pairs, Pod Sharing, and `/dev/shm` IPC):** (a) A new network namespace has only a down `lo` interface and is wired to a host bridge (`docker0`/`cni0`) via a virtual Ethernet (`veth`) pair; in a Kubernetes Pod, all containers share the `pause` container's `net`, `ipc`, and `uts` namespaces while having separate `mnt` namespaces; (b) Docker's default `64 MiB` `/dev/shm` (`tmpfs`) causes PyTorch `DataLoader` and NCCL shared-memory transfers to crash with `Bus error` (`SIGBUS`) unless raised via `--shm-size`, `--ipc=host`, or a memory-backed `emptyDir`.
5. **Exercise 5 (User Namespaces, `uid_map`, and HPC Shared Storage Pitfalls):** Given `/proc/PID/uid_map` `0 100000 65536`, container `UID 0` (`root`) executes on the host as unprivileged `UID 100000` (and container `UID 1000` as `101000`); while this hardens multi-tenant containers, remapped UIDs mismatch real user UIDs on shared HPC filesystems (NFS, Lustre, GPFS, BeeGFS), which is why Slurm/Enroot/Apptainer run containers as the user's real UID.
6. **Exercise 6 (Observability Traps Inside Containers and GPU CDI Injection):** (a) Inside a container, `/proc/cpuinfo`, `/proc/meminfo`, `/proc/stat`, `free`, `top`, and `nproc` still report the **host's** total CPUs and RAM because those `/proc` files are not namespaced (inspect `/sys/fs/cgroup/cpu.stat` and `memory.current` instead, and trace from the host with `nsenter -t PID -n`); (b) to expose a GPU, the runtime (`nvidia-container-toolkit` / CDI) bind-mounts `/dev/nvidia*` into the mount namespace, grants major/minor access in the devices cgroup, and bind-mounts host-matched `libcuda.so.1` and `nvidia-smi`.
