## 4. One-Line Expected Exercise Solutions

1. **Exercise 1 (UDP Semantics, Buffer Overflows, Connected UDP Sockets, and `iperf3 -u`):** UDP (`RFC 768`) adds an `8`-byte header (`src port, dst port, length, checksum`), preserves datagram boundaries, and has no flow/congestion control; receive buffer drops increment `UdpRcvbufErrors` in `nstat -az`, sending to a closed UDP port returns ICMP Type 3 Code 3 (`Port Unreachable`, reported as `ECONNREFUSED` only on a `connect()`ed UDP socket), and `iperf3 -u` measures receiver packet loss percentage and jitter.
2. **Exercise 2 (ICMPv4 and ICMPv6 Types/Codes and Firewall Rules):** Never block IPv4 ICMP Type `3` Code `4` (`Fragmentation Needed and DF set`) or Type `11` (`Time Exceeded`), and never block ICMPv6 Types `1`, `2` (`Packet Too Big`), `3`, `4`, or `133`–`137` (`Neighbor Discovery`); blocking them breaks Path MTU Discovery (causing large transfers to hang) and breaks IPv6 address resolution and router discovery completely.
3. **Exercise 3 (Reading `ping`, `traceroute`, and `mtr`: Control-Plane Rate Limiting vs. Real Loss):** Using `classify_mtr_hop_loss()`: a hop showing `* * *` or `45%` loss while subsequent hops and the final destination show `0.0%` loss is harmless router control-plane ICMP rate limiting (`icmp_control_plane_rate_limiting_only`), whereas loss that starts at hop `N` and persists across every subsequent hop to the destination (`[0, 0, 5.2, 5.1, 5.3]`) is genuine forwarding packet loss at or immediately after hop `N`.
4. **Exercise 4 (Diagnosing and Fixing Path MTU Black Holes):** When a tunnel or middlebox lowers the path MTU (e.g., to `1400` B) and a firewall drops ICMP Type 3 Code 4 / ICMPv6 Type 2, small packets (TCP handshake, short pings) succeed while full-MTU packets (`1500` B with `DF=1`) are silently dropped (`ssh` hangs at `SSH2_MSG_KEXINIT`, `curl` hangs after `Connected`); detect with `ping -M do -s 1472` (`compute_max_ping_df_payload()`) and `tracepath -n`, and fix by setting proper overlay MTUs, permitting ICMP, clamping TCP MSS (`--clamp-mss-to-pmtu`), or enabling `net.ipv4.tcp_mtu_probing=1`.
5. **Exercise 5 (Calculating Overlay MTUs and Inner TCP MSS):** Using `compute_overlay_mtu_and_mss()` on a `1500`-byte IPv4 underlay: VXLAN (`50` B) and Geneve (`50` B) require inner MTU `1450` (inner TCPv4 MSS `1410`), GRE (`24` B) -> `1476`, IPIP (`20` B) -> `1480`, and WireGuard (`60` B IPv4 / `80` B IPv6) -> `1420` / `1400` (and on a `9000` jumbo underlay, VXLAN inner MTU is `8950`).
6. **Exercise 6 (Jumbo Frames and RoCEv2 MTU Validation in AI Clusters):** Configure all hosts in an L2 domain to `MTU 9000` and switch ports to `9216`, allowing RoCEv2 NICs to run at their maximum `4096`-byte InfiniBand payload MTU (`ibv_devinfo`), and validate every rail pair end-to-end with `ping -M do -s 8972 -I <rail_nic> <peer_rail_ip>` before launching `nccl-tests`.
