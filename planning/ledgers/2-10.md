## 4. One-Line Expected Exercise Solutions

1. **Exercise 1 (HTTP Semantics, Status Codes `401`/`403`/`413`/`429`/`499`/`502`/`503`/`504`, and `HTTP/1.1` vs. `HTTP/2` vs. `HTTP/3`):** (a) `401` is unauthenticated whereas `403` is unauthorized; `502` is a bad/reset response from the upstream backend, `503` means no healthy upstream endpoints exist, `504` means the upstream model server exceeded the gateway's read timeout, `413` means the prompt/upload exceeded `client_max_body_size`, and `499` means the client disconnected before the server finished; (b) `compute_connection_setup_rtts()` shows cold `TCP + TLS 1.2` takes `3` RTTs, `TCP + TLS 1.3` takes `2` RTTs, and `HTTP/3` (`QUIC`) takes `1` RTT (`0` RTTs on resumption) while eliminating `HTTP/2`'s TCP-level head-of-line blocking.
2. **Exercise 2 (Cryptographic Primitives, Forward Secrecy, Web of Trust vs. Hierarchical PKI, and Data-Exhaust Privacy):** TLS combines asymmetric crypto (X25519/P-256 ephemeral Diffie-Hellman key exchange for **forward secrecy** + RSA/ECDSA/Ed25519 certificate signatures to defeat MitM) with fast **AEAD** symmetric ciphers (`AES-GCM`, `ChaCha20-Poly1305`) for bulk data; unlike a decentralized *Web of Trust* (`CN` Ch. 10), TLS uses a **Hierarchical PKI** (Offline Root CA -> Online Intermediate CA -> Leaf certificate), while metadata ("data exhaust") is protected via ECH, MAC randomization, or onion routing.
3. **Exercise 3 (The TLS 1.3 1-RTT Handshake, `SNI`, `ALPN`, and `0-RTT` Replay Risk):** In TLS 1.3, the client sends its key share (`X25519`), `SNI`, and `ALPN` (`h2`, `http/1.1`) in the very first `ClientHello` so both sides derive handshake keys after `ServerHello` (`1 RTT`) and encrypt the server's `Certificate` and `CertificateVerify`; `0-RTT` early data is vulnerable to **replay attacks** if a packet is duplicated, so it must only be used for idempotent requests (`GET`).
4. **Exercise 4 (X.509 Certificate Validation, `SAN` Wildcards, Missing Intermediates, and Trust Stores):** Using `validate_x509_leaf_certificate()` and `match_san_dns_pattern()`: modern clients match hostnames exclusively against **Subject Alternative Names (`SAN`s)** where `*.lab.internal` matches single-label `api.lab.internal` but not `a.b.lab.internal` or `lab.internal`; omitting the **intermediate CA** from the server's bundle causes `curl`/Go/Python to fail with `unable to get local issuer certificate` even when browsers succeed via AIA fetching.
5. **Exercise 5 (`curl` and `openssl s_client` / `x509` Diagnostics):** Use `curl --resolve api.example.com:443:10.0.0.5 https://api.example.com/` to test a specific backend IP while sending the proper `SNI` and `Host:` header (never leaving `curl -k` in production), `openssl s_client -connect host:443 -servername host -showcerts </dev/null` to inspect the presented chain, and `openssl x509 -in cert.pem -noout -checkend 2592000` to check if a certificate expires within `30` days (`2,592,000 s`).
6. **Exercise 6 (PKI in Kubernetes and AI Platforms: `kubeadm`, `cert-manager`, Containerd Private CAs, and mTLS):** Monitor and rotate `/etc/kubernetes/pki` (`kubeadm certs check-expiration`, `1`-year default), automate Ingress/workload certs with **`cert-manager`** (`ACME` `DNS-01` for wildcards/private clusters or Vault/step-ca), install private registry CAs in `/etc/containerd/certs.d/<registry>/hosts.toml` + `/usr/local/share/ca-certificates/`, and enforce `chrony` time sync so mTLS (Istio/Linkerd/SPIFFE) never fails on clock skew.
