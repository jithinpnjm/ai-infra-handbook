| **RadixAttention, 2-Level Memory Pool & LRU Tree Eviction** | Stores KV cache in a compressed prefix tree (radix tree) in CPU memory whose edges map to physical GPU KV tensors in a `2`-level memory pool (Level 1: request-to-token KV index table; Level 2: physical KV buffer `[num_layers, max_tokens, num_heads, head_dim]`, as of SGLang `v0.5`). Unlike vLLM hash-based APC (which matches only at fixed `16`- or `32`-token block boundaries), RadixAttention matches arbitrary-length token subsequences (`seq1=[1,2,3,4,5]`, `seq2=[1,2,3,6,7]`, `seq3=[1,2,8,9]`, query `[1,2,3,4,10,11]` -> `match_len = 4` on `5 x 32 x 128` tensor). For `100` concurrent users sharing a `500`-token system prompt (`50,000` total prompt tokens), RadixAttention computes the `500`-token prefix once (`500` tokens vs `50,000` tokens = `99%` system-prompt compute saved), cutting total prefill compute by up to `90%` and reducing follow-up TTFT latency by `2-3x` (`50-90%` TTFT reduction). When VRAM fills (`mem_fraction_static`), recursive leaf-first **LRU eviction** evicts unreferenced leaf nodes (`ref_count == 0`) while keeping shared ancestor prefix nodes (`ref_count > 0`) pinned. | `DAI` Ch. 7; `V12` Ch. 6 & 8; `HLS` Ch. 6 |
| **Cache-Aware Scheduling, RAG Ordering & Multi-Tenant Isolation** | SGLang's scheduler sorts waiting requests by longest matching prefix length in the radix tree to maximize batch cache hit rates. In RAG and agentic workflows, placing static `<system>` and deterministically formatted, sorted `<context>` chunks (`Document 1..4`) before dynamic `<user>` queries maximizes prefix hits, whereas inconsistent spacing or chunk order causes cache misses. In multi-tenant deployments, shared prefixes across tenants create a timing side-channel (Customer A inferring Customer B's cached documents via fast TTFT); mitigate by injecting `<id> {tenant_id}` immediately after `<system>` so tenants share the system prompt node but branch into isolated context subtrees. Also, naive chunked prefill can drop prefix cache hit rates from `45%` to `8%` (`5.6x` drop) unless radix matching is chunk-boundary aware. | `DAI` Ch. 7; `HLS` Ch. 6; `V12` Ch. 8 |
| **Structured Output Decoding (`XGrammar`, `Outlines`, Jump-Forward)** | Naive runtime grammar checking across a `128,000`-token (`128K`, e.g., `Llama-3` `128,256`) vocabulary on CPU for every decode step stalls generation. SGLang uses `XGrammar` (default), `Outlines`, and `llguidance` to precompile JSON schemas, regexes, and context-free grammars (CFGs) into compressed finite-state machines (FSMs) and pushdown automata with tree-based stack management, applying bitmasking directly inside GPU logit/softmax kernels (keeping overhead to low single-digit percent). **Jump-Forward Decoding**: when an FSM state permits only a deterministic string transition (such as JSON structural boilerplate `{"name": "`, `", "age": `, `", "occupation": "` in a `Person` schema), SGLang splices the multi-token string directly into the sequence without running autoregressive decode forward passes, turning decode steps into cheap prefill/append operations. | `DAI` Ch. 7; `V12` Ch. 6; `ASP` Ch. 15 |
| **Zero-Overhead Scheduler, Operator Fusion & `FlashInfer` Backend** | Serial scheduling idles the GPU during CPU batch preparation (`50%+` overhead). SGLang's **Zero-Overhead Scheduler** splits host work into a `Scheduler CPU` (radix tree matching, memory allocation, post-scheduling completion checks) and a `Launch CPU` (kernel launch), using a **token placeholder mechanism** to overlap Batch `N+1` pre-scheduling and Batch `N-1` post-processing with Batch `N` GPU execution—yielding up to `2x` throughput. Operator fusion combines LayerNorm + Linear + Activation and MoE routing + GEMM. For attention kernels, `FlashInfer` is recommended for non-Hopper GPUs (`A100`, `A40`) and `FlashAttention-3` for Hopper GPUs (`H100`, `H200`, `H20`), alongside `FlashMLA` for DeepSeek MLA decoding. | `DAI` Ch. 7; `HLS` Ch. 6; `ASP` Ch. 18 |
| **SGLang Model Gateway (Router), Policies & Session Affinity** | Sits above independent `SRT` workers to eliminate cross-request synchronization (while keeping intra-worker `TP`/`PP`/`EP` collectives intact). Control plane: Worker Manager, Health Checker (`/health` probes + `5`-consecutive-failure circuit breaker), Load Monitor, Kubernetes Service Discovery. Data plane: HTTP Router, PD Router, gRPC Router. Four routing policies: `cache_aware` (maintains per-worker approximate radix tree; `--cache-threshold 0.5 --balance-abs-threshold 10 --balance-rel-threshold 1.5`), `round_robin`, `shortest_queue`, `power_of_two_choices`. `session_id` affinity pins multi-turn conversations to the warm worker (`2-3x` latency reduction) and migrates sessions on worker failure (incurring `1` cold prefill). | `DAI` Ch. 7 |
| **Prefill/Decode Disaggregation, DP Attention & Hybrid MoE Scaling** | Prefill uses `85%` compute / `40%` memory bandwidth; decode uses `25%` compute / `90%` memory bandwidth. SGLang PD disaggregation routes prompts to prefill workers (`--disaggregation-mode prefill`) and transfers KV blocks directly worker-to-worker via `Mooncake` RDMA (`--disaggregation-ib-device mlx5_roce0`), `NIXL` (`--disaggregation-transfer-backend nixl`), or `ASCEND` to decode workers (`--disaggregation-mode decode`), using `2:1` or `3:1` prefill:decode ratios for long-context RAG and `1:2` for chat. **DP Attention** (`--enable-dp-attention --dp-size 8 --tp-size 8`) avoids `8x` KV cache duplication when `H_kv < TP` (e.g., `1` KV head with `TP=8`), running attention data-parallel with an `AllGather` before the `TP`-sharded MLP for up to `1.9x` higher decode throughput. MoE scaling combines `--tp 8 --ep 16` (`microsoft/Phi-tiny-MoE-instruct`) or `--tp 4 --ep 16 --pp 2` (`Qwen/Qwen3-235B-A22B`) with `--moe-a2a-backend deepep`, `--moe-runner-backend deep_gemm`, and `--enable-two-batch-overlap` (`TBO`) or `--enable-single-batch-overlap` (`SBO`). Deployment sweet spots: `< 10B` -> router DP (`50-100 ms` TTFT, `1,000+` QPS, `60-80%` hit rate); `10B-100B` -> intra-node TP (`2-8` GPUs) + router DP; `> 100B` -> multi-node TP+PP. | `DAI` Ch. 7 |
