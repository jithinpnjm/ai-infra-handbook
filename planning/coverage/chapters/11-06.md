## Checklist of Concepts, Numbers, and Patterns to Cover
1. **Why `nvidia.com/gpu: N` is a quantity contract, not a data-path contract (`V10 Ch 8`, `V07 Ch 2 & 8`, `ASP Ch 3`):**
   - The four ordered placement questions: `1. Capacity`, `2. Eligibility`, `3. Locality`, `4. Coordination`.
   - Two-stage scheduler-to-kubelet pipeline (`Filter -> FilterOK? -> Score -> Bind -> Kubelet -> AllocOK? -> Device`).
   - Physical motherboard data paths:
     - PCIe Gen4 x16 (`32 GB/s` per direction) vs PCIe Gen5 x16 (`64 GB/s` per direction) vs H100 HBM3 (`3,350 GB/s`).
     - NVLink 4.0 on H100 (`900 GB/s` bidirectional, `4` NVSwitch 3.0 chips on HGX H100/H200) vs NVLink 5.0 on Blackwell (`1.8 TB/s` per GPU across `18` links at `100 GB/s` each; `NVSwitch 4.0` has `72` ports per chip / `144` ports per dual-chip tray at `14.4 TB/s`; `GB200 NVL72` connects `72` GPUs with `130 TB/s` total GPU bandwidth; Grace-Blackwell NVLink-C2C coherent CPU-GPU link at `~900 GB/s`).
     - Local vs remote NUMA memory latency (`~80 ns` local vs `~139 ns` cross-socket UPI/xGMI = `~75%` latency increase; CPU pinning yields `5%–10%` training throughput gain; pinned memory `pin_memory=True` is `2–3x` faster than pageable DMA; Transparent Hugepages `2 MB` / `1 GB` vs `4 KB` give `~3%–5%` training throughput gain, while `transparent_hugepage=never` or `madvise` is preferred for latency-sensitive inference).
2. **`nvidia-smi topo -m` legend and topology diagnosis (`V04 §13.1`, `V07 Ch 2`, `V10 Ch 8`):**
   - Matrix legend: `X` (self), `NV#` (`NV4`, `NV12`, `NV18` NVLink), `PIX` (same PCIe switch), `PXB` (multiple PCIe switches), `PHB` (same PCIe host bridge / CPU root complex), `NODE` (across host bridges within one NUMA node), `SYS` (across inter-socket QPI/UPI/xGMI link).
   - `train-worker-2` slow-step diagnosis: `GPU0 <-> GPU1` over `PHB` (`CPU Affinity 0-31` NUMA `0` vs `32-63` NUMA `1`) compared against a healthy node with `NV4` (running `3-4x` slower when peer topology degrades).
   - `FailedScheduling` 3-clause breakdown on `train-worker-2` (`0/12 nodes are available: 4 Insufficient nvidia.com/gpu, 6 node(s) had untolerated taint {pool: inference-only}, 2 node(s) didn't match Pod's node affinity/selector`).
3. **Kubernetes QoS classes, CPU Manager (`static`), and Topology Manager (`V07 Ch 8`, `ASP Ch 3`):**
   - Why exclusive CPU pinning requires `Guaranteed` QoS (`requests == limits` for all containers, integer CPU cores) + `kubelet` `--cpu-manager-policy=static` + `--pass-device-specs=true` on the device plugin.
   - The four `Topology Manager` policies (`none`, `best-effort`, `restricted`, `single-numa-node`).
   - **The `TopologyAffinityError` 5th-Pod Customer Scenario (`V07 Ch 8`):** Dual-socket HGX server with `8` GPUs (`4` on NUMA `0`, `4` on NUMA `1`) and `128` CPU cores (`64` on NUMA `0`, `64` on NUMA `1`) running `single-numa-node`:
     - Pods 1–4 each request `1` GPU and `16` CPU cores -> consume `4 * 16 = 64` cores and `4` GPUs on NUMA `0` (`0` cores, `0` GPUs left on NUMA `0`).
     - On NUMA `1`, all `4` GPUs (`GPU 4..7`) are free, but OS/system daemons consume `2` CPU cores, leaving only `62` cores (`64 - 2 = 62`).
     - Pod 5 (`16` cores) lands on NUMA `1` (`46` cores left), Pod 6 (`30` cores left), Pod 7 (`14` cores left) — or if `2` cores on NUMA `1` are reserved after 3 pods (`48` cores used, `14` left), the next `16`-core Pod fails with `TopologyAffinityError` because only `14` cores remain on NUMA `1` while `4` GPUs (or `1` GPU) sit idle. Reducing the Pod request from `16` cores to `12` cores (`8 * 12 = 96` cores total, `4 * 12 = 48 <= 62` per NUMA node) allows all `8` Pods to run with strict `single-numa-node` alignment.
4. **OS & PyTorch DataLoader NUMA Binding (`ASP Ch 3`):**
