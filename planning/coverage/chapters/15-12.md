| **1. CUDA Graphs for Decode Batch Sizes, Padding Buckets & Time-Series Prewarming** | **Why CUDA Graphs for Decode:** Decode steps are memory-bandwidth-bound with small per-kernel execution times (`~5–20 us`), so Python/driver launch overhead (`~5–15 us`/kernel across `300+` kernels per step) can exceed actual GPU compute time. Wrapping the decode forward pass in `torch.cuda.CUDAGraph` (`cudaGraphLaunch`) collapses `300` kernel launches into `100` (`1.00 ms -> 0.75 ms`, `1.33x` speedup in microbenchmarks, and `1.2x–2.5x` decode token throughput on small batches). **Decode Batch Padding Buckets:** Because CUDA Graphs require static tensor shapes and static HBM addresses, engines like `vLLM`, `SGLang`, and `TensorRT-LLM` capture a discrete pool of batch sizes—e.g., `[1, 2, 4, 8, 16, 24, 32, 48, 64, 96, 128, 192, 256]` (or power-of-two/stepped buckets up to `max_num_seqs` / `256` or `512`). An incoming decode batch of `B_actual = 19` is padded to the smallest bucket `B_bucket = 24` (`5` dummy tokens = `20.83%` padding overhead, which is still faster than eager dispatch because memory-bound GEMV cost scales weakly with small batch increments below the Roofline ridge point). **Decreasing-Batch Shared Memory Pool (`ASP` Ch. 13):** FireworksAI captures CUDA Graphs in **decreasing batch-size order** (`[8, 4, 2, 1]` or `[256, 128, 64, ..., 1]`) sharing a single `torch.cuda.graph_pool_handle()` so the largest batch size (`256` or `8`) allocates the high-water workspace once and all smaller graphs reuse the same HBM pool without linear memory bloat. **Time-Series Prewarming (`ASP` Ch. 19):** Uses `ARIMA` or `Prophet` traffic forecasts (e.g., ahead of a `9:00 AM` daily surge) on low-priority CUDA streams (`cudaStreamCreateWithPriority`) to pre-compile JIT kernels, pre-capture CUDA Graph buckets, and pre-stage KV/weights before live requests arrive. | `ASP` Ch. 12, Ch. 13, Ch. 19 |

On a `64`-expert MoE model, `torch.compile` reduces step time from **`248.0 ms` to `173.0 ms` (`75.0 ms` / `30.24%` reduction, `1.43x` speedup)** (`mode="reduce-overhead"` wraps subgraphs in CUDA Graphs; `mode="max-autotune"` profiles Triton/CUTLASS/cuBLASLt configs; `TORCHINDUCTOR_CACHE_DIR` / `save_cache_artifacts()` persists the mega-cache). **Custom Fused Kernels (`RMSNorm`, `RoPE`, `SwiGLU`, `AllReduce`):** Unfused eager execution reads/writes HBM on every elementwise op (`fusedL2Norm` cuts memory traffic `3x`, from `36 B` to `12 B`). In LLM decode (`[B, H]` activations): (1) **Fused Add + RMSNorm** combines residual addition `r = x + res` and `y = r * rsqrt(mean(r^2) + eps) * w` in a single SRAM pass (`4` HBM tensor passes -> `2` passes, `2.0x` HBM traffic reduction, or `3 -> 2` with residual out); (2) **Fused RoPE (Rotary Position Embedding)** applies sinusoidal rotation to `Q` and `K` in-place in registers without materializing `cos`/`sin` intermediate tensors; (3) **Fused SwiGLU (`SiLU(x W_gate) * (x W_up)`)** fuses the elementwise `silu` activation and Hadamard product into a single Triton epilogue/kernel (`3` HBM passes -> `2` passes); (4) **Custom Fused AllReduce (`One-Shot` / `Two-Shot` over `NVSHMEM` / PyTorch `SymmetricMemory`):** For small decode TP buffers (`<= 256 KB–1 MB`), standard ring `ncclAllReduce` suffers multi-hop latency; a custom Triton/CUDA one-shot kernel reads peer GPU pointers directly over NVSwitch and fuses `AllReduce + Residual + RMSNorm` inside one CUDA Graph-capturable kernel. **Runtime Kernel Autotuning & Occupancy (`ASP` Ch. 19 Table 19-3):** Attention breakeven at `L = 128..256` (standard global-memory kernel for `L < 256` vs tiled FlashAttention for `L >= 256`). | **3. Dynamic Speculative Decoding (`Draft-Target`, `EAGLE-1/2/3`, `Medusa`, Self-Speculative) & Draft-Length (`K`) Adaptation** | **Speculative Verification Math (`ASP` Ch. 15, `AIE` Ch. 9):** Draft model proposes `K` tokens sequentially (`K * t_draft`); target model verifies all `K + 1` positions in a single parallel forward pass (`t_verify ≈ t_target` because decode is memory-bandwidth-bound with idle FLOPs). Under token acceptance probability `alpha` (`0 <= alpha <= 1`), expected accepted tokens per verification cycle is **`E[N_tokens] = (1 - alpha^(K+1)) / (1 - alpha)`** (or `K + 1` when `alpha = 1`). Cycle wall time is `T_cycle = K * t_draft + t_verify`, and **Net Speedup** is **`S(K, alpha, c) = E[N_tokens] / (1 + K * c)`**, where `c = t_draft / t_target` is the draft-to-target cost ratio. **Concrete Benchmarks:** (1) `Chinchilla-70B` (`t_target = 14.1 ms/tok`) + `4B` draft (`t_draft = 1.8 ms/tok`, `c = 1.8 / 14.1 = 0.1277`, `7.83x` faster draft): at `K = 5` and `alpha = 0.80`, `E[N_tokens] = (1 - 0.8^6) / 0.2 = 3.6893` tokens in `5 * 1.8 + 14.1 = 23.1 ms` (`6.26 ms/tok` vs `14.1 ms/tok` = **`2.25x` speedup**). (2) **`EAGLE` (`ASP` Ch. 15):** `EAGLE-1` (`4`-token feature-level draft) achieves **`3.5x`** speedup; `EAGLE-2` (context-aware dynamic draft tree) is **`20%–40%` faster** than `EAGLE-1`; `EAGLE-3` (multi-layer fused feature-to-token prediction) is **`1.4x` faster** than `EAGLE-2` and up to **`6.5x`** over baseline. (3) **`Medusa` (`ASP` Ch. 15, `AIE` Ch. 9):** Multi-head depth-2 binary tree proposes `4` tokens/pass (`100` tokens in `25` passes), achieving **`1.9x` on HGX H200** (`Llama 3.1`) and **`2.2x–3.6x`** across Medusa-1/2. (4) **Self-Speculative (`ASP` Ch. 15):** Skips half of target layers during draft for **`~2x` speedup** (`~3x` with consistent decoding) with zero extra draft-model VRAM. **Dynamic Draft-Length (`K`) Adaptation:** Static `K` fails when acceptance `alpha` drops (e.g., high-entropy creative text where `alpha = 0.30` at `K = 8, c = 0.1277` gives `S = 1.428 / 2.021 = 0.71x` **slowdown!**) or when batch size `B` grows and pushes target verification `t_verify(B, K)` over the Roofline ridge point. Dynamic engines track an EMA of acceptance rate `alpha_ema` and adjust `K` per step (expanding `K` up to `6–8` on structured code/JSON where `alpha >= 0.85`, shrinking `K -> 1..2` on high-entropy text, and disabling speculation `K = 0` when active batch size `B >= B_cutoff` such as `32–64`). | `ASP` Ch. 15, Ch. 19; `AIE` Ch. 9; `HLS` Ch. 4 |
