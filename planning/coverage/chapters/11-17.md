## Checklist of Concepts, Numbers, and Patterns to Cover
1. **Why Standard Device-Plugin Sharing Is Rigid and How KAI Scheduler Unifies Fractional GPUs:**
   - Standard Kubernetes `nvidia.com/gpu` only accepts whole integers (`1, 2, 4`).
   - Static device-plugin `timeSlicing` (`replicas: 4` or `10`) divides every GPU into fixed uniform tokens (`1/4` or `1/10`), cannot mix a `0.5`-GPU pod and two `0.25`-GPU pods on the same card dynamically, and cannot enforce memory quotas per pod.
   - **How KAI Scheduler implements Dynamic Fractional GPUs (`gpu-fraction` and `gpu-memory`):**
     - Workloads declare exact fractional compute/memory intent via annotations:
       - `gpu-fraction: "0.25"` or `"0.5"` (fraction of a physical GPU's compute/memory)
       - `gpu-memory: "10000"` (explicit GPU memory request in MB/MiB, e.g., `10 GB` on an `80 GB` GPU)
     - KAI Scheduler's `Allocate` and `Consolidate` actions bin-pack heterogeneous fractions (`0.5 + 0.25 + 0.25 = 1.0` physical GPU) onto a single physical GPU while keeping remaining GPUs `100%` whole for `1.0`-GPU or `8.0`-GPU training jobs.
     - How `binder` and **GPU Reservation Pods** work under the hood: because `kubelet` only understands integer `nvidia.com/gpu: 1` requests, KAI's `binder` creates a lightweight **reservation pod** that claims `nvidia.com/gpu: 1` from `kubelet` on the target node and binds the multiple fractional user pods (`0.5 + 0.25 + 0.25`) to that reserved physical GPU UUID.
2. **Measuring the Safe Sharing Envelope (`volume-11/chapter-04` A100 80GB Notebook Benchmark):**
   - Why you must never pick a replica or fraction ratio without an empirical concurrency envelope test:
     - **1 notebook:** `25%` SM, `12 GB / 80 GB` VRAM, `p99 = 8 ms`.
     - **2 notebooks:** `~40%` SM each, `24 GB / 80 GB` VRAM, `p99 = 25 ms`.
     - **4 notebooks:** `~55%` SM each, `48 GB / 80 GB` VRAM (`32 GB` free), `p99 = 120 ms` (safe limit: `replicas: 4` with `>= 20 GB` headroom).
     - **8 notebooks:** `~65%` SM, `96 GB > 80 GB` VRAM -> **OOM crash**, `p99 = 500 ms`.
   - Preventing accidental best-effort placement in production namespaces via `ResourceQuota` (`nvidia.com/gpu.shared: "0"`).
3. **Hardware-Isolated Sharing with MIG (`volume-24/chapter-06` H100 80GB 3-Workload Capstone) and Dynamic MIG in KAI:**
   - H100 `80 GB` (`989` TFLOPS BF16 dense, `3.35 TB/s`) MIG profile table: `7g.80gb` (`7/7`, `80 GB`, `989` TFLOPS), `4g.40gb` (`4/7`, `40 GB`, `565` TFLOPS), `3g.40gb` (`3/7`, `40 GB`, `424` TFLOPS), `2g.20gb` (`2/7`, `20 GB`, `283` TFLOPS), `1g.10gb` (`1/7`, `10 GB`, `141` TFLOPS).
   - Right-sizing the three competing workloads onto `1` H100 (`Driver 535.21`):
     1. **Batch CNN (`ResNet-50`, `25.5M` params, `4 GB` VRAM, batch `32` = `150 MB`, `~2.56 TFLOP/s`):** Assigned **`1g.10gb`** (`141` TFLOPS, `10 GB`) -> achieves **`65.2 img/s`** (`>= 50` target) and **`p99 = 42.3 ms`** (`< 50 ms` target).
     2. **Online Embedding (`768 -> 512 -> 128`, `99 KB` weights, `< 1 GB` VRAM, `526K` FLOPs/query = `~0.1 TFLOP/s`):** Assigned **`1g.10gb`** (`141` TFLOPS, `10 GB`) -> achieves **`6,120 req/s`** (`>= 5,000` target) and **`p99 = 4.8 ms`** (`< 5 ms` target).
     3. **Research Training (`1.3B` LLM, `12.4 GB` VRAM, `~0.3 TFLOP/s`):** Assigned **`2g.20gb`** (`283` TFLOPS, `20 GB`) -> achieves **`92 samples/s`** and **`12%` loss delta** (`>= 0.5%` target).
     - Total consumed: `2/7 + 1/7 + 1/7 =` **`4/7` compute slices and `40 / 80 GB` memory**, leaving **`3/7` slices and `40 GB` free** for a 4th tenant (`3g.40gb`).
