## Checklist of Concepts, Numbers, and Patterns to Cover
1. **The Kubernetes Operator Pattern & `ClusterPolicy` Desired State:**
   - Why a single `ClusterPolicy` CRD (`apiVersion: nvidia.com/v1`, `kind: ClusterPolicy`) replaces manual host scripts and independent Helm charts.
   - Why `ClusterPolicy.status.state: ready` (`reason: OperandsReady`) is a controller-level summary claim, not per-node operand proof: the `25`-node DaemonSet example (`DESIRED 25 / CURRENT 25 / READY 25` on `nvidia-driver-daemonset` and `nvidia-container-toolkit-daemonset`, vs `25 24 24 25 24` on `nvidia-device-plugin-daemonset` with `pod/nvidia-device-plugin-daemonset-h9x2q` in `CrashLoopBackOff` with `6` restarts over `14m`).
   - Per-component node-targeting labels (`nvidia.com/gpu.deploy.driver=true`, `nvidia.com/gpu.deploy.container-toolkit=true`, `nvidia.com/gpu.deploy.device-plugin=true`, `nvidia.com/gpu.deploy.gpu-feature-discovery=true`, `nvidia.com/gpu.deploy.dcgm=true`, `nvidia.com/gpu.deploy.dcgm-exporter=true`, `nvidia.com/gpu.deploy.node-status-exporter=true`, `nvidia.com/gpu.deploy.operator-validator=true` from `bcm11-containerization`).
2. **Operand Dependency Graph & Init-Container Validation Chain:**
   - Why reconciliation is an interdependent evidence chain (`DriverOK` fork), not a blind shell script.
   - How `initContainers` enforce ordering on each node (`bcm11-containerization` Section 6.7.5):
     - `nvidia-container-toolkit-daemonset` has `driver-validation (init)` + `nvidia-container-toolkit-ctr` (installing to `/usr/local/nvidia/toolkit` and patching `/etc/containerd/config.toml` or `/cm/local/apps/containerd/var/etc/conf.d/nvidia-cri.toml`).
     - `nvidia-device-plugin-daemonset` has `toolkit-validation (init)` + `nvidia-device-plugin-ctr`.
     - `nvidia-operator-validator` has four sequential init containers: `driver-validation (init)` (runs `chroot /run/nvidia/driver nvidia-smi`), `toolkit-validation (init)`, `cuda-validation (init)` (spawns Job-style `nvidia-cuda-validator` which runs to `0/1 Completed`), and `plugin-validation (init)` (spawns `nvidia-device-plugin-validator` which runs to `0/1 Completed`), before the main container prints `all validations are successful`.
3. **Driver Containers vs Host-Managed vs Hybrid Ownership Models:**
   - How a privileged Driver Container mounts `/usr/src`, `/lib/modules`, and `/dev`, compiles `nvidia.ko` (or pulls a precompiled image `usePrecompiled: true`), runs `insmod`/`modprobe` into the host kernel, and sleeps until termination (when it runs `rmmod nvidia_uvm` and `rmmod nvidia`, failing if `lsof /dev/nvidia*` shows open file descriptors).
   - Three ownership models (`Operator-managed driver and runtime`, `Host-managed driver and runtime` with `driver.enabled: false`, and `Hybrid`, including BCM 11 defaults where `toolkit.enabled=true`, `driver.enabled=false`, `nfd.enabled=true` on DGX OS images, with GPU Operator `v26.3.3` / `v26.3.0` / `v25.10.1` on Kubernetes `v1.34.7`).
   - Five readiness gates (`1. Infrastructure`, `2. Driver`, `3. Runtime`, `4. Kubernetes`, `5. Acceptance`) and the driver gate output (`NVIDIA H100 80GB HBM3` on `00000000:65:00.0`, `34C`, `P0`, `118W / 700W`, `0MiB / 81559MiB` vs `Failed to initialize NVML: Driver/library version mismatch` vs `Unknown Error` inside a container).
4. **Blast-Radius & Maintenance Window Math (`60`-node canary vs `40`-node rolling drain):**
   - **Canary vs unpooled `ClusterPolicy` (`volume-10/chapter-06`):** `60` GPU nodes under one `ClusterPolicy` where `35` nodes run a newer incompatible kernel (`6.5.0-1015-aws` vs `nvcr.io/nvidia/driver:550.90.07-ubuntu22.04`) degrades `35 / 60 = 58.33%` (`~58%`) of total fleet capacity at once, whereas a `3`-node canary pool caps blast radius at `3 / 60 = 5.0%` leaving `57` nodes untouched.
   - **Maintenance window & concurrent GPU loss (`volume-10/chapter-07`):** `40`-node (`8` GPUs/node = `320` GPUs) driver DaemonSet upgrade at `6` minutes per node:
     - `maxUnavailable: 4` -> `40 / 4 = 10` batches × `6` min = `60` minutes total wall-clock time, taking `4 * 8 = 32` GPUs offline concurrently (violating a `28`-GPU inference headroom SLO).
     - `maxUnavailable: 2` -> `40 / 2 = 20` batches × `6` min = `120` minutes wall-clock time, taking only `2 * 8 = 16` GPUs offline concurrently (staying safely within the `28`-GPU headroom budget with `12` GPUs of margin).
5. **GPU Operator vs NVIDIA Network Operator (`NicClusterPolicy`) boundary:**
   - Why MOFED, `rdma/rdma_shared_device_a: 8`, SR-IOV VFs, and Multus secondary CNI belong to **NVIDIA Network Operator** (`26.1.1` in BCM 11) rather than GPU Operator, and the 3-step RDMA verification sequence (`kubectl describe node` `rdma/rdma_shared_device_a: 8`, `kubectl describe pod nccl-worker-2`, and `kubectl exec -it nccl-worker-2 -- ibv_devinfo` showing `hca_id: mlx5_0`, `InfiniBand (0)`, `fw_ver: 20.36.1010`, `state: PORT_ACTIVE (4)`).
