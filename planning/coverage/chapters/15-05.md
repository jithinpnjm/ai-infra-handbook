## Key topics, numbers, and formulas extracted

1. **TensorRT Graph Compilation, Layer/Kernel Fusion, and Tactic Autotuning (`V12` Ch. 4):**
   - **5-Stage Compilation Pipeline:** (1) Network Parsing (`nvinfer1::IParser` -> `nvinfer1::INetworkDefinition` with explicit batch or `Q/DQ` nodes), (2) Graph Optimization & Rewriting (dead code elimination, constant folding, vertical fusion, horizontal fusion), (3) Tactic Selection & Calibration (empirical SM kernel benchmarking + `IInt8EntropyCalibrator2`), (4) Engine Serialization (`IBuilder` + `IBuilderConfig` -> `ICudaEngine` -> `.engine` / `.plan` binary), (5) Runtime Execution (`IRuntime` -> shared immutable `ICudaEngine` -> per-thread/per-stream `IExecutionContext` calling `enqueueV3()`).
   - **Vertical Fusion (`Conv + BN + ReLU`):** Folds Batch Normalization parameters `(mu, sigma^2, gamma, beta)` into Convolution weights `W` and bias `b` at compile time:
     - `W_hat[i,j] = W[i,j] * (gamma_i / sqrt(sigma_i^2 + epsilon))`
     - `b_hat[i] = (b_i - mu_i) * (gamma_i / sqrt(sigma_i^2 + epsilon)) + beta_i`
     - Eliminates intermediate HBM reads/writes between Convolution, BatchNorm, and Activation.
   - **Horizontal Fusion (`QKV` Projection):** Concatenates parallel projections sharing the same input tensor `X` (`Q = X * W_Q`, `K = X * W_K`, `V = X * W_V`) into `W_QKV = [W_Q | W_K | W_V]`, cutting 3 kernel launches to 1.
   - **Tactic Autotuning & Workspace Memory:** Evaluates candidate kernels (*tactics*) empirically on the target GPU at `kOPT` dimensions while allocating scratch workspace for `kMAX` dimensions (`MemoryPoolType::kWORKSPACE`, e.g., `2 GB` or `4 GB`).
   - **Optimization Profile (`IOptimizationProfile`):** Defines `(kMIN, kOPT, kMAX)`. Misconfiguring `MAX=(128, 3, 4096, 4096)` in FP32 allocates `128 * 3 * 4096 * 4096 * 4 = 25,769,803,776 B` (`~25.7 GB`) per activation layer (or `128 * 8192 * 8192 * 4 = 34.36 GB` / `34 GB` in sequence models), crashing an `80 GB` A100 builder with `std::bad_alloc`. Bounding `min=(1,3,256,256)`, `opt=(8,3,1024,1024)`, `max=(32,3,2048,2048)` with a `4 GB` workspace limit completes compilation in `4.2 minutes` at `6.1 GB` peak VRAM and cuts runtime latency at `B=8, 1024x1024` from `48 ms` to `11.3 ms` (`4.25x` speedup).

2. **Hardware/Driver Portability Constraints & Multi-Threaded Runtime (`V12` Ch. 4 & Ch. 5):**
   - **Hardware Lock-In:** `.engine` / `.plan` files embed SASS assembly and tactic parameters tuned for the exact SM compute capability (`sm_80` A100, `sm_89` L4/L40S, `sm_90a` H100/H200, `sm_100` B200/GB200), TensorRT major/minor version, and exact `tp_size` / `pp_size` world topology. An engine compiled on an `A100` cannot execute on an `H100`.
   - **Thread Safety:** `ICudaEngine` is immutable and thread-safe (load once per GPU), whereas `IExecutionContext` holds mutable per-stream tensor addresses (`setTensorAddress`) and workspace pointers and is **not thread-safe** (must maintain one `IExecutionContext` per worker thread/CUDA stream in a thread-local or mutex-guarded pool).

3. **TensorRT-LLM Checkpoint Conversion, `trtllm-build`, `trtllm-serve`, and Parallel Execution Graphs (`V12` Ch. 5, `V05`, `HLS` Ch. 8):**
   - **Production 70B Scenario:** `Llama-3-70B` (`140 GB` FP16 weights) on `8x H100 SXM5` (`TP=8`) at `150` concurrent sessions: naive PyTorch Hugging Face pipeline suffers `115 ms/tok` ITL (violating `< 25 ms/tok` SLA), `12%–98%` GPU utilization swings, and OOM at `> 8,192` tokens. TensorRT-LLM reduces ITL from `115 ms` to `18.4 ms` (`6.25x` faster) and doubles throughput.
   - **Two-Step Build Pipeline:**
     1. `convert_checkpoint.py` (`--model_dir`, `--output_dir`, `--dtype bfloat16`, `--tp_size`, `--pp_size`) shards Hugging Face Safetensors weights into rank-specific checkpoints (`rank0.safetensors .. rank{N-1}.safetensors`).
     2. `trtllm-build` (`--checkpoint_dir`, `--output_dir`, `--gemm_plugin bfloat16`, `--gpt_attention_plugin bfloat16`, `--use_paged_context_fmha enable`, `--max_batch_size 128`, `--max_input_len 4096`, `--max_seq_len 8192`, `--max_num_tokens 8192`) compiles rank-specific `.engine` plans (`rank0.engine .. rank{N-1}.engine`).
     3. `trtllm-serve` / Python `LLM` API / C++ `Executor` & Triton `tensorrtllm` backend (`decoupled: True`, `max_tokens_in_paged_kv_cache: 256000`, `kv_cache_free_gpu_mem_fraction: 0.85..0.90`, `enable_chunked_context: true`) serves the compiled engines.
   - **Megatron-Style Tensor Parallelism Math:**
     - `ColumnParallelLinear` splits `W` column-wise (`QKV` projection and MLP `Gate/Up` projection) with **0 communication**.
     - `RowParallelLinear` splits `W` row-wise (`Attention Output W_O` and MLP `Down` projection) and executes **1 `AllReduce-Sum`** per sub-layer (**`2` `AllReduce` operations per Transformer layer**).
     - Per-rank `AllReduce` volume: `Data_Volume = 2 * ((TP - 1) / TP) * B * S * H * BytesPerElement`.
     - Fused custom plugins (`TwoShotAllReduce` / `KernelFusedAllReduce` / `set_nccl_plugin`) fuse matrix multiplication output with NVLink reduction inside SM registers.
     - Multi-node `130B` failure mode: running `TP=8` across `2` nodes (`4x H100` each) over PCIe/InfiniBand spikes latency `> 30x` and deadlocks `GptManager` after `300 seconds`; restructuring to `TP=4` (intra-node NVLink) and `PP=2` (inter-node IB) starts in `< 14 seconds` and cuts inter-node IB traffic by `88%`.

4. **Custom Attention/GEMM Plugins (`FlashAttention-2`, `FlashDecoding`, `XQA`, `MHARunner`) (`V12` Ch. 5):**
   - **Prefill (`contextFMHA` / `FlashAttention-2`):** Reduces attention HBM traffic from `O(S^2)` to `O(S)` via tiled online softmax in SM shared memory. Without paged/chunked context FMHA, prefill workspace for `B=8, S=2048, heads=8` requires `450 MB` of temporary attention buffers.
   - **Decode (`FlashDecoding` & `XQA` / `MHARunner`):** During single-token decode (`S_query = 1`), standard `FlashAttention-2` assigns 1 thread block per head, leaving an `H100` (`132` SMs) under-utilized when `H_kv` is small. `FlashDecoding` splits the historical KV cache across `N` chunks (e.g., `256` tokens/chunk) and reduces partial softmax statistics in a second stage, delivering up to **`8x` decode speedup** on long contexts. TensorRT-LLM's `MHARunner` dispatches `XQA` (eXtended Query Attention) kernels specifically optimized for Grouped-Query Attention (`GQA`, e.g., `H_q = 64`, `H_kv = 8` on `Llama-3-70B`), packing multiple query heads per KV head into a single Tensor Core MMA tile during decode.

5. **In-Flight Batching and Paged KV Cache (`KVCacheManager`, `GptManager`, `Executor`) (`V12` Ch. 5):**
   - **KV Cache Sizing Formula:** `KV_Bytes_Per_Token = 2 * L * H_kv * d_head * BytesPerElement`.
     - For `Llama-3-70B` (`L=80, H_kv=8, d_head=128`): `2 * 80 * 8 * 128 = 163,840` elements/token.
     - In `FP16`/`BF16` (`2 B`): `327,680 B = 320 KB/token` (`1.31 GB` / `1,342,177,280 B` per `4,096`-token sequence across ranks, or `320 KB / TP` per rank).
     - In `FP8` (`1 B`): `163,840 B = 160 KB/token` (`0.65 GB` / `671,088,640 B` per `4,096`-token sequence, **50% VRAM savings**).
   - **Block Fragmentation & Memory Fraction:** Setting `tokens_per_block = 128` wastes nearly `50%` of KV memory when sequences finish at `129` tokens (`2` blocks = `256` token slots allocated for `129` tokens -> `127` wasted slots = `49.61%` internal fragmentation). Reducing `tokens_per_block` from `128` to `32` (`129` tokens -> `5` blocks = `160` slots, `31` wasted = `19.38%`), enabling `FP8` KV cache (`KvCacheQuantMode::FP8()`), and lowering `kv_cache_free_gpu_memory_fraction` from `0.95` to `0.85` (reserving `15%` for activation workspace) increases max concurrent sessions on `4x A100` (`TP=4`) from **`64` to `210` (`3.28x`)** and raises effective KV cache utilization from **`52%` to `91%`**.

6. **Quantization with NVIDIA ModelOpt (`FP8`, `INT8 SmoothQuant`, `INT4 AWQ`, `NVFP4`) (`V12` Ch. 4 & 5, `ASP` Ch. 8 & 9, `HLS` Ch. 6):**
   - **TensorRT Precision Comparison (`V12` Ch. 4):**
     - `FP32`: `32-bit`, `1.0x` latency, `100%` memory, `0.0%` loss.
     - `FP16`/`BF16`: `16-bit`, `2.0x–3.5x` speedup, `50%` memory, `< 0.1%` loss.
     - `INT8 PTQ` (`IInt8EntropyCalibrator2` KL divergence over `2048` bins, `500–1,000` samples): `8-bit`, `3.0x–6.0x` speedup, `25%` memory, `0.5%–3.0%` loss.
     - `INT8 QAT` (Explicit `Q/DQ` nodes): `8-bit`, `3.5x–6.5x` speedup, `25%` memory, `< 0.2%` loss.
     - `FP8` (`E4M3` weights/activations + `E5M2` gradients/KV cache on Hopper/Blackwell): `8-bit`, `4.0x–8.0x` speedup vs FP32 (`2–3x` vs FP16), `25%` memory, `< 0.2%` loss.
   - **LLM Quantization Modes via `nvidia-modelopt` (`modelopt.torch.quantization`):**
     - `SmoothQuant (W8A8 INT8)`: Migrates activation outliers (up to `100x` baseline) into weights via per-channel smoothing scale `s = max(|X|)^alpha / max(|W|)^(1 - alpha)`: `X_hat = X * diag(s)^(-1)`, `W_hat = diag(s) * W`.
     - `INT4 AWQ / GPTQ (W4A16 Weight-Only)`: `4-bit` weights (`0.5 B/param`) dequantized on-the-fly in SM registers to `FP16`; ideal for low-concurrency memory-bandwidth-bound decode (`B = 1..16`), whereas `FP8 W8A8` wins at high concurrency (`B >= 32`) because both weights and activations execute on `FP8` Tensor Cores without dequantization overhead (`HLS` Ch. 6).
     - `NVFP4 (W4A4 / E2M1 with Two-Level Microscaling on Blackwell)`: Uses `4-bit` `E2M1` (`0.5 B/param`) with per-microblock (`16`-element) `FP8` scale factors and a second-level per-tensor `FP32` scale, executed via Blackwell `tcgen05.mma` and `256 KB` `TMEM` at **`10 PFLOPS` dense on `B200`** (`15 PFLOPS` on `B300`, vs `80 TFLOPS` FP32). Shrinks `Llama-3-70B` weights from `140 GB` (FP16) to `70 GB` (FP8) and `~35–39.4 GB` (`NVFP4` / `INT4 AWQ`), and fits `gpt-oss-120b` (`117B * 0.5 = 58.5 GB`) on a single `80 GB` GPU (`HLS` Ch. 6, `ASP` Ch. 8 & 9).
