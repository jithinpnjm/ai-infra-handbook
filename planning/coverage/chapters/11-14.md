## Checklist of Concepts, Numbers, and Patterns to Cover
1. **KAI Scheduler Microservice Control-Plane Architecture:**
   - Why KAI Scheduler splits scheduling into specialized Kubernetes controllers rather than a single monolithic binary:
     1. **`pod-grouper`:** Watches incoming workload objects (`Pod`, `Job`, `PyTorchJob`, `TrainJob` / `JobSet`, `LeaderWorkerSet`, `MPIJob`, `RayJob`) and automatically synthesizes or reconciles **`PodGroup`** custom resources (`minMember`, queue binding, gang topology constraints) without requiring users to write `PodGroup` YAML by hand.
     2. **`queue-controller`:** Reconciles **`Project`** (`kai.run.ai/v1`) and hierarchical **`Queue`** (`scheduling.run.ai` / `kai.scheduler`) custom resources, tracking real-time allocated, guaranteed (`nominal` / `gpuQuota`), and borrowed GPU/CPU/memory quantities across parent departments and child team queues.
     3. **`kai-scheduler` (Core Scheduling Engine):** Runs a session-based batch scheduling cycle (`Snapshot -> Reclaim -> Preempt -> Backfill / Allocate -> Consolidate / Binpack`) across `PodGroup`s and `Queue`s for all Pods with `spec.schedulerName: kai-scheduler`.
     4. **`binder` (and `BindRequest` / Reservation Pods):** Executes atomic binding of pods to nodes, coordinates fractional/shared GPU device reservations (creating/managing GPU reservation pods or device-sharing annotations), and ensures gang members bind only when all node preconditions succeed.
     5. **`admission` / Mutating & Validating Webhooks:** Validates project/queue entitlements, injects `schedulerName: kai-scheduler` onto pods belonging to KAI-managed namespaces/projects (`kai.run.ai/project: ml-team-a`), and translates fractional GPU annotations (`gpu-fraction: "0.5"`, `gpu-memory`) into scheduler-visible contracts.
2. **Core KAI Scheduler Custom Resource Definitions (CRDs) and API Objects:**
   - **`Project` (`kai.run.ai/v1`, `GAK` Example 7-5):** High-level tenant boundary (`metadata.name: ml-team-a`, `spec.gpuQuota: 8`) referenced via `kai.run.ai/project: ml-team-a`.
   - **`Queue` (`scheduling.run.ai/v2` / `kai.scheduler`):** Represents a node in the two-level (or multi-level) scheduling tree (`Parent Queue` = Department, `Child Queue` = Project/Team), tracking `gpu` (`quota`, `overQuotaWeight`, `limit`), `cpu`, and `memory` resources.
   - **`PodGroup`:** The atomic unit of scheduling in KAI Scheduler (`minMember`, `queue`, `priorityClassName`, `topologyConstraint`), automatically generated by `pod-grouper` with ownerReferences pointing back to the parent `PyTorchJob`, `JobSet`, or `LeaderWorkerSet`.
   - **`Topology` & Node Group Labels:** Captures cluster hardware domains (NVSwitch domain, rack, InfiniBand leaf switch) consumed by the KAI topology plugin.
   - **`BindRequest`:** Decouples the scheduler's in-memory placement decision from the asynchronous node binding and fractional-GPU reservation handshake handled by `binder`.
3. **Inside the KAI Scheduling Cycle (Session Actions & Plugins):**
   - Step 1: **Cluster State Snapshot** (nodes, `Allocatable` GPUs, MIG slices, fractional reservation pods, active `PodGroup`s, and `Queue` usage).
   - Step 2: **Order `Queue`s and `PodGroup`s** (by `PriorityClass`—such as `inference-critical: 1000`, `training-high-priority: 100`, `research-best-effort: 0` in `volume-24/chapter-07`—and fair-share deficit ratio).
   - Step 3: **Action Pipeline:**
     - `reclaim`: Reclaims borrowed GPUs when an under-quota `Queue` submits pending `PodGroup`s.
     - `preempt`: Preempts lower-priority `PodGroup`s within the same `Queue` (`1000 > 100 > 0`).
     - `allocate` / `backfill`: Places full-GPU, multi-GPU gang, and fractional-GPU (`0.5`, `0.25`) `PodGroup`s onto nodes using bin-packing and NVLink/NVSwitch topology scoring.
     - `consolidate`: Defragments partially occupied fractional/single-GPU nodes so contiguous multi-GPU gangs can fit.
4. **Worked 8-GPU, 20-Job Scheduling Simulation (`volume-24/chapter-07`):**
   - `2` nodes (`node-1`, `node-2`), `4` GPUs and `320 GB` GPU memory per node (`8` GPUs total).
   - `20` jobs arrive: `6` Type B Inference jobs (`0.5` GPU each = `3.0` GPUs total, `priority: 1000`, `p99 < 10 ms` SLO), `10` Type A Training jobs (`1.0` GPU each, `priority: 100`, capped at `60%` = `4.8` GPUs / `4` whole GPUs concurrently), and `4` Type C Research jobs (`0.25` GPU each = `1.0` GPU total, `priority: 0`).
   - Exact packing layout: `6` Inference jobs (`6 * 0.5 = 3.0` GPUs) + `4` Training jobs (`4 * 1.0 = 4.0` GPUs, `<= 4.8` cap) + `4` Research jobs (`4 * 0.25 = 1.0` GPU) = **`8.0` of `8.0` GPUs (`100%` packed, `> 85%` utilization target)** with zero starvation across all three classes.
