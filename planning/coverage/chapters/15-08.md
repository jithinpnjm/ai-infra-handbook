| **1. Why Colocated Serving Fails & DistServe Goodput Math** | **Prefill vs Decode interference:** Prefill is compute-bound (`O(N^2)` attention / parallel GEMMs saturating Tensor Cores; `AI >> 100 FLOPs/B`), whereas decode is memory-bandwidth-bound (sequential GEMV reading all weights + KV cache per token; `AI ~ 1–2 FLOPs/B`, `140 GB / 3,350 GB/s = 41.7 ms` / `24 tok/s` single-stream ceiling on H100). Colocating both phases on the same GPUs causes head-of-line blocking (long prefills stall active decode streams, spiking ITL/TPOT) and forces a single suboptimal batching/parallelism configuration. **MLPerf Inference v5.0 (2025) p99 SLOs (`ASP` Ch. 17):** `Llama-2-70B` targets **`450 ms` p99 TTFT** and **`40 ms` p99 TPOT**; `Llama-3.1-405B` targets **`6,000 ms` (`6 s`) p99 TTFT** and **`175 ms` p99 TPOT** (interactive chat often targets `< 200–300 ms` p99 TTFT and `< 25–30 ms` ITL). **DistServe Goodput Benchmark (`ASP` Ch. 17 Fig. 17-2):** Under `P90 TTFT <= 0.4 s` (`400 ms`) and `P90 TPOT <= 0.04 s` (`40 ms`), a colocated 1-GPU system sustains `~3.0 RPS` under the TTFT bound alone but only **`1.6 RPS` under the TPOT bound**, yielding a colocated goodput of **`1.6 RPS/GPU`**. Disaggregating into **`2P1D` (`2` prefill GPUs + `1` decode GPU = `3` GPUs total)** achieves `5.6 RPS` per prefill worker (`5.6 * 2 = 11.2 RPS` total prefill capacity) and `10.0 RPS` on the decode worker: `Goodput_total = min(11.2, 10.0) = 10.0 RPS` across `3` GPUs = **`3.33 RPS/GPU` (`3.3 RPS/GPU`, a `2.08x` per-GPU goodput gain)**. Across broader workloads, DistServe reports up to **`7.4x` higher goodput** or **`12.6x` tighter latency SLOs**. | `ASP` Ch. 15, Ch. 17; `V12` Ch. 1, Ch. 8, Ch. 9; `HLS` Ch. 7 |
| **2. NVIDIA Dynamo Architecture: Decode-Centric Control Plane, Smart Router & GPU Planner** | **NVIDIA Dynamo Stack (`ASP` Ch. 4, 15, 17, 18):** Open-source modular distributed inference framework (written in Rust and Python, supporting `TensorRT-LLM`, `vLLM`, `SGLang`, and `PyTorch`) that achieved up to **`30x` higher inference throughput** on a **`680B`-parameter MoE model (`DeepSeek-R1`)** on a **`72`-GPU `GB200 NVL72`** rack (`130 TB/s` NVSwitch domain). **4 Core Components:** (1) **Dynamo Smart Router (KV-Cache-Aware Router)**, (2) **Dynamo GPU Planner (SLO-Driven Capacity & Role Controller)**, (3) **NVIDIA Inference Transfer Library (`NIXL`)**, and (4) **Distributed KV Cache Manager**. **Coordination & Decode-Centric Flow (`ASP` Ch. 17 & 18):** Uses **`etcd`** for worker discovery and lease management and **`NATS`** for low-latency distributed request/event messaging and global prefill queues. In Dynamo's decode-centric flow, requests arrive at a decode worker (or Smart Router), which checks **`should_offload_prefill()`** using effective uncached prompt length `eff_len = max(0, prompt_length - prefix_cached_length)`: offloads to the remote prefill queue (`Put RemotePrefillRequest`) if `(eff_len >= 256 and prefill_queue_size < 10)` or `(decode_active_reqs >= 8 and eff_len >= 64)`; otherwise executes prefill locally on the decode worker (graceful load-shedding fallback when prefill pool is saturated or prefix cache hit is high). **Smart Router Composite Latency Cost (`ASP` Ch. 17 Table 17-3):** `latency_cost = 3.0 * occupancy_percent + 1.0 * active_reqs - 10.0 * int(cache_match_flag) + 0.5 * mem_bw_percent - 1.0 * int(recent_prefix_flag)` (lower is better; simpler 2-term variant `0.7 * occupancy_percent + 0.3 * active_req_count`). Conversely, Dynamo's `disaggregated_router` score (`higher = remote`) weights `prefill_length > 256` (`weight: 0.7`, `prefer_remote`) vs `prefill_queue_depth > 10` (`weight: 0.3`, `prefer_local`) against `remote_prefill_min_score: 0.5`. **Dynamo GPU Planner (`ASP` Ch. 17 & 18):** Continuously monitors TTFT, TPOT, queue depths, GPU utilization, and KV cache usage to scale prefill (`min_replicas: 4, max_replicas: 12`, scale up at `queue_length: 8, gpu_utilization: 80%`, scale down at `queue_length: 2, gpu_utilization: 40%`) and decode (`min_replicas: 8, max_replicas: 24`, scale up at `queue_length: 16, kv_cache_usage: 75%`, scale down at `queue_length: 4, kv_cache_usage: 30%`), and enforces QoS tiers (`premium: 10%` reserved, `priority: 100`; `standard: 30%`, `priority: 50`; `free: 60%`, `priority: 10`) and early rejection (`low_priority_threshold_ms: 500`, `est_ttft = Q_p * t_p + Q_d * t_d > ttft_slo_ms`). | `ASP` Ch. 4, Ch. 17, Ch. 18 |
| **3. NIXL (`NVIDIA Inference Xfer Library`): Asynchronous Point-to-Point Data Plane** | **NCCL vs NIXL (`ASP` Ch. 4 Table 4-5):** NCCL handles synchronous many-to-many collectives (`AllReduce`, `AllGather`, `ReduceScatter` with barrier semantics across all ranks), whereas **NIXL (`0.5.x`)** handles nonblocking, asynchronous one-to-one and one-to-few point-to-point transfers across heterogeneous memory and storage tiers (`GPU VRAM <-> GPU VRAM`, `CPU DRAM`, `Local NVMe SSD via GDS`, and `Remote Object/Shared Storage` such as S3/Lustre) without blocking compute streams. **NIXL C++ API Lifecycle (`ASP` Ch. 4):** Configure `nixl_agent_config` (`backends = {"UCX", "GDS"}`, `thread_safe = true`), instantiate `nixlAgent("srcAgent", cfg)` and `nixlAgent("dstAgent", cfg)`, build `nixl_desc_t` (`addr`, `len = 1 << 20` [`1 MiB`], `devId`, `seg = VRAM_SEG`), call `registerMem()` and `trim()` to create compact metadata-free transfer descriptors (exchanged via `etcd`), prepare and launch nonblocking write via `prepXfer(NIXL_WRITE, ...)` and `postXfer(NIXL_WRITE, ...)`, poll completion via `checkXfer(reqHandle)` (`NIXL_INPROGRESS` -> `NIXL_SUCCESS`), and clean up with `releaseReqH()` and `deregisterMem()`. Uses **GPUDirect RDMA** and **InfiniBand GPUDirect Async (`IBGDA`)** so the GPU/NIC initiates transfers without CPU intervention. **Page Collation & Transfer Math (`ASP` Ch. 18, `HLS` Ch. 7):** For a `70B` model (`M_token = 327,680 B = 320 KiB/tok` in FP16 GQA, or `1.31 MB/tok` in `32`-head MHA), a `7,500`-token prompt with `16`-token PagedAttention blocks generates `ceil(7500 / 16) = 469` (`~470`) tiny non-contiguous transfers taking **`20 ms`** due to RDMA WQE/doorbell overhead; collating into **`>= 128`-token slabs (`59` transfers)** cuts RDMA transfer time by **`2.5x` to `8 ms`**. At `16 RPS` and `1.0–1.5 GB` KV per request, aggregate KV transfer demand is **`16–24 GB/s` (`~25 GB/s`)**, which easily fits intra-node NVLink (`900 GB/s` H100, `1,800 GB/s` B200) or multi-rail InfiniBand/RoCE RDMA (`50–100 GB/s` per `400G`/`800G` ConnectX-7/8 NIC, or `500–600 Gbps` cluster fabric), but saturates non-RDMA PCIe/TCP (`10 GB/s` / `10–20 Gbps` pod Ethernet). **LMCache + NIXL Config (`ASP` Ch. 18):** `pd_buffer_size: 1073741824` (`1 GiB`), `pd_proxy_port: 7500`, `pd_peer_init_port: 7300`, `pd_peer_alloc_port: 7400`, `UCX_RNDV_THRESH=16384`, `UCX_MAX_EAGER_RAILS=1`, `UCX_TLS=cuda_ipc,rc,rdmacm,cuda_copy,tcp`. | `ASP` Ch. 4, Ch. 15, Ch. 17, Ch. 18; `HLS` Ch. 7; `GAK` Ch. 4 |
| **4. Distributed KV Cache Manager, Tiered Offloading & Heterogeneous Hardware/Parallelism** | **4-Tier KV Cache Hierarchy (`ASP` Ch. 4 Fig. 4-5, Ch. 18, `HLS` Ch. 7):** Tier 1: **GPU HBM** (`80–192 GB`/GPU, `3.35–8.0 TB/s`); Tier 2: **CPU / Superchip DRAM** (`Grace Hopper` / `Grace Blackwell` `LPDDR5X` over **`900 GB/s` NVLink-C2C**, or x86 host pinned DRAM over `64 GB/s` PCIe Gen5, expanding KV capacity by **`3x`**); Tier 3: **Local NVMe SSD** accessed via **GPUDirect Storage (`GDS`)** (expanding KV capacity by **`50x`**); Tier 4: **Remote Shared / Network Storage** (`Lustre`, `3FS`, `Redis`, `S3`). **Measured Speedups (`ASP` Ch. 4 Fig. 4-9 & 4-10, `HLS` Ch. 7 Fig. 7-25 & 7-27):** Offloading KV cache to host DRAM on an **x86 + H100** PCIe system delivers up to **`14x` faster TTFT** on long sequences compared to recomputing prefill; **Grace Hopper (`GH200`)** with **`900 GB/s` NVLink-C2C** delivers an additional **`2x` faster TTFT** over x86 + H100 (`28x` effective gain over recompute). In `LMCache` multi-turn benchmarks (`Qwen3-14B`, `150 GB` CPU cache), CPU KV retrieval takes **`1.0 s` vs `6.0–7.0 s`** cold prefill recomputation and boosts 5-concurrency throughput by **`16x`** over vanilla vLLM (`75,200 tok/s` vs `4,700 tok/s`). For a `250,000`-token context on a `70B` model (`32` KV heads, `1.31 MB/tok`), FP16 KV is **`328 GB`** (`100–150 GB` in FP8). **Heterogeneous Hardware & Parallelism (`ASP` Ch. 17 & 18, `HLS` Ch. 7):** Pair compute-dense GPUs for prefill with memory-bandwidth/capacity GPUs for decode: e.g., `4x B200` prefill + `8x B300` decode (`180 GB` HBM, `70 GB` weights -> `~110–122 GB` KV pool), or `H100` prefill + `H200` (`141 GB`, `4.8 TB/s`) / `L40S` decode, or **Splitwise `4x H100` prefill + `4x A100` decode** achieving **`2.35x` RPS** at iso-cost/power (and `1.4x` throughput at `20%` lower cost; **HexGen-2** achieves `2.0x` peak / `1.3x` avg throughput or `-30%` cost; **Arrow** adaptive instance scaling achieves up to **`5.6x` request rate** under shifting workloads). When `TP_p != TP_d` (e.g., `TP_p = 2, PP_p = 2` or `TP_p = 8` vs `TP_d = 1` or `TP_d = 4`), Dynamo executes an on-the-fly **KV layout transpose kernel** (`[TP_p] -> [TP_d]`) immediately after the NIXL read. | `ASP` Ch. 4, Ch. 17, Ch. 18; `HLS` Ch. 7 |
