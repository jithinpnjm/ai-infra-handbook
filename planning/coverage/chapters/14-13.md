## Key topics, numbers, and formulas extracted

1. **When to Fine-Tune vs Prompt Engineering vs RAG (`AIE` Ch. 7, `LEH` Ch. 5, `LLO` Ch. 5, `GAK` Ch. 6):**
   - **Form vs Facts rule:** *"Finetuning is for form, and RAG is for facts"* (`AIE` Ch. 7). Information-based failures (missing private data or outdated cutoff, e.g., 10 vs 11 studio albums) require RAG (starting with BM25 before vector search). Behavioral/formatting failures (tone, domain syntax, JSON/YAML/DSL compliance, safety) require fine-tuning.
   - **Benchmark evidence (`AIE` Ch. 7 Tables 7-1 & 7-2):**
     * *BloombergGPT (50B)* trained on `1.3 million` A100 GPU hours (`$1.3M–$2.6M` compute cost) scored `75.07` on FiQA and `43.41` on ConvFinQA, whereas zero-shot `GPT-4-0314` scored `87.15` and `76.48`.
     * *Ovadia et al. (2024) current-events QA (`Table 7-2`):* `Mistral-7B` base (`0.481`) -> `Base + RAG` (`0.875`) vs `FT-reg` (`0.504`), `FT-par` (`0.588`), `FT-reg + RAG` (`0.810`), `FT-par + RAG` (`0.830`); `Llama 2-7B` base (`0.353`) -> `Base + RAG` (`0.585`) vs `FT-reg` (`0.219`), `FT-par` (`0.392`); `Orca 2-7B` base (`0.456`) -> `Base + RAG` (`0.876`) vs `FT-reg` (`0.511`), `FT-par` (`0.566`). Across MMLU, combining RAG + fine-tuning improved over RAG alone `43%` of the time and did not improve `57%` of the time.
     * *Small task-specific models:* Grammarly's fine-tuned `Flan-T5` outperformed a `60x` larger `GPT-3` model on text editing using `82,000` `(instruction, output)` pairs (`AIE` Ch. 7).
     * *Code Llama context extension:* Long-context fine-tuning extended `Llama 2` context from `4,096` to `16,384` tokens (`AIE` Ch. 7).
     * *Cost economics (`LLO` Ch. 5):* Fine-tuning is an upfront capital cost (e.g., `$25,000` per million tokens for proprietary `GPT-4o` fine-tuning, or GPU hours in-house), whereas long few-shot prompts act like a per-request "mortgage" (paying input token latency and KV-cache memory on every query). If a model's lifespan is `2` years, prepaying a `10`-year break-even upfront is uneconomical.
     * *Tokenizer domain adaptation (`LLO` Ch. 5):* `tokenizer.add_tokens(custom_vocab)` + `model.resize_token_embeddings(len(tokenizer))` keeps domain terms (chemical formulas, legal citations) as atomic tokens rather than fragmented subwords.

2. **Supervised Fine-Tuning (SFT), Dataset Engineering, and Chat Templates (`LEH` Ch. 5, `AIE` Ch. 2 & 7):**
   - **Dataset sizing (`LEH` Ch. 5, `AIE` Ch. 2):**
     * Pre-training uses `98%` of compute while post-training uses `~2%` (`InstructGPT`, `AIE` Ch. 2). `InstructGPT` used `13,000` demonstration pairs (~`30` minutes and `$10` per pair = `$130,000`, with `~90%` college-educated and `> 33%` master's-educated labelers); `OpenAssistant`/`LAION` used `13,500` volunteers to collect `10,000` conversations (`161,443` messages in `35` languages, `461,292` ratings).
     * `LIMA` showed `1,000` high-quality curated examples suffice for a `70B` model, whereas smaller `7B–8B` models need more examples (e.g., `3,335` domain pairs upsampled with `10,000` `FineTome` samples = `13,335` samples in `LEH` Ch. 5) just to reliably learn the chat template.
     * General-purpose SFT: `Yi` (`< 10,000`), `OpenHermes` / `Dolphin` (`~1,000,000`), `Llama 3` (`10,000,000` total post-training samples). Task-specific SFT: `100` to `100,000` samples (`LEH` Ch. 5) or `100` to `1,000` for PEFT (`GAK` Ch. 6).
   - **Curation & quality pipeline (`LEH` Ch. 5):**
     * Three quality pillars: **Accuracy**, **Diversity**, **Complexity**.
     * Rule-based filtering (length bounds, keyword exclusion, syntax/JSON format check), **Exact deduplication** (MD5 / SHA-256), **Fuzzy deduplication** (MinHash + Jaccard similarity over shingles), **Semantic deduplication** (embeddings + cosine/Euclidean distance + K-means/DBSCAN clustering), and **Data decontamination** against evaluation benchmarks.
     * Quality scoring: **LLM-as-a-judge** (`1–4` rubric or pairwise ranking, aiming for `~80%` human agreement, mitigating position bias via order randomization, length bias via length normalization, and family/intra-model bias via a multi-LLM jury), **Reward models** (`ArmoRM-Llama3-8B-v0.1` multi-objective regression/gating over helpfulness, correctness, coherence, complexity, verbosity; `RewardBench`), and **Fast encoder classifiers** (`fineweb-edu-classifier` on `snowflake-arctic-embed-m`, `20` epochs on `450,000` `Llama-3-70B` annotations).
     * Augmentation: **Evol-Instruct** (`AutoEvol` in-depth evolving adding `10` to `20` words via constraints, deepening, concretizing, multi-step reasoning, complicated input; plus in-breadth evolving) and **UltraFeedback**.
   - **Storage formats and Chat Templates (`LEH` Ch. 5 Tables 5.5–5.7):**
     * Storage formats: `Alpaca` (`instruction`, optional `input`, `output`), `ShareGPT` (`conversations`: `[{"from": ..., "value": ...}]`), `OpenAI` (`messages`/`conversations`: `[{"role": ..., "content": ...}]`), `OASST`, and `Raw text` (continual pre-training).
     * Chat templates (`Jinja`, `add_generation_prompt=True`): `ChatML` (`<|im_start|>role\n...\n<|im_end|>`), `Llama 3` (`<|begin_of_text|><|start_header_id|>role<|end_header_id|>\n\n...<|eot_id|>`), `Phi-3`, `Gemma`, `Alpaca`. Whitespace, newlines, and explicit `EOS_TOKEN` are critical: missing `EOS_TOKEN` causes infinite generation at inference time; changing an instruct model's template causes severe performance regression.
     * **Prompt loss weight / completion-only loss (`AIE` Ch. 7):** Setting prompt loss weight to `0%` (masking prompt tokens with `-100` in cross-entropy) or `10%` default ensures the model optimizes response generation rather than memorizing user prompts.
     * **Sequence packing (`LEH` Ch. 5):** Concatenating short samples (e.g., three to four `200–300`-token examples into a `1,024` or `2,048` context window) with block-diagonal/sample-isolated attention masks so attention never crosses sample boundaries.

3. **Full Fine-Tuning vs PEFT, LoRA, and DoRA Memory & Parameter Math (`AIE` Ch. 7, `LEH` Ch. 5, `KFG` Ch. 4, `LIP` Ch. 9):**
   - **Full fine-tuning memory baseline (`LEH` Ch. 5 & `AIE` Ch. 7):**
     * `LEH` Ch. 5 baseline (`16 bytes/param`): `2` bytes (`FP16`/`BF16`) or `4` bytes (`FP32`) weights + `4` bytes gradients + `8` bytes Adam states = `16 B/param` -> **`112 GB` VRAM for a `7B` model** and **`1,120 GB` VRAM for a `70B` model** (before activations).
     * `AIE` Ch. 7 pure 16-bit calculation (`8 bytes/param` before activations): For a `7B` model in 16-bit (`2 B`), weights = `14 GB`, gradients + 2 Adam states = `7B * 3 * 2 B = 42 GB`, total = **`56 GB`** (exceeding `12–24 GB` consumer GPUs and `48 GB` mid-tier GPUs). For a `13B` model in 16-bit: weights = `26 GB` (`31.2 GB` inference with `1.2x` KV/activation factor); training gradients + Adam states = `13B * 3 * 2 B = 78 GB` (or `6 GB` if only `1B` parameters are trainable).
   - **Why PEFT works (`AIE` Ch. 7):** Pre-trained LLMs have a **low intrinsic dimension** (`Aghajanyan et al., 2020`). Houlsby et al. (2019) serial adapters achieved within `0.4%` of full fine-tuning on GLUE with `3%` trainable parameters (whereas partial fine-tuning needed `~25%`), but serial adapters add inference latency.
   - **LoRA formulation (`Hu et al., 2021`; `AIE` Ch. 7, `LEH` Ch. 5, `LIP` Ch. 9):**
     * For frozen weight matrix `W_0` of shape `(d_in, d_out)` (or `n x m`), LoRA adds low-rank matrices `A` of shape `(d_in, r)` initialized with Gaussian noise (`sigma = 1 / sqrt(r)` or Kaiming uniform) and `B` of shape `(r, d_out)` initialized to `0` (`ΔW = 0` at step 0), scaled by `alpha / r`:
       `W' = W_0 + (alpha / r) * (A @ B)`.
     * Trainable parameters per adapted matrix: `P_LoRA = r * (d_in + d_out)` vs `d_in * d_out` full parameters.
     * **Worked examples from sources:**
       - Single `4,096 x 4,096` matrix (`16,777,216` / `16.8M` params) with `r = 8`: `4,096 * 8 * 2 = 65,536` trainable params (`0.39%` of full matrix). Across `100` customer adapters (`AIE` Ch. 7): storing `100` merged matrices requires `16.8M * 100 = 1.68B` params, whereas storing `1` base matrix + `100` `(A, B)` adapter pairs requires `16.8M + 65,536 * 100 = 23.3M` params (**`72.1x` storage reduction**).
       - `GPT-3 175B` (`96` layers, `d_model = 12,288`, `AIE` Ch. 7 Table 7-5): Applying `r = 2` to all `4` attention matrices (`W_q, W_k, W_v, W_o`) yields `(12,288 * 2 * 2) * 4 = 196,608` params/layer, or **`18,874,368` (`18.87M`, `0.01%`)** trainable params across `96` layers (`37.7 MB` in 16-bit vs `350 GB` base weights), achieving `73.7%` on WikiSQL and `91.7%` on MultiNLI (outperforming `r = 8` on a single matrix at `70.4%`/`70.0%`). At smaller rank, LoRA matched full fine-tuning with `~4.7M` (`0.0027%`) params.
       - `Llama 2 13B` (`AIE` Ch. 7 Table 7-6): `26 GB` base weights (16-bit) vs `3.28M` LoRA params (`6.55 MB` adapter in 16-bit).
       - `Llama 3 8B` (`LEH` Ch. 5): Targeting all `7` linear modules (`q_proj, k_proj, v_proj, o_proj, gate_proj, up_proj, down_proj`) with `r = 16` yields **`41,943,040` (`~42M`)** trainable params out of `8.03B` (**`0.5196%`**); with `r = 32, lora_alpha = 32`, `83,886,080` (`~84M`) params; in `KFG` Ch. 4 (`r = 32, lora_alpha = 64` including `lm_head`), `88,121,344` trainable params vs `4,628,721,664` quantized base params (`1.90%`, `~98%` parameter reduction).
     * **Target modules & DoRA:** Applying LoRA to all linear layers (attention + MLP `gate_proj, up_proj, down_proj`) outperforms attention-only LoRA (`Databricks` / `LEH` Ch. 5). **DoRA (Weight-Decomposed Low-Rank Adaptation)** decomposes weights into magnitude vector `m` and directional matrix `V = W_0 + (alpha/r)BA`, updating magnitude and low-rank direction separately; **ReLoRA** and **GaLore** (low-rank gradient projection up to `1B–7B`); **X-LoRA** (MoE adapter routing, `GAK` Ch. 6); **LongLoRA** (`AIE` Ch. 7).

4. **QLoRA Internals: 4-Bit NormalFloat (`NF4`), Double Quantization, and Paged Optimizers (`Dettmers et al., 2023`; `AIE` Ch. 7, `LEH` Ch. 5, `KFG` Ch. 4):**
   - **Three QLoRA innovations:**
     1. **4-bit NormalFloat (`NF4`):** Information-theoretically optimal 4-bit data type (`16` quantile bins over `[-1, 1]`) for zero-mean normal weight distributions `N(0, sigma^2)`. Weights are normalized by their block-wise absolute maximum (`absmax`) into `[-1, 1]` using block size `B_1 = 64`. During forward and backward passes, `NF4` base weights are dequantized on the fly into `BF16` (`bnb_4bit_compute_dtype=torch.bfloat16`) to compute matrix products with `BF16` LoRA adapters.
     2. **Double Quantization (`bnb_4bit_use_double_quant=True`):** Standard block-wise `NF4` stores one `FP32` (`32`-bit) quantization scale per `64` weights, adding `32 / 64 = 0.5 bits/param` overhead. Double Quantization quantizes those first-level scales into `FP8` (`8`-bit) in blocks of `B_2 = 256` with a second-level `FP32` scale, reducing scale overhead from `0.5 bits/param` to `8 / 64 + 32 / (64 * 256) = 0.125 + 0.001953125 = 0.127 bits/param`—saving **`0.373 bits/param`** (`~3.0 GB` on a `65B` model, or `~0.35 GB` on a `7B–8B` model) and bringing effective storage to **`4.127 bits/param`**.
     3. **Paged Optimizers (`paged_adamw_8bit` / `paged_adamw_32bit`):** Uses NVIDIA CUDA Unified Memory to automatically page optimizer states between GPU HBM and host CPU DRAM during transient activation memory spikes (e.g., long sequences), preventing OOM crashes.
   - **Concrete memory and speed benchmarks (`LEH` Ch. 5 & `AIE` Ch. 7):**
     * On a `7B` model (`LEH` Ch. 5): LoRA requires **`14.0 GB`** at initialization and **`15.6 GB`** peak during fine-tuning (`14–18 GB` typical range), whereas QLoRA requires **`9.1 GB`** at initialization (**`35%` reduction**) and **`9.3 GB`** peak during fine-tuning (**`40%` reduction**, and up to `75%` vs higher-precision baselines), at the cost of **`~30%` slower training throughput** due to `NF4 -> BF16` dequantization overhead.
     * On a `65B` model (`AIE` Ch. 7 Table 7-7): QLoRA fine-tunes `Guanaco 65B` (`41 GB` footprint) on a **single `48 GB` GPU**, achieving `1022` Elo vs `ChatGPT`'s `966` Elo (`Guanaco 33B` = `21 GB` / `992` Elo; `Guanaco 13B` = `10 GB` / `916` Elo; `Guanaco 7B` = `6 GB` / `879` Elo; `GPT-4` = `1348` Elo).
     * **Unsloth + Liger Kernel (`LEH` Ch. 5, `GAK` Ch. 6):** Custom Triton kernels (`Unsloth`, `Liger Kernel`, `FlashAttention`) deliver **`2x–5x` faster training** and **up to `80%` less memory** (`50` minutes on 1 `A100` for `3` epochs of `TwinLlama-3.1-8B` on `13,335` samples with `packing=True`, `per_device_train_batch_size=2`, `gradient_accumulation_steps=8`, effective batch size `16`, `lr=3e-4`, `adamw_8bit`).

5. **Preference Alignment: RLHF (`PPO`), `DPO`, `GRPO`, `ORPO`, and `KTO` (`LEH` Ch. 6, `AIE` Ch. 2, `GAK` Ch. 6, `HSO` Ch. 10):**
   - **Why SFT is not enough:** SFT clones demonstration behavior (`argmax` cross-entropy on tokens) but cannot penalize plausible-sounding bad habits, stylistic drift, or safety boundary violations, and labeler-model knowledge mismatch can teach hallucinations (`Leo Gao` / `John Schulman`, `AIE` Ch. 2).
   - **Bradley-Terry Reward Modeling (`AIE` Ch. 2, `LEH` Ch. 6):**
     * Given preference triple `(x, y_w, y_l)` (prompt, chosen/winning response, rejected/losing response), the reward model `r_theta(x, y)` (decoder backbone + scalar linear head) minimizes:
       `L_RM(theta) = -E[ log sigma( r_theta(x, y_w) - r_theta(x, y_l) ) ]`.
     * Human comparison economics (`AIE` Ch. 2): Comparing two responses takes `3–5` minutes (`LMSYS`) and costs `$3.50` per comparison vs `$25.00` to write a demonstration response from scratch (`Llama 2`), with `~73%` inter-labeler agreement (`InstructGPT`). Ranking `K` responses produces `K*(K-1)/2` pairs (`3` responses `A > B > C` -> `3` pairs).
   - **RLHF with PPO (`Schulman et al., 2017`; `Ouyang et al., 2022`; `LEH` Ch. 6, `HSO` Ch. 10):**
     * Maximizes expected reward with a reverse-KL penalty against the frozen SFT reference policy `pi_ref`:
       `R_total(x, y) = r_phi(x, y) - beta * KL( pi_theta(y|x) || pi_ref(y|x) )`.
     * **Infrastructure & memory footprint (4 models in VRAM):**
       1. **Actor (`pi_theta`):** Trainable policy (weights + gradients + Adam states).
       2. **Critic / Value network (`V_psi`):** Trainable value model estimating token returns (weights + gradients + Adam states).
       3. **Reference policy (`pi_ref`):** Frozen SFT model (inference weights only).
       4. **Reward model (`r_phi`):** Frozen reward model (inference weights only).
     * Even for a `7B–8B` model, hosting `2` full trainable models + `2` frozen inference models consumes `> 160–240 GB` of VRAM across multiple GPUs. Furthermore, **`OpenRLHF` reports that `80%` of RLHF step time is spent in autoregressive sample generation (`rollouts`)** on `vLLM` or `SGLang` serving replicas (`HSO` Ch. 10), requiring periodic weight broadcast from training ranks to inference engines and batch-invariant deterministic decoding.
   - **Direct Preference Optimization (`DPO`, `Rafailov et al., 2023`; `LEH` Ch. 6):**
     * Analytically solves the KL-constrained reward maximization objective to express implicit reward directly through the policy and reference log-probabilities:
       `r_hat(x, y) = beta * log( pi_theta(y|x) / pi_ref(y|x) )`.
     * Substitutes `r_hat` into the Bradley-Terry loss:
       `L_DPO(pi_theta; pi_ref) = -E[ log sigma( beta * log(pi_theta(y_w|x)/pi_ref(y_w|x)) - beta * log(pi_theta(y_l|x)/pi_ref(y_l|x)) ) ]`.
     * **Key DPO parameters & metrics (`LEH` Ch. 6):**
       - `beta` (typically `0.1` to `0.5`; `0.1` default, `0.5` in `TwinLlama-3.1-8B-DPO` to prevent formal/verbose drift); learning rate `10x–100x` smaller than SFT (`2e-6` in DPO vs `3e-4` in SFT); `1` epoch (vs `3` in SFT).
       - **Reference-free PEFT adapter trick (`ref_model=None`):** When using LoRA/QLoRA, the frozen base model *with adapters disabled* serves as `pi_ref`, eliminating the second copy of model weights in VRAM!
       - **Tracked metrics:** `rewards/chosen`, `rewards/rejected`, `rewards/margins = rewards/chosen - rewards/rejected` (should increase and plateau), and `rewards/accuracies` (fraction of pairs where `rewards/chosen > rewards/rejected`).
   - **Group Relative Policy Optimization (`GRPO`, `DeepSeek`, `GAK` Ch. 6), `ORPO`, and `KTO`:**
     * **GRPO** eliminates the trainable **Critic/Value network (`V_psi`)** of PPO—cutting trainable model memory in half—by sampling a group of `G` outputs `(y_1, ..., y_G)` per prompt from the old policy and computing the baseline advantage via group z-score normalization:
       `A_i = (r_i - mean(r_1..r_G)) / (std(r_1..r_G) + eps)`, regularized by a direct KL penalty against `pi_ref`.
     * **ORPO (Odds Ratio Preference Optimization)** combines SFT cross-entropy loss and log-odds ratio preference penalty in a single stage without `pi_ref`. **KTO (Kahneman-Tversky Optimization)** aligns from binary thumbs-up/thumbs-down feedback without requiring paired `(chosen, rejected)` triples.

6. **Model Merging, Multi-LoRA Serving, and Kubernetes Training Operations (`AIE` Ch. 7, `GAK` Ch. 6, `HSO` Ch. 10):**
   - **Model Merging (`AIE` Ch. 7):**
     * **Summing:** Linear combination / Task Arithmetic (`delta_t = W_ft - W_base`) and **SLERP** (Spherical Linear Interpolation along the unit hypersphere geodesic with factor `t in [0, 1]`).
     * **Pruning before merging:** **TIES-Merging** (*TrIm, Elect Sign, and merge* — keeping top `20%` of task-vector parameters preserves `~100%` of single-task accuracy while eliminating sign interference) and **DARE** (*Drop And REscale* — randomly dropping delta parameters with probability `p` and rescaling by `1 / (1 - p)`).
     * **Layer stacking (Frankenmerging / Depthwise Upscaling / Sparse Upcycling):** `SOLAR 10.7B` created from two `32`-layer `7B` models by summing `16` layers (`32 * 2 - 16 = 48` layers); `Goliath-120B` from two `Llama 2-70B` models (`72` of `80` layers each); Sparse Upcycling dense checkpoints into MoE models.
   - **Multi-LoRA Serving & Kubernetes (`AIE` Ch. 7, `GAK` Ch. 6, `HSO` Ch. 10):**
     * Merge-and-unload (`merge_and_unload()`, zero inference latency overhead, best for high-traffic single models) vs **Multi-LoRA serving** (`vLLM`, `LoRAX`, `TGI`, `NVIDIA NIM` using **Punica** segmented gather-scatter GEMM kernels to batch requests across `100+` co-located adapters on `1` base model).
     * **Kubeflow Trainer (`GAK` Ch. 6):** Platform admins define `ClusterTrainingRuntime` (`trainer.kubeflow.org/v1alpha1`) and data scientists submit `TrainJob` via `TrainerClient` (`CustomTrainer` / `BuiltinTrainer`), which reconciles into a gang-scheduled Kubernetes `JobSet`.
