## Key topics, numbers, and formulas extracted

1. **VRAM Sizing Across Full SFT, LoRA, QLoRA, DPO, PPO, and GRPO:**
   - **Full SFT (Mixed-Precision AdamW):** Static memory is `16 * Psi` bytes (`2B` BF16 weights + `2B` BF16 gradients + `4B` FP32 master weights + `4B` FP32 momentum + `4B` FP32 variance; on-disk checkpoint is `14 * Psi` bytes). For `7B`, static = `112 GB`; for `8B`, static = `128 GB`; for `13B`, static = `208 GB`; for `70B`, static = `1,120 GB` (`> 1.2 TB` with activations). Pure BF16 Adam without FP32 master weights takes `8 * Psi` bytes (`56 GB` static for `7B`, `64–72 GB` with activations).
   - **LoRA (16-bit base weights + trainable rank-`r` adapters):** Base weights are frozen in BF16/FP16 (`2 * Psi_base` bytes) with zero base gradients and zero base optimizer states. Trainable parameters are `Psi_lora = L * M_targets * 2 * d_model * r` (for symmetric `d x d` projections, or exact sum of `(d_in + d_out) * r` across target modules `q_proj, k_proj, v_proj, o_proj, gate_proj, up_proj, down_proj`).
     - GPT-3 `175B` (`L=96, d=12288, r=2, 4` attn matrices): `(12,288 * 2 * 2) * 4 = 196,608` params/layer -> `18,874,368` (`18.87M`, `0.01%` of `175B`), taking `37.7 MB` in 16-bit vs `350 GB` base weights (`AIE` Ch. 7 Table 7-6).
     - Llama-2 `13B` (`r=2, q & k`): `3.28M` trainable params = `6.55 MB` adapter vs `26 GB` base weights (`AIE` Ch. 7 Table 7-6).
     - Llama-3 `8B` (`r=16`, all linear modules): `42M` trainable params (`0.5196%` of `8B`, `LEH` Ch. 5). With `r=32, alpha=64` across `8` modules in `K8GS` Ch. 4: `88,121,344` trainable params (`~1.90%` / `~2%` of `4,628,721,664` 4-bit quantized tensor elements, `98%` reduction).
     - `7B` LoRA total VRAM: `14–18 GB` (`15.6 GB` benchmarked peak in `LEH` Ch. 5; `14 GB` INT8-base LoRA in `V22` Ch. 3: `7 GB` weights + `0.8 GB` grads + `1.6 GB` opt + `2 GB` act + buffer = `14 GB`).
   - **QLoRA (4-bit NF4 base weights + double quantization + paged 8-bit AdamW):**
     - Base weights in 4-bit NormalFloat (`NF4`, `0.5 B/param`) + double quantization overhead (`~0.04–0.05 B/param` -> `~0.55 B/param` effective).
     - On `7B` (`LEH` Ch. 5): initialization VRAM drops `35%` from `14.0 GB` (LoRA) to `9.1 GB` (QLoRA); fine-tuning peak VRAM drops `40%` from `15.6 GB` (LoRA) to `9.3 GB` (QLoRA) (and up to `75%` vs unoptimized baselines), at the cost of `~30%` slower training throughput due to on-the-fly `NF4 -> BF16` dequantization in forward and backward passes.
     - Guanaco QLoRA footprints (`AIE` Ch. 7 Table 7-7): `7B` = `6 GB`, `13B` = `10 GB`, `33B` = `21 GB`, `65B` = `41 GB` (fits on a single `48 GB` L40S/A6000 GPU).
   - **Alignment Methods (DPO vs GRPO vs PPO RLHF):**
     - **Full-weight DPO:** Requires `1x` trainable policy (`16 * Psi` bytes) + `1x` frozen reference policy (`2 * Psi` bytes in BF16) = `18 * Psi` bytes static (`126 GB` for `7B`, `144 GB` for `8B`), plus forward/backward activations for both `chosen` and `rejected` sequences (`2x` sequence pass per pair).
     - **LoRA / QLoRA DPO (`ref_model=None`):** Because the base model weights are frozen, disabling the adapter yields the exact reference policy logits without loading a second model copy (`LEH` Ch. 6). Static memory stays at `1x` LoRA/QLoRA (`~15.6–18 GB` for `7B/8B` LoRA, `~9.3–11 GB` for `7B/8B` QLoRA)!
     - **GRPO (Group Relative Policy Optimization, DeepSeek / TRL `GRPOTrainer`):** Eliminates the separate critic/value network of PPO (`16 * Psi` saved!) by sampling a group of `G` completions (typically `G = 4..16`) per prompt and normalizing rewards within the group. Requires Policy (`16 * Psi` full or `1x` LoRA) + Reference (`2 * Psi` or `0` with PEFT) + reward function/model + KV-cache/activation memory for `G` rollouts.
     - **PPO (4-Model RLHF Topology):** Simultaneously holds Actor/Policy (`16 * Psi` full), Critic/Value model (`16 * Psi` full), Frozen Reference Policy (`2 * Psi`), and Frozen Reward Model (`2 * Psi`) = **`36 * Psi` bytes static** (`252 GB` for `7B`, `288 GB` for `8B`, `2,520 GB` for `70B`) before rollout KV caches and activations!

2. **GPU Selection Matrix (`L4`, `L40S`, `A100`, `H100 PCIe`, `H100 SXM5`, `H200 SXM`, `B200`) and PCIe vs NVLink Crossover:**
   - Exact datasheet specs, TDP, interconnect bandwidth (`PCIe Gen4 x16` `32 GB/s`, `PCIe Gen5 x16` `64 GB/s`, `NVLink 3` `600 GB/s`, `NVLink 4` `900 GB/s`, `NVLink 5` `1,800 GB/s`), unit prices, and `$/BF16 TFLOP` from `V04` Ch. 2, 4, 5, 6 and `V21` Ch. 2.
   - **The PCIe vs SXM Crossover:**
     - When a fine-tuning job fits on **1 GPU** (e.g., `7B/8B` QLoRA at `9.3 GB`, `7B/8B` LoRA at `15.6 GB`, or `65B/70B` QLoRA at `41–44 GB` on a `48 GB` L40S), inter-GPU collective bandwidth is `0 GB/s`. A `$8,000` `L40S` (`48 GB`, `362` BF16 TFLOPS, `$22/TFLOP`) or `$24 GB` `L4` (`g6.2xlarge` Spot) delivers the lowest cost per run.
     - Once a job requires **multi-GPU FSDP/ZeRO-3 or Tensor Parallelism** (e.g., `70B` Full SFT at `1,120 GB` static across `4–8` nodes, or `70B` LoRA/DPO across `4–8` GPUs), FSDP executes `AllGather` before every layer in forward and backward plus `ReduceScatter` on gradients (`3 * Psi` bytes moved per step). On PCIe Gen5 (`64 GB/s` vs `900 GB/s` NVLink 4 — a `14.1x` bandwidth gap), communication stalls `90%` of step time and makes `70B` fine-tuning `5x` slower (`V04` Ch. 4), wiping out the `25%–30%` PCIe hardware discount (`$215K` vs `$285K` per 8-GPU node).

3. **Token Throughput, Time-to-Train, and Cost-per-Run Economics:**
   - **Token FLOPs & Duration Formula:**
     - `Total_Tokens = N_samples * Seq_Len * Epochs` (or packed effective tokens).
     - For Full SFT: `FLOPs_per_token = 6 * Psi` (standard) or `8 * Psi` (with full activation checkpointing).
     - For LoRA / QLoRA: Frozen base weights still execute the forward (`2 * Psi`) and input-gradient backward (`2 * Psi`) matmuls, while weight-gradient matmuls (`2 * Psi`) are skipped for frozen weights and computed only for `Psi_lora` (`~4 * Psi` model FLOPs/token, or `~6 * Psi` with activation checkpointing, plus `~30%` dequantization time penalty for QLoRA).
     - `Step_or_Run_Time_sec = Total_Tokens / (N_GPUs * Throughput_tok_per_sec_per_gpu)`.
     - `Run_Cost_USD = N_GPUs * (Run_Time_sec / 3600) * Hourly_Rate_per_GPU`.
