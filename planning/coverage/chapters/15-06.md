| **1. Triton C++ Core Architecture, Model Repository Layout & `config.pbtxt`** | **Why Triton:** Replaces GIL-bound single-model Python wrappers (`FastAPI`/`Flask`) with a multi-framework C++ core (`TensorRT`, `TensorRT-LLM`, `vLLM`, `ONNX Runtime`, `PyTorch`/`LibTorch`, `OpenVINO`, `Python`, custom C++). **Ports:** `:8000` (KServe v2 HTTP/REST `/v2/...`), `:8001` (KServe v2 gRPC Protobuf), `:8002` (Prometheus `/metrics`), plus in-process **C API**. **Repository layout:** `/var/model_repository/<model_name>/config.pbtxt` + numeric version directories (`1/model.plan`, `2/model.plan`, `1/model.onnx`). **Version policies:** `latest: { count: 1 }`, `all: {}`, `specific: { versions: [ 1, 2 ] }`. **`config.pbtxt` & TensorRT profile rules:** When `max_batch_size > 0` (e.g., `64`), Triton prepends implicit batch dimension `0` to `input`/`output` `dims` (e.g., `[3, 224, 224]` -> `[B, 3, 224, 224]`); when `max_batch_size: 0`, full shape `[1, 3, 224, 224]` is declared explicitly. Triton's `max_batch_size` must be `<= TensorRT` optimization profile `max` (`min=1, opt=16, max=64`). Requests with `batch > max_batch_size` (e.g., `128 > 64`) fail immediately at ingress with `HTTP 400 Bad Request ("inference request batch size exceeds maximum allowed")`. **Model Control Modes:** `--model-control-mode=none` (static startup load), `--model-control-mode=poll` (dangerous in production: polling every `5 s` during a `1.2 GB` NFS copy causes `Magic number mismatch` and `HTTP 503` readiness outage), and `--model-control-mode=explicit` (atomic `mv tmp_2 2` + `POST /v2/repository/models/<model>/load` and `/unload`). | `V12` Ch. 3, Lab 01, Lab 02; `hands-on-llm-serving-and-optimization` Ch. 3 |
| **2. Batch Schedulers: Dynamic, Sequence, and Decoupled Continuous Batching (`TensorRT-LLM` / `vLLM`)** | **Stateless Dynamic Batcher (`dynamic_batching`):** Groups independent requests up to `max_batch_size` across `preferred_batch_size` multiples of `8` or `16` (e.g., `[4, 8, 16]`, `[8, 16, 32]`, `[16, 32, 64]`), waiting up to `max_queue_delay_microseconds` (`5,000 us` = `5 ms`, budgeted at `10%–20%` of total SLA). **Lab 02 `dense_net` (`onnxruntime_onnx`) benchmarks (`C=1..64`):** (1) **Profile A (`dense_net_nobatch`, `max_batch_size: 0`):** `450.0` (or `520`) RPS peak at `C=64`, `p99 = 2.1 ms` at `C=1`, `p99 = 121.5 ms` at `C=64`, realized batch `1.0`. (2) **Profile B (`dense_net_conservative`, `max_batch_size: 16`, `preferred: [4, 8, 16]`, `delay: 5,000 us`):** `450.0 infer/sec` at `C=1` (`2,218 us` client avg, `3,100 us` / `3.1 ms` p99; server `1,950 us` = `150 us` overhead + `200 us` queue + `1,600 us` compute input), scaling to **`2,850 RPS`** at `C=64` (`5.48x` over no-batch) with **`8.9 ms` p99** and realized avg batch **`13.0`**. (3) **Profile C (`dense_net_aggressive`, `max_batch_size: 64`, `delay: 50,000 us`):** **`3,400 RPS`** at `C=64` (realized batch **`48.2`**, `p99 = 48.5 ms`), but at `C=1` `p99` jumps to **`51.2 ms`** because single requests wait the full `50 ms` timer. (4) **Misconfigured `500,000 us` (`500 ms`) delay at `C=2`:** Throughput collapses to **`~4 RPS`**, `p99 > 500,000 us` (`500 ms`), realized batch **`2.0`**. **Stateful Sequence Batcher (`sequence_batching`):** Routes streaming ASR/RNN/session chunks sharing a `correlation_id` (`START`, `READY`, `END` flags) to the same GPU model instance slot (`Direct` or `Oldest` strategy). **Decoupled Continuous Batching (`model_transaction_policy { decoupled: true }`):** Why request-level dynamic batching fails for LLMs (`10`-token request trapped behind `2,048`-token request with `B=32, tau=50 ms`, spiking `p99 ITL` to `420 ms`, `p99 TTFT` to `14.2 s`, and dropping SM occupancy to `18%`). Switching to iteration-level continuous batching (`TensorRT-LLM` `GptManager` / `Executor` API or `vLLM` backend) with chunked prefill drops `p99 ITL` from **`420 ms` to `19.1 ms`** (`3.8x` throughput increase) and cuts `70B` `TP=8` `ITL` from **`115 ms` to `18.4 ms`** (`KV Memory Per Token = 2 * L * H_kv * d_head * BytesPerElem = 327,680` bytes `~ 320 KB` in FP16 = `1.31 GB` per `4,096`-token session vs `0.65 GB` in FP8, increasing max sessions on `4x A100` from `64` at `52%` util to `210` at `91%` util). | `V12` Ch. 3, Ch. 5, Ch. 7, Lab 02; `ai-systems-performance-engineering` Ch. 16 |
| **3. Instance Groups, Multi-Model Concurrency & VRAM vs CUDA Stream Contention** | **`instance_group` mechanics:** Defines parallel execution instances per device (`KIND_GPU`, `KIND_CPU`, `KIND_MODEL`), each with its own weights/execution context and separate CUDA stream. **VRAM footprint formula:** `M_total = N_instances * M_instance + M_workspace_and_kv`. **Worked Failure Scenario (`transformer_enc` ONNX on `80 GB` A100, `V12` Ch. 3):** Each instance requires **`9.5 GB`** VRAM. Setting `count: 8` consumes **`8 * 9.5 GB = 76.0 GB`**, leaving only **`4.0 GB`** free (`nv_gpu_memory_used_bytes = 81,180,000,000` bytes). Workspace allocation fails (`Failed to allocate 1024MB workspace buffer`), `8` competing instances stall **`84 ms`** on the CUDA driver stream mutex (`cudaLaunchKernel`), and average compute latency quadruples from **`25 ms` to `110 ms` (`110,400 us`)** at **`180 RPS`**. **Fix:** Lowering to `count: 2` (`2 * 9.5 GB = 19.0 GB` VRAM, leaving **`61.0 GB`** free) and enabling `dynamic_batching` (`max_batch_size: 32`, `preferred_batch_size: [8, 16, 32]`, `max_queue_delay_microseconds: 5000`) boosts throughput by **`+340%` (`4.4x`, from `180 RPS` to `792 RPS`)** and cuts `p99` latency from **`110 ms` to `18.4 ms`**. | `V12` Ch. 3 |
| **4. Multi-Model Pipelines: Ensembles vs Business Logic Scripting (BLS)** | **Ensemble Models (`platform: "ensemble"`):** Declarative static DAG defined in `config.pbtxt` (`ensemble_scheduling { step [ ... ] }`), wiring `ModelA.out -> ModelB.in` (e.g., `Image Ingress -> Python Preprocess -> TensorRT ResNet -> Python Postprocess`). Zero-copy tensor handoff via C++ core memory/CUDA IPC, but **no conditional branching (`if/else`) or dynamic loops**. **Business Logic Scripting (BLS):** Imperative execution inside a Python backend model (`triton_python_backend_utils.InferenceRequest` / `exec_async`) or C++ backend calling other Triton models in-process. Supports conditional routing, dynamic loops (e.g., RAG retrieve -> rerank -> conditional LLM generation), and token streaming. **Zero-copy memory transfer:** Using **CUDA Shared Memory (`cudaIpcMemHandle`)** or `pb_utils.Tensor.from_dlpack()`, intermediate tensors stay in GPU HBM between DAG stages without `H2D`/`D2H` PCIe copies. **Ensemble starvation:** When `16` CPU threads spin at `90%+` and `queue_time_us` hits `50–200 ms`, enable `scheduler { default_queue_policy { allow_timeout_override: true } }`. | `V12` Ch. 3 |
| **5. Transport Protocols & Shared Memory: HTTP/REST vs gRPC vs C API vs System/CUDA SHM** | **Protocols:** KServe v2 HTTP/REST (`:8000`, JSON + binary tensor extension), KServe v2 gRPC (`:8001`, HTTP/2 + Protobuf), and in-process C API (`TRITONSERVER_ServerNew`). **gRPC message limit:** Default gRPC max message size is **`4 MB` (`4,194,304` bytes)**; sending a **`6.2 MB`** batch/prompt payload triggers `[INTERNAL] received message larger than max_receive_bytes limit`, fixed by setting `grpc.max_send_message_length` / `grpc.max_receive_message_length` or registering **Shared Memory**. **Host vs CUDA Shared Memory (`V12` Ch. 2 & Ch. 3):** Standard pageable `malloc()` requires a CPU double-copy into an OS page-locked staging buffer before PCIe DMA, limiting `PCIe Gen5 x16` (`64 GB/s` theoretical) transfer throughput to **`10–14 GB/s`** and adding **`5–15 ms`** per batch of `64` requests. **Pinned Host Memory (`cudaHostAlloc` / `cudaHostRegister` / POSIX System Shared Memory `/dev/shm` with `--shm-size=1g` or `2Gi–8Gi` `emptyDir { medium: Memory }`)** enables direct DMA at **`55–62 GB/s`** (`~4.5x–5x` faster). **CUDA Shared Memory (`cudaIpcGetMemHandle`)** passes a `64`-byte IPC handle when client and server share the same GPU node, reducing tensor payload copy time across the socket to near zero. | `V12` Ch. 2, Ch. 3, Lab 01 |
