## Checklist of Concepts, Numbers, and Patterns to Cover
1. **Why a Kubernetes Pod Cannot Span Multiple Nodes (`GAK Ch 3 & 7`, `ASP Ch 3`):**
   - A Kubernetes `Pod` is the atomic unit of node binding (`Pod.spec.nodeName` is a single string; all containers inside a Pod share one network namespace, IPC namespace, and local ` kubelet` lifecycle).
   - Consequently, if a job needs `64` GPUs across `8` `8`-GPU nodes (or `16` GPUs across `2` nodes, or `2` MIG `2g.45gb` slices when `2` nodes each have `1` slice), a single Pod requesting `nvidia.com/gpu: 64` stays permanently `Pending` (`Insufficient nvidia.com/gpu`).
   - Multi-node jobs must be decomposed into **multiple coordinated Pods** (`1` Pod per node, e.g., `8` Pods × `8` GPUs/Pod = `64` GPUs), which immediately introduces the **partial-allocation deadlock problem**.
2. **The Partial-Allocation Rendezvous Deadlock & Gang Scheduling (`GAK Ch 7`, `volume-06/04-distributed-orchestration-masterclass.md`):**
   - Microservices vs Batch/AI Training paradigm shift (`volume-06` Part 2.1 Table: `Lifecycle`, `Scheduling`, `Queueing`, `Preemption`, `Network`).
   - **PyTorch Rendezvous Barrier (`GAK Ch 7`):** Workers connect to a rendezvous backend (TCP store or `etcd`) to discover peers, assign ranks `0` to `world_size - 1`, synchronize at an atomic blocking barrier, and exchange P2P/NCCL connection details.
   - **7-of-8 Deadlock Scenario (`GAK Ch 7` & `volume-06`):** An `8`-Pod (`64`-GPU) job is submitted when only `56` GPUs (`7` nodes) are free (or two `8`-Pod jobs contend on a `12`-node cluster). Default `kube-scheduler` places `7` of `8` workers (`56` GPUs Running at `0%` compute waiting at the rendezvous barrier) while the `8th` Pod stays `Pending`. At `$10–$30/hour` per GPU node (`GAK Ch 7`), this burns hundreds of dollars per hour with zero training progress.
   - **Gang Scheduling (Coscheduling / All-or-Nothing):** Holds all Pods in a pending/queued state until `minAvailable` / `minMember` (`4` or `8`) can be placed atomically (`scheduleTimeoutSeconds: 300`). Also covers `KEP-4671` (native Kubernetes `Workload` API proposal) and `PodDisruptionBudget` (`minAvailable: 4` with `scheduling.x-k8s.io/pod-group: llm-training-group` in `GAK` Example 7-2).
3. **Bin Packing (`MostAllocated`) vs Descheduler Alignment (`GAK Ch 7`):**
   - `KubeSchedulerConfiguration` `binpack-scheduler` using `NodeResourcesFit` `MostAllocated` with `nvidia.com/gpu` `weight: 5`, `cpu` `weight: 1`, `memory` `weight: 1` (Example 7-1).
   - Descheduler strategies (`Table 7-1`: `HighNodeUtilization` must pair with `MostAllocated`; `LowNodeUtilization` must pair with `LeastAllocated`; `RemovePodsViolatingNodeAffinity`; `RemovePodsViolatingInterPodAntiAffinity`; never enable `HighNodeUtilization` and `LowNodeUtilization` simultaneously or an eviction loop occurs).
4. **Head-of-Line Blocking, Backfill Scheduling, Thundering Herd, and API Server OOM (`volume-06` Parts 1, 4, 5):**
   - **Head-of-Line Blocking & Backfill (`volume-06` §4.1):** A `1024`-GPU job sits at the head of the queue when `1000` GPUs are free (waiting for `24` more GPUs). Backfill scheduling allows smaller `8`-GPU jobs to jump the queue *only if* their declared `TimeLimit` (wall time) finishes before the `1024`-GPU job's calculated start time.
   - **Thundering Herd (`50,000` jobs in `2` seconds, `volume-06` §4.2 & §5.1):** Overwhelms `etcd`/`kube-apiserver` or locks `slurmctld` RPC queue (causing `SlurmdTimeout=120` / `MessageTimeout=30` node ping timeouts and `UNKNOWN` nodes). Fixed via Kubernetes API Priority and Fairness (`APF`) or Slurm Job Arrays (`sbatch --array=1-50000`, raising `MaxArraySize` from default `1001`, `MaxJobCount=500000`, `MinJobAge=300`) and `job_submit` C/Lua plugin (`NO_VAL` time limit check, routing `min_nodes > 16` to `super_train`).
   - **API Server / `etcd` OOM on Impossible Gang (`volume-06` §5.2):** Submitting a Volcano Job with `minAvailable: 1000` on a `500`-node cluster creates `1000` Pending Pods that churn `etcd` and watch caches until gated by Kueue admission control.
   - **Slurm & Hybrid Orchestration (`volume-06` Parts 1 & 3, `GAK Ch 7`):** `slurmctld`, `slurmd`, `slurmdbd`, `MUNGE`, `dgx-h100-[001-128]` (`CPUs=224 Sockets=2 CoresPerSocket=56 ThreadsPerCore=2 RealMemory=2000000 Gres=gpu:h100:8`, `COREs=0-27`, `28-55`, `56-83`, `84-111`), `srun --mpi=pmix -n 1024`, SchedMD **Slinky** / **Sunk** (Virtual Kubelet), Checkpoint Storms (`10,000` GPUs, burst buffers, `2 * base_model_size + checkpoint_overhead`: `100 GB` for Llama 3.1 8B LoRA, `500 GB+` for 70B full fine-tuning), and Ray (`6379`, `8265`, `10001`) / PyTorch `NetworkPolicy` security.
