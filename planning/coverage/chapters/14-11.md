## Key topics, numbers, and formulas extracted

1. **Why Checkpointing & Fault Tolerance Matter (Fleet Reliability & The Checkpoint Pause):**
   - **Pause overhead:** Pausing for `5` minutes every `1` hour (`60` minutes) wastes `5 / 60 = 8.33%` (`~8%`) of cluster GPU time (`V13 Ch. 9`).
   - **Scale of model state:** Llama-3-70B (`70B` parameters) has `140 GB` FP16/BF16 weights and `> 1.2 TB` total training memory (`1,120 GB` checkpoint payload at `16 bytes/param`, or `980 GB` at `14 bytes/param` when omitting `2 bytes/param` BF16 gradients; `V13 Ch. 1, Ch. 9`, `V21 Ch. 4`). GPT-3 (`175B`) requires `700 GB` for FP32 weights alone (`8.75x` an `80 GB` H100) and `1.46 * 10^18` FLOPs per step (`4,679 s` / `~78 min` on `1` A100 at `312 TFLOPS` vs `~37 s` on `128` A100s; `V13 Ch. 1`). A `7B` FP32 model requires `28 GB` weights + `28 GB` gradients + `56 GB` Adam states + `60–80 GB` activations + `5–10 GB` buffers = `180–190 GB` (`79,456 MiB / 79,559 MiB` used, `103 MiB` free -> `2.45 GiB` OOM; `V13 Ch. 1`).
   - **Fleet failure probability:** For `N` GPUs with daily per-GPU survival probability `p = 0.999` (`99.9%` daily reliability, `lambda_gpu = 0.001 / day`), the probability that all `N = 100,000` GPUs survive 24 hours without a single failure is `0.999^100,000 ≈ 3.7 * 10^-44`, with `~100` expected failures per day (`MTBF ≈ 14.4 minutes`; `DAI Ch. 11`). On `1,024` GPUs over `30` days (`V13 Ch. 9`) or `10,000` GPUs over `3` months (`90` days), hardware failure is a mathematical certainty (`~100%`).
2. **Checkpoint Anatomy & Deterministic Recovery (`V13 Ch. 9`, `V13 Lab 04`, `DAI Ch. 3 & Ch. 8`):**
   - **Five required state components:** (1) Model weights (`model_state_dict`), (2) Optimizer state (`optimizer_state_dict` — Adam FP32 first moment `m` and second moment `v`; omitting causes immediate loss spike upon resume), (3) Learning rate scheduler state (`scheduler_state_dict`), (4) DataLoader state (exact dataset/batch offset `step` / `epoch`), and (5) RNG state (`rng_state` across Python, NumPy, and CUDA; omitting causes silent trajectory divergence from the uninterrupted control run).
   - **Lab 04 control vs interrupted verification:** Run `5` epochs uninterrupted (`torchrun --nproc_per_node=4 train.py`); interrupt at epoch `3`, resume from `./checkpoints/epoch_3.pt`, and verify epochs `4` and `5` match the control loss bit-for-bit behind `dist.barrier()`.
   - **Megatron-LM `8.03B` `.distcp` checkpoint layout (`DAI Ch. 8`):** `8.03B * 2 bytes = 16.06 GB` BF16 weights + `8.03B * 8 bytes = 64.24 GB` FP32 Adam state = `80.30 GB` theoretical vs `108.0 GB` actual on disk (`4 x 27.0 GB` `.distcp` shards + `24 KB` `common.pt` + `4.0 KB` `metadata.json`).
3. **Naive Rank-0 Gather vs Parallel Sharded Checkpointing (`V13 Ch. 9`, `V13 Lab 03`, `DAI Ch. 4`):**
   - **70B model on 128 H100 GPUs (`16 bytes/param`):** Total payload `70B * 16 bytes = 1,120 GB` (`~1.09 TB`); per-GPU shard `1,120 GB / 128 = 8.75 GB`.
   - **Naive gather-to-rank-0 (`FULL_STATE_DICT`):** Network gather `1,120 GB / 25 GB/s = 44.8 s` (`~45 s`) + single-node storage write `1,120 GB / 5 GB/s = 224.0 s` = **`268.8 s` (`~269 s` / `4.5 minutes`)**, plus high risk of rank-0 CPU/GPU OOM (`V13 Lab 03`).
   - **Distributed parallel write (`SHARDED_STATE_DICT` / PyTorch DCP):** Ideal per-rank write at `5 GB/s` is `8.75 GB / 5 GB/s = 1.75 s`. Aggregate demand `128 * 5 GB/s = 640 GB/s` exceeds the `400 GB/s` Lustre filesystem ceiling, throttling each rank to `400 / 128 = 3.125 GB/s` (`~3.1 GB/s`) for a realistic write time of **`8.75 GB / 3.125 GB/s = 2.8 s`** (`~96x`—nearly two orders of magnitude—faster than `268.8 s`).
   - **64-GPU Llama-70B tiered NVMe staging (`V21 Ch. 4`):** At `14 bytes/param` (`2 B` BF16 weights + `4 B` FP32 master weights + `8 B` FP32 Adam `m, v`), total checkpoint is `980 GB` (`~15.3125 GB` / `~15 GB` per GPU on `64` GPUs, `~122.5 GB` / `~122 GB` per 8-GPU node). Writing `122 GB` to local PCIe Gen4 NVMe (`8 x 3.84 TB = 30.72 TB` at `7 GB/s` per drive, or `10–20 GB/s` node aggregate) takes `~6–12 s` (`~10 s`), vs `980 GB / 10 GB/s = ~98–100 s` directly to shared NAS.
4. **Young-Daly Optimal Checkpoint Interval & Cluster Goodput Math (`V13 Ch. 9`):**
   - **Young-Daly Formula:** `T_opt = sqrt(2 * M * T_c) - T_c`, where `M` is cluster MTBF (seconds) and `T_c` is checkpoint write time (seconds).
   - **Worked Example 1 (`1,024` GPUs, `V13 Ch. 9`):** `M = 8 hours = 28,800 s`, `T_c = 180 s` (`3 minutes`) -> `T_opt = sqrt(2 * 28,800 * 180) - 180 = sqrt(10,368,000) - 180 ≈ 3,220 - 180 = 3,040 s ≈ 50.7 minutes`.
   - **Worked Example 2 (`400B` model on `2,048` GPUs, `V13 Ch. 9`):** `M = 6 hours = 21,600 s`, `T_c = 240 s` (`4 minutes`) -> `T_opt = sqrt(2 * 21,600 * 240) - 240 = sqrt(10,368,000) - 240 ≈ 3,220 - 240 = 2,980 s ≈ 49.7 minutes` (round down to `30–40 minutes` in production for clustered failures).
   - **Goodput comparison (`M = 28,800 s`, `T_c = 180 s`, recovery overhead `R = 120 s`):** Checkpointing every `5` minutes (`300 s`) wastes `180 / (300 + 180) = 37.5%` on checkpoint writes; checkpointing every `4` hours (`14,400 s`) loses `7,200 s` (`2 hours`) of expected rework per crash; checkpointing at `T_opt = 3,040 s` maximizes net training goodput (`~88.5%` before restart overhead, or `~96%+` when async checkpointing reduces blocking pause `T_c` from `180 s` to `2 s` DtoH copy).
5. **Asynchronous Checkpointing, Dynamic Resharding (PyTorch DCP), and Elastic Training (`V13 Ch. 9`, `V21 Ch. 7`, `DAI Ch. 3, 4, 8, 11`):**
   - **Two-phase async save (`dcp.async_save`):** Phase 1 copies GPU VRAM state to pinned host DRAM over PCIe (`100 GB` in `< 2 s` or `< 1 s` per node; `V13 Ch. 9`); Phase 2 flushes host DRAM to Lustre/S3 in background threads while GPUs immediately resume the next forward pass. Cached save plans and background threads yield a `6x` checkpoint speedup (`DAI Ch. 11`).
   - **Dynamic resharding across topology changes:** Resuming a `64`-GPU checkpoint on `48` GPUs (`6` nodes after `2` nodes drain) with naive per-rank files fails with `RuntimeError: Number of shards in checkpoint (64) does not match world size (48)` (`V13 Ch. 9`). PyTorch DCP (`FileSystemReader` / `dcp.load`) stores global tensor metadata (`metadata.json` / `.metadata`) and dynamically reshards the `1,120 GB` payload from `64 x 17.50 GB` shards to `48 x 23.33 GB` shards at load time.
   - **Elastic training (`torchrun` / TorchElastic):** Fault-tolerant fixed-size (`--nnodes=4 --max_restarts=3`) vs elastic variable-size (`--nnodes=2:4 --nproc_per_node=8 --max_restarts=3 --rdzv_id=job_1411 --rdzv_backend=c10d --rdzv_endpoint=MASTER_HOST:29400`). When `WORLD_SIZE` shrinks from `64` to `48`, the global batch size drops by `48 / 64 = 0.75x` unless `gradient_accumulation_steps` is scaled proportionally (e.g., from `3` to `4` steps to keep global batch size constant at `192 * micro_batch`) or learning rate is adjusted via linear/sqrt scaling (`V21 Ch. 7`, `DAI Ch. 3`).
   - **Failure detection, watchdogs, and preemption signals:** Heartbeat detector (`1–5 s` interval, `3–5` missed heartbeats = `3–25 s` detection vs `30-minute` / `1,800 s` default NCCL watchdog timeout; `DAI Ch. 11`, `V13 Ch. 8`), Slurm `#SBATCH --signal=SIGUSR1@90` + `SIGTERM` graceful preemption (`DAI Ch. 8`), and ECC `Xid 48` / `Xid 63` / `Xid 79` / `Xid 13` node drain remediation (`V13 Ch. 12`, `V13 Lab 01`).
