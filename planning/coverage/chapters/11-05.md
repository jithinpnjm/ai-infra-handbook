## Checklist of Concepts, Numbers, and Patterns to Cover
1. **Why `STATUS: deployed` is not a GPU platform (`volume-10/chapter-10`):**
   - The 6-step installation pipeline (`Qualify -> Ownership -> Policy -> Render -> Reconcile -> Ready? -> Accept -> Operate`).
   - Six pre-deployment ownership decisions (`Driver ownership`, `Runtime ownership`, `Node scope`, `Image supply chain`, `Sharing policy`, `Operations`).
   - Concrete canary install failure: `helm install gpu-operator nvidia/gpu-operator --namespace gpu-operator --create-namespace --version 24.9.1 -f canary-values.yaml --wait --timeout 15m` prints `STATUS: deployed` (`REVISION: 1`) across a `6`-node canary pool, while `kubectl get clusterpolicy cluster-policy -o jsonpath='{.status.state}{"\n"}'` prints `notReady` because `nvidia-driver-daemonset-7q2kd` is in `CrashLoopBackOff` (`5` restarts) on `gpu-node-04` (`modprobe: ERROR: could not insert 'nvidia': Key was rejected by service`, `mount: /run/nvidia/driver/usr/src/nvidia-535.129.03: No such file or directory`, `Failed to install the kernel module through DKMS`) while the other `5` canary nodes succeed.
2. **The 7-Criterion Production Acceptance Contract (`volume-10/chapter-10`):**
   - 1. Expected GPUs detected & driver healthy; 2. Runtime path creates GPU container & initializes CUDA; 3. Device plugin advertises allocatable resource (`8 capacity / 8 allocatable` on `gpu-node-04`); 4. Hardware & policy labels/taints match design; 5. Scheduled workload receives expected device & passes functional test (`gpu-validate-node04` prints `GPU 0: NVIDIA H100 80GB HBM3 (UUID: GPU-3a91...)` and `CUDA_VALIDATED`); 6. DCGM telemetry scraped with matching device UUID (`DCGM_FI_DEV_GPU_UTIL{gpu="0",UUID="GPU-3a91...",node="gpu-node-04"} 97` on port `9400`); 7. Controlled drain, reboot, and return-to-service restores the node without manual repair.
   - Installation troubleshooting failure signatures:
     - `gpu-node-07` has `nvidia.com/gpu.present=true`, `gpu.count=8`, `gpu.deploy.device-plugin=true`, but `allocatable` is `<no value>`.
     - `gpu-validate-node07` fails at start (`Warning Failed 8s kubelet ... open /run/nvidia/driver/dev/nvidia0: no such file or directory`) vs in-application CUDA init failure (`CUDA error: no CUDA-capable device is detected`).
     - `nvidia-dcgm-exporter-9fvqk` is `1/1 Running` on `gpu-node-07`, yet `curl -s gpu-node-07:9400/metrics | grep -c DCGM_FI_DEV_GPU_UTIL` returns `0`.
3. **Compatibility-Set Upgrades & Canary Batch Sizing (`volume-10/chapter-11`):**
   - Six change surfaces (`Kernel or node image`, `Driver`, `Container runtime or toolkit`, `Operator or chart`, `Kubernetes or kubelet`, `Firmware`).
   - Worked `120`-node fleet canary & progressive batch sizing math (`4` hardware batches × `30` nodes each, `8` GPUs/node = `960` total GPUs):
     - Canary: `2` nodes per hardware batch = `8` nodes (`8 / 120 = 6.67%`, `~7%` of fleet; `64` GPUs).
     - Batch 1: `10%` of fleet = `12` nodes (`96` GPUs; `90%` of fleet remains serving).
     - Progressive doubling: `12 -> 24 -> 76` nodes (`8` canary + `12` batch 1 + `24` batch 2/3 + `76` final = `120` nodes).
     - If a hardware-batch-specific regression is caught at the `24`-node batch: `24 * 8 = 192` GPUs affected out of `120 * 8 = 960` GPUs (`20.0%` of fleet GPU capacity) rather than `100%`.
   - Post-upgrade per-node asymmetry: `nvidia-device-plugin-daemonset` reports `8/8 Ready` on an `8`-node batch, yet `gpu-node-11` reports `allocatable: 0` while sibling `gpu-node-12` reports `allocatable: 8`.
4. **Controlled Upgrade Execution & Why `helm rollback` Alone Can Be Unsafe (`Lab 04`):**
   - Archiving baseline (`helm-history-before.txt`, `values-before.yaml`, `manifest-before.yaml`, `canary-before.yaml`).
   - Cordon and drain with `--ignore-daemonsets --delete-emptydir-data --grace-period=120 --timeout=20m` (evicting `ml-training/resnet-worker-3` while keeping `nvidia-driver-ds-7z4kd` on `gpu-node-07`).
   - Upgrading from `gpu-operator-24.6.0` (`REVISION 1`) to `gpu-operator-24.9.1` (`REVISION 2`, `--timeout 20m`), validating `GPU_UPGRADE_VALIDATED` and `journalctl -u kubelet --since '30 minutes ago'`.
   - The `Recheck` rollback gate: running `helm rollback gpu-operator 1 --namespace gpu-operator --wait --timeout 20m` prints `Rollback was a success!`, yet `kubectl get node "$CANARY_NODE" -o jsonpath='{.status.allocatable.nvidia\.com/gpu}{"\n"}'` still prints `0` because `helm rollback` only reverts Kubernetes control-plane objects, not the host kernel module or OS image state loaded by `24.9.1`.
