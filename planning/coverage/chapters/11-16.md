## Checklist of Concepts, Numbers, and Patterns to Cover
1. **Why Gang Scheduling Without Topology Awareness Fails (`GAK Ch 7`, `volume-02/labs/lab-04`, `volume-24/chapter-10`):**
   - A gang scheduler without topology awareness ensures all `8` Pods start simultaneously, but may scatter those `8` GPUs across `8` separate Ethernet/InfiniBand nodes (`10–100 Gbps` or `200–400 Gbps`) instead of co-locating them on `1` `8`-GPU NVSwitch node (`900 GB/s` per GPU).
   - How Parallelism Strategies Dictate Interconnect Sensitivity (`GAK Ch 7` "Communication Patterns in Distributed Training"):
     1. **Tensor Parallelism (`TP`):** Splits weight matrices within every layer; executes synchronous `AllGather` / `ReduceScatter` of activations on every forward and backward pass -> requires intra-node **NVLink / NVSwitch** (`600–900 GB/s` to `1.8 TB/s`) or `1` NVL72 rack (`130 TB/s`).
     2. **Fully Sharded Data Parallelism (`FSDP` / `ZeRO-3`):** Shards parameters, gradients, and optimizer states; gathers parameter shards "just-in-time" on every layer (`AllGather`) and reduces gradients (`ReduceScatter`) -> highly sensitive to both bandwidth and latency (`NVSwitch` intra-node + `InfiniBand` / `RoCEv2` GPUDirect RDMA inter-node).
     3. **Data Parallelism (`DDP`):** Synchronizes gradients (`AllReduce`) once per step (`900 GB` gradients in `50ms` ring `AllReduce` vs `100ms` compute = `150ms < 300ms` step target in `volume-24/chapter-10`).
     4. **Pipeline Parallelism (`PP`):** Point-to-point `Send/Recv` between adjacent stages; benefits from co-locating adjacent stages on the same rack/leaf switch to minimize hops (`log2(12) = 3.6` hops on `12` `8`-GPU nodes vs `25` `4`-GPU nodes).
2. **How KAI Scheduler Combines Gang Scheduling and Multi-Level Topology Placement (`GAK Ch 7`):**
   - Automatic gang synthesis (`pod-grouper` creating `PodGroup` with `minMember` and `topologyConstraint` for `PyTorchJob`, `TrainJob` / `JobSet`, `LeaderWorkerSet`, and `MPIJob`).
   - Hierarchical **`Topology`** tree in KAI Scheduler (`Level 1: Spine / Cluster -> Level 2: Rack / InfiniBand Leaf Switch -> Level 3: Node / NVSwitch Domain -> Level 4: NUMA / NVLink Peer Group`):
     - **`Required` vs `Preferred` Topology Constraints:** A job can *require* all members of a sub-group (such as a `TP=4` or `TP=8` shard group in `LeaderWorkerSet` or `JobSet`) to land inside a single NVSwitch node or NVL72 rack, while *preferring* that all data-parallel replicas land under the same InfiniBand leaf switch.
3. **Host-Level Topology Verification (`volume-02/labs/lab-04`):**
   - The `4`-GPU H100 (`81,559 MiB`) dual-socket server layout:
     - Group A (`NUMA 0`, CPUs `0–15`, `257,698 MB` RAM, NUMA distance `10` local vs `21` remote): `GPU0` (`0000:1b:00.0`) <--> `GPU1` (`0000:3d:00.0`) via **`NV4`** + `NIC0` (`0000:18:00.0`, `ConnectX-6 Dx` `[15b3:101d]`) via **`PIX`**.
     - Group B (`NUMA 1`, CPUs `16–31`, `258,043 MB` RAM): `GPU2` (`0000:9a:00.0`) <--> `GPU3` (`0000:c3:00.0`) via **`NV4`** + `NIC1` (`0000:9d:00.0`) via **`PIX`**.
     - Why naive `2`-GPU + `1`-NIC placement picking `{GPU1, GPU2, NIC1}` crosses `SYS` (`NUMA 0 <-> NUMA 1`) and breaks both GPU peer NVLink and GPU-to-NIC `PIX` locality.
   - Detecting silent NVLink degradation on a "preferred" pair: `nvidia-smi nvlink --status` showing `Link 0: 26.562 GB/s`, `Link 1: 26.562 GB/s`, **`Link 2: 0.000 GB/s`**, `Link 3: 26.562 GB/s` (`25%` bandwidth loss while `nvidia-smi topo -m` still prints `NV4`).
