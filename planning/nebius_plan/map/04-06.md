# 4.6 Ansible playbooks: tasks, modules, idempotency and check mode
Words: ~11,100 | Read time: 74 min | File: docs/part-04-automation/06-ansible-playbooks-tasks-modules-idempotency-and-check-mode.md
One-line purpose: Teaches how a playbook is built (plays, phases, tasks), why idempotency matters, how to make `command`/`shell` safe, how check mode and diff preview a change, and how to roll it out in batches with failure limits.
Beginner friendly: partly. Needs 04-03 (ad-hoc and first playbook) and 04-04 (YAML quoting) first. Idempotency and batching ideas are easy to follow; the module tables are reference material.
Nebius rounds served: R2 (primary: playbook design, idempotency, rolling change, exit codes in CI), R4 (safe change control, canary and failure policy), R1 (command/shell and Linux probes such as `nvidia-smi`, `dpkg` hold)

Hands-on to do:
- `python3 code/part04/ansible_playbook_execution_lab.py` from the handbook root (folder exists) to see phase order and serial batches.
- Write a small `site.yml` and run `ansible-playbook site.yml --syntax-check`, then `--check --diff`, then apply, then rerun and confirm `changed=0` in the recap.
- Fall into the idempotency trap on purpose: add `{{ ansible_date_time.iso8601 }}` to a template and watch every run report `changed`. Then remove it.
- Run a canary: `ansible-playbook site.yml --limit gpu01 --check --diff` and then `--list-tasks --list-hosts --step` to see each task before it runs.
- Make one host fail on purpose, compare `any_errors_fatal` and `max_fail_percentage`, and record each exit code with `echo $?`. Also make one host unreachable (wrong port) and record the code 3 result.
- Run `ansible-lint site.yml` and fix the `fqcn`, `no-changed-when` and `risky-file-permissions` findings.

6. How do you use tags, and what are the risks of relying on them?
