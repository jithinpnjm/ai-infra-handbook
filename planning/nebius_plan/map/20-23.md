# 20.23 Kubernetes failure drills for GPU platforms
Words: ~9,180 (about 8% is code and YAML) | Read time: 61 | File: /Users/jithinpjoseph/Documents/GitHub/ai-infra-handbook/docs/part-20-nebius-sre-interview/23-kubernetes-failure-drills-for-gpu-platforms.md
One-line purpose: Gives a fixed kubectl debugging order and twelve spoken drills (Pending GPU pods, image pulls, probe kills, NotReady nodes, eviction, PDB-blocked drains, DNS, Services without endpoints, HPA, device plugins, etcd, webhooks) so you can say the owner, the evidence and the fix out loud.
Beginner friendly: no on first read. It assumes you can read pod objects and run kubectl, and it names the Kubernetes object owners (scheduler, kubelet, EndpointSlice controller, HPA, node controller) without teaching them. Read first: Part 5 chapter 03 (Kubernetes architecture: what talks to what), chapter 07 (pods, Deployments, DaemonSets and Jobs), chapter 09 (kubelet, probes, QoS and eviction), chapter 10 (Services, endpoints and kube-proxy), chapter 18 (scheduling, taints and tolerations) and chapter 25 (troubleshooting from the node). For the GPU pieces read Part 11 chapter 02 (device plugin) and chapter 29 (quotas and health on GPU clusters), as cited.
Nebius rounds served: R2 (primary: the Kubernetes troubleshooting round and the 30-minute incident stage that may use Kubernetes), R1 (node-level checks such as journalctl and crictl), R4 (deep-dive follow-ups on platform failures you handled)

| 12 | Drill 2: ImagePullBackOff on a huge model image | A new node pool cannot reach or authenticate to the registry, so fix the egress rule or pull secret, then measure pull time per pool before scaling into it. | intermediate | Cold-start and image-size follow-up | SHOULD | 2.7 |
| 13 | Drill 3: CrashLoopBackOff, OOM or probe kill | A liveness probe with a 5-second start and one failure kills a 90-second weight load; add a startup probe sized to the measured load time and separate OOM from liveness kills. | intermediate | Restart-loop question, R2 | MUST | 2.9 |

| 15 | Drill 5: Eviction storm | Batch pods request 2Gi and use 14Gi, so the kubelet evicts under MemoryPressure and replacements repeat the growth; fix requests and separate pools, and do not clear the taints by hand. | advanced | Eviction and noisy-neighbour follow-up | SHOULD | 3.0 |

Hands-on to do:
1. `cd ai-infra-handbook/code/part20 && python3 -m pytest -q test_c23_triage.py` (expect 13 passed).
2. `python3 c23_triage.py samples/c23_describe_pending_gpu.txt`, then the same with `samples/c23_describe_oomkilled.txt` and `samples/c23_describe_node_notready.txt`. Check the ranked causes against the drills, and say which evidence line decided each one.
3. `python3 c23_triage.py samples/c23_describe_pending_gpu.txt --events samples/c23_get_events_mixed.txt`. Sort the mixed events into separate problems, as the helper did.
4. `kubeconform -strict -summary c23_manifests_broken.yaml` and the fixed file. Both pass schema checks, so explain why only a cluster would reject the broken one.
5. If you have any local cluster, create a pod that requests a GPU you do not have, then run `kubectl describe pod` and `kubectl get events`, and find the FailedScheduling line.

Likely interview questions from this chapter:

- "Half of your DNS lookups take five seconds on a healthy cluster. How do you find the one bad backend?"
