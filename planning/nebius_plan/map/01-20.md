One-line purpose: A hands-on lab that assembles a container step by step (rootfs, chroot, namespaces, OverlayFS with pivot_root, cgroup limits, veth/NAT, reduced privilege) and compares it with `docker run`.

Hands-on to do:
- `sudo unshare --pid --fork --mount --uts --ipc --net --mount-proc=/lab/base/proc chroot base /bin/sh`, then `hostname container1; ps aux; ip link`. Note PID, interfaces, and whether the host sees the hostname change.
- Step 4 overlay: `mount -t overlay overlay -o lowerdir=/lab/base,upperdir=/lab/upper,workdir=/lab/work /lab/merged`, then `unshare ... /lab/enter.sh`; inside create `/newfile` and `rm /etc/hostname`; on host check `ls /lab/upper` and `ls -l /lab/upper/etc` (whiteout is `0, 0`).
- Caution (Step 6): the chapter writes `$$` from inside `unshare --pid --fork`, which is PID 1 in that namespace, to `/lab/ctr.pid` and then uses it as the host PID for `ip link ... netns $PID`. Resolve the host PID with `pgrep -f 'sleep 3600'` instead.
- Step 5 cgroup: set `cpu.max`, `memory.max=128M`, `pids.max=64` under `/sys/fs/cgroup/lab-ctr`, run a busy loop, then read `cpu.stat` and `memory.events` on the host.
- Step 8: `docker run -d --name real --cpus 0.5 --memory 128m --pids-limit 64 alpine:3.20 sleep 3600`, then `grep Cap /proc/$P/status` and `grep Seccomp /proc/$P/status` to see what Docker adds beyond your build.

Likely interview questions from this chapter:
- What are the minimum kernel mechanisms that together make a container? (namespaces, cgroups, rootfs, privilege limits)
- Why is `chroot` not a container, and what does `pivot_root` do that it does not?
- Why do you need `mount --make-rprivate /` before `pivot_root`?
- How do you limit a container to half a CPU, 128 MiB and 64 processes, and where do you check if it was hit?
- Walk me through giving a container network access: bridge, veth, NAT and ip_forward.
- What does Docker add on top of a bare namespace-and-cgroup setup? (capabilities, seccomp, masked paths)
