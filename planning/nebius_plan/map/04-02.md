# 4.2 CI/CD pipelines: concepts and design
Words: 14700 | Read time: 98 | File: /Users/jithinpjoseph/Documents/GitHub/ai-infra-handbook/docs/part-04-automation/02-ci-cd-pipelines-concepts-and-design.md
One-line purpose: Explains how an infrastructure pipeline should work: CI produces evidence and CD controls mutation, with saved plans, OIDC instead of stored keys, policy as code, golden images, staged fleet rollouts, drift checks and pipeline security.
Beginner friendly: partly. The principles and the gate diagram are clear, and the chapter explains CI versus CD in plain terms. But it leans on Network Programmability and Ansible-book material (Jenkins JCasC, Templatizer, Junos XML), and the GitHub Actions and Rego examples assume you already read YAML and Terraform. Read 4.1 first (Git workflow), then sections 0-3, 5, 7, 9 and 11 before the rest.
Nebius rounds served: R1, R2, R4
Chapter verdict: READ-SECTIONS (intro, 1, 2, 3, 5, 9, 11, 12, 14, 15 and checkpoints 1, 4, 6, 8, 9, 11, 15, 16-17), because the "evidence versus mutation" framing, the saved-plan rule, staged rollouts with halt thresholds, drift handling and pipeline security are what a senior SRE is asked in R2 and R4; skip the Jenkins/AWX and Junos material and the long tool lists.

Hands-on to do:
- Save and apply a plan: `terraform plan -out=tfplan`, then `terraform show -json tfplan > plan.json`, then `terraform apply tfplan` in a sandbox (sections 2, 3 and 7).
- Run a drift check: `terraform plan -input=false -detailed-exitcode` and read the exit code (0 no drift, 2 drift, 1 error) (section 11).
- Validate a policy: `conftest test plan.json --policy policies/` on a sample plan, then change one resource to see the deny message (section 7).
- Write a canary-then-batch Ansible play with `serial:` and `max_fail_percentage:` and inject one failure to see it halt (section 9; exercise 8 in the chapter).

Likely interview questions from this chapter:
- Design a pipeline for Terraform changes to a GPU cluster, from pull request to production apply.
- How do you give CI access to the cloud without storing keys, and why do plan and apply use separate identities?
- How do you roll a kernel or driver change out to 1,000 GPU nodes, and what stops the rollout?
- What policies would you enforce as code, and how do you stop a plan that would create 20 GPU instances by mistake?
- How do you detect drift, and when do you auto-heal versus alert only?
- What makes a CI pipeline itself a security risk, and how do you reduce it?
