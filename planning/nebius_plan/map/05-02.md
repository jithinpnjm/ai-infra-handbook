# 5.2 Container runtimes: containerd, runc, CRI and OCI
Words: 12,900 | Read time: 86 | File: docs/part-05-kubernetes/02-container-runtimes-containerd-runc-cri-and-oci.md
One-line purpose: Maps the node-side stack (kubelet, CRI, containerd or CRI-O, shim, OCI runtime, kernel), how a pod starts through CRI calls, how to configure containerd and the NVIDIA runtime, and which node tool to use for each layer.
Beginner friendly: partly. Read 5.1 first (it defines container, image, layer). Cgroup drivers and the systemd/cgroupfs split assume you know what a cgroup is and roughly how systemd works. The stack diagram and the CRI call sequence in section 1 are readable as a beginner.
Nebius rounds served: R2 (node-level troubleshooting: ContainerCreating, PLEG, runtime and cgroup mismatch, crictl), R1 (Linux process/cgroup/namespace view of a container), R3 (node pool design, GC and disk sizing for 30 GB images), R4 (GPU node runtime config for own project)
Chapter verdict: READ-SECTIONS. Sections 1, 2 (Configuration), 5, 6, 7 and 9 are needed for R2 node troubleshooting and GPU nodes. Sections 3 and 4 are needed only at a recall level (runtime comparison, RuntimeClass). Section 8 is worth a read for operations answers. Skip the Virtual Kubelet and Kata deep dives unless time is left.

Hands-on to do:
- On a kind cluster (its nodes are Docker containers): `docker exec -it <kind-node-name> crictl ps` and `docker exec -it <kind-node-name> crictl pods`. This is the easiest route for a Mac user, because containerd does not run natively on macOS. Use a Linux VM for the rest.
- Namespace trap: `ctr containers ls` (empty), then `ctr -n k8s.io containers ls` (shows Kubernetes containers). Confirm you understand why.
- Check the stuck-pod path: `crictl pods`, `crictl ps -a`, `crictl inspectp <pod-id> | jq '.status.network'`, `crictl logs --tail 100 <ctr-id>`.
- Config check: `containerd config default | head -50`, then `containerd config dump | grep -i systemd` and compare with the kubelet's `cgroupDriver`.
- Stop containerd on a lab VM with running pods (`systemctl restart containerd`) and check that the containers survive. Run this only on a lab node.
