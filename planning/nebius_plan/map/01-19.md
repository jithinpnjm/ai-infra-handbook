# 1.19 Namespaces: the kernel feature behind containers
Words: 10857 | Read time: 72 | File: /Users/jithinpjoseph/Documents/GitHub/ai-infra-handbook/docs/part-01-linux/19-namespaces-the-kernel-feature-behind-containers.md

One-line purpose: Explains that a container is not a kernel object but a set of namespaces, cgroups, a root filesystem and capabilities, and shows how to inspect and debug each piece.

Beginner friendly: partly. Terms like namespace, cgroup, PID 1 and overlay are new; read 1.8 (processes/signals), 1.10 (kernel interfaces), 1.12 (mounts), 1.18 (cgroups) first.

Nebius rounds served: R1, R2, R4 (and R3 for multi-tenant GPU isolation framing)

Chapter verdict: MUST-READ-FULL - container internals, PID 1 signal behaviour, overlay copy-up, and `nsenter` debugging are asked directly in troubleshooting rounds and are the basis of most container failure modes.

Hands-on to do:
- `ls -l /proc/$$/ns/; lsns; sudo nsenter -t <PID> -n ip addr` (enter a process's network namespace from the host).
- `sudo unshare --pid --fork --mount-proc bash`, then `ps aux`, and from another terminal `pstree -p` to see two PIDs for one process; try `kill -9 1` inside.
- `sudo unshare --mount bash`, mount a tmpfs, check `findmnt -o TARGET,PROPAGATION` from a second shell (propagation test).
- `ipcmk -M 1024; ipcs -m; sudo unshare --ipc ipcs -m` (IPC namespace isolation), then compare with `docker run --ipc=host`.

Likely interview questions from this chapter:
- What is a container at the kernel level, and why is there no "container" object in Linux?
- Your training container ignores SIGTERM and never checkpoints. Why, and how do you fix it?
- Inside a pod, `free` and `nproc` show 128 CPUs and 2 TiB. How do you find the real limits?
- PyTorch DataLoader crashes with a bus error in a container. What is the cause and the fix?
- A container's writes to a big file in the image filled the node disk. What happened (copy-up) and what should you do?
- Walk me through how `kubectl exec` enters a running container.
