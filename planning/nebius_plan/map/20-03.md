# 20.3 Triage method for a sick Linux box
Words: ~10600 | Read time: 71 | File: /Users/jithinpjoseph/Documents/GitHub/ai-infra-handbook/docs/part-20-nebius-sre-interview/03-triage-method-for-a-sick-linux-box.md
One-line purpose: Gives a spoken, repeatable method for a slow or failing Linux server (problem statement, 60-second checklist, USE sweep, RED for the service, hypothesis loop) and a one-hour console-round narration plan.
Beginner friendly: partly. The method is plain, but the chapter reads load average, run queue, PSI, vmstat, iostat and page cache with no warm-up. Read first: 1.8 (processes, signals), 1.10 (procfs and sysfs), 1.17 (memory management, swap, OOM), 1.18 (CPU scheduling and cgroups), and 1.23 (performance methodology, USE and drill-down) before sections 4-6. Section 11 assumes 5.x Kubernetes basics (pods, nodes, cgroup limits); read 5.9 (kubelet, cgroups, QoS, eviction) first.
Nebius rounds served: R1 (practical Linux console and troubleshooting, the core of this chapter), R2 (kubernetes-side host checks in section 11), R4 (the "how did you debug it" follow-up).
Chapter verdict: MUST-READ-FULL, because it is the spine of the Linux console round and every later Part-B chapter (20.4 to 20.7) builds on its 60-second checklist and USE sweep; plan about 70 minutes, and do the container-run section after your first pass.

Hands-on to do:
1. On a Linux VM or container (not macOS; the scripts exit on non-Linux), run `bash triage_first60.sh /tmp/base` then `python3 triage_report.py /tmp/base` (files in `code/part20/`). Confirm the ten-command output.
2. Start a CPU hog with `python3 triage_repro.py cpu --seconds 25 &`, wait 5 seconds, then run `vmstat 1 5` and watch column `r` rise above the CPU count while `load` lags.
3. Run `iostat -sxz 1 4` by hand while `python3 triage_repro.py disk --mb 2048 --seconds 40 &` writes; say aloud why `%util` high with `await` under 1 ms is busy, not saturated.
4. Run `bash triage_use_sweep.sh` and write down which cells you could not fill (dmesg, PSI, interconnects) as known-unknowns.

Likely interview questions from this chapter:
- A server is slow. Walk me through your first minute, out loud.
- Load average is 40 on a 16-core machine. Is that bad?
- CPU is mostly idle but the app is slow. Why?
- Disk shows 100 percent utilisation. Is it the bottleneck, and how do you prove it?
- Memory looks nearly full. Is that a problem? How do you tell?
- How do you decide whether the problem is the host or the service?
