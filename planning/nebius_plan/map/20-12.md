# 20.12 Estimation toolkit for inference capacity
Words: 11639 | Read time: 78 | File: docs/part-20-nebius-sre-interview/12-estimation-toolkit-for-inference-capacity.md
One-line purpose: Teaches the back-of-envelope chain (weights, KV cache per request, requests that fit, prefill and decode ceilings, GPUs for a QPS with headroom and spare, cost per million tokens, goodput, sanity checks) that an inference SRE says aloud in a design round.
Beginner friendly: no for a reader new to LLM serving. Read first: `docs/part-15-inference/02-batching-the-kv-cache-and-quantization-fundamentals.md` (KV cache, batching, quantisation), `docs/part-10-gpu-cuda/05-the-roofline-model-and-performance-modelling.md` (ridge point and arithmetic intensity), and `docs/part-15-inference/14-benchmarking-genai-perf-latency-percentiles-and-goodput.md` (percentiles and goodput). Also 20.10 section 5 (divide-before-deciding arithmetic). Part 2/10 basics are not needed for the chain itself.
Nebius rounds served: R3 (system design: capacity estimation and availability, primary), R2 (on-call triage of KV-cache alerts in Scenario 3), R4 (cost per token and utilisation trade-offs in the team-lead discussion)
Chapter verdict: READ-SECTIONS (intro; 1 estimation chain; 3 KV per request; 4 concurrency per GPU; 5 prefill vs decode only the practical formulas; 6 batching table; 8 GPUs for QPS with headroom and N+1; 9 cost per million; 10 goodput; 11 sanity checks; 12 numbers table; "How to answer out loud"; Scenarios 1 and 3; Drill questions). SKIM 2 (weights shortcut) and 7 (per-GPU rate and Little's law) and Scenarios 2 and 4. RUN, do not read, the code in the Hands-on lab. SKIP Sources and Verification log. Reason: the chain plus the five answer outlines is the whole R3 estimation skill; the rest is derivation detail.

The estimation chain | Six-step forward chain: weights, KV per request, requests that fit, decode and prefill ceilings, requests per second per GPU, GPUs for QPS plus headroom plus spare. Work forward from hardware, let load be the last comparison. | intermediate | "How many GPUs for this load?" | MUST | 3 |
| 2 | ### 2. Weights memory by precision | Parameters x bytes per parameter (FP32 4, BF16 2, FP8 1, 4-bit 0.5); keep decimal GB throughout; weights are the fixed cost that subtracts first. Qwen3-8B 16.4 GB in BF16. | basic | First sanity check: "does it fit at all?" | SHOULD | 3 |
| 3 | ### 3. KV-cache memory per token and per request | KV bytes per token = 2 x layers x kv_heads x head_dim x bytes; size by prompt plus output; grouped-query attention cuts KV 4x vs 32 heads (Qwen3-8B 147,456 bytes/token, a 2,500-token request about 0.37 GB). | intermediate | "How much memory does one request use?" Very likely. | MUST | 4 |
| 4 | ### 4. Concurrent requests per GPU | Budget: 80 GB x 0.90 minus weights minus overhead (5 GB assumed) divided by KV per request = 137 requests on one H100 (Qwen3-8B BF16). Fit is a ceiling, not a target. Four-GPU 72B case gives 149. | intermediate | Memory-budget subtraction, said in a fixed order. | MUST | 4 |
| 5 | ### 5. Prefill is compute-bound, decode is bandwidth-bound | Arithmetic intensity against ridge point (H100 about 295 FLOP/byte, dense 989.5 TFLOPS / 3.35 TB/s); decode at batch one is about 1 FLOP/byte so bandwidth sets speed; prefill ceiling formula with assumed MFU 0.40. Utilisation counts kernel time, not useful work. | advanced-intermediate (needs the roofline chapter first) | "Why is decode slow and prefill fast?" Very likely. | MUST | 5 |
| 6 | ### 6. How batching changes the numbers | Decode step = (weights + batch x context x bytes per token) / bandwidth; table shows throughput 200 to 6,744 tokens/s from batch 1 to 128 while per-request speed falls 200 to 53; returns flatten because the cache read grows. Choose batch by latency target, not largest fit. | intermediate | Throughput-versus-latency trade-off question. | MUST | 5 |
| 7 | ### 7. Tokens per second and requests per second per GPU | Prefill and decode seconds add on one GPU: 0.0829 s + 0.0933 s gives 5.68 requests per second at batch 64; Little's law check gives 22.4 ms per output token. Quote the per-GPU rate with its batch and latency. | intermediate | "What is one GPU's capacity?" | SHOULD | 3 |
| 8 | ### 8. GPUs for a target QPS, with headroom and N+1 | Replicas = ceil(QPS / (replica QPS x 0.9)) + spare; 40 QPS gives 8 plus 1 spare = 9 GPUs; peak-only sizing is unsafe because a single failure moves the peak onto survivors; spares are whole replicas for multi-GPU replicas. | intermediate | "How many GPUs do you ask for, and what buffer?" | MUST | 3 |
| 9 | ### 9. Cost per million tokens | cost = price per GPU-hour x GPUs / (tokens per second x 3600 x utilisation) x 1e6; $4.50 H100 gives $0.44 at full use, $1.47 at 30%; Nebius list price fetched 2026-11-09 and must be dated; levers in order: utilisation, batch, quantisation, cheaper GPU. | intermediate | "What does a million tokens cost, and how do you lower it?" | MUST | 3 |
| 10 | ### 10. Utilisation and goodput | nvidia-smi utilisation is not efficiency; goodput is the rate of requests meeting latency objectives (DistServe example: colocated 1.6 per GPU within both bounds); cost per good token = cost per token / fraction within objective. | advanced-intermediate | Shows you know the dashboard lies; links to 20.19 SLOs. | MUST | 2 |
| 11 | ### 11. The sanity checks | Four checks: weights under about 60% of usable memory; batch-one decode ceiling about 204 tokens/s; Little's law; units. Then compare to a benchmark; a gap over about 30% means a wrong input (usually prompt length). | intermediate | "How do you know your estimate is right?" Very likely. | MUST | 3 |
| 12 | ### 12. Hands-on to do:
1. From `code/part20`: `python3 -m pytest -q test_capacity_estimator.py` (expect 13 passed).
2. `python3 code/part20/capacity_estimator.py` with no arguments. Expect `fits 137 requests`, `5.68 req/s`, `9 replicas, 9 GPUs`, `$0.44 per million`.
3. By hand, without the script: `(80 x 0.90 - 16.4 - 5) / 0.36864` and confirm 137. Then `python3 code/part20/capacity_estimator.py --bytes-per-param 1 --kv-bytes 1` and check the 319 fit.
4. `python3 code/part20/capacity_estimator.py --model qwen2.5-72b --tp 4 --qps 10 --batch 32` (expect 149 fit, 2.61 req/s, 24 GPUs, $3.84 per million).
5. Change `--mfu` to 0.2 or `--overhead-gb` to 10 (the author did not run this). Write one sentence on which assumption the answer is most sensitive to.

Likely interview questions from this chapter:
