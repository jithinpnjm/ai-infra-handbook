# 5.8 The life of a pod end to end, including what the kernel does

One-line purpose: Traces one pod from `kubectl apply` through scheduling, kubelet admission, volumes, CNI sandbox, image pull and runc, probes, OOM versus eviction, and termination, naming the component and the node-side artefact at each hand-off.

Hands-on to do:
- Trace the path of one pod: `kubectl get events -w` in one terminal while you `kubectl apply -f pod.yaml` in another; then `kubectl get pod trainer-0 -o json | jq -r '.status.conditions[] | "\(.type) \(.lastTransitionTime)"'` to get the timeline.
- On a Linux node with the pod running: `CTR=$(crictl ps --name trainer -q | head -1); PID=$(crictl inspect $CTR | jq -r '.info.pid'); ls -l /proc/$PID/ns` and compare inode numbers with the pause container (net, ipc and uts should match).
- Read the cgroup enforcement: `cat /proc/$PID/cgroup`, then `cat $CG/memory.max $CG/cpu.max $CG/memory.events` (using the CG path from the chapter), and watch `oom_kill` after a memory test.
- Find the veth pair: `nsenter -t $PID -n ip link show eth0` (note `@ifN`), then `ip link | grep '^N:'` on the host.
- Offline: `python3 code/part05/pod_lifecycle_kernel_trace_lab.py` (startup intervals, namespace inode check, GPU device isolation).
