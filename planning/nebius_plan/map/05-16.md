# 5.16 Configuration, secrets and RBAC

One-line purpose: Covers how config and secrets reach pods (ConfigMaps, Secrets, projected tokens, external stores), how the API server authenticates callers, and how RBAC limits what they can do, including the escalation paths to watch.

Beginner friendly: partly. ConfigMaps, Secrets and the basic RBAC shape (who, which verb, which resource, where) are learnable from scratch. The authentication, token-review and escalation sections assume you already know the API server request path (5.5) and Pods, Deployments and ServiceAccounts (5.7). Read 5.5 and 5.7 first. The document also repeats a section heading ("6. Configuration management patterns for AI workloads" appears twice at lines 1243-1245); ignore the duplicate.

Nebius rounds served: R2 (RBAC "forbidden" errors, CreateContainerConfigError, secret handling in a cluster), R4 (how you handled secrets and access in your own project), R1 (only the file-permission and key-name basics)

Hands-on to do:
- Test the ConfigMap update behaviour: create `kubectl create configmap my-config --from-literal=LOG_LEVEL=info`, mount it once as an env var and once as a volume, change the value with `kubectl create configmap my-config --from-literal=LOG_LEVEL=debug --dry-run=client -o yaml | kubectl replace -f -`, then check the volume file after one or two minutes and the env var in a new `kubectl exec`.
- Check authorization for a ServiceAccount: `kubectl auth can-i --list -n team-a --as=system:serviceaccount:team-a:trainer` and `kubectl auth can-i get secrets -n team-a --as=system:serviceaccount:team-a:trainer`. Predict the answer before you run each.
- Read a token: `kubectl create token <sa> -n <ns> --duration=30m --audience=vault`, then decode the JWT payload (base64 middle segment) and find `aud` and `exp`. (The chapter's exercise 6 asks for this.)
- Test subresource permission: `kubectl auth can-i get pods --subresource=logs -n <ns>`, then `kubectl auth can-i create pods --subresource=exec -n <ns>`.
- Impersonation drill from section 5e: apply the four manifests (`cluster-admin-view`, `cluster-admin-crb`, `cluster-admin-impersonator`, `cluster-admin-impersonate`) in a test cluster, then run a write as a read-only user and again with `--as=cluster-admin`, and read the audit log.
- Dry-run an RBAC change before merging: `kubectl auth reconcile -f <rbac-file> --dry-run=client`.

Likely interview questions from this chapter:
- Are Kubernetes Secrets secure, and what would you do to protect them?
- A ConfigMap changed, but the app still uses the old value. What happened, and how do you fix it?
- What is the difference between a Role, ClusterRole, RoleBinding and ClusterRoleBinding? Can a RoleBinding reference a ClusterRole, and what does that give?
- Name RBAC permissions that are effectively cluster-admin. Why is create on pods in a namespace close to reading all its secrets?
- How do pods reach cloud storage without static keys, and what is a bound ServiceAccount token?
- How would you design access for 20 research teams on a shared GPU cluster, with a platform team and a set of ML engineers?
