# 5.17 Storage internals: volumes, PV and PVC, CSI and mounts
Words: ~14000 | Read time: ~93 | File: /Users/jithinpjoseph/Documents/GitHub/ai-infra-handbook/docs/part-05-kubernetes/17-storage-internals-volumes-pv-and-pvc-csi-and-mounts.md

One-line purpose: Explains how a pod gets storage (volume types, PV/PVC/StorageClass binding, the CSI controller and node call sequence, mount mechanics) and the AI storage patterns for datasets, checkpoints and model weights, with the failure modes that stall them.

Beginner friendly: partly. The volume-type table and the PV/PVC/StorageClass explanations are readable from first principles. The mount section (bind mounts, staging paths, inodes, FUSE) assumes Linux block devices, filesystems and mounts (Part 1, 1.12-1.16). Read those first, and read 5.7 (StatefulSets) before section 2's StatefulSet part.

Nebius rounds served: R1 (df versus df -i, findmnt and lsblk, mount and disk troubleshooting), R2 (Pending PVC, FailedMount, Multi-Attach, ContainerCreating), R3 (checkpoint and dataset throughput and cold-start arithmetic: this is the capacity estimation the round asks for), R4 (your own project's storage choices)

Chapter verdict: READ-SECTIONS (1 volume table, 2 PV/PVC/StorageClass key properties and binding modes, 3 CSI controller and node services and the seven-step lifecycle, 4 mount mechanics (bind mounts, subPathExpr, FUSE, inodes), 5 AI storage patterns and the division arithmetic, 6 capacity, troubleshooting table and data protection, 8, 9). Skip the CSI driver ecosystem list and the AWS driver install and secret examples, the GPUDirect Storage requirements (Part 13 material), and the CyberArk and vendor names. The reason: the binding-mode trap, the CSI call chain and the troubleshooting table are the likely R2 questions, and the throughput arithmetic is the most likely R3 capacity exercise.

Hands-on to do:
- Binding modes on kind or minikube with local-path: create one PVC with the default `WaitForFirstConsumer` and one with `Immediate`, then `kubectl get pvc,pv` and `kubectl describe pvc <name>` before and after a pod consumes the claim. Note which one sits in Pending.
- Mount inspection: inside a pod run `df -h /data` and `df -i /data`; on the node run `findmnt -T /var/lib/kubelet/pods/<uid>/volumes/...` and `lsblk -f`. Explain the difference between bytes and inodes using the chapter's ENOSPC case.
- Multi-attach drill: two pods on different nodes sharing one RWO PVC; read the events with `kubectl describe pod` and find the `Multi-Attach error` message.
- CSI check: `kubectl get csinode -o yaml` and read `allocatable.count` and `topologyKeys` for each node. `kubectl get volumeattachment` during a mount.
- Arithmetic on paper (the R3 drill): checkpoint stall = checkpoint size / aggregate write bandwidth (for example, 1,000 GB at 2 GB/s = 500 s); cold start = weights size / read bandwidth (140 GB at 2 GB/s = 70 s); replicas multiply the bytes moved when each pulls its own copy (16 x 140 GB = 2.24 TB).
- Run `python3 code/part05/csi_storage_simulator_lab.py` (the lab named in the chapter) to check the binding, Multi-Attach and timing functions against your hand numbers.
