# 5.24 Observability for Kubernetes
Words: 15280 | Read time: 102 | File: /Users/jithinpjoseph/Documents/GitHub/ai-infra-handbook/docs/part-05-kubernetes/24-observability-for-kubernetes.md
One-line purpose: How to see inside a Kubernetes and GPU platform (metrics, logs, events, traces), how to alert only on user-facing symptoms with SLO burn rates, and how to scale and secure the monitoring stack.
Beginner friendly: partly. The signal table, RED/USE and the alert principles are readable from zero. PromQL, the Prometheus Operator YAML and the Go code are not, until you have run kube-prometheus-stack once. Read 5.3, 5.9 and 5.19 first. Know what a counter and a histogram are before the Prometheus model section.
Nebius rounds served: R2 (how you find the fault: decision tree, PromQL, events, logs), R3 (SLO design, alerting, monitoring-stack availability), R4 (what you monitored and what you page on)
Chapter verdict: READ-SECTIONS (1 signals and RED/USE; 2 "Prometheus model", "kube-prometheus-stack", "Reading a ServiceMonitor", "Key exporters and sources", "Essential PromQL"; 3 "Principles", "Alertmanager", "GPU-fleet specific alerts"; 4 "Architecture" and "Kubernetes Events"; 6 dashboards; 7 cardinality and reliability; 8 diagnosis flows; 9 lab; 10, 11; checkpoints 1, 4, 5, 6, 8, 9, 10, 11, 14, 16, 17, 18, 20). Skip the Go instrumentation code, the Go tracer code, the trace vocabulary and the Sources. Read section 5 only for the idea of head versus tail sampling.

Hands-on to do:
- Install kube-prometheus-stack with the chapter's `helm upgrade --install` command on kind, then `kubectl -n monitoring port-forward svc/<prometheus-svc> 9090` and run `sum(kube_node_status_condition{condition="Ready",status="true"} == 0)` and `sum by (namespace, pod) (rate(kube_pod_container_status_restarts_total[15m])) > 0.01` in the UI.
- Fall into the release-label trap on purpose: create a ServiceMonitor with no `release: kps` label, check Status, then Targets, and fix it.
- `kubectl get events -A --sort-by=.lastTimestamp | tail -20`, then note that events expire after about one hour and export one to a file before it does.
- Write a recording rule and an alert with `for:` in a PrometheusRule, and test it with `promtool test rules` using a synthetic series.
- Run the chapter's lab: `python3 code/part05/k8s_observability_slo_sim_lab.py`, then change the burn-rate target from 99.5% to 99.9% and read the new thresholds.

- What GPU metrics and alerts would you set up for a training fleet? Why is GPU utilisation not enough?
- How do you handle high cardinality, and how would you scale Prometheus across many clusters?
