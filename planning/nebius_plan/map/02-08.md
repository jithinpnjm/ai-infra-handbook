# 2.8 DNS in depth: resolution, records, resolvers and caching
Words: ~9450 | Read time: ~63 min | File: docs/part-02-networking/08-dns-in-depth-resolution-records-resolvers-and-caching.md
One-line purpose: Explains how a name becomes an address (stub, recursive, authoritative, caches, TTL), the Linux resolver files, and the Kubernetes ndots and conntrack DNS failure modes that cause slow or stalled calls.
Beginner friendly: partly. The lookup path and record types are beginner-reachable; the Kubernetes, conntrack and DNSSEC parts are intermediate. Read 2.4 (IP addressing) and 2.7 (UDP and ports) first, and 2.6 for why TCP port 53 exists.
Nebius rounds served: R1 (dig vs getent, resolv.conf, nsswitch, reverse DNS), R2 (5-second stalls, CoreDNS and ndots overload, "works with dig but not curl"), R3 (DNS availability and redundancy as part of a design answer), R4 (how your service finds its dependencies and names its nodes)
Chapter verdict: READ-SECTIONS. Read 1 (zones, delegation, glue, stub vs recursive vs authoritative), 2 (lookup walk-through, TTL, negative caching, UDP/TCP and response codes), 3 (record table and reverse DNS only), 4 (dig flags and the dig vs getent distinction), 5 (nsswitch, resolv.conf, ndots worked example, timeouts, per-program caching), 6 (pod resolv.conf and ndots:5), 10 (diagnostic routine), 11 (5-second case study), 12 (lab steps 1, 3, 4 and the Python lab), 13 and 14, exercises 3 to 5. SKIM 7 (HPC naming), 8 (DNSSEC internals) and 9 (running BIND/dnsmasq). Reason: DNS is the most common hidden cause of slow calls, so the lookup path and the ndots/5-second story are high-value, while DNSSEC and server operations are unlikely to be drilled at this level.

Hands-on to do:
- Trace a cold lookup: `dig +trace www.example.com`, then `dig www.example.com` twice a few seconds apart and watch the TTL drop (cache hit).
- Compare layers: `dig www.example.com`, `getent hosts www.example.com`, `resolvectl query www.example.com`. Add a bogus line to `/etc/hosts` for a real name and see which tools return it (lab step 2).
- Time a dead resolver: put an unreachable nameserver first in a test resolv.conf (or namespace /etc/netns/<ns>/resolv.conf), time `getent hosts <name>`, then try `options timeout:1 attempts:1`.
- Count the ndots fan-out: run `tcpdump -ni any port 53` while `curl http://short-name` and `curl http://name.with.trailing.dot.` run, and count queries for each.
- Python lab: `python3 code/part02/dns_in_depth_lab.py` (ndots expansion, reverse name for 10.20.0.45, glibc failover delay).
