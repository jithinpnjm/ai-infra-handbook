# 5.15 NetworkPolicy and the kernel: netfilter, conntrack and eBPF
Words: ~11500 | Read time: ~77 | File: /Users/jithinpjoseph/Documents/GitHub/ai-infra-handbook/docs/part-05-kubernetes/15-networkpolicy-and-the-kernel-netfilter-conntrack-and-ebpf.md

One-line purpose: Explains the NetworkPolicy API precisely (additive, isolation on selection, AND/OR selectors), how Calico and Cilium enforce it in the kernel, the traps that break DNS and probes, and how to test and debug a blocked flow.

Beginner friendly: partly. The NetworkPolicy API (sections 1 and the kuard test) is approachable if you know Services and labels (5.10). The kernel part (section 3: netfilter hooks, conntrack, ipsets, BPF maps) needs Part 2 Linux networking (2.23) first. Read 5.13 before section 3.

Nebius rounds served: R2 (policy broke DNS or probes, debug a blocked flow), R1 (iptables, conntrack and the trace commands in a console task), R3 (tenant isolation in a multi-tenant GPU design), R4 (defending your platform's isolation choices)

Chapter verdict: READ-SECTIONS (1 full, the kuard default-deny test, 2 trap table, 3 netfilter/conntrack and the Calico and Cilium enforcement subsections, 5 zone design rules, 6 testing and debugging, 8, 9). Skip the Dikastes/Istio and "Network identity" subsection of section 4 and the Calico/Cilium extended-API details beyond recall, since they go beyond what a Senior SRE interview at an inference platform is likely to test. The reason: NetworkPolicy semantics and the "policy broke DNS" debugging are the likely R2 questions; the identity material is a service-mesh topic from another book.

Hands-on to do:
- Run the kuard three-step test (Section 1d) in a scratch namespace: `kubectl create ns kuard-networkpolicy`, deploy the kuard Pod, expose it, `wget` from a busybox pod, apply `default-deny-ingress`, then add `access-kuard` and retest. Write down the timeout versus the success.
- Practise the AND/OR truth table: write the same `from` block with and without the dash in the YAML, apply both, and test with a netshoot pod from a labelled namespace.
- Debug a blocked flow with the section 6 commands, in order: `kubectl get netpol -n <ns> -o wide`, `kubectl describe netpol <name> -n <ns>`, `curl -m 3 -v http://<svc>:<port>`, `nc -vz -w 3 <pod-ip> <port>`.
- On a Calico node, read the enforcement: `sudo iptables -L cali-tw-<iface> -n -v --line-numbers` and `ipset list | head`, then send traffic and watch the counters move.
- On a Cilium node: `cilium policy trace --src-k8s-pod <ns:pod> --dst-k8s-pod <ns:pod> --dport 8000/tcp` and `hubble observe --verdict DROPPED --last 20`.
- Test the probe trap: apply default-deny ingress to a namespace that has a readiness probe and confirm the pod still goes Ready (kubelet probes come from the node), then block DNS egress and observe name resolution fail.

Likely interview questions from this chapter:
- How does NetworkPolicy work? What is the default, and what does additive mean?
- Write a policy that lets only the gateway namespace reach model servers on port 8000, with DNS egress allowed.
- In a from list, what is the difference between one dash with two selectors and two dashes with one selector each?
- You applied default-deny and everything broke. What did you forget, and how do you find it?
- Why does an existing TCP connection survive a new deny rule, and how do you cut it off?
- How would you isolate tenants on a shared GPU cluster, and how do you handle the RDMA network that NetworkPolicy does not see?
