# 5.22 Multitenancy and platform services
Words: 18050 | Read time: 120 | File: /Users/jithinpjoseph/Documents/GitHub/ai-infra-handbook/docs/part-05-kubernetes/22-multitenancy-and-platform-services.md
One-line purpose: How to share one Kubernetes GPU cluster safely and fairly between teams (tenancy models, quotas, RBAC, GPU sharing, self-service onboarding, platform services, showback).
Beginner friendly: partly. The tenancy table and the quota and RBAC examples are readable. Kueue, MIG and the operator sections assume you know RBAC, admission and quotas. Read 5.16 (RBAC) and 5.18 (scheduling and Kueue) first, and 5.21 (admission) for the guardrail parts. The Pinterest and Waypoint examples are background only.
Nebius rounds served: R3 (multi-tenant GPU platform design, isolation, fairness, onboarding), R4 (platform-as-a-product and cost ownership), R2 (quota and "why is my pod pending" triage)
Chapter verdict: READ-SECTIONS (1 trust-level table and "Isolation layers"; 2 ResourceQuota/LimitRange, GPU sharing options, node isolation; 3 Capsule and vCluster paragraphs; 4 tenant spec and onboarding objects; 5 platform services table and "Building blocks"; 6 showback methods; 7 symptom table; 9, 10; checkpoints 1, 3, 7, 8, 15, 17, 18, 20). Skip the four-stage abstraction prose (Stages 1 to 4), the Pinterest and Waypoint examples, the Helm template details and the Sources. They are useful for taste, not for the interview.

Hands-on to do:
- On kind: `kubectl create ns team-a`, apply a ResourceQuota with `requests.nvidia.com/gpu: "2"` and `count/pods`, then create a pod that asks for 3 fake GPUs and read the `exceeded quota` error. Then run `kubectl describe quota -n team-a`.
- Isolation check: create a RoleBinding to the built-in `view` ClusterRole in `team-a`, then run `kubectl auth can-i list pods -n team-b --as=<user>` and `kubectl auth can-i list pods -n team-a --as=<user>`.
- Apply a default-deny NetworkPolicy in a test namespace, then `kubectl run` a curl pod in another namespace and show that the connection fails.
- Preview the Pod Security label with `kubectl label --dry-run=server --overwrite ns <ns> pod-security.kubernetes.io/enforce=baseline` (from 5.21).
- Run the chapter's lab: `python3 code/part05/multitenancy_quota_reconciler_lab.py`, then change one quota value and read the result.

Likely interview questions from this chapter:
- How do you design multi-tenancy on a shared GPU Kubernetes cluster? Which isolation layers do you close first?
- Soft vs hard multi-tenancy: when do you use virtual clusters, and when a cluster per tenant?
- How do you share GPUs fairly across teams? Compare Kueue quotas, preemption, MIG and time-slicing.
- How do you stop one tenant from overwhelming the API server or the shared storage?
- How would you onboard a new team in 10 minutes, and offboard it without losing checkpoints?
- How do you attribute GPU cost to teams, and what do you charge: requested or utilised GPU-hours?
