# 17.7 Failure modes and detection
Words: 10400 | Read time: 67 | File: /Users/jithinpjoseph/Documents/GitHub/ai-infra-handbook/docs/part-17-operations/07-failure-modes-and-detection.md
One-line purpose: Catalogues the GPU, network, storage, scheduler, image and model-serving failures an AI platform hits, with the symptom, detection signal and first action for each, and how to keep that catalogue current.
Beginner friendly: partly. The "symptom, detect, first action" tables are easy to use as a checklist, and the OOMKilled-versus-CUDA-OOM and NCCL-timeout sections are the best teaching in the chapter. But it assumes Xid, NCCL, DCGM and Kubernetes pod states. Read 17.4 (DCGM) and the Part 4/11 Kubernetes basics first, and read 8.1 and 9.8 as the closing checklist.
Nebius rounds served: R2, R3, R4
Chapter verdict: READ-SECTIONS (intro table, 1.1, 1.2, 1.3, 2.2, 2.3, 3.1, 4.1, 4.2, 5.1, 6.1, 6.3, 8 with 8.4 and 8.5, 9.8), because the failure-mode checklist and the NCCL, OOMKilled and ECC reasoning are exactly what R2 troubleshooting and R3 availability questions probe; skip the lab, the catalogue YAML and most of the script stubs.

Hands-on to do:
- Trigger the difference yourself: run a container with a memory limit and watch for `OOMKilled` and exit code 137 in `kubectl describe pod`, then contrast with a CUDA OOM in the application log (section 4.2).
- Read the NCCL signal: set `NCCL_DEBUG=WARN` on a small two-process test and find `NCCL_COMM_FAILURE` or the watchdog line in the logs (section 2.2-2.3).
- Run `ansible all -m ping` (or `ping`) from two hosts on different sides of a suspected split and compare the unreachable sets (section 2.3).
- Run `kubectl get events -n <ns> --field-selector reason=Failed` to see image or admission failures (section 5.2), and `trivy image <image>` on one container you own (section 5.3).

Likely interview questions from this chapter:
- A distributed training step is stuck on an NCCL watchdog timeout. Walk me through how you find the real cause.
- A pod was OOMKilled. Is it host memory or GPU memory, and what do you change for each?
- A GPU's correctable ECC count is climbing. What is the escalation path?
- Pods are stuck in ImagePullBackOff. Give me your checklist.
- One GPU failure is about to breach the cluster SLO. How do you stop the cascade?
- A model's error rate is flat but customers say the answers got worse. How do you detect it?
