# 4.19 Terraform state in depth: backends, locking and drift

One-line purpose: Explains what Terraform state holds and why it is dangerous, how remote backends and locking protect it, how to split state by blast radius, how to recover from lost or stale state, and how to handle drift and secrets in state.
Beginner friendly: partly. The "why not Git" reasons and the locking explanation are clear. The S3 and GCS backend blocks, the state-surgery commands and the OpenTofu encryption details need the 4.18 basics first. Read 4.18 (plan and apply loop) before this chapter, then sections 1, 2, 4, 8, 9 and 10.

Hands-on to do:
- Read a state file: `terraform state pull | jq '{version, serial, lineage}'` and `terraform state list` on a local-provider config; then change a value and watch `serial` increase (section 1 and checkpoint 1).
- Take a backup before any change: `terraform state pull > backup-$(date +%F-%H%M).tfstate` (section 7.1).
- Read a lock conflict: start two `terraform plan` runs against one S3 or local backend and note the `LockID` and `Who` fields in the error (section 4).
- Run `terraform init -reconfigure` and `terraform init -migrate-state` on a scratch backend and note the difference (section 3.6).
- Check a secret in state: `terraform state show <addr>` on a `random_password` resource and find the plaintext (section 10).
