Hands-on to do:
- Test records from a debug pod: `kubectl run -it --rm dns --image=registry.k8s.io/e2e-test-images/jessie-dnsutils:1.3 --restart=Never -- sh`, then `nslookup kubernetes.default`, `dig +short SRV _https._tcp.kubernetes.default.svc.cluster.local`, `cat /etc/resolv.conf`.
- Bypass layers to find the fault: `dig @<coredns-pod-ip> kubernetes.default.svc.cluster.local` against `dig @10.96.0.10 ...` (or the kube-dns ClusterIP). If the pod IP answers and the ClusterIP does not, look at kube-proxy or the CNI.
- Count the ndots queries: `dig +search +showsearch api.github.com` (or `getent hosts api.github.com`), then run `tcpdump -ni any port 53` in a second shell and count A and AAAA queries for each search suffix.
- Read the CoreDNS state: `kubectl -n kube-system logs deploy/coredns --tail=50` and `kubectl -n kube-system get cm coredns -o yaml`; look for `Loop detected`, SERVFAIL and forward errors.
- Offline: `python3 code/part05/coredns_ndots_resolver_lab.py` (search-query expansion, headless records, forwarding-loop detection).
