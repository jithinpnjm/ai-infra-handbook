# 20.6 Network debugging from socket to switch
Words: ~13000 | Read time: 87 | File: /Users/jithinpjoseph/Documents/GitHub/ai-infra-handbook/docs/part-20-nebius-sre-interview/06-network-debugging-from-socket-to-switch.md
One-line purpose: Teaches a spoken method for network faults on Linux (read the error word, split the path in half, read `ss` states and queues, then check backlog, port budget, conntrack, DNS ndots, MTU, tcpdump, TLS, idle timeouts and the Kubernetes Service path), with six reproducible scenarios.
Beginner friendly: no for the full chapter; partly for sections 1-3 and 7. It assumes you already know TCP handshakes, ports, MTU and DNS resolution. Read first: 2.1 (what happens when you curl a URL), 2.2 (layers and encapsulation), 2.6 (TCP handshake, windows, retransmission), 2.7 (ping, traceroute, mtr), 2.8 (DNS resolution and caching), 2.10 (HTTP, TLS and PKI basics), 2.17 (VXLAN overlays, which the chapter cites for the 50-byte overhead), and 2.22 and 2.23 (inspecting state with ip and ss; netfilter and conntrack). For section 12 read 5.10 (Services, endpoints, kube-proxy) and 5.11 (CoreDNS), which the chapter cites.
Nebius rounds served: R1 (console networking: ss, connect failures, tcpdump, DNS), R2 (Kubernetes Service path, CoreDNS ndots, kube-proxy), R3 (streaming and idle timeouts in a serving design), R4 (the incident story: streams dropping at a fixed time).
Chapter verdict: READ-SECTIONS: intro, 1, 2, 3, 4, 5, 7, 11, 12, How to answer out loud, Scenarios 1, 2, 4 and 6, and drill questions; SKIM sections 6 (conntrack), 8 (MTU), 9 (tcpdump) and 10 (TLS) for the one-line rule and the command, not the arithmetic; skip the Python code listings unless you want Python practice.

Hands-on to do:
1. Accept-queue demo on a Linux VM: `python3 code/part20/net06_accept_queue_demo.py 5 10 4`, and in a second shell `ss -ltn` and `nstat -az TcpExtListenOverflows TcpExtListenDrops`. Read the listener row as `Recv-Q Send-Q`.
2. Idle-timeout demo: `python3 code/part20/net06_idle_reset_demo.py`. Explain why the silent client only fails on its next write.
3. Count states on your own host: `ss -tan | awk 'NR>1 {c[$1]++} END {for (s in c) print s, c[s]}'`, then read `sysctl net.ipv4.ip_local_port_range` and do the port-budget arithmetic aloud.
4. DNS cost: `printf 'search ml.svc.cluster.local svc.cluster.local cluster.local\noptions ndots:5\n' | python3 code/part20/net06_resolv_ndots.py api.example.com`, then say how many queries a single call costs.

Likely interview questions from this chapter:
- A client's connect fails. Walk me through it, starting from the exact error text.
- Users see slow connects at peak while CPU is fine. What is your next command and why?
- A service has thousands of TIME_WAIT sockets and new calls fail. Is that a problem, and how do you fix it?
- Small requests work but large responses hang between pods. What is your first suspect and how do you test it?
- A token stream dies after about a minute with no server error. What do you check, and how do you fix it?
- A pod cannot reach a Kubernetes Service. What do you check, in what order?
