# 1.17 Memory management: virtual memory, NUMA, huge pages, OOM
Words: ~13,700 | Read time: ~91 min | File: /Users/jithinpjoseph/Documents/GitHub/ai-infra-handbook/docs/part-01-linux/17-memory-management-virtual-memory-numa-huge-pages-oom.md

One-line purpose: Explains how Linux manages RAM (virtual memory, reclaim, OOM killer, NUMA, huge pages, allocators, cgroup limits, pinned memory) and how to diagnose host-memory problems on GPU training nodes, starting from exit code 137.
Beginner friendly: no. The chapter is marked Advanced. Start with the opening "six symptoms" list and section 4 "How Linux frees memory" in the order given. Read 1.8 (processes, `vmstat`, page faults), 1.11 (address space) and 1.15 (cgroups, `MemoryMax`) first, and 1.10 for sysctl.
Nebius rounds served: R1 (memory triage: `free`/`available`, OOM logs in `dmesg`, `sar -B`, `ulimit -l`), R2 (GPU job killed with exit 137, NUMA-bound data loaders, `memlock` and RDMA registration failures, Kubernetes OOMKilled and QoS, node-level sysctl policy), R3 (host RAM budgeting for a GPU node and a fleet memory policy), R4 (how you diagnosed memory on your own project)
Chapter verdict: READ-SECTIONS. Read in full: section 2 "Swap" and "Overcommit" (short), section 3 "NUMA trap" paragraph and "Discover the topology" commands, section 4 (watermarks, `vm.swappiness`, direct reclaim), section 5 (the whole OOM section, incl. the OOM-report walk-through), section 6 "The summary view" and "Pressure and activity" and "The method for memory problems", section 7 "Policies and binding" and the GPU-loader paragraph, section 8 "THP" guidance paragraph, section 11 (`memory.max` / `memory.events` list, `memlock` consequences, host RAM budget, node-type table), and "How it fails". Skim allocator tables (section 9), the `sysctl` table (section 10), and the page-table walk details in section 2. Skip the Sources list.

Hands-on to do:
- `free -h; grep -E 'MemAvailable|Cached|AnonPages|Slab|Mlocked|Committed_AS' /proc/meminfo; cat /proc/pressure/memory`. Explain why `available` matters more than `free`.
- Run the cgroup OOM drill (lab step D): `sudo systemd-run --scope -p MemoryMax=300M ...`, then `dmesg -T | grep -i oom`. Find the cgroup constraint line.
- `numactl --hardware; numastat; nvidia-smi topo -m` on any multi-GPU or multi-socket machine. Name each GPU's NUMA node.
- `ulimit -l`, then lower it with `ulimit -Sl 64` and try an `mlock` of 1 MiB (lab step I). Note the errno.

4. A pod is OOMKilled while the host has plenty of RAM. How do you tell the cause, and what Kubernetes settings matter?
5. RDMA memory registration fails, but the GPU has free memory. What limit do you check?
