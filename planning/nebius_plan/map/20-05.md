# 20.5 CPU, memory, disk and the scheduler
Words: ~11600 | Read time: 77 | File: /Users/jithinpjoseph/Documents/GitHub/ai-infra-handbook/docs/part-20-nebius-sre-interview/05-cpu-memory-disk-and-the-scheduler.md
One-line purpose: Shows how to prove which resource (CPU, memory, disk) is short on a Linux host or container, using PSI, cgroup throttle counters, the OOM log, iostat and pinned-memory budgets, with six runnable scenarios.
Beginner friendly: partly. Load average, PSI, `free` vs `MemAvailable` and iostat columns are explained from first principles, but the cgroup, OOM-log and pinned-memory sections assume you already know processes, cgroups and memory. Read first: 1.17 (virtual memory, swap, OOM) and 1.18 (CPU scheduling and cgroups v1/v2) before sections 2, 3, 6-8; 1.23 (USE method and drill-down) before section 1; 1.24 (perf, BPF) before sections 10-11; 5.9 (kubelet, requests and limits, QoS, eviction) before sections 3 and 8. For section 12 read 10.12 (CUDA pinned memory, as the chapter itself points to) first.
Nebius rounds served: R1 (console: load, PSI, memory and disk triage), R2 (Kubernetes: CPU throttling, OOMKilled, QoS, eviction), R3 (host-memory budget for a GPU inference pod), R4 (incident/debugging stories).
Chapter verdict: READ-SECTIONS: intro, 1, 2, 3, 6, 7, 8, 9, 12 (budget arithmetic only), How to answer Q1-Q5, Scenarios 1-5, drill questions; SKIM sections 4, 5, 10 and 11 (steal, NUMA, perf, eBPF are useful names and one-line answers, not depth); skip the hands-on perf/flame-graph step unless you have a Linux host with perf.

Hands-on to do:
1. On a Linux VM (not a shared host), run `bash code/part20/c05_s1_dstate_load.sh` and read `vmstat 1 3` (`b`, `wa`) and `ps -eo stat,pid,comm | awk '$1 ~ /^D/'` while it runs.
2. Run `docker run --rm --cpus=0.5 alpine:3.20 sh -c 'cat /sys/fs/cgroup/cpu.stat; ...'` with four busy loops, or run `bash code/part20/c05_s2_cpu_throttle.sh`, then compare `nr_throttled` and `throttled_usec` before and after.
3. Run `bash code/part20/c05_s4_page_cache.sh` and compare `MemFree` with `MemAvailable` before and after the 512 MiB write.
4. Run `bash code/part20/c05_s5_disk_latency.sh` and say aloud why the dsync run is busy but fast. Optional: `bash code/part20/c05_s3_cgroup_oom.sh` and read the `CONSTRAINT_MEMCG` line.

Likely interview questions from this chapter:
- Load average is 30 and CPU is 40 percent busy. What do you check, in what order?
- A container has bad p99 latency but the node CPU is low. How do you prove throttling?
- A pod was OOMKilled while the node has free memory. How do you tell a cgroup kill from a node kill?
- `free` shows almost no free memory on a host. Is that a problem, and what do you alert on instead?
- A disk shows 100 percent utilisation. Is it saturated, and how do you prove it?
- A GPU inference pod is killed on host memory while the GPUs are idle. How do you size the limit?
