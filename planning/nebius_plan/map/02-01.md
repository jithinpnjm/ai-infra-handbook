# 2.1 What happens when you curl a URL: a packet's journey end to end

One-line purpose: Follows one `curl https://example.com/` through every layer (process, DNS, route, ARP, switch, NAT, TCP, TLS, HTTP, teardown) so each later networking chapter has a place to land.
Beginner friendly: partly. Plain-language analogies, but it names many terms at once. Read 2.2 (layers and encapsulation) first, and Part 1 chapters 1.1 to 1.9 (Linux shell) as the chapter's own prerequisite.

Hands-on to do:
- `curl -sS -o /dev/null -w 'dns=%{time_namelookup} connect=%{time_connect} tls=%{time_appconnect} ttfb=%{time_starttransfer} total=%{time_total}\n' https://example.com/` then subtract phases by hand.
- `ip route get 93.184.216.34` and `ip neigh show`, then read which gateway and which MAC the host would use.
- `getent hosts example.com` run twice (cold vs cache), then `resolvectl query example.com`.
- On a disposable VM: `sudo tcpdump -nn -i any 'host <example.com IP> and tcp' -c 20` while running curl; label SYN, SYN-ACK, ACK, ClientHello.
- Break-and-restore: point a copy of /etc/resolv.conf at an unused IP and time the failure; run `curl --cacert /dev/null https://example.com/` and read the exit 60 message.

Likely interview questions from this chapter:
- Walk me through what happens when I run `curl https://example.com`, and name a command for each step.
- What is the difference between "connection refused" and "connection timed out" at the packet level?
- A pod cannot resolve an external name but the node can. Where do you look first, and why does ndots matter?
- What changes at each router hop, and what stays the same end to end? Where does NAT change that?
- A curl to a site fails with "certificate verify failed". Which layer is it, and how do you prove it with openssl s_client?
- A large file download stalls while small requests work. What do you check first?
