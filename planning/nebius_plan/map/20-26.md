# 20.26 The stress interview: production incident role-play
Words: ~11,880 | Read time: ~80 min (full chapter; the Python code blocks in section 6 can be skipped at ~15 min of that) | File: docs/part-20-nebius-sre-interview/26-the-stress-interview-production-incident-role-play.md
One-line purpose: Trains a 30-minute production-incident drill: take control in two minutes, mitigate before finding the root cause, narrate ranked hypotheses, post status on a cadence, avoid destructive fixes, and practise ten scripted incidents.
Beginner friendly: no. It assumes you can read `kubectl` output, know what a liveness probe, a DNS search path and an fsync are, and have run basic Linux triage. Read first: 20.3 (triage method for a sick Linux box), 20.5 (CPU, memory, disk), 20.6 (network debugging), 5.9 (kubelet and probes), 5.11 (CoreDNS), 17.11 (incident response). Also 20.18 (how LLM serving fails) for the inference incidents.
Nebius rounds served: R2 (troubleshooting and Kubernetes incidents, main), R1 (Linux console part: incidents 6 and 8), R3 (capacity and retry arithmetic in incidents 4 and 5), R4 (the "how did you handle an incident" part of your project talk). Nebius has not published that this stage exists; the chapter says to ask the recruiter.
Chapter verdict: MUST-READ-FULL. This is the chapter the reader most needs to rehearse, and the method (sections 1-5) and the ten incidents are the material. Skip the Python code in section 6 unless you want to run the drill runner.

Hands-on to do:
1. `cd code/part20 && python3 ch26_incident_drill.py list` (expect ten lines, five `inference` and five `general`; checked on this machine, works).
2. Reproduce a deleted-but-open file: `head -c 5000000 /dev/zero > big.log; tail -f big.log > /dev/null &; rm big.log; lsof +L1 | grep big.log`, then `kill %1`. Read the `(deleted)` row. Do it on a Linux container too (`docker run --rm ubuntu:24.04 ...`), because the chapter's Linux output differs from macOS.
3. Run the `/proc` truncation on a tmpfs (step 7 in the chapter): `: > /proc/$PID/fd/3`, and watch `df` drop while `du` was already at zero.
4. Run `openssl req -x509 ... -days 1`, then `openssl x509 -checkend 86400` (exit 1) and `-checkend 0` (exit 0), so you can say what the exit code means.
5. Solo drill, time-boxed: `python3 ch26_incident_drill.py run dns-intermittent-failures --minutes 30`. Do incident 1 first, then the four incidents marked MUST in the table.

Likely interview questions from this chapter:
- "It is 14:05. The p99 time-to-first-token alert fired on the chat endpoint in eu-north. You are on call. Talk me through it."
- "Your rollout is stuck and the team wants to restart every replica. What do you do?"
- "Kubernetes says all pods are ready, but one customer sees timeouts. What do you check?"
- "The disk is full, but `du` adds up to much less than `df`. Why, and how do you fix it?"
- "Three layers each retry three times. How many requests reach the backend for one user request, and what do you do about it?"
- "You have an etcd member with slow fsync. What do you do, and what do you not do?"
