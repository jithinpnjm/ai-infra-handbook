# 1.18 CPU scheduling and cgroups v1 and v2
Words: ~13,200 | Read time: ~88 min | File: /Users/jithinpjoseph/Documents/GitHub/ai-infra-handbook/docs/part-01-linux/18-cpu-scheduling-and-cgroups-v1-and-v2.md

One-line purpose: Explains how the Linux scheduler places and prioritises runnable tasks, how to read CPU saturation and throttling, how cgroups v1 and v2 enforce weights, quotas and cpusets, and how Kubernetes, systemd, Docker and Slurm map onto them.
Beginner friendly: no. The chapter is marked Advanced and assumes 1.8 (processes, `nice`), 1.15 (systemd resource control) and 1.17 (memory). The opening symptoms and the "Observing CPUs" command list are the readable parts. Read 1.8 and 1.15 section 10 first.
Nebius rounds served: R1 (CPU triage: `top`, `mpstat`, load average, `%steal`, `nproc`), R2 (Kubernetes CPU throttling with low average use, `cpu.max`, QoS classes, cgroup driver mismatch, GPU device rules after `daemon-reload`), R3 (CPU isolation and placement design for GPU feeding), R4 (how you configured CPU limits on your own project)

Hands-on to do:
- `lscpu -e; cat /sys/devices/system/cpu/cpu0/topology/thread_siblings_list; mpstat -P ALL 1 5`. Identify the sockets, cores, SMT siblings and any CPU with high `%steal` or `%soft`.
- `stat -fc %T /sys/fs/cgroup/; cat /proc/self/cgroup`. Say whether the host runs v1 or v2, from the output.
- Build a cgroup by hand (lab steps 4 to 6): `mkdir`, enable `+cpu`, set `cpu.max` to `50000 100000`, run `stress-ng --cpu 4` in it, and read `cpu.stat` for `nr_throttled`.
- `docker run --rm --cpus 0.5 ubuntu bash -c 'cat /sys/fs/cgroup/cpu.max; nproc'` if Docker is available. Explain why `nproc` still shows the host's CPUs.
