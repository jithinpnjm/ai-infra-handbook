Two port directives in `/cm/local/apps/cmd/etc/cmd.conf` control how CMDaemon listens. `Port = 8080` is the non-SSL HTTP port, with a default of `8080`. By default it is used only during `init` / pre-init boot, and it is required when `bootloaderprotocol` is set to `HTTP`, the default, because most bootloaders do not support HTTPS. `SSLPort = 8081` is the SSL port, with a default of `8081`. CMDaemon writes many system files, and it owns them. A generated file carries the header "This file was automatically generated by cmd. Do not edit manually!" If a generated file has a hand edit and is not frozen, CMDaemon raises an event and saves your copy in `/var/spool/cmd/saved-config-files`. This one rule prevents many confusing "my change disappeared" tickets.

The second area is the Mellanox adapter settings, which you manage with `mlxconfig`. The `mlxconfig` command in `device` mode inspects and sets ConnectX adapter firmware parameters. Examples include `mlxconfig node001 --adapters`, `--interface ib0`, and `--pci-address 0000:03:00.0 --port 1`, with `--detail-level 1` for more detail. ---

A few helper commands cover nodes and DPUs. `nodeoverview` shows uptime, load, memory, WLM slots, and NIC and disk use. `minimalconfig` shows the exact category, overlays, head nodes and data producers applied to a node. `checkremotemount -n node001 /cm/shared` checks a remote mount, and it takes the options `--file`, `-f` and `--clear`. `proxysettings` and `selinuxsettings` are also available. ---

Overallocation is easy to miss. If a profile list asks for more than 7 GPU slices, BCM does not reject the whole string. Instead, the slices that come after the budget of 7 is used up are silently left unallocated. Take `5*1g.5gb,2g.10gb`. Five `1g` slices and one `2g` slice add up to 7, so everything fits. Now take `6*1g.5gb,2g.10gb`. The six `1g.5gb` instances use 6 slices, and the `2g.10gb` needs 2 more, which makes 6 + 2 = 8 in total. BCM allocates the six `1g.5gb` instances and none of the `2g.10gb` instance. The same thing happens with `7*1g.5gb,2g.10gb`, which allocates seven `1g.5gb` instances and no `2g.10gb`. It also happens with `70*1g.5gb,2g.10gb`, which allocates 7 `1g.5gb` instances and no `2g.10gb`.

## FILE docs/part-08-bcm/11-monitoring-health-checks-and-alerts-in-bcm.md

A **trigger** is a condition on a measurable. When the condition is met, the trigger launches **actions**. An action is either built in or a script, and a script counts as successful when it exits 0. **Severity** and **AlertLevel** tell you how bad things are, and the next section covers both.

---

A trigger watches one measurable. The **zone** is the region where its condition is true. For example, the zone for `CPUUser > 50` is every sample above 50. The manual defines four launch options, and each one answers a different question about the zone:

---

The Event Bucket at `/var/spool/cmd/eventbucket` turns a line into a BCM event, and the default severity is `info`. Add a prefix to choose the severity: `EVENT_SEVERITY_DEBUG:`, `EVENT_SEVERITY_INFO:`, `EVENT_SEVERITY_NOTICE:`, `EVENT_SEVERITY_WARNING:`, `EVENT_SEVERITY_ERROR:` or `EVENT_SEVERITY_ALERT:`. Regex filters live in `/cm/local/apps/cmd/etc/eventbucket.filter`, and the `EventBucket` and `EventBucketFilter` directives in `cmd.conf` control them.

---

1. **Write the health check script to return `PASS`, `FAIL [severity]`, or `UNKNOWN` plus fd 3 `InfoMessage`:**
   A standalone health check script lives in `/cm/local/apps/cmd/scripts/healthchecks/`, both on the head node and inside the software image. It must follow a strict output contract. Print `PASS`, `FAIL`, or `UNKNOWN` to standard output (`fd 1`). `FAIL` may carry a custom severity integer, such as `FAIL 40`, which overrides the default 15. `UNKNOWN` defaults to severity 10. You can also write a short reason to file descriptor 3 (`>&3`). CMDaemon captures it as the check's `InfoMessage`, as in `echo "Scratch mount /scratch is read-only" >&3`, and substitutes it into `{infomessage}` in administrator alert emails.
2. **Register the measurable and tune its data producer (`Fuzzy offset` and `prejob`):**
   In `cmsh`, open `monitoring setup`. Add the health check script, limit it to the right node categories with `nodeexecutionfilters`, and set a sampling interval of 120 s. Add a `Fuzzy offset` of 0.25, so that a thousand nodes spread their runs across a thirty-second window instead of spiking at once. If the check verifies something a training job needs, such as an InfiniBand port in `ACTIVE` state or a responsive parallel scratch mount, set `prejob yes` on the check. Also set `enableprejob yes` on the Slurm WLM instance. BCM then runs the check just before it allocates any job to the node, which prevents **Black Hole Node Syndrome**.
3. **Wire the trigger (`Enter` vs `During` vs `State flapping`) and validate before committing:**
   Create a trigger that watches the new measurable. Use an **`Enter`** action when you want something like `Drain` plus `Send e-mail to administrators` to fire once, at the moment the check moves from `PASS` to `FAIL`. Suppose you also want a **`State flapping`** action (5 crossings in 300 s) to catch an intermittently bouncing optical link. Then you must shorten the data producer's sampling interval, to 15 s or 30 s. A 120 s sampler can never cross a threshold five times inside a five-minute window. Finally, run `validate` before `commit`. It checks that your measurable regex matches a real measurable and that at least one action is attached.

## FILE docs/part-08-bcm/12-high-availability-and-head-node-failover.md

1. The passive head enters fencing mode. It records what it does as a backlog, so the two heads can compare and sync that backlog if they reconnect before any failover happens.
2. It needs proof that the active head is off. That proof comes either from an administrator's manual confirmation or from STONITH, which stands for "shoot the other node in the head". With STONITH, the passive head powers the active head off through its BMC or PDU, then checks that the power is really off.
3. It needs a quorum first. The passive head asks all nodes whether they also cannot reach the active head. It proceeds only if more than half of them confirm. This stops a passive head with its own network fault from powering off a healthy active head. Nodes that do not answer within Quorum time are not counted. The manual leaves open whether "half" means half of the responders or half of all nodes. The lab defaults to responders and can use the total instead.
4. Once the active head is proven off, the fencing head becomes active.

---

Once the pair is running, most of your time goes to checking its state and tuning its timers. A head can be in one of several states, and `cmha status` shows the current one. The same state appears in the login banner and in `/var/spool/cmd/state`. The states are `INIT`, `FENCING`, `ACTIVE`, `PASSIVE`, `BECOMEACTIVE`, `BECOMEPASSIVE`, `UNABLETOBECOMEACTIVE` and `ERROR`. If a mount script misbehaves, look in `/var/log/cmdaemon`. Then run `cmha makeactive` to tell a head to try again.

---

The first row explains the order. The active head goes first, and the passive head follows only after `cmha status` looks healthy. The migrating-services row reverses the pattern on purpose. You update the passive head, move the active role to it, and then update the former active head. Problems show up while you can still inspect the old head.

---

When you switch the active regular node with `makeactive`, the active head node runs one fixed sequence, and you can follow it step by step. In step 1, every group node runs the `Prefailover script`. In step 2, the old active node stops its service and runs the `Unmount script`. If that script exits with anything above 0, all the remaining actions are skipped. If STONITH powers off the old active, the old-active sequence aborts. Otherwise the old active stops the active IP, starts the passive IP and starts its passive services. In step 3, the new active node stops its service, runs the `Mount script`, stops the passive IP, starts the active IP and starts its service. In step 4, every group node runs the `Postfailover script`.

## FILE docs/part-11-gpu-kubernetes/22-sr-iov-for-nics-and-gpus.md

Platform teams need both bare-metal passthrough speed and hardware sharing on the same physical card. The PCIe specification handles this trade-off with Single-Root I/O Virtualization, known as SR-IOV. One SR-IOV card can present dozens of independent, hardware-sliced Virtual Functions on the PCIe bus, and each one can be handed to a different tenant.

---

1. **SR-IOV without an IOMMU is a direct memory access backdoor.** Slicing a network card into Virtual Functions does not restrict which host physical RAM addresses those Virtual Functions can read. The motherboard IOMMU must stay active to enforce per-VF DMA Remapping tables.
2. **SR-IOV makes guest traffic invisible to standard host monitoring tools.** Because SR-IOV Virtual Functions talk straight to PCIe hardware rings, host OS block and network tools no longer see the traffic.

A renewal cycle takes the cluster's update lock, then runs a health gate before and after each node. The gate requires stable membership, ready nodes, reachable agents, enough etcd voters and healthy static pods. A failed cycle can keep the lock, and then upgrades and node changes return 409 until you follow the ownership-checked recovery procedure. Exactly two control plane nodes are excluded from automatic renewal **[source-code]**.

NVKE observes actual certificate expiry dates independently of renewal, through the node agent, and exports them as metrics. The controller chart ships a Prometheus rule file with alerts such as `NVKECertificateExpiring`, `NVKECertificateRenewalFailed`, `NVKECertificateRenewalStuck`, `NVKEKubeletServingCSRFailed` and `NVKEEtcdKeyRotationStuck` **[source-code]**. Install them. They are the earliest warning that a tenant's cluster will stop working in a month.

Someone asks the question every operations review asks. What is the recovery plan if the management cluster's disks are lost? The answer is short and unpleasant. NVKE provides no procedure to back up or restore the management cluster or its state, and no procedure to move the management plane to a later NVKE release **[official]**. The management cluster does not manage itself. The roadmap lists backup and restore of workload clusters and the management plane, and a supported management plane upgrade path, as items being explored, with management cluster self-management as coming soon **[official, roadmap]**.
