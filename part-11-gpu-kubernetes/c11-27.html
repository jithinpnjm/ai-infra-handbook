Why this matters for AI infrastructure​

Chapter 11.24 showed how Multi-Instance GPU, or MIG, isolates GPU compute, HBM memory capacity, L2 cache banks, memory controllers and crossbar paths in silicon. That raises a direct question for AI platform engineers. Why run Virtual Machines with KubeVirt, or MicroVMs with Kata Containers, inside a Kubernetes cluster when hardware MIG already exists? Two hard security and operational problems answer that question. Both come from the GPU sharing and confidential computing threat models. A threat model is the written list of who might attack a system and how they would do it.

The first problem is that standard Linux containers still share one host OS kernel, even with MIG enabled. The kernel is the core of the operating system, and every container on the node makes its system calls into it. The isolation tiers compare in plain terms. Time-Slicing is a hostel room, MIG is a set of concrete-walled hotel suites, and vGPU or VM virtualization is a VIP penthouse guarded by a hypervisor. All seven MIG containers on a bare-metal worker node still make syscalls to the same host Linux kernel. A syscall is the request a program makes to the kernel for a service, such as opening a file. Picture a hostile tenant in MIG Instance 0 who exploits a Linux kernel vulnerability to escape the container and gain host root. That tenant can then run nvidia-smi mig on the host, destroy sibling partitions and inspect host memory. The walls of the hotel suites do not help, because the tenant went through the floor.

The second problem is Data in Use. Disk encryption protects Data at Rest, and network encryption protects Data in Transit. Neither one protects proprietary LLM weights or classified user prompts while they sit decrypted in system RAM and GPU VRAM during inference. The model weights are the learned numbers that make the model work, and a prompt is what a user types in. Protecting Data in Use against an untrusted cloud hypervisor takes a hardware-encrypted Confidential Virtual Machine. That VM pairs a CPU Trusted Execution Environment, such as AMD SEV-SNP or Intel TDX, with NVIDIA Hopper H100 Confidential Computing and Remote Attestation. A Trusted Execution Environment, or TEE, is a protected region of the CPU that the host software cannot read.

Kubernetes can now schedule standard OCI containers and hardware-isolated Virtual Machines on the same cluster. OCI stands for Open Container Initiative, the set of industry specifications for container images and runtimes. Platform teams use two complementary architectures to get that isolation. Each one keeps the Kubernetes API and adds a different kind of boundary underneath it.

Kata Containers runs standard OCI container images inside a dedicated, fast-booting MicroVM. A MicroVM is a very small virtual machine with a minimal guest kernel. Kata uses QEMU, Cloud Hypervisor, or AWS Firecracker through the containerd v2 shim API. The shim is the small process that containerd starts to manage each runtime, so Kata looks like a normal container to Kubernetes.

KubeVirt runs full, persistent Linux or Windows Virtual Machines inside a launcher Pod. A launcher Pod is the ordinary Kubernetes Pod that holds one virtual machine's process. It integrates with the NVIDIA GPU Operator sandboxed workload operands for VFIO passthrough and vGPU attachment. VFIO is the Linux framework that hands a physical device to a virtual machine safely.

Before you pick a runtime for a tenant, decide whether a host-kernel escape belongs in your threat model. If it does, a shared kernel is not enough, and you need one of the VM-based options. If it does not, standard containers with MIG may be the simpler and cheaper answer. That one question sets the rest of the design.

Concepts: basics to intermediate to advanced​

1. Basics: From OCI/CRI containers to Kata MicroVMs and KubeVirt VMs​

1. How kubelet, CRI, and OCI Launch Workloads​

When a Pod fails to start on a GPU node, you need to know which layer between the kubelet and the Linux kernel broke. As Josh Rosso et al. explain in Production Kubernetes Chapter 3, Kubernetes hands container creation to a pluggable runtime. That runtime works to two industry standards, the Open Container Initiative and the Container Runtime Interface. Think of the kubelet as a manager that asks a worker to do the job, and the runtime as the worker that does it.

The Open Container Initiative defines three core specifications, and each one covers a different job. The OCI Runtime Specification defines the filesystem bundle, the config.json mounts, the process arguments and the environment variables. A bundle is the folder that holds a container's root filesystem and its configuration. It also defines four strict container lifecycle stages, which runc implements. runc is the low-level tool that actually creates and starts containers on Linux.

The OCI Image Specification defines how a multiplatform image index points to an architecture-specific image manifest. An image index is a list of platform choices, so one name can serve several CPU types. Each manifest holds a configuration document and content-addressable tar+gzip filesystem layers. Content-addressable means each layer is named by a hash of its contents, so an identical layer is stored once. The OCI Distribution Specification standardizes the HTTP API that container registries use to push and pull OCI image manifests and blobs.

The Container Runtime Interface is a gRPC and Protocol Buffers API. gRPC is a remote procedure call system, and Protocol Buffers is the binary format its messages use. The interface exposes two services, RuntimeService and ImageService, over a local Unix domain socket. A socket here is a file path that two local programs use to talk to each other. When kubelet starts a Pod on a worker node, it invokes five CRI gRPC methods in exact sequential order. Use the table below as a lookup. 5-Step Remote Attestation Sequence:
Step 1: Confidential VM boots and requests a cryptographic attestation quote from the CPU TEE and NVIDIA H100 GPU.
Step 2: Hardware generates a signed attestation report containing exact firmware hashes, boot state measurements, and proof that Confidential Computing mode is active.
Step 3: The chip signs this quote using an unextractable private key fused into the silicon during manufacturing.
Step 4: The enterprise Key Management Server (KMS) validates the quote against an independent Attestation Service (NVIDIA Remote Attestation Service).
Step 5: Only if the cryptographic signature and measurements pass verification does the enterprise KMS transmit decryption keys into the enclave to unlock the encrypted model weights.

If you design for classified or proprietary models, plan for all three mechanisms and for attestation together. If you design for classified or proprietary models, plan for all three mechanisms and for attestation together. Leaving any one of them out leaves a gap that an attacker or an administrator can use. A design review should show each mechanism on its own line, with the evidence that it is active.

Checkpoint questions​

Consider these questions as a way to check the ideas above. Work through each one before you open its answer.

1. What are the three specifications defined by the Open Container Initiative, and what are the four lifecycle stages of a container in the OCI Runtime Specification?
  • Three OCI specifications: The OCI Runtime Specification, which runc implements, the OCI Image Specification and the OCI Distribution Specification.
  • Four OCI container lifecycle stages: A container moves in order through creating, created, running and stopped.
2. What two gRPC services make up the Kubernetes Container Runtime Interface, and what five CRI methods does kubelet call in order to start a Pod?
  • Two CRI gRPC services: RuntimeService handles Pod and container lifecycle operations. ImageService handles listing, pulling and removing images.
  • Five CRI startup methods in order: If you start a Pod, the kubelet calls RunPodSandbox, then ImageStatus, then PullImage when the image is missing locally, then CreateContainer, and finally StartContainer.
3. Contrast the Unix domain socket paths, process monitors, and containerd namespaces of Docker dockershim, containerd, and CRI-O.
  • containerd: It listens on /run/containerd/containerd.sock, spawns a containerd shim per Pod, and stores Kubernetes containers in the k8s.io namespace.
  • Docker dockershim: It used /var/run/dockershim.sock, encoded Pod metadata into container names, and stored containers in the containerd moby namespace.
  • CRI-O: It listens on /var/run/crio/crio.sock and spawns conmon as the parent container monitor process, which you inspect via crictl.
4. How does Kata Containers integrate with Kubernetes and containerd when Kata does not implement the CRI directly?

If you use Kata, note that it does not speak CRI itself. It plugs into containerd through the v2 runtime shim API, using containerd-shim-kata-v2. The kubelet still talks standard CRI gRPC to containerd. When a Pod specifies runtimeClassName: kata-containers, containerd calls the Kata shim, which boots a lightweight guest-kernel VM for that Pod.

5. What is the architectural difference between Kata Containers and KubeVirt on Kubernetes?
  • Kata Containers is a CRI runtime shim, selected through RuntimeClass, that wraps a standard OCI Pod inside a lightweight Linux MicroVM. It does not change the Kubernetes Pod or Deployment API.
  • KubeVirt is a full Virtual Machine management add-on. It adds VirtualMachine and VirtualMachineInstance custom resources, and it runs persistent Linux or Windows guest OS images with full disk, network and live-migration lifecycles.
6. How do the four KubeVirt components work together to boot a GPU VirtualMachine on a Kubernetes node?
  • virt-api: Validates and serves the KubeVirt VirtualMachine and VirtualMachineInstance custom resources.
  • virt-controller: Watches VirtualMachineInstance objects and creates a matching virt-launcher Pod that requests the required CPU, RAM and GPU extended resources.
  • virt-handler: Runs as a DaemonSet on every node and coordinates node-level device initialization with the launcher Pod.
  • virt-launcher: Runs libvirtd and qemu-kvm inside the Pod cgroup, boots the guest OS and attaches the passed-through GPU or vGPU.
7. What happens on a worker node when you enable sandboxed workloads in the NVIDIA GPU Operator ClusterPolicy and label the node for VM passthrough?

When you enable that label, the GPU Operator stops the standard container driver DaemonSet on that node and deploys two VM operands instead.

  • nvidia-vfio-manager: Unbinds the physical GPUs and their IOMMU group siblings from host drivers, then binds them to vfio-pci.
  • nvidia-kubevirt-gpu-device-plugin: Discovers the VFIO-bound GPUs and advertises them to the scheduler for KubeVirt VirtualMachine manifests.
8. How does a node labeled for VM vGPU differ from VM passthrough under the NVIDIA GPU Operator?

If you label a node vm-vgpu, the GPU Operator deploys nvidia-vgpu-manager and the vGPU device plugin, which slice each physical GPU into multiple vGPU profiles. Several KubeVirt VMs can then share one physical GPU. Under vm-passthrough, the operator binds the entire physical GPU to vfio-pci for whole-GPU assignment to a single VM.

9. Compare Time-Slicing, MIG, and vGPU or VM Virtualization across memory isolation and host-kernel risk.
  • Time-Slicing: It gives zero hardware memory or compute isolation, because all containers share one VRAM pool and L2 cache.
  • MIG: It gives each instance hardware-isolated crossbar ports, L2 cache banks, memory controllers and DRAM address buses. All MIG containers still share the same Host OS kernel.
  • vGPU or VM Virtualization: It adds a hardware hypervisor and a dedicated guest OS kernel per tenant, so an attacker would need a full hypervisor VM escape to compromise the host.
10. Why is MIG secure against GPU-level attacks, but still vulnerable to OS-level container escapes?

Every MIG partition on a bare-metal container host is managed by the same shared Linux host kernel. If a malicious tenant exploits a Linux kernel vulnerability inside their container to gain host root privileges, they can run nvidia-smi mig on the host. From there they can destroy or reconfigure sibling MIG partitions and inspect host memory.

11. In the university customer scenario, why was running HIPAA medical research in a separate Kubernetes Namespace on a time-sliced HGX H100 cluster a severe compliance violation, and how did the architect fix it?

Kubernetes Namespaces only isolate Kubernetes API objects in etcd. Under software time-slicing they give no hardware isolation on the shared GPU VRAM pool. The architect quarantined a dedicated HGX H100 server, disabled time-slicing and formatted the H100 GPUs with hardware MIG. They also applied Kubernetes Node Taints, so student coursework pods could never schedule onto the HIPAA medical nodes.

12. Define Data at Rest, Data in Transit, and Data in Use encryption, and explain why traditional cloud VMs fail to protect Data in Use.
  • Data at Rest: Encrypts files stored on disk or SSD using AES-256.
  • Data in Transit: Encrypts packets moving across the network using TLS or IPSec.
  • Data in Use: Protects data while it is actively loaded into CPU RAM and GPU VRAM during computation.

If you run an LLM in a traditional cloud VM, the weights and prompts must be decrypted into plaintext RAM and VRAM to run matrix math. A rogue cloud administrator with hypervisor root access, or a PCIe bus analyzer, can dump that plaintext memory.

13. What two hardware components must be paired to create a Confidential AI Virtual Machine, and can an NVIDIA H100 GPU provide Confidential Computing without a CPU TEE?

You must pair a CPU Trusted Execution Environment, specifically AMD SEV-SNP or Intel TDX, with an NVIDIA Hopper H100 GPU in Confidential Computing mode. The GPU alone does not make a VM confidential. The CPU side needs an AMD SEV-SNP or Intel TDX TEE to encrypt system RAM.

14. How does NVIDIA Hopper H100 Confidential Computing protect GPU VRAM and CPU-to-GPU PCIe transfers against a compromised host hypervisor or PCIe logic analyzer?
  • Protected GPU Memory: H100 VRAM sits inside a hardware-protected region that the host OS and hypervisor are blocked from reading.
  • Encrypted PCIe Bounce Buffers: All data sent between the Confidential VM CPU TEE and the H100 GPU over the PCIe bus is encrypted through bounce buffers. The cryptographic keys are negotiated directly between the CPU TEE and the GPU hardware Root of Trust.
15. Walk through the five steps of the Cryptographic Remote Attestation Protocol.
  • Step 1: The Confidential VM boots and requests a cryptographic quote from the CPU TEE and the NVIDIA GPU hardware.
  • Step 2: The hardware generates a cryptographic document with exact firmware hashes, boot state measurements and proof that the Secure Enclave is active.
  • Step 3: The hardware signs this document with an unextractable private key fused into the silicon during manufacturing.
  • Step 4: The enterprise Key Management Server sends the quote to an independent Attestation Service, which verifies the silicon signature and measurements.
  • Step 5: Only after the signature is mathematically verified does the KMS transmit the decryption keys into the enclave to unlock the model weights.
16. In the military customer scenario, why did the military compliance officer reject encrypting only the cloud VM hard drives for a classified drone-footage AI model, and what architecture satisfied the requirement?

For example, hard drive encryption only protects Data at Rest. Once the model loads into RAM and VRAM as Data in Use, a rogue cloud administrator with hypervisor root access can dump the VM memory. The approved architecture ran a Confidential VM on AMD SEV-SNP or Intel TDX, paired with NVIDIA Hopper H100 Confidential Computing. It also required Remote Attestation from the enterprise on-premises KMS before releasing model decryption keys.

17. In Production Kubernetes Chapter 3, what arguments were passed to qemu-system-x86_64 when launching a Pod with Kata Containers?

The host process table showed /snap/kata-containers/690/usr/bin/qemu-system-x86_64 -name sandbox-c136a9... -uuid aaae32b3-... -machine pc,accel=kvm,kernel_irqchip -cpu host -m 2048M,slots=10,maxmem=65005M. When you read those flags, they configure hardware KVM acceleration, host CPU passthrough, and initial memory with hotplug slots.

18. How does an OCI Image Index enable multiplatform container images in Production Kubernetes Chapter 3?

An OCI Image Index is a top-level manifest with a manifests[] array. Each entry points to a platform-specific image manifest digest, annotated with its CPU architecture and operating system. That lets containerd select the manifest that matches the worker node's CPU architecture during image pulls.

19. What is Virtual Kubelet in Production Kubernetes Chapter 3, and how does it differ from a CRI container runtime like containerd or Kata Containers?

Virtual Kubelet is not a node-level CRI runtime. It is a software component that registers with the Kubernetes API server as a virtual Node. It translates Pod creations into API calls to external serverless backends, such as AWS Fargate, Azure Container Instances or HashiCorp Nomad.

20. When should an AI platform architect choose Standard Containers with MIG, Kata Containers with VFIO or MIG, KubeVirt with vGPU or VFIO, or Confidential VMs?
  • Standard Containers with MIG: Best for internal enterprise multi-tenancy where tenants are not attempting host-kernel escapes and host administrators are trusted.
  • Kata Containers with VFIO or MIG: Best for cloud-native teams that want standard Pod workflows with a dedicated guest Linux kernel per Pod, to block host-kernel escapes.
  • KubeVirt with vGPU or VFIO: Best for workloads that need persistent Virtual Machine lifecycles, Windows guest OS support or regulated VM boundaries alongside containers.
  • Confidential VMs: Required for classified or proprietary models on an untrusted public cloud, where Data in Use across RAM, VRAM and PCIe must stay encrypted.
