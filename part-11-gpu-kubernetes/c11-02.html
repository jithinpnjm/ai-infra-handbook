Why this matters for AI infrastructure​

Picture an application engineer who submits a training Pod. The Pod requests a single GPU, on a cluster where every node reports eight allocatable GPUs. The scheduler binds the Pod at once, and the container starts running. Everything looks right in the dashboard. Seconds later, PyTorch crashes with CUDA_ERROR_NO_DEVICE, because /etc/containerd/config.toml lost its NVIDIA runtime handler during an OS image update. The scheduler did its job, and the container runtime quietly lost the piece that gives the container a GPU.

That story is the core of this chapter. Scheduling a GPU in Kubernetes is not the same operation as giving a Linux container process a usable GPU. Three distinct software contracts stand between a Pod manifest and a working CUDA context. A CUDA context is the state that CUDA creates before any kernel can run on a GPU. Each contract runs across a different infrastructure boundary, and each one can fail on its own. Confusing those boundaries is the single largest source of wasted incident-response hours on Kubernetes GPU platforms, because people fix the layer that looks guilty instead of the layer that actually broke.

The first contract sits on the inventory and scheduling boundary. The NVIDIA Device Plugin queries the host driver through the NVIDIA Management Library. It opens a gRPC stream to the local kubelet and advertises healthy devices as the extended resource nvidia.com/gpu. Only after kubelet patches the Node status object in the API server can kube-scheduler bind a GPU Pod to that machine. Think of this contract as the list of parking spaces the node claims to have. It says how many spaces exist and whether they are usable, but it does not say which car sits in which space.

The second contract sits on the device allocation boundary. Binding a Pod to a node only reserves an integer count in control-plane accounting. Before the container starts, kubelet calls the device plugin's allocation gRPC method to select specific physical GPU UUIDs. That call returns the exact device paths, environment variables, or Container Device Interface annotations the container runtime needs. A UUID is the unique identifier of one physical GPU card, and the Container Device Interface, or CDI, is a standard file format that describes how to attach a device to a container. This is the step that turns "one of the eight" into "this particular card."

The third contract sits on the sandbox construction boundary. Standard Linux containers isolate filesystems and device access through kernel namespaces and control groups. By default, a container cannot see host character devices such as /dev/nvidia0, or the host user-mode driver library. So at container creation, containerd or CRI-O must invoke the NVIDIA Container Toolkit or apply a Container Device Interface specification. That step bind-mounts the allocated devices and driver libraries into the sandbox. A bind mount makes a file or device on the host appear at a path inside the container, without copying it.

Before you change anything, decide which of these three boundaries the failure sits on. A missing allocatable count points at the first contract. A Pod that binds and then cannot open a device points at the second or third. Knowing which contract failed tells you which logs and which node files to read first.

Prerequisites and outcomes​

Prerequisites​

You should already know the GPU readiness dependency chain from Chapter 11.1. That chain runs through PCIe, the host driver, the container runtime, the device plugin, node labels, the scheduler, and workload validation. PCIe is the bus that connects the GPU to the motherboard. You also need working knowledge of Linux character devices, shared-library dynamic linking with LD_LIBRARY_PATH, and Kubernetes Pod resource requests and limits. A character device is a file under /dev that a program reads and writes as a stream of bytes. The dynamic linker is the part of Linux that loads shared libraries when a program starts, and LD_LIBRARY_PATH is the environment variable that tells it where to look first.

Concepts: basics to intermediate to advanced​

1. Basics: The host kernel/user-space split and Linux container isolation​

When a GPU container fails to initialize CUDA, engineers often rebuild the application image. It feels like the natural move, because the error appears inside the container. In many cases, though, the real fault sits in the host kernel driver or in the character device nodes, and a new image will fail the same way. Before any container runtime or device plugin can expose a GPU, the Linux host must drive the physical hardware. The NVIDIA UNIX driver stack divides that work between two privilege domains: the Kernel-Mode Driver and the User-Mode Driver. The first runs inside the kernel with full hardware access. The second runs as an ordinary library in user space, where normal programs live.

The split matters because each side fails in its own way. A kernel problem stops every program on the host from touching the GPU, and it usually shows up as a missing module or a message in the kernel log. A user-space problem affects only the programs that load a particular library, and it usually shows up as a version error when CUDA starts. Learning to tell the two apart is the first step in any GPU incident.

The Kernel-Mode Driver and character devices​

The Kernel-Mode Driver is a set of loadable kernel modules, compiled against the exact running host kernel. These modules talk to the GPU directly over the PCIe bus. They manage initialization, memory tables, interrupts, and DMA mappings. DMA, or direct memory access, lets the card move data to and from memory without the CPU copying each byte. If you find any required kernel module or character node missing, every call to cuInit(0) or cudaMalloc() fails immediately. Those two calls are the first things CUDA does, so a missing module blocks the whole program before any real work starts.

If a container has the first two but not the third, you can expect CUDA to fail at startup even though the GPU is visible.

The User-Mode Driver vs the CUDA Runtime​

Two distinct sets of shared libraries sit above the character-device boundary. Mixing up the host user-mode driver with the container CUDA runtime leads to version mismatch errors. Those errors break container startup across the whole fleet. The mix-up is easy to make, because both are called "CUDA" in everyday talk, and both show up in the same error messages.

The User-Mode Driver includes libcuda.so.1 and libnvidia-ml.so.1. Both ship as part of the host NVIDIA driver package. The library implements the low-level CUDA Driver API, and it talks to the kernel module through a private, version-locked system-call ABI. ABI stands for application binary interface, the exact low-level contract that two pieces of compiled code agree on. Because it must match the exact version of the kernel module loaded in the host kernel, the host owns it and bind-mounts it into containers at runtime. The container never carries its own copy of this library.

The CUDA Runtime and Toolkit libraries, including libcudart.so, libcublas.so, and libnccl.so, ship inside the application container image. PyTorch links against the CUDA Runtime, which turns high-level runtime calls into Driver API calls. The host-injected user-mode driver handles those calls. Keeping the kernel module and user-mode driver on the host means you can patch a driver defect across a 500-node fleet once, without rebuilding hundreds of tenant images. That split is what makes GPU fleets manageable. Teams can update the host driver on its own schedule, and the application images stay the same.

The example below shows what a version mismatch looks like in practice.

Version-Locked Kernel vs. User-Mode ABI Mismatch Example (volume-04):
- Host kernel module (nvidia.ko) version: 525.105.17 (or 535.154.05 on upgraded fleet)
- Mismatched user-mode client (libcuda.so.1) version: 535.104.05
- Exact kernel log error:
  NVRM: API mismatch: the client has the version 535.104.05, but this kernel module has the version 525.105.17

The last line is the message to look for. It names both versions, so the gap is visible at a glance. When you see this line in dmesg, the fix is on the host. The container image does not need a rebuild.

CUDA Forward Compatibility​

Here is a common bottleneck. A research team wants a container built on a newer CUDA Toolkit, such as CUDA 12.2. Meanwhile, the production fleet kernel driver is pinned to an older enterprise branch, such as Driver 525.105.17 from CUDA 12.0. Unloading the kernel module across 500 production nodes would mean draining every GPU Pod or rebooting the hosts. Neither choice is cheap, so the team needs another way for the new image to run on the old driver.

NVIDIA solves this across supported major and minor version boundaries with CUDA Forward Compatibility. A forward-compatible container image packages a newer user-mode driver bundle inside /usr/local/cuda/compat/. That bundle includes the forward-compatible libcuda.so.535.104.05, the NVVM compiler library, and the PTX JIT compiler library. PTX is NVIDIA's portable intermediate code, and a JIT compiler turns it into machine code for the GPU at run time.

The trick works through the dynamic linker. When the container entrypoint prepends /usr/local/cuda/compat to LD_LIBRARY_PATH, the Linux dynamic linker resolves the newer compat library before the older host-mounted one. That newer user-mode library translates CUDA 12.2 runtime calls down to the older 525 kernel-mode driver ABI. If the version gap exceeds the supported compatibility matrix, the user-mode driver returns an initialization error, and the workload exits cleanly. A clean exit is better than a silent wrong answer, because it tells you the gap is too wide.

# Inside container entrypoint to activate CUDA Forward Compatibility (untested here)
export LD_LIBRARY_PATH=/usr/local/cuda/compat:$LD_LIBRARY_PATH

Before you blame the application image, check the host kernel driver, the device nodes, and the driver versions. Forward Compatibility is a bridge across a version gap, and it is not a repair for a missing kernel module. A container that uses the compat path on a host with no loaded driver will still fail.

2. Intermediate: Evolution of GPU containerization — Toolkit, RuntimeClass, and CDI​

Standard Linux containers use kernel namespaces to isolate filesystem mounts, process trees, and network stacks. They use control groups to meter CPU and RAM. When containerd starts a standard container through runc, the container gets a private temporary device filesystem. runc is the low-level tool that actually creates a container from its specification. That filesystem holds only safe pseudo-devices, such as /dev/null and /dev/zero. Without special runtime injection, the container has neither /dev/nvidia0 nor the host user-mode driver library. The isolation is working as designed, and the GPU stack has to punch a controlled hole through it.

The intermediate question is how that hole gets punched. The answer has changed several times, and the history explains why today's clusters contain several overlapping settings.

The four generations of NVIDIA container integration​

Over the past decade, the mechanism that injects GPU device nodes and host driver libraries into a container went through four architectural generations. Knowing these four stages explains why legacy environment variables still coexist with modern Container Device Interface YAML files. Old settings tend to stay in clusters long after the tool that needed them is gone, so when you read a node, you may see parts of more than one generation.

  1. Generation 1 (nvidia-docker) was a standalone CLI wrapper around the Docker daemon. It queried the host driver and passed --device=/dev/nvidia0 and volume-mount flags on the command line. That approach was brittle, because every run needed the right flags typed in exactly, and it did not work with Kubernetes CRI runtimes. CRI, the Container Runtime Interface, is the API that kubelet uses to talk to containerd or CRI-O.
  2. Generation 2 (nvidia-docker2) replaced the Docker runtime with a custom one, tied specifically to the Docker daemon architecture. This removed the need for wrapper flags, but it still depended on Docker, which Kubernetes stopped using as its runtime.
  3. Generation 3 (NVIDIA Container Toolkit with OCI pre-start hooks) arrived as Kubernetes standardized on containerd and CRI-O and removed dockershim. The NVIDIA runtime became a thin wrapper around runc. When a container starts with NVIDIA_VISIBLE_DEVICES set, an OCI pre-start hook calls nvidia-container-cli. An OCI hook is a program that the runtime runs at a fixed point in the container's startup, and this one runs before the process starts. That hook bind-mounts the device nodes and host driver libraries into the container namespace.
  4. Generation 4 (CDI, the Container Device Interface) is the modern CNCF-standardized specification. It replaces custom OCI hook wrappers with a declarative file at /var/run/cdi/nvidia.yaml or /etc/cdi/nvidia.yaml. When containerd with enable_cdi = true receives a request for a qualified device name such as nvidia.com/gpu=0, it parses the CDI specification directly. It then attaches the character nodes and read-only library mounts. A declarative file is easier to review than a hook, because you can read exactly what will be mounted before any container starts.

Inside a generated CDI specification​

On a GPU worker node, nvidia-ctk inspects the loaded driver and the hardware topology. It then generates the CDI specification on the fly. The command below is the one that writes the file, and it needs root because it writes into a system directory.

# Generate CDI specification on a GPU worker node (untested here)
sudo nvidia-ctk cdi generate --output=/var/run/cdi/nvidia.yaml

When you open /var/run/cdi/nvidia.yaml, you see the exact container edits applied when a container requests nvidia.com/gpu=0. Every host binary and shared library is bind-mounted with [ro, nosuid, nodev, bind], so a compromised container process cannot overwrite /usr/bin/nvidia-smi or the user-mode driver on the worker host. The options mean read-only, no setuid programs, no device nodes, and a plain bind. Each of those choices removes a way for a container to change the host.

# /var/run/cdi/nvidia.yaml (illustrative, abbreviated)
cdiVersion: 0.5.0
kind: nvidia.com/gpu
devices:
  - name: "0"
    containerEdits:
      deviceNodes:
        - path: /dev/nvidia0
          type: c
          major: 195
          minor: 0
        - path: /dev/nvidiactl
          type: c
          major: 195
          minor: 255
        - path: /dev/nvidia-uvm
          type: c
          major: 238
          minor: 0

        - hostPath: /usr/lib/x86_64-linux-gnu/libcuda.so.1
          containerPath: /usr/lib/x86_64-linux-gnu/libcuda.so.1

Read the file from top to bottom. The deviceNodes block says which character devices to create inside the container, and the mounts block says which host files to bind in. The file is a plan, and the runtime carries it out when a container asks for that device.

Three mechanisms, three distinct questions​

Platform engineers, and interview candidates, regularly conflate the NVIDIA Container Toolkit, Kubernetes RuntimeClass, and CDI. Each mechanism works at a different architectural scope, and each answers a different question. The mix-up usually happens because all three appear in the same GPU setup guide, and they all seem to "turn on the GPU." The table sets them side by side, so you can see which question each one answers.

MechanismQuestion It AnswersArchitectural ScopeWhat It Does NOT Do

A RuntimeClass object is only a pointer. It names a handler, such as handler: nvidia, and that handler must already exist in each eligible node's /etc/containerd/config.toml. Suppose a Pod sets runtimeClassName: nvidia and lands on a node where nobody wrote the nvidia handler stanza. The Pod fails at sandbox creation, before the container image entrypoint ever runs. The entrypoint is the first command the image runs, so a failure before it means the image never got a chance to act.

      [plugins."io.containerd.grpc.v1.cri".containerd.runtimes]
        [plugins."io.containerd.grpc.v1.cri".containerd.runtimes.runc]

        [plugins."io.containerd.grpc.v1.cri".containerd.runtimes.nvidia]

          [plugins."io.containerd.grpc.v1.cri".containerd.runtimes.nvidia.options]
            BinaryName = "/usr/bin/nvidia-container-runtime"

When a Pod fails at sandbox creation, check the containerd handler stanza before you look at the image. The stanza is the part of the file that names the handler, and a missing or misspelled name is a common cause of this failure.

3. Advanced: The Kubernetes Device Plugin gRPC contract and resource model​

Once the host kernel driver and container runtime are configured on a worker node, the Kubernetes control plane still has no idea that the machine owns eight healthy GPUs. Until a device plugin advertises those devices to kubelet, kube-scheduler leaves every GPU Pod stuck in Pending. This is the same gap that Chapter 11.1 describes, seen here from the plugin's side.

Kubernetes closes this gap through the Device Plugin Framework under k8s.io/kubelet/pkg/apis/deviceplugin/v1beta1. Every major AI accelerator vendor implements the same four-function gRPC contract. That contract covers device discovery, resource allocation, health monitoring, and scheduler integration. Because every vendor uses the same contract, kubelet does not need to know anything special about NVIDIA, AMD or Google hardware. It only needs the plugin to speak the contract.

The Kubelet gRPC handshake: Register, ListAndWatch, and Allocate​

On an NVIDIA GPU node, the nvidia-device-plugin DaemonSet talks to the local kubelet over UNIX domain sockets inside /var/lib/kubelet/device-plugins/. A UNIX domain socket is a file-based channel between two programs on the same machine, which is why it never leaves the node. The sequence diagram below shows the full path, from registration through allocation.

The diagram has three branches in the middle, and they are the part that matters in production. A healthy node advertises all eight devices. A node with three failing devices advertises five. A plugin that crashes leaves the node with its old capacity and no allocatable GPUs, which is why a crashed plugin looks different from a sick GPU in kubectl.

The startup log of a healthy device-plugin Pod shows three steps, in order. First, the plugin starts a filesystem watcher on /var/lib/kubelet/device-plugins/. That lets it notice socket removal and register again whenever kubelet restarts. Second, the plugin starts its gRPC server on /var/lib/kubelet/device-plugins/nvidia-gpu.sock or nvidia.sock. Third, it dials /var/lib/kubelet/device-plugins/kubelet.sock to call Register(), which prompts kubelet to open the long-lived ListAndWatch() stream. The stream stays open for the life of the plugin, so kubelet hears about health changes as they happen.

I0812 09:14:02.912004       1 main.go:337] Retrieving plugins.

Extended resource rules in Pod manifests​

Because nvidia.com/gpu is an extended resource, the Kubernetes API server enforces three strict admission rules on every Pod manifest. Admission is the step where the API server checks a new object before it is stored. A Pod that breaks any of these rules is rejected before kube-scheduler ever sees it. The rules are short, but each one catches a mistake that people make often.

  1. Quantities must be integers. You cannot request a fractional value such as 0.5 GPUs. Sub-GPU sharing means configuring the device plugin to advertise discrete MIG resources, such as nvidia.com/mig-1g.5gb: 1, or time-sliced replicas. For example, replicas: 10 on an 8-GPU node advertises 80 virtual units to kubelet. The card in the next example is a single 24 GB NVIDIA L4 GPU on a g6.2xlarge instance. Running one 1.8 GB Llama-3.2-1B replica without sharing leaves 92% of its VRAM unused. Enabling time-slicing with 10 replicas lets multiple Pods share the card. Sharing is therefore a plugin setting, and a Pod cannot ask for a fraction on its own.
  2. The request must be specified in limits. A Pod may specify resources.limits["nvidia.com/gpu"]: 1 alone, or specify both requests and limits with identical integer values. Specifying requests without limits, or mismatched integers such as 1 and 2, gets the Pod rejected by the API server. The limit is the number the scheduler counts, so it has to be present and it has to be the same number on both sides.
  3. There is no implicit overcommit. Without explicit time-slicing or Multi-Process Service configuration, each unit of nvidia.com/gpu maps to exclusive physical device assignment during allocation. Multi-Process Service is NVIDIA's mechanism for letting several processes share a GPU at the same time. Overcommit would mean handing out more units than the hardware has, and the default setting never does that.

If you want more than one Pod on a card, configure time-slicing or Multi-Process Service explicitly before you schedule them. A Pod that asks for a shared card without the plugin setting in place will simply wait, or it will get an exclusive card, depending on the request.

Quantifying the underspecified request trap​

The kube-scheduler treats nvidia.com/gpu as a plain integer counter. So a bare resource request states a capacity need, not a hardware need. Put a latency-sensitive workload with no node affinity on a mixed cluster, and it guarantees intermittent SLA violations. An SLA violation is a missed service target, such as a response time that goes above the agreed limit. The scheduler is not making a mistake here. It is simply counting, and it does not know which GPUs are the fast ones.

Consider a production fleet of 40 GPU worker nodes, each advertising eight allocatable GPUs. Of those, 25 newer nodes have NVLink-connected GPUs. Those links run at NV12, which is 600 GB/s on A100 or 900 GB/s on H100. The same nodes also show NIC-local PCIe switch placement, labelled PIX. The other 15 older nodes have PCIe-only GPUs that traverse cross-socket SYS links. Cross-socket traffic has to cross the link between the two CPU sockets, which is slower than a path that stays local.

Suppose a developer deploys the latency-sensitive service with only a single-GPU limit, and no nodeSelector or nodeAffinity. Then all 40 nodes satisfy the scheduler predicate. A predicate is a test that the scheduler applies to decide whether a node is a candidate. Under uniform availability, kube-scheduler has a 15 / 40 = 37.5% chance of placing the Pod on one of the 15 unqualified PCIe nodes. Publishing a node label such as gpu.platform.example/class=latency-optimized on the 25 qualified nodes, and enforcing requiredDuringSchedulingIgnoredDuringExecution node affinity, reduces the wrong-pool placement risk from 37.5% to 0.0%. The label gives the nodes a name, and the required affinity makes the scheduler respect that name every time.

Before you deploy, decide which node pool the service needs, and enforce that choice with node affinity. The label alone does nothing until a Pod asks for it.

PID namespaces and why nvidia-smi inside a container hides host PIDs​

You run nvidia-smi inside a busy GPU container. It shows 98% GPU utilization and 40000MiB of framebuffer memory in use, yet the process table is empty. That looks like a broken driver, but it is an expected result of Linux PID namespace isolation. The framebuffer is the memory on the card that holds the data and the model weights, so the number tells you the GPU really is busy. The empty table is a question of which process IDs the container is allowed to see.

On the worker node host, nvidia-smi queries NVML in the root PID namespace. It lists every GPU process with its host PID, such as 2051234. It also shows the physical device UUID, such as GPU-e461a384-5f4c-7c08-0131-0dfbc6c483b2 or GPU-173ced1d-4c1d-072d-6819-86522b018187. The root namespace is the view that sees every process on the machine, and that is why the host can name the owner of each GPU job.

Inside the container, the workload runs in its own PID namespace, where the Python entrypoint is PID 1. When nvidia-smi inside the container queries the host driver through /dev/nvidia0, the driver returns host PID 2051234. That PID does not exist in the container process tree, so the tool leaves it out. The GPU is shared, but the names of the processes are hidden, which is the point of the isolation.

Never set hostPID: true on tenant workloads just to see process IDs, because that setting breaks container process isolation. Attribute GPU processes to Pods on the worker host instead, or scrape dcgm-exporter metrics on port 9400. The useful metrics are DCGM_FI_DEV_GPU_UTIL, DCGM_FI_DEV_FB_USED, and DCGM_FI_DEV_MEM_COPY_UTIL. These metrics are per GPU, so they tell you which card is busy, and a join with the Pod labels can tell you which Pod owns that card.

dcgm-exporter 4.9.0 version note. dcgm-exporter 4.9.0 (2026-11-06) renamed many default metrics and changed some units. For example DCGM_FI_DEV_GPU_UTIL (percent) became DCGM_FI_DEV_GPU_UTIL_RATIO (0 to 1), and DCGM_FI_DEV_FB_USED (MiB) became DCGM_FI_DEV_FB_USED_BYTES. The metric names in this chapter are the 4.8.x names. On a 4.9.0 exporter use the full mapping in 17.4, and change thresholds together with the unit.

Use host-side attribution or DCGM metrics, so you can find which Pod is using the GPU. The process list inside the container is never the right place to look for that answer.

Four device-plugin settings are worth enforcing across production clusters. The first is --fail-on-init-error=true. It forces the plugin into CrashLoopBackOff when NVML fails to initialize. If you leave it false, a broken plugin can stay Running while it silently advertises zero GPUs. The second is DEVICE_LIST_STRATEGY=cdi-annotations, or cdi-cri, which tells the plugin to request CDI injection from the CRI runtime. The third is --pass-device-specs=true, which passes explicit device node paths in allocation responses. The fourth is --device-discovery-strategy=auto|nvml|tegra, which selects the discovery backend. Tegra is the NVIDIA platform for embedded Jetson-class boards, so the flag matters only when you run that kind of hardware.

Pin these settings in your values file, so that a broken plugin fails visibly instead of hiding behind a Running status. A visible crash is much easier to act on than a healthy-looking Pod that advertises nothing.

How it fails​

A live outage is the worst moment to start restarting things. Picture a GPU node that drops its allocatable GPUs during a busy afternoon, with jobs queued behind it and a manager asking for an update every ten minutes. The reflex is to restart the device plugin DaemonSet and hope. When a node drops its allocatable GPUs, or containers fail at startup, resist that urge until you have preserved evidence. A restart erases the logs and the Pod state that would have told you which boundary broke. Follow the dependency-ordered decision tree instead. It helps you isolate the exact failing boundary, working from the bottom up.

The tree starts with the hardware and moves upward, one question at a time. Each question has a yes branch that goes further up the stack and a no branch that stops at the layer that is broken. Because the layers depend on each other, a failure low in the tree makes everything above it look broken too.

Checkpoint questions​

1. Why does adding a Kubernetes RuntimeClass not make a GPU workload schedulable by itself?

RuntimeClass only tells kubelet and the CRI runtime which configured handler to use when building the container sandbox. It can also set a scheduling nodeSelector, tolerations, and Pod overhead. It knows nothing about physical GPU inventory. A GPU becomes schedulable only after the NVIDIA Device Plugin finds healthy devices through NVML, registers with kubelet, and publishes a non-zero allocatable GPU count to the API server.

2. What are the four kernel modules in the NVIDIA Kernel-Mode Driver stack and what does each do?

The core module, nvidia.ko, handles hardware initialization, context state, interrupts, and power. The nvidia-uvm.ko module handles Unified Virtual Memory, which covers shared CPU-GPU virtual address spaces and page-fault migration through /dev/nvidia-uvm. The nvidia-modeset.ko module handles display mode-setting. The nvidia-peermem.ko module enables GPUDirect RDMA, so InfiniBand or RoCE NICs can DMA directly into GPU memory over PCIe.

3. What character device nodes must exist inside a container device filesystem for a single-GPU CUDA workload on GPU 0 to initialize?

At minimum, the container needs /dev/nvidia0 with major 195 and minor 0, /dev/nvidiactl with major 195 and minor 255, and /dev/nvidia-uvm with dynamic major 238 and minor 0. If Multi-Instance GPU partitioning is enabled, it also needs the /dev/nvidia-caps/* capability nodes.

4. Why is the user-mode driver kept on the host and bind-mounted into containers rather than baked into every application container image?

The user-mode driver talks to the kernel-mode driver through a version-locked system-call ABI. All containers on a node share the running host kernel and its loaded kernel module. If you baked a fixed user-mode driver into every application image, any change to the host driver would cause API mismatch errors. Injecting libcuda.so.1 from the host at startup keeps user space and kernel space in step, and container images can still carry portable CUDA runtime libraries.

5. How does CUDA Forward Compatibility allow a newer CUDA container such as CUDA 12.2 to run on an older host kernel driver such as Driver 525?

A forward-compatible image packages a newer user-mode driver bundle, including libcuda.so.535.104.05, inside /usr/local/cuda/compat/. It prepends that path to LD_LIBRARY_PATH. The dynamic linker then loads the newer compat library ahead of the host-mounted one. That compat library translates newer CUDA runtime calls to the older kernel driver ABI, across the supported compatibility matrices.

6. How did GPU container injection evolve across the four generations from legacy Docker wrappers to CDI?

Suppose you trace the history from the oldest generation. Generation 1 (nvidia-docker) was a standalone wrapper script around the Docker CLI. Generation 2 (nvidia-docker2) was a custom Docker daemon runtime. Generation 3 added an OCI pre-start hook around runc, which calls nvidia-container-cli to parse NVIDIA_VISIBLE_DEVICES and mount the GPU device nodes and host libraries. Generation 4, the Container Device Interface 0.5.0, uses a vendor-neutral declarative file at /var/run/cdi/nvidia.yaml. You generate that file with nvidia-ctk cdi generate, and containerd and CRI-O parse it natively, without custom OCI hooks.

7. Why are host files such as the user-mode driver and nvidia-smi mounted with read-only, nosuid, and nodev options in a CDI specification?

Those files live on the host OS filesystem, and every GPU container on the worker node shares them. Read-only mounts stop a container from modifying host driver binaries. The nosuid option ignores set-user-ID bits, and nodev blocks device interpretation. Together they stop a privileged process inside a container from escalating privileges on the node.

8. What is the difference between proving runtime injection with crictl inspect on the node and proving execution with nvidia-smi -L inside the container?

When you see /dev/nvidia0 in the crictl inspect devices array, it proves that the CRI runtime and the NVIDIA Container Toolkit or CDI edited the container spec and attached the device node. It does not prove that the container's dynamic linker, user-mode driver library, and CUDA runtime are compatible with the host driver. Only nvidia-smi -L succeeding inside the container proves the workload is ready to run end to end.

9. What are the three gRPC steps in the Kubelet Device Plugin contract and when does each happen?

First, when the plugin starts, Register() dials /var/lib/kubelet/device-plugins/kubelet.sock to register the resource name nvidia.com/gpu and its socket. Second, kubelet immediately opens a long-lived ListAndWatch() stream, which delivers discovered device UUIDs and continuous health updates. Third, after kube-scheduler binds a GPU Pod to the node, kubelet calls Allocate() with the chosen UUIDs. The reply gives containerd the device paths, mounts, environment variables, or CDI annotations it needs.

10. How does the NVIDIA Device Plugin recover automatically if the node kubelet service restarts?

When the plugin starts, it launches a filesystem watcher on /var/lib/kubelet/device-plugins/. When kubelet restarts, it wipes and recreates that directory and kubelet.sock. The watcher sees that the plugin's socket was removed, recreates nvidia-gpu.sock, and calls Register() again automatically.

11. On gpu-node-07, Capacity is 8, Allocatable is 8, and Allocated resources is 6. How many GPUs can kube-scheduler still assign to new Pods on gpu-node-07?

Kube-scheduler can assign 2 more GPUs, because 8 minus 6 leaves 2. Allocatable shows the total healthy inventory on that node, not the unallocated remainder. Kube-scheduler subtracts the requests of Pods already bound to the node from Allocatable to get the free count.

12. What does it mean when a node shows Capacity of 8 GPUs, but Allocatable of 5 GPUs?

Picture a node where all 8 physical GPUs were discovered when the device plugin registered, so Capacity is 8. Afterward, 3 of those 8 GPUs failed health checks, with faults such as an uncorrectable ECC error (Xid 48) or a bus-off error (Xid 79). The plugin reported them as Unhealthy over the device-plugin stream.

13. What is the difference between a node showing Capacity: 8 with no Allocatable line versus a node having no nvidia.com/gpu line in Capacity or Allocatable at all?

Consider a node with Capacity of 8 and no Allocatable line. That means the device plugin registered 8 GPUs in the past. Since then, the plugin container has crashed or lost its registration with kubelet. A node with no nvidia.com/gpu line in either Capacity or Allocatable has never completed registration since its Node object was created.

14. Why does Kubernetes reject a Pod manifest that specifies a GPU request without specifying a GPU limit?

Kubernetes extended resources cannot be overcommitted by kubelet. So Kubernetes requires them in resources.limits as a positive integer. If you also set resources.requests, you must make the two values match.

15. In a 40-node cluster with 25 NVLink-connected GPU nodes and 15 older PCIe-only GPU nodes, why does a bare single-GPU request have a 37.5% chance of landing on the wrong hardware tier?

nvidia.com/gpu is an opaque integer count, so kube-scheduler sees all 40 nodes as identical. Without a nodeSelector or a requiredDuringSchedulingIgnoredDuringExecution nodeAffinity rule that targets a hardware-class label, nothing separates the pools. So 15 of the 40 eligible nodes belong to the older PCIe pool, a 37.5% chance, which is 15 out of 40.

16. How do you distinguish a capacity shortage from a label or affinity mismatch when a GPU Pod is stuck in Pending?

Check the FailedScheduling event in kubectl describe pod <pod>, because it tells you which clause blocked the Pod. In the message 0/40 nodes are available: 15 Insufficient nvidia.com/gpu, 25 node(s) didn't match Pod's node affinity/selector, the first clause says 15 nodes had no free GPUs. The second clause says 25 nodes were filtered out by scheduling policy before GPU capacity was checked.

17. On an affected node, lspci shows the A100 GPU and lsmod shows the driver loaded, but host nvidia-smi fails and the kernel log shows RmInitAdapter failed (0x62:0xffff:1487). Meanwhile, the device plugin is in CrashLoopBackOff logging could not load NVML library. Which component is the root cause?

The root cause is the host driver and hardware initialization layer, which shows up as RmInitAdapter failed in journalctl -k. The device plugin's CrashLoopBackOff is only a downstream symptom, because NVML cannot initialize when the host driver fails to initialize the GPU adapter. Fix the host driver or the hardware, and do not redeploy the device plugin.

18. Why should --fail-on-init-error=true be enabled on the NVIDIA Device Plugin in production?

With --fail-on-init-error=true, the plugin exits and enters CrashLoopBackOff when NVML fails to initialize at startup, which triggers Pod restart alerts right away. If you set it to false, the container stays Running and silently reports 0 GPUs. That hides the node failure from standard DaemonSet health checks.

19. Why does running nvidia-smi on the worker node host show PID 2051234 (python3, 40000MiB), whereas running nvidia-smi inside the container shows no processes listed?

The container runs in its own PID namespace, where its Python process is PID 1. That process maps to PID 2051234 in the host's root PID namespace. When nvidia-smi inside the container queries the host kernel driver through /dev/nvidia0, the driver returns host PID 2051234. The container's process filesystem cannot resolve that PID, so it goes unlisted.

20. When a Pod fails with nvidia-container-cli: mount error: file creation failed: .../nvidia0: no such device, did the failure happen during scheduling, allocation, or runtime sandbox creation?

The failure happened at runtime sandbox creation, before the container entrypoint ran. Scheduling and kubelet device allocation had already succeeded. When containerd invoked the NVIDIA Container Toolkit hook, the runtime could not find or mount /dev/nvidia0 on the host.
