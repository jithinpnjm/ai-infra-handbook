8.12 High availability and head node failover

LevelIntermediate
Priority tier1
Lab venueLaptop
PartPart 8: NVIDIA Base Command Manager
StatusDrafted (ha_lab.py: 50 checks pass; cluster commands untested on live BCM)

Why this matters for AI infrastructure​

Suppose the head node stops answering. It holds CMDaemon, the database, the DHCP and TFTP services, the LDAP directory, the master image copies and often the Slurm controller. DHCP hands out network addresses, TFTP serves the boot files that nodes need, and LDAP is the directory of users. While the head node is down, you cannot provision, change or monitor anything. Running jobs usually keep going, but nothing new can be managed.

A second head node costs one server, so the hardware is the easy part. The harder part is making sure a failover happens when needed and never when not. A wrong failover can corrupt shared storage, because two machines writing to one filesystem at the same time damage each other's data. A missed failover leaves the cluster down. The rest of this chapter keeps coming back to that tension between the two risks.

Prerequisites and outcomes​

Before you start, make sure you have covered chapters 8.1 to 8.8 and 8.11. This chapter builds directly on the cluster and provisioning ideas from those pages. You will need to explain the roles of the two heads, the shared addresses and the storage they share, and you will need to know what split brain means and how fencing and STONITH prevent it. You also need to choose between automatic and manual failover, build a pair with cmha-setup, and check it with cmha status.

The chapter then covers how to test a failover in a way that proves something, how to keep two heads in sync during updates, and what HA means for regular nodes. Each section names the level that owns its setting, so you always know where a change should go.

If any of these still feels vague, reread the matching section before you touch a live pair. A live pair is one that serves real users, and a mistake there costs more than a mistake on paper.

1. The pair​

Think of two head nodes that present one identity to the outside world. Users and compute nodes only ever talk to the shared addresses, so they never need to know which physical box is in charge. A head node is the server that runs the cluster's management software. The diagram shows the parts that make this work.

Two names describe each head, and they answer different questions. The primary and secondary names are fixed. One head is the primary and the other is the secondary, and that never changes. The active and passive roles do change, so the primary can be passive at any given time. Think of the names as labels on the machines and the roles as the jobs they are doing this week. BCM's "primary" is not the same thing as Slurm's "primary", which chapter 8.8 explains.

The active head leads and the passive head follows. Think of the passive head as a standby copy of the active head, ready to take over when you need it to. MySQL runs in master-slave mode, so CMDaemon writes to the active head while the passive head trails behind. The master holds the authoritative copy of the database, and the replica copies each change as it happens. The passive head also watches the active head all the time, so it knows when something has gone wrong.

Shared IP addresses are the next piece. There are two virtual IPs, one internal and one external. They are alias interfaces such as eth0:0, which means a second address hung on the same network port. Whichever head is active hosts them. Users log in through the shared external IP. Nodes use the shared internal IP, for example for NFS, so their mounts survive a failover. The point of a shared address is that the clients never have to learn a new name. Picture a user whose login script points at the external address. After a failover, the same script still works, because the address now lives on the other head. Nothing on the user's side changes, and that is the whole goal. If you bond the head interfaces, rename the shared alias interfaces to the bond alias, as chapter 8.3 describes. Bonding joins two network ports into one logical link, which adds redundancy or speed.

Last comes the failover network. It is a dedicated link between the heads that carries the heartbeat. A heartbeat is a short message that one head sends the other on a regular timer, so each side knows the other is alive. The best practice is a direct cable with no switch, so that a switch reset cannot disturb the heartbeat. A switch shared with the rest of the cluster can fail in ways that look exactly like a dead head, and that is the last thing you want during a real outage.

Plan the heartbeat cable first, because every other setting depends on the two heads being able to check on each other.

2. What runs where​

Picture the night the active head fails. The passive head has to pick up the services that move, while the services that run everywhere keep answering. Not every service can run on both heads at the same time. Some services must run everywhere, while others can run only on the active head and therefore move during a failover. The table shows how that split works. A service that runs on both heads is either replicated or load balanced, so either head can answer. A service that migrates is one that would corrupt data if two copies ran at once.

On both heads at all timesMigrates to the active head
CMDaemon (including provisioning), DHCP (load balanced), TFTP, LDAP (replication), MySQL (replication), NTP, DNS, workload manager (one fully active, the other standby)NFS, the user portal, slurmdbd (Slurm accounting), and the LSF batch daemons

Both heads take the provisioning role. Nodes can be provisioned from either head, and the passive head is provisioned from the active one. Each head gets its own provisioninginterface, which is the network interface it uses to serve nodes during their install.

The replication scope is the part that surprises people. By default, only the cmdaemon and slurm_acct_db databases are copied. Any other database is not copied. A third-party application database is a good example, and the manual's example is AJR. That database will be missing after a failover unless you list it in extradbclone.xml. From BCM 11.34, cmha-setup can optionally replicate all non-system databases, along with users and grants. Grants are the permissions that decide who may read or write each database. The setup prompt asks "Replicate all non-system MySQL databases?", and the express option is --replicate-all-databases. System databases are never replicated: mysql, information_schema, performance_schema and sys. Those hold MySQL's own bookkeeping, and each head builds them for itself.

Inventory every database on the head before you promise "full HA". Full HA means you have checked that nothing important stays behind when the head fails. The lab's missing_after_failover check does this for you, but you still need to know which databases exist on your own head.

3. Shared storage​

Picture a failover where the new active head mounts /home while the old head still has it mounted. Two machines writing to one filesystem is how data gets corrupted. Each machine caches its own view of the files, so the two views drift apart, and the last writer wins without anyone noticing.

The usual setup shares /home and /cm/shared. BCM 11 uses NAS, commonly NFS, and also names Lustre and GPFS. NAS means network-attached storage, a file server on the network. Lustre and GPFS are parallel filesystems that many machines can use at once. The shared filesystems are mounted only on the active head, by a configurable mount script. The unmount script releases them again. The two scripts are the handover, and their exit codes tell CMDaemon whether the handover worked.

That rule has three consequences. First, the passive head shows the old local contents of those directories, so point your users to the shared IP instead of letting them log in there. A user who logs in to the passive head sees stale files that look real but are not the current ones. Second, the pre-failover unmount script must return a non-zero exit code when it has problems unmounting. A non-zero code is the way a script reports failure. Otherwise the storage can be mounted twice in the post-failover stage, and that can corrupt data. A head stuck in UNABLETOBECOMEACTIVE usually means a mount or unmount script returns the wrong exit codes. Third, imported NFS cannot be re-exported, so nodes mount from the NAS directly.

Test the failure path of your unmount script before you trust it, because a script that always returns 0 hides the one error that matters. A quick way to test it is to make the unmount fail on purpose, in a test window, and check that the head refuses to become active.

4. One active head, always: split brain, fencing, quorum, STONITH​

Imagine the link between the two heads breaks while both heads keep running. The passive head cannot tell whether the active head has crashed or only lost its network link. That doubt is called split brain, because each side now believes it is the only one in charge. Two heads writing to shared storage is the failure you must prevent, so the passive head works through four steps in order. Each step makes the next one safe.

  1. The passive head enters fencing mode. Fencing here means the head stops acting as a normal standby and holds back. It records what it does as a backlog, so the two heads can compare and sync that backlog if they reconnect before any failover happens.
  2. It needs proof that the active head is off. That proof comes either from an administrator's manual confirmation or from STONITH, which stands for "shoot the other node in the head". With STONITH, the passive head powers the active head off through its BMC or PDU, then checks that the power is really off. The check matters, because a command that was sent is not the same as a machine that has stopped.
  3. It needs a quorum first. A quorum is a count of votes that must agree before anyone acts. The passive head asks all nodes whether they also cannot reach the active head. It proceeds only if more than half of them confirm. This stops a passive head with its own network fault from powering off a healthy active head. Nodes that do not answer within Quorum time are not counted. The manual leaves open whether "half" means half of the responders or half of all nodes. The lab defaults to responders and can use the total instead.
  4. Once the active head is proven off, the fencing head becomes active.

Now the trigger. cmha status shows four checks from each head's view: failoverping (the dedicated link), ping (the management network), status (CMDaemon answers REST calls) and mysql (replication). REST calls are requests sent over the web, which CMDaemon answers as its API. BCM prepares to fail over only when ping, failoverping and status are all not OK. In that case the active head is "all dead". If only some of those checks fail, the head is "mostly dead", which the manual calls slightly alive. BCM takes no automatic action then, and an administrator decides. The head can be powered off after someone has examined it. A failing mysql check on its own is reported, but it does not trigger a failover, because a broken copy of the database is a repair job, not a reason to move the whole cluster.

Think of this rule as a difference in intent. A planned reboot is a decision someone made, and an unplanned crash is not. BCM can only tell the two apart from the signals it sees, so it leaves the planned case alone.

A reboot or a graceful shutdown of the active head does not trigger one either. BCM assumes that kind of shutdown is intentional, so it does not try to take over from a head that is going down on purpose. If you want to switch on purpose, run cmha makeactive on the passive head.

A power-off and a pulled cable look similar in a test, but BCM treats them differently. A power-off switches off the main board and leaves the BMC running, so BCM can still verify the power state. Pulling the power cable usually takes the BMC down too. BCM then cannot tell a dead head from a network failure, so it does not fail over automatically and waits for manual confirmation. The BMC is the small controller that keeps running on a server even when the server is off, and it is the only way to confirm that the server has stopped.

Before you trust a failover test, decide how the active head will go down, because a power-off and a pulled cable lead to different results.

5. Automatic or manual failover​

Picture a head that stops answering at night, with nobody on call. Automatic failover needs power control defined for both heads, as chapter 8.7 describes. If that power control is in place, automatic failover is tried by default. The active head is powered off when it stops responding and the quorum agrees.

Manual failover is the other path. The administrator starts the failover and confirms that the old active head is off. You end up with manual failover in four situations: when there is no power control, when disableautomaticfailover is set, when power control is broken, or when the active head is mostly dead. To set the flag, run partition failover base; set disableautomaticfailover yes. A flag is a switch that turns a behavior on or off, and this one turns off the automatic path.

Before you rely on automatic failover, check power control with device power status -n head1,head2. A head cannot always reach its own BMC when there is no dedicated BMC port. In that case, ping the counterpart's BMC address from the other head instead. The check tells you whether the passive head can actually switch the active one off, which is the step that automatic failover depends on.

The lab's failover_decision combines all of these rules, so you can see what the passive head does for each combination.

Settle the mode before an outage, and check power control now, since a manual failover waits for an administrator to confirm the old active head is off. An outage is a bad moment to learn that the power path does not work.

6. Building and checking the pair (15.2)​

Build the pair with cmha-setup. The manual is explicit that building it by hand is not supported, so use the tool. The build runs in stages, and each stage depends on the one before it. Skipping ahead leaves a half-built pair, which is harder to fix than a clean failure.

Start with preparation on the primary. Power off the other nodes if you can, and test bonding before you go further. Testing bonding means confirming that the joined network links carry traffic before the pair depends on them. Then run cmha-setup, choose Setup, then Configure. The tool checks the license first, because HA needs an HA-enabled license. You can see the MAC addresses in verify-license info, and an HA license shows two. A MAC address is the hardware identity of a network port, and the two MACs belong to the two heads. Next the tool asks for the shared internal and external IPs and the alias interface names. It also asks for the passive head's host name, the failover network and its interfaces, and the secondary's other interfaces, such as InfiniBand and BMC. It then shows a summary. External addresses must be static, because DHCP does not work for HA. The last question is for the MySQL root password, and whether to replicate all non-system databases.

Next, clone the secondary. PXE boot the secondary into the rescue environment from the primary. PXE is network booting, and the rescue environment is a small temporary system used for repair and copying. Log in as root with no password, then run /cm/cmcloneinstall --failover. Give the boot interface, confirm the disk layout and the erasing, and wait for the syncing to finish. Erasing is destructive, so read the disk layout before you confirm it. Then choose Finalize on the primary. Identical hardware and BIOS clocks set to local time are strongly recommended. The BIOS clock is the hardware clock that starts before the operating system, and a mismatch between the heads makes their timestamps disagree. An ARM64 secondary needs a workaround. Put set -e grub yes and set -e bootloaderprotocol tftp in one commit, because the generated PXE file name can be wrong. ARM is a processor family used in many servers, and a wrong file name stops the boot before it starts.

After that, set up the shared storage on NAS, and optionally set up automated failover with power control. Check the result with cmha status from either head. The asterisk marks the active head. failoverping only starts working after the passive head has rebooted, so a fresh failing check right after setup is not yet a fault.

Installing a new license invalidates existing user certificates. Install the HA-enabled license before you create certificates, as chapter 8.6 explains. A certificate is the digital identity that a user or service presents, so changing the license after the certificates exist forces you to make them again.

To change an HA configuration, remove the old one with the "Undo Failover" menu option, then run the procedure again. Re-cloning rebuilds a head. Use cm-clone-install --clone, or --failover to replace a failed passive. A prepared "spare" snapshot is discouraged, because it goes stale. A snapshot taken today starts to disagree with the cluster as soon as the next update lands, so the spare would need its own updates before it could be trusted.

Cloning exclude files and Btrfs snapshots need a separate look. Btrfs is a filesystem that can take snapshots, which are frozen copies of its state at one moment. cm-clone-install reads two files from /cm/ on the clone node. CMDaemon does not maintain them, and excludelistmanipulatescript does not change them. An exclude list is a set of paths that the clone should skip. Do not confuse these with the five image exclude lists in chapter 8.4. The first file is /cm/excludelistnormal, which cm-clone-install uses without --failover. The second is /cm/excludelistfailover, which cm-clone-install --failover uses. Cloning logs to /var/log/clone-install-log. If you clone a Btrfs partition, only mounted snapshots are cloned by default. Passing --btrfs-full-clone clones all snapshots, but it duplicates the data by bypassing copy-on-write. Copy-on-write is the trick that lets snapshots share their unchanged blocks, so bypassing it copies everything in full. That can greatly increase the filesystem size.

6.1 Express CLI setup without ncurses (cmha-setup -x)​

For scripted deployments, cmha-setup has an express mode that skips ncurses. Ncurses is the library behind the text menus, so skipping it lets the tool run from a script with no menus. You drive it with an XML file that you can edit by hand. The recommended path for that file is /cm/local/apps/cluster-tools/ha/conf/failoverconf.xml.

cmha-setup [ -x -c <configfile> [-s <type>] <-i|-f[-r]> [-p <mysqlrootpassword>] [-a] ]

The express workflow has four steps, and every step uses the same XML file. Keep the file under version control, so you can see exactly which values each run used.

  1. Initialize on the active head with -i|--initialize. First shut down all regular nodes and prepare failoverconf.xml. Then run cmha-setup -x -c failoverconf.xml -i. Add -p <mysqlrootpassword> to avoid the interactive password prompt. On BCM 11.34.0 and later, add -a|--replicate-all-databases to replicate all non-system MySQL databases, along with users and grants. This step updates the shared internal, external and failover interfaces. It also clones the master object in the CMDaemon database.
  2. PXE boot and clone the passive head. Boot the passive head into the rescue environment and run /cm/cm-clone-install --failover. The clone copies the active head's system onto the passive one, so the two start from the same state.
  3. Finalize on the active head and reboot the passive head. Run cmha-setup -x -c failoverconf.xml -f -r. The -f|--finalize option updates the secondary MAC, initializes failover on head2, clones the database and permissions, and checks the dedicated failover network. The -r|--finalizereboot option reboots head2 when it completes. Finalize is the step that turns two separate machines into a pair.
  4. Configure the shared storage with cmha-setup -x -c failoverconf.xml -s nas.

Express mode does very little validation. An invalid entry in failoverconf.xml can therefore make cmha-setup hang, instead of stopping with a clear error. Check every value in the file by reading it twice before you run the first step.

Do not call the pair finished until cmha status looks right from either head. Looking right from both heads confirms that each head sees the same active and passive roles.

7. Operating the pair​

Picture a quiet Thursday when cmha status shows the pair healthy, but a mount script has failed in the logs. Once the pair is running, most of your time goes to checking its state and tuning its timers. A timer here is a number of seconds that decides how long the pair waits before it reacts. A head can be in one of several states, and cmha status shows the current one. The same state appears in the login banner and in /var/spool/cmd/state. The states are INIT, FENCING, ACTIVE, PASSIVE, BECOMEACTIVE, BECOMEPASSIVE, UNABLETOBECOMEACTIVE and ERROR. If a mount script misbehaves, look in /var/log/cmdaemon. Then run cmha makeactive to tell a head to try again.

The failover parameters live in partition failover base. In Base View you find them at Cluster > Partition[base] > Settings > Failover. Dead time is how long a head can go without an answer before the active head is treated as dead and a quorum starts. Warn time is when BCM logs a warning, and Init dead replaces Dead time while a head is just starting. A starting head is slow to answer, so it needs a longer wait. Keep alive sets the check interval, and Quorum time sets how long the quorum poll waits. Failover network names the heartbeat network. The Mount script and Unmount script handle shared storage. The Prefailover script runs on both heads once the decision is made, before the change. It must unmount and return a non-zero code on problems. The Postfailover script runs on both heads after the former passive head becomes active. The list also includes Disable automatic failover and Secondary headnode. The manual's show output gives these defaults:

SettingDefault
Dead time10 s
Disable automatic failoverno
Failover networkfailovernet
Init dead30 s
Keep alive1 s
Quorum time60 s
Warn time5 s

To fail over by hand, run cmha makeactive on the head that should become active. Cancel any provisioning in progress first, with softwareimage cancelprovisioningrequest -a. Provisioning that is still running when the roles swap can leave nodes half installed. If the active head is mostly dead, think carefully before you answer the prompt. You can also use the same command for planned maintenance. Switch the active role, update the former active head, and then optionally switch back.

If MySQL replication breaks after a hard crash, run cmha dbreclone <host> to copy the MySQL database to the other head again. That command needs CMDaemon stopped, so cmsh and Base View cannot run it. A hard crash can leave cmha status showing a failed replication on the returned head. dbreclone is the fix for that. It rebuilds the copy from the good head, so the damaged copy is replaced rather than repaired.

Testing comes next. A good test has a clear start, a clear expected result and a clear way to undo it. Write down what you expect the passive head to do before you run the test, so you can tell a surprise from a success. Check power control and BMC reachability first, as section 5 describes. A graceful shutdown tests nothing, because BCM does not treat it as a failure. To test automatic failover, crash the kernel on the active head with echo c > /proc/sysrq-trigger. The sysrq trigger is a kernel feature that lets an administrator force an immediate crash, which is a realistic failure. The passive head then powers the frozen head off and becomes active. Run this in a test window, because it is a real failover, and clients will feel it.

Updates are where two heads most often drift apart. Drift means the two heads slowly stop matching, and the mismatch only shows up when a failover happens. The rules below come from section 15.4.5 of the manual.

ItemRule
CMDaemon and MySQL packagesupdate the active first, confirm cmha status, restart cmd, then the passive (a CMDaemon update can contain a MySQL schema migration). On Ubuntu update mysql separately before cmdaemon (a known stall, internal reference BCM-31089)
DHCP, LDAP, NTP, DNSany order
Migrating services (NFS, sgemaster)update the passive, cmha makeactive on it, then update the former active, so problems show up while you can still inspect
Software imagesnot on shared storage by default; run updateprovisioners on the active right after an image change, or a failover soon after can leave the new active with stale images (the passive is only synced at midnight or on a provisioning request; provisioningstatus showing it "out of date" is normal)
Changes outside CMDaemon (RPMs, local apps, /cm/node-installer/ files, other config)do them on both heads by hand. BCM does not sync them on purpose, so a bad change cannot break both heads at once

The first row explains the order. The active head goes first, and the passive head follows only after cmha status looks healthy. A schema migration changes the layout of the database, so the active head must finish it before the passive one follows. The migrating-services row reverses the pattern on purpose. You update the passive head, move the active role to it, and then update the former active head. Problems show up while you can still inspect the old head, and a bad update lands on the head you can roll back. The software-images row is the one people forget, and it is worth a reminder each time an image changes.

Build a bare-metal cluster as a single head first, get it right, then set up HA, so the secondary is cloned from a good system. In practice this means you finish the install, run the cluster for a while, and only then add the second head. Adding HA to a head that is still changing means the clone starts moving targets. A clone of a broken head copies the breakage too.

8. HA for regular nodes and edge directors (15.5)​

Picture a print service that your cluster offers to users, where the one node running it goes down. BCM can also make regular nodes highly available, and it supports edge directors too. An edge director is a node that sits at the boundary between the cluster and an outside network. Regular node HA has been available since BCM 7.0, and edge directors since 9.2. Use it for extra services that you run on regular nodes. Do not use it to move the default head node services, because those are already optimized as they are.

The mechanism looks familiar. It uses power control, warn and dead times, mount and unmount scripts, pre and post failover scripts, and a shared virtual IP, just like head node HA. The differences start with configuration. You set it up in the failovergroups submode, at partition[base]->failovergroups, or with cmha nodestatus [groups] and cmha makeactive <node>. A submode is a set of settings nested under one object. A group needs two or more nodes, with one active and the rest passive. There is no failover network, so the heartbeat travels over the regular node network. The active head node runs the health checks and STONITH itself, instead of a node-wide quorum. There is also no cmha-setup for this. For edge directors, use cm-edge-setup, and never edit failovergroups by hand for them.

Setting up a regular node group takes a few commands. Add the group with failovergroups; add cupsgroup; set nodes node001..node002; commit. Then add the service on each member with set runif active; set autostart yes; set monitored yes. The runif active setting means the service runs only on the active member, which is what keeps a second copy from starting. Add a shared alias interface on each member with interfaces; add alias bootif:0; set ip 10.141.240.1; set startif active; set network internalnet; set additionalhostnames cups; commit, and reboot the group nodes afterwards. Use the same additionalhostnames across all members, because the shared VIP must not carry a different name on each node. A VIP is a virtual IP, the shared address that moves between machines. If each member gave the VIP a different name, a client resolving the name would get different answers depending on timing, and the service would appear to flicker. In failovergroups, Automatic failover after graceful shutdown defaults to no.

When you switch the active regular node with makeactive, the active head node runs one fixed sequence, and you can follow it step by step. In step 1, every group node runs the Prefailover script. In step 2, the old active node stops its service and runs the Unmount script. If that script exits with anything above 0, all the remaining actions are skipped. If STONITH powers off the old active, the old-active sequence aborts. Otherwise the old active stops the active IP, starts the passive IP and starts its passive services. In step 3, the new active node stops its service, runs the Mount script, stops the passive IP, starts the active IP and starts its service. In step 4, every group node runs the Postfailover script. Because each step waits for the one before, a failure at step 2 leaves the old node in charge and the new one untouched.

8.1 Workload manager job continuation across failover​

Running workload manager jobs can continue through a head node failover. Queued jobs wait, then start once resources are available after the handover, unless a BCM prejob health check rejects them. A prejob check is a health check that runs just before a job starts on a node. Three conditions must all be met.

The first condition is a supported WLM setup. The workload manager must have been configured either during the initial BCM installation or with cm-wlm-setup. The second is shared storage that supports job continuity. The HA storage setup must support it for that workload manager, and NAS does this for Slurm and LSF. The third is application tolerance for a brief NFS pause. During the failover, the shared filesystem is unmounted and remounted across the head nodes. The workload manager client daemons have default timeouts longer than the HA Dead time, so the scheduler survives. However, user code that does unbuffered I/O to /home or /cm/shared at that exact second can fail if it does not retry. Unbuffered I/O means the program writes straight to the filesystem without holding data in memory, so it sees the pause directly. Code that retries after a short wait does not notice.

Before you build a group, decide which extra services really need HA, because each one adds scripts and failover steps. Every extra step is another place for a failure to hide.

9. Failure scenarios​

When a failover does not go the way you expected, start with the symptom in the left column. The middle column names the likely cause, and the right column tells you what to check first. Work down the list once you have the symptom in view, and check the most likely cause before the rare ones.

SymptomLikely causeCheck

Start with the power path, because automatic failover cannot happen without it. Run device power status and see whether the passive head can reach the BMC of the active one. If that check fails, the answer is in the BMC network, not in the cluster software. Only after the power path checks out should you look at disableautomaticfailover, since a flag set months ago by someone else can explain a silent passive head. Work through the causes in that order, and write down what you found at each step, so the next person does not repeat the same checks.

10. Common first mistakes​

Each of these mistakes is easy to avoid before a failover and hard to diagnose during one. Read the list as a checklist for your own pair, and be honest with yourself about which items you have already done. Several of them look harmless on a quiet day.

  1. Testing failover by pulling the cable or by a graceful shutdown. Pulling the cable does not fail over automatically, and a graceful shutdown tests nothing.
  2. Promising full HA without first listing every database on the head.
  3. Putting a switch in the heartbeat path.
  4. Taking the external head addresses from DHCP.
  5. Writing an unmount script that always returns 0.
  6. Updating the passive CMDaemon before the active one.
  7. Forgetting updateprovisioners before a planned switch.
  8. Installing software on the active head only, outside CMDaemon.
  9. Letting users log in to the passive head.
  10. Assuming a license change leaves certificates valid.

10.1 Deep dive: Anatomy of a head-node failover from second 0 to ACTIVE​

Every detail in this chapter matters at once: the direct heartbeat cable, the NAS unmount exit codes, BMC power control and node quorum. The timeline below shows you why, second by second. It follows the active head node, head1, through a kernel panic in a production AI factory. A kernel panic is the moment the Linux kernel gives up and halts, so the machine stops doing anything at all.

  1. At T = 0 s, head1 panics. The Linux kernel on head1 halts. As you read, notice what happens on the compute nodes first. Running Slurm and Kubernetes jobs do not die. slurmd, srun, kubelet and containerd keep executing user GPU kernels. If head1 and head2 use an external NAS for /home and /cm/shared, or if compute nodes mount /scratch directly from Lustre or WekaFS, compute node storage I/O continues without interruption. The compute nodes do not depend on the head node for every operation, which is why the jobs survive the first seconds.
  2. From T = 1 s to T = 5 s, the passive head head2 polls head1 once every second. It polls over internalnet with ping, over failovernet with failoverping, and on port 8081 with status. Keep alive is 1 s and Warn time is 5 s. At T = 5 s, head2 logs a warning that head1 has stopped answering. The warning comes early on purpose, so an administrator can start looking before anything changes.
  3. At T = 10 s, which is Dead time, head2 moves to FENCING and starts a cluster quorum poll. The quorum window is Quorum time = 60 s. By then ping, failoverping and status are all NOT OK, so head1 is "all dead" rather than "mostly dead". head2 asks the regular compute nodes whether they also lost contact with head1. When more than half of the responding nodes confirm that head1 is unreachable, head2 knows the failure is not a local NIC fault on head2. A NIC is a network interface card, the port that connects the machine to a network.
  4. With quorum established and disableautomaticfailover = no, head2 contacts the BMC of head1, or the rack PDU, over bmcnet. It issues a hard power-off, which is STONITH. It then polls power status until the BMC confirms that main chassis power is OFF. This explains why pulling head1's AC cords during a test blocks automatic failover. If head1's BMC has no standby AC power, head2 cannot get proof that head1 is powered off. Standby power is the small supply that keeps the BMC alive while the main power is off.
  5. Now that head1 cannot write to shared storage, head2 moves to BECOMEACTIVE. It runs the Prefailover script, which includes /cm/local/apps/cmd/scripts/slurm.takeover.sh when Slurm HA is configured with slurmctldstartpolicy = TAKEOVER. Then it runs the Mount script to mount the shared NAS at /cm/shared and /home. It brings up the shared internal virtual IP, eth0:0 or bond0:0, and the shared external virtual IP, eth1:0. It sends gratuitous ARP broadcasts so that compute nodes and external SSH users route to head2 seamlessly. A gratuitous ARP is a broadcast message that tells the network a new machine now owns an address, so every client updates its records at once. Finally it starts the active-only services, nfs-server, slurmdbd and the User Portal, and moves to ACTIVE.
  6. When head1 is repaired and boots, it sees that head2 is now active, and it comes up in PASSIVE. If the hard crash left the MySQL binlog replication on head1 out of sync, the mysql check fails in cmha status. The binlog is MySQL's log of changes, which the replica follows. To fix that, stop cmd on head1 and run cmha dbreclone head1. That command re-clones a clean snapshot of cmdaemon and slurm_acct_db from head2 to head1. You can then watch cmha status until head1 reports a healthy mysql check again.

12. Interview angles​

These are questions you may hear in an interview, with a short answer for each. The short answer is the one to give first, and the detail behind it is in the chapter.

  • "How does BCM avoid two active heads?" Answer with four mechanisms: fencing, proof of power-off through STONITH, a quorum across the nodes, and shared storage mounted only on the active head.
  • "What does BCM not replicate?" Everything outside CMDaemon-managed state. That covers non-default databases, unless you use the 11.34 option or extradbclone, and it covers local packages and files.
  • "Why did my failover test not fail over?" Most likely you used a graceful shutdown or pulled the cable. BCM deliberately does not treat either one as a failover trigger.
  • "How would you update the head nodes?" Update the active head first for CMDaemon and MySQL, confirm with cmha status, then update the passive head. Migrate services by switching first.
  • "Is a second head enough for HA?" No, not on its own. You also need shared storage, power control, a heartbeat link, static addresses, an HA license and tested scripts.

Checkpoint questions (20)​

1. In BCM head-node High Availability, what is the difference between Primary / Secondary and Active / Passive?

Primary and Secondary are fixed hardware identities, assigned at installation. They never change. Active and Passive are runtime roles that swap on failover. After a failover, the Secondary head becomes Active and the Primary becomes Passive.

2. Which services run simultaneously on BOTH head nodes at all times?

CMDaemon runs on both heads, including provisioning. So do DHCP (load balanced), TFTP, OpenLDAP (replicated), MySQL (master-replica replication), NTP, DNS, and the workload manager controller, which has one active instance and one standby.

3. Which services run ONLY on the currently Active head node and migrate during failover?

You will find NFS exports, the User Portal, slurmdbd (the Slurm accounting daemon) and the LSF batch daemons only on the Active head. They migrate during a failover.

4. Which MySQL databases are replicated between head nodes by default, and what happens to third-party databases after failover if nothing else is configured?

By default, only cmdaemon and slurm_acct_db are replicated. Any other database is not copied. Without further configuration, it will be missing after a failover unless you list it in extradbclone.xml.

5. What new option did BCM 11.34 add to cmha-setup for MySQL replication?

BCM 11.34 added an option to replicate all non-system MySQL databases, along with users and grants. In express mode you can use --replicate-all-databases, or -a. System databases, namely mysql, information_schema, performance_schema and sys, are never replicated.

6. How are the shared internal and external IP addresses implemented on the head nodes?

They are virtual IP alias interfaces, such as eth0:0 and eth1:0, or bond0:0 when the interfaces are bonded. They come up only on whichever head is currently Active.

7. Why does the manual recommend using a direct crossover/patch cable with no switch for failovernet?

With no switch in the path, a management switch reboot, spanning-tree reconvergence or a switch firmware bug cannot interrupt the heartbeat between the two heads. That means no false split-brain alarm.

8. On which head node are /home and /cm/shared (from the NAS) mounted during normal operation, and what happens if the pre-failover unmount script exits 0 when an unmount actually failed?

The shared storage is mounted only on the Active head. If the unmount script fails to unmount the old active head but still exits 0, both heads could mount the shared storage at once. The filesystem could then be corrupted. That is why the unmount script must return non-zero on failure, which places the node in UNABLETOBECOMEACTIVE.

9. What is a split-brain condition in cluster HA?

Split brain happens when communication between the two heads breaks while both are still running. The passive head cannot tell from the heartbeat alone whether the active head crashed or only the network link failed.

10. What is Fencing mode (FENCING state in cmha status)?

Fencing mode is the protective state the passive head enters when it loses contact with the active head. It tags local changes as a backlog. While in this state, it runs the quorum check and verifies power-off with STONITH before it becomes Active.

11. What is STONITH, and why is it mandatory for automatic failover?

STONITH stands for "Shoot The Other Node In The Head". It forcibly powers off the unresponsive active head through its out-of-band BMC or PDU. The passive head then checks that the power state is OFF before it mounts shared storage and takes the shared IPs. This proof is why STONITH is mandatory for automatic failover.

12. How does the Quorum check work before the passive head executes STONITH?

The passive head asks all regular compute nodes within Quorum time, which defaults to 60 s, whether they can still reach the active head. It proceeds with STONITH only if more than half confirm that the active head is unreachable. This stops a passive head with a bad NIC from shooting a healthy active head.

13. Which four checks appear in cmha status, and which three must all fail for the active head to be classified as "all dead"?

The four checks are failoverping, ping, status (the CMDaemon REST check) and mysql. Automatic failover triggers only when ping, failoverping and status are all NOT OK, which is the "all dead" state.

14. What does "mostly dead" ("slightly alive") mean in BCM HA, and what does the passive head do?

Mostly dead, or slightly alive, means that some of ping, failoverping and status failed, but not all three. For example, CMDaemon might hang so that status fails while ping still answers. The passive head takes no automatic failover action. It alerts the administrator, who inspects the head and fails over manually.

15. Why does yanking the AC power cords out of the active head node NOT trigger an automatic failover when power control is via the BMC?

If you pull the AC cords, you also take down the active head's BMC. When the passive head tries to query that BMC to verify or command power-off, the BMC does not answer. BCM cannot prove the active head is off, so it waits for manual confirmation.

16. Why does a clean reboot or shutdown -h now on the active head node not trigger automatic failover?

BCM treats a graceful OS shutdown or reboot of the active head as intentional maintenance. If you want to switch active heads on purpose, run cmha makeactive on the passive head.

17. How do you disable automatic failover during maintenance while keeping HA replication running?

In cmsh, run partition failover base; set disableautomaticfailover yes; commit.

18. What is the manual's recommended command to test automatic failover realistically in a maintenance window?

If you want to test automatic failover, trigger an immediate kernel panic on the active head with echo c > /proc/sysrq-trigger. It freezes the host OS just like a real crash, and the BMC stays powered on, so STONITH can succeed.

19. When updating cmdaemon and mysql packages on an HA head-node pair, which head node must be updated first and why?

Update the Active head node first, so you can verify with cmha status and restart cmd before you touch the other head. Only then update the Passive head. A CMDaemon update may include a MySQL schema migration, and that migration must be applied on the master database first. On Ubuntu, update mysql separately before cmdaemon.

20. Give four architectural differences between Regular Node HA (failovergroups) and Head Node HA (cmha-setup).
  1. Regular node HA is configured through partition[base] -> failovergroups, while head node HA uses cmha-setup.
  2. A regular node group supports two or more nodes, with one active node and $N-1$ passive nodes.
  3. Regular node HA uses no dedicated failovernet cable, because heartbeats travel over the regular internal network.
  4. The active head node runs the health checks and STONITH directly, instead of a cluster-wide node quorum poll.
