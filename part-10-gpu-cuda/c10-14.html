Why this matters for AI infrastructure​

Picture a team that has done all the memory homework from the previous chapter. An engineering team fixes every memory-layout defect from Chapter 10.13. Global loads coalesce into four sectors per request, vectors use wide types, shared-memory tiles have zero bank conflicts, and the Tensor Memory Accelerator prefetches buffers asynchronously. The team feels finished. Yet Nsight Compute still shows the kernel running far below hardware peak. Both DRAM bandwidth and Tensor Core utilization sit below a third of capacity. The memory side is clean, so the next question is what the warps are doing while they wait. That question leads to occupancy, branch divergence, and instruction-level parallelism.

This slowdown happens when Streaming Multiprocessors lack enough ready warps or independent instructions per thread to hide execution latency. Execution latency is the delay between issuing an instruction and getting its result. Think of a kitchen. If only a few cooks are on the line, and each one waits for the oven before doing anything else, the kitchen sits idle even though the ovens work fine. The fix is either more cooks who can take over while one is waiting, or a cook who can start a second dish before the first one comes out. Those are the two levers in this chapter.

It also happens when warps waste half their cycles executing divergent conditional branches. A divergent branch is one where the threads of a warp do not all take the same path. Even the fastest memory subsystem cannot save a kernel whose warps spend most of their time stalled at scoreboard dependencies or serialized conditional passes. A scoreboard is the hardware table that tracks which registers are still waiting for a result.

Four execution bottlenecks govern whether a GPU kernel turns raw memory bandwidth into useful compute throughput. Raw memory bandwidth alone does not produce results. The kernel must keep the math units fed, and the four bottlenecks below are the places where that feeding breaks down.

First, kernels move through four distinct execution regimes: underutilized, latency bound, memory bound, and compute bound. A regime is a label for what currently limits the kernel, and the label decides the fix, so it comes first. When both DRAM throughput and math pipe utilization are low, the kernel is not bandwidth-limited. A math pipe is the group of arithmetic units that carries out one kind of operation. Either the launch grid is too small to fill all Streaming Multiprocessors, or warps are latency bound because the number of eligible warps per cycle falls below the four warp schedulers on each SM. An eligible warp is one that is ready to issue its next instruction on this cycle. Think of the four warp schedulers as four cooks at the pass, each needing one ready dish per turn.

Second, register pressure and block sizing control how many warps can reside on an SM at once. Register pressure means each thread's live values need more of the SM's register file, so fewer threads fit. Resident warps are the warps that sit on the SM at the same time, and they are the workers in the kitchen. Data-center Ampere, Hopper, and Blackwell B200 GPUs support up to 64 resident warps per SM. Workstation and desktop Blackwell GPUs support 48 warps per SM. Using __launch_bounds__ guides the compiler to cap per-thread registers so enough blocks fit on each SM without spilling registers into slow HBM local memory. A spill sends a value that did not fit in registers to local memory, which lives in HBM and is slow to reach.

Third, data-dependent branches inside a warp serialize SIMT execution. SIMT, which stands for single instruction, multiple thread, means one instruction stream drives all 32 lanes of a warp. When a threshold check splits a warp evenly between two branches, the hardware runs both paths back-to-back with half the lanes masked off on each pass. Think of a line cook who plates either the fish or the salad for each order in a batch, one order at a time. Only half the crew moves on each pass, while the other half stands still. Replacing short branches with predication cuts dynamic instructions in half and doubles kernel speed. Predication means every lane runs the same instructions, and a per-lane flag decides which results are kept.

Fourth, Instruction-Level Parallelism hides latency inside each individual warp, so fewer resident warps are needed to saturate the SM. Instruction-level parallelism, or ILP, means a single thread has several independent operations in flight at once. With only one operation in flight per thread, saturating a Blackwell SM requires roughly three-quarters occupancy. Occupancy is the share of the SM's warp slots that are filled. Exposing four independent operations per thread cuts the required warps by threefold while nearly doubling instructions issued per cycle. In kitchen terms, ILP is a cook who starts a second dish while the first one is still in the oven, so fewer cooks are needed to keep the line moving.

None of them were rerun on live hardware for this handbook. Read the tables for their direction and rough size, and check the same effects on your own kernels before you rely on them.

Second, several numeric cutoffs in this chapter are handbook rules of thumb rather than strict hardware constants. Use the cutoffs to decide where to look first, not as a pass or fail line.

1. Profiling Bottlenecks, Warp Stall Reasons, and the Four Execution Regimes​

When an AI training or inference job runs slowly, running a kernel profiler blindly across thousands of launches wastes hours. It also produces gigabytes of unusable counter logs. Think of a mechanic who opens every panel of a car before listening to the engine. The faster way is to start with the symptom, then open only the panel that matches. Engineers need a structured top-down workflow that first isolates whether the GPU is waiting on the CPU, and then identifies the exact hardware stall inside the hottest kernels.

1.1 The two-tier profiling stack: Nsight Systems, Nsight Compute, and torch.profiler​

GPU performance engineering always proceeds top-down, from the system timeline to per-kernel hardware performance counters. Top-down means you start with the widest view and narrow down. First, Nsight Systems (nsys) paired with torch.cuda.nvtx annotations captures the end-to-end timeline of CPU dataloader threads, host-to-device DMA transfers, and stream concurrency. Annotations are labels you place in the code, and NVTX is the NVIDIA tooling that carries those labels into the profile. The timeline also records user-defined ranges for forward and backward passes. If the GPU timeline shows empty gaps while CPU threads prepare batches, the bottleneck is upstream in the data pipeline rather than inside any CUDA kernel.

Second, PyTorch Profiler (torch.profiler), powered by Kineto, CUPTI, and Linux perf, correlates high-level Python operators with underlying GPU kernel launches. Kineto is the tracing library PyTorch uses, CUPTI is the CUDA profiling interface that reads GPU events, and perf collects the CPU-side events on Linux. It exports timelines for Chrome tracing or Perfetto, which are two timeline viewers. Keep an important limitation in mind when reading torch.profiler reports. Enabling FLOP estimation computes formula-based estimates for known operators like matrix multiplication rather than reading actual hardware performance counters. Custom CUDA or Triton kernels can show zero FLOPs in torch.profiler even while saturating Tensor Cores. Treat those FLOP numbers as a guess from the operator shape, not as a measurement.

Third, Nsight Compute (ncu) replays individual hot kernels compiled with -lineinfo to collect exact hardware counters across the Streaming Multiprocessors, L1 and shared memory, the shared L2 cache, and HBM. Replay means the tool runs the same kernel again, with each pass collecting a different set of counters. Nsight Compute plots the kernel on the Roofline chart. It then attributes warp stall reasons to exact C++, PTX, and SASS lines. PTX and SASS are the intermediate and machine-level forms of the compiled kernel, so the attribution can reach below the code you wrote.

1.2 Decoding Nsight Compute's Warp Stall Reasons​

Every clock cycle, each of the four warp schedulers on a Hopper or Blackwell SM inspects its assigned warps. It issues one instruction, or two dual-issued instructions, from an eligible warp. Whenever a resident warp is not eligible to issue on a given cycle, Nsight Compute records the hardware stall reason. Think of a scheduler as a cook at the pass, glancing at the tickets. A warp that cannot move on this cycle is a ticket still waiting on the oven, and the stall reason says what that ticket is waiting for.

Reading the stall breakdown in practice​

A stall name tells you where a warp is waiting, but one stall rarely settles the question on its own. Read the whole breakdown and start with the largest slice. The table above gives a short meaning for each reason. The notes below explain how the big slices look in a real profile. A profile is a snapshot, so look at the mix of stalls rather than a single number.

Memory-related stalls come first. When a kernel waits on global memory loads, Stall: Long Scoreboard climbs. The scoreboard tracks each warp's outstanding memory requests, so a high Long Scoreboard share means warps keep waiting on slow DRAM loads. The same stall also appears when spilled local memory moves to and from device memory. Picture a cook waiting on a delivery from a far warehouse. Nothing nearby can fix that wait except asking for the ingredient earlier.

Stall: Short Scoreboard is the on-chip version. It means a warp waits for data moving between shared memory and registers. That delay is shorter than a DRAM load, but it still leaves the warp idle. It is the cook waiting on the prep bowl at the next station, rather than the long walk to the warehouse.

Two more memory signs are Stall: Memory Throttle and Stall: Not Selected. Memory Throttle means the load and store pipelines are saturated, so the hardware queues are full and no new memory request can be issued. Not Selected means the warp could issue, but it had to wait for free memory transaction slots. When these memory reasons dominate, the kernel is memory bound.

Use the source code view in Nsight Compute to find the lines behind these stalls. It highlights scoreboard dependencies and other hardware limits, such as special function unit throughput. Start at the hottest line in the view, then ask whether the warps are waiting on memory, on math, or on a barrier.

Stall: Exec Dependency means warps often wait for the result of an earlier instruction. The usual cause is too little instruction-level parallelism inside each thread, or an ALU latency bottleneck. An ALU is the arithmetic logic unit that does the math. A chain of dependent arithmetic forces each step to wait for the one before it, like a recipe in which no step can start until the last one finishes. When this reason dominates, the kernel is latency bound on compute.

When Stall: Compute Unit Busy is high, or the FP32 cores or Tensor Cores are almost always active, the kernel is compute bound. The math units are saturated, so warps are ready but cannot run any faster. This often shows as near-peak ALU pipe busy time, and it can match high power draw. On some GPUs the matching reason is Stall: Math Pipe Throttle, which means the math pipelines were full on every cycle. The cooks are busy and the oven is full, so the kitchen is limited by its equipment rather than by its people.

Other reasons are rarer. Stall: Memory Dependency is close to Long Scoreboard, because an operation waits on an earlier memory operation. Stall: Texture Throttle points to a busy texture caching subsystem. No Eligible or Idle means the scheduler had no warp ready to issue that cycle, often after a synchronization or because too few warps were launched. Rare reasons are still worth a look when they climb, but they seldom decide the fix on their own.

You do not need to memorize every reason. Look at the largest parts. Memory stalls that dominate mean a memory-bound kernel. Execution dependency stalls that dominate mean a latency-bound kernel on ALU work. Almost no stalls with a nearly full pipeline mean a compute-bound kernel. Keep this short list handy when you open a new profile.

Collect these numbers from realistic runs. A tiny test kernel can show a different stall profile from your real application, so do not draw conclusions from a toy case. Profile the same input size and batch size that production uses, or the stall mix will mislead you.

1.3 The Four Kernel Execution Regimes​

As you iteratively optimize a kernel with Nsight Compute, it typically progresses through four distinct performance regimes: underutilized, memory bound, latency bound, and compute bound. The chart below turns that progression into a set of questions you can answer from the profile. Work from the top, and stop at the first question that matches your kernel.

Read the flowchart as a series of yes-or-no questions. The first asks whether both DRAM throughput and compute are low while the SMs show little work. A yes sends you to the underutilized branch, where the fix is to launch more work. A no moves you to the second question, which asks whether DRAM is near its peak. A yes there means the kernel is memory bound. A no moves you to the third question, about the math pipes. The last two branches separate a latency-bound kernel, where warps wait with too few ready to issue, from a compute-bound kernel, where the math units are full. Each branch names a fix, so the flowchart ends with an action rather than a diagnosis.

In the underutilized regime, both DRAM bandwidth and compute pipe utilization sit low because the launch grid does not have enough blocks to keep all SMs busy. Imagine a kitchen with many empty stations. Increasing batch size, launching more blocks, or capturing short kernels in CUDA Graphs fills the SMs. A CUDA Graph records a sequence of launches once, so the CPU does not have to send each launch one at a time.

In the memory-bound regime, DRAM bandwidth approaches peak capacity while math pipelines wait on Long Scoreboard and Memory Throttle stalls. Shared-memory tiling, kernel fusion, and lower-precision formats reduce off-chip traffic. Fusion means combining two or more operations into one kernel, so the intermediate result never travels to HBM and back.

In the latency-bound regime, neither DRAM bandwidth nor compute utilization is near peak. Instead, warps stall on Long Scoreboard, Short Scoreboard, or Execution Dependency because the SM has fewer than four eligible warps per cycle. Raising occupancy or exposing per-thread ILP hides those latencies. Finally, in the compute-bound regime, math pipelines and Tensor Cores saturate with Math Pipe Throttle stalls, and further gains require lower precision or structured sparsity. Structured sparsity means a fixed pattern of zeros in the weights that the hardware can skip.

Always classify a slow kernel into one of the four execution regimes before changing code. That classification prevents you from applying memory optimizations to a latency-bound or underutilized kernel. It is the same habit as a doctor who names the condition before choosing the treatment.

GPUs can stall for four different reasons: underutilization, latency bound, memory bound, and compute bound. The regimes are related, but each needs its own fix. Fixing one bottleneck often reveals the next one. A kernel might move from underutilized to latency bound, then to memory bound, and finally to compute bound. Expect the label to change as you work, and classify again after each change.

1.4 Checking the data pipeline and host-side waits​

A GPU can look slow when the real delay happens somewhere else. Nsight Systems shows the whole pipeline, including data loading and preprocessing. If the GPU sits idle while the CPU prepares batches or runs augmentation, the bottleneck is usually the data pipeline, not the kernel. Augmentation means random changes to training images, such as crops or flips, applied before the batch reaches the GPU. This pattern is common in training loops.

Tune the pipeline only after you test it on a realistic, representative dataset. You can raise the number of data loader threads. You can overlap CPU preprocessing with GPU compute using double buffering. You can also move more of the preprocessing onto the GPU. Before you rewrite a kernel, confirm that the slowdown really sits inside it. A faster kernel does not help a GPU that is waiting for the next batch.

Use NVTX ranges to mark the regions you care about. Nsight Systems can then capture only those ranges. The CUDA profiler Start and Stop API also controls capture, but NVTX ranges are the recommended choice for framework workflows. In PyTorch, torch.cuda.nvtx provides range push and pop calls. You can label phases such as forward pass and backprop, so the timeline shows which iterations matter. A range push opens a labeled span, and a range pop closes it.

For years, the Nsight tools could not see Python code, and many PyTorch developers avoided them for that reason. Modern Nsight Systems can collect Python backtrace sampling. Sampling means it takes periodic snapshots of the Python call stack. It also has a PyTorch-focused mode with Python call-stack sampling and a PyTorch domain for correlated tracing. If you work in PyTorch, it is worth using these tools again for a fuller, linked view of the system.

The torch.profiler API works alongside them. It collects operator-level times, GPU kernel launches, memory copies, and hardware counter metrics. It relies on the Kineto library, which uses CUPTI for GPU events and Linux perf for CPU events. Kineto merges everything into one time-ordered trace. You can view that trace in the PyTorch profiler UI, in the Nsight Systems GUI, or in a Chrome browser. One trace from one run is easier to read than a set of separate tools with separate clocks.

Nsight Compute reads the device code side of the story. Compile device code with -lineinfo so that Nsight Compute maps counters to source lines. Use torch.cuda.nvtx ranges from Python to link model code to the kernels it launches. The source view shows the instruction mix and a throughput breakdown for each line that stalls. Device code is the code that runs on the GPU, as opposed to the host code that runs on the CPU.

The two tools work best as a pair. Start with Nsight Systems to find the hot kernels and the idle gaps on the timeline. Then zoom into each hot kernel with Nsight Compute for a detailed diagnosis. Both tools are updated for new GPU architectures, so the same workflow helps when you move a workload to a newer GPU generation. Keep the pair in mind as a map and a magnifying glass.

Before a kernel change, check for host-side waits. Remove unnecessary cudaDeviceSynchronize() calls and other host waits that stall the GPU. A host wait is a point where the CPU stops and waits for the GPU, so the GPU's queue runs dry for the time it takes to restart. Small workloads can be batched with other work, or several instances can run at once on separate CUDA streams.

A quick test helps decide whether the host side is the real problem. Run the same kernel twice, once with the data already resident on the GPU and once with a fresh copy before each run. If the second run is much slower, the copies are the wait, and no kernel change will help until those copies overlap with compute. The timeline in Nsight Systems tells the same story as a gap between kernels.

1.5 Fixing each regime and re-profiling​

Pick the fix from the regime, not from a favorite trick. A memory-bound kernel needs less traffic per result. A latency-bound kernel needs more work in flight. A compute-bound kernel needs more arithmetic throughput. An underutilized GPU needs more launched work. Each change should target one of these four problems. A favorite trick applied to the wrong regime can make the kernel slower, even when it looks clever on paper.

Nsight Compute's guided analysis helps here. Its rules can flag messages such as Memory Bound: L2 transactions per FLOP high or Compute Bound: issue stall reasons indicate pipe contention. These rules are updated for each architecture, including Blackwell. They confirm whether the limit is memory throughput, instruction dispatch, or latency hiding, and they point you to the metrics that matter. Read the message as a hint about where to look next, then check the counters that back it up.

Underutilization comes first in the usual order. The kernel has not launched enough threads or work. FLOPS and memory bandwidth both stay low, and the timeline shows idle gaps. Once you add parallelism, warps start to stall on memory loads, and the kernel becomes latency bound. Each fix moves the bottleneck, which is normal.

A latency-bound kernel moves fewer bytes per second than the hardware can deliver. Individual loads stall the warps. The fix is more overlap: raise occupancy, add ILP, prefetch data, and pipeline the work. You can also use async copies inside the kernel and several CUDA streams to overlap copies with compute. Merge many tiny kernels with cooperative groups or kernel fusion when launch overhead dominates. Launch overhead is the fixed cost the CPU pays to start each kernel, and it adds up when kernels are tiny.

A memory-bound kernel saturates DRAM bandwidth while the ALUs sit idle. The problem is not a stall. The memory pipe simply cannot supply more data each second. To fix it, raise arithmetic intensity. Use tiling to reuse data in shared memory, fuse kernels to avoid extra round trips, use the caches (L1 and texture), and reduce precision to move fewer bytes. Make sure accesses are coalesced and avoid bank conflicts. Think of a kitchen where one pantry door is the only way in. Speeding up the cooks does nothing. The fix is to carry more food through each trip to the pantry.

A compute-bound kernel is limited by its arithmetic pipes, such as CUDA cores and Tensor Cores. Use more ILP per thread through overlapping independent instructions, loop unrolling, and software pipelining. Software pipelining starts the next iteration's work while the current one is still finishing. Reduce dependencies and fuse work where it helps. If the kernel is at the compute roof, lower precision can give more speed, moving from FP32 to FP16, then FP8, then FP4.

Blackwell adds specialized hardware for this. Its Tensor Cores expose fifth-generation MMA instructions in PTX as tcgen05.mma, with matching loads and stores such as tcgen05.ld and tcgen05.st. MMA stands for matrix multiply-accumulate, the operation Tensor Cores perform in one instruction. PTX is the intermediate assembly language that NVIDIA's compiler produces. The Tensor Cores accelerate microscaling formats, including MXFP8, MXFP4, and NVIDIA's NVFP4. Microscaling formats attach a small shared scale to each small group of values. The hardware also supports block-scaled matrix multiplies, which libraries pick automatically when scale metadata is present. TMEM and TMA support these fast data paths. TMA is the Tensor Memory Accelerator, and TMEM is the tensor memory that sits beside the Tensor Cores.

For an underutilized GPU, make sure the grid is large enough to keep every SM busy. A common mistake is to launch one thread per element, even though each thread does only a little work. Sometimes you need several passes, or more threads per element, to fill the device. Check the grid size against the number of SMs before you tune anything else.

Work through the regimes in order, then verify each change. After a fix, profile again and confirm that the targeted stall or metric improved. Memory stalls should drop after tiling, and achieved occupancy should rise after you tune the block size. Also watch total runtime, because one bottleneck can hide another. A counter that improves while the runtime stays flat is a warning, not a win.

Keep correctness in view as you go. Test each lower-precision or new parallel version against a reference result, with assertions or numeric comparisons. Compare results with an FP32 baseline. Techniques such as FP16 and even FP8 are usually validated to have a negligible accuracy effect on AI models, but confirm that for your model. A fast kernel that returns slightly wrong numbers will cost more in debugging than it saved in runtime.

2. Occupancy Tuning: Hardware Limits, Eligible Warps, and Launch Bounds​

A developer writes a complex fused kernel with dozens of local variables per thread. Each thread consumes 80 registers, so a 256-thread block requires 20,480 registers. Because a Blackwell SM has 65,536 registers in total, only three blocks can reside on the SM at once. Theoretical occupancy drops to three-eighths of peak, and warp schedulers frequently run out of ready warps whenever a memory load stalls. The kernel is correct, but the SM has room for fewer workers than it needs.

2.1 Theoretical vs. achieved occupancy across GPU architectures​

Occupancy is the ratio of active warps resident on an SM to the maximum number of warps that the SM hardware can host. Think of occupancy as the number of workers who fit in the kitchen. A bigger kitchen with more stations can host more cooks, but they still share the same ovens and knives. On data-center Ampere, Hopper, and Blackwell B200 GPUs, each SM supports at most 64 resident warps or 2,048 threads. Each SM also provides 65,536 registers and 227 KB usable shared memory. When Nsight Compute reports 30 percent achieved occupancy on a B200 SM, only about 19 warps are active on average.

Workstation and desktop Blackwell GPUs, including the NVIDIA RTX PRO 6000 and Spark DGX with the GB10 Superchip, carry a higher compute capability number. However, their SMs support at most 48 resident warps or 1,536 threads per SM. Compute capability is NVIDIA's version number for a chip's feature set, and a higher number does not mean more warp slots. Always check your target GPU's maximum warps per SM before translating thread counts into occupancy percentages.

Chasing one hundred percent occupancy is not always beneficial. Moving from very low occupancy to moderate occupancy on a memory- or latency-bound kernel delivers a large speedup, because the four warp schedulers finally have enough warps to cover DRAM stalls. Once occupancy reaches roughly 50 to 75 percent, inspect Active Warps per Scheduler alongside Eligible Warps per Cycle in Nsight Compute. If Eligible Warps per Cycle is already four or higher, every warp scheduler has a ready warp to issue on every cycle. Squeezing registers further to reach full occupancy often slows the kernel down by spilling registers to HBM. A higher number on the occupancy bar is not the goal. The goal is a cook ready for every station.

The text block below collects the hardware ceilings and three worked examples. Read the ceilings first, because every example depends on them. The register example starts from the register file size and divides it by the register demand of one block. The shared-memory example does the same with shared memory. The launch-bounds line runs the calculation backward: it starts from the target number of threads and works out how many registers each thread may use. Each example ends with the name of the limiter, so you can see which resource ran out first.

2.2 Controlling occupancy with __launch_bounds__, -maxrregcount, and the Occupancy API​

When Nsight Compute reports that a kernel is limited by registers per thread, you have three mechanisms to guide register allocation and block sizing.

First, attach __launch_bounds__ directly to the __global__ kernel declaration. Specifying __launch_bounds__(256, 8) promises the compiler that the kernel will never launch with more than 256 threads per block and asks it to fit at least eight blocks per SM. Because eight blocks of 256 threads equal 2,048 threads per SM, nvcc automatically caps register usage at 32 registers per thread for that specific kernel. Other kernels in the same source file remain unaffected. Think of it as a sign on the door that sets the crew size for this one recipe, while the other recipes keep their own sizes.

__global__ __launch_bounds__(256, 8)
void myKernel(const float* __restrict__ in, float* __restrict__ out, int N) {
    // Promising maxThreadsPerBlock = 256 and minBlocksPerSM = 8 targets
    // 256 * 8 = 2,048 threads/SM (64 warps = 100% occupancy on B200).
    // nvcc automatically caps register usage at 65,536 / 2,048 = 32 regs/thread.
}

Second, pass -maxrregcount to nvcc to cap registers per thread across an entire compilation unit. A compilation unit is one source file and everything it builds. Use this flag with caution. Setting the cap too low forces the compiler to spill live registers to slow Local Memory in HBM, which immediately inflates Long Scoreboard stalls.

Third, call the CUDA Runtime Occupancy API functions cudaOccupancyMaxPotentialBlockSize and cudaOccupancyMaxActiveBlocksPerMultiprocessor at launch time. These functions inspect the compiled kernel's exact register and shared-memory footprint on the current GPU. They then return the block size and grid size that maximize theoretical occupancy. The API is the runtime's way of answering a question you would otherwise work out by hand.

int minGridSize = 0, bestBlockSize = 0;
cudaOccupancyMaxPotentialBlockSize(&minGridSize, &bestBlockSize,
                                   myKernel, /*dynamicSmemBytes=*/0, /*blockSizeLimit=*/0);
myKernel<<<minGridSize, bestBlockSize>>>(d_in, d_out, N);

In PyTorch workloads, you rarely set thread block bounds by hand. Instead, enable torch.compile with max-autotune for steady-state training and inference, or reduce-overhead for small-batch loops. When CUDA Graphs are unsuitable, use max-autotune-no-cudagraphs, and pass fused=True to torch.optim.AdamW so TorchInductor fuses tiny elementwise launches into high-occupancy kernels. Steady state means the shapes and the loop stay the same from one step to the next, which is when compilation pays off.

Use __launch_bounds__ rather than file-wide -maxrregcount when tuning register-limited kernels. Stop pushing occupancy higher once Eligible Warps per Cycle stays at or above four. A file-wide cap touches every kernel in the file, while the launch-bounds annotation changes only the one kernel you are tuning.

2.3 Reading achieved occupancy and its limiters​

Theoretical occupancy is the ceiling set by the hardware and the kernel's resources. Achieved occupancy is what the profiler measures while the kernel runs. It is the average share of warp slots that were filled on each SM. If a kernel's achieved occupancy is far below its theoretical value, the launch is probably too small to keep the SMs full. The gap between the two numbers is the first clue to check.

Nsight Compute also names the resource that limits the theoretical occupancy. Limited by max registers per thread means register usage stops more warps from being scheduled on each SM. Limited by shared memory per block means the shared memory each block allocates is the bottleneck. Limited by thread count means the launch configuration, meaning the grid or block size, did not request enough threads to fill the GPU. Read the limiter as the sign on the door that says which resource ran out first.

Each limiter points to a different fix. For registers, use fewer live variables or a __launch_bounds__ hint so more blocks fit. For shared memory, use smaller tiles and store only what the kernel needs. For thread count, launch more blocks or larger grids. Changing the wrong resource leaves the limiter in place, so match the fix to the named limit.

Higher occupancy is not always faster. Very low occupancy, around 10 to 20 percent, hurts performance because too few warps can hide latency. Pushing occupancy to 100 percent does not always help, because memory bandwidth and instruction dependencies can become the limit instead. You should check other hardware counters before you chase a higher number. A fuller kitchen with the same ovens is not a faster kitchen.

Nsight Compute reports several of these counters: achieved memory bandwidth in GB/s, achieved FLOPS in TFLOPS, instructions per cycle, issue-slot utilization, and other resource statistics. These show how close the kernel runs to the physical limits. If ALU utilization is low while memory throughput is at 95 percent of peak, the kernel is memory bandwidth bound. If ALU utilization is near its maximum and memory throughput stays modest, the kernel is compute bound. Issue-slot utilization is how often the scheduler actually has an instruction to send.

A compute-bound kernel gains speed only by raising arithmetic throughput. The usual route is lower-precision types, such as FP16, FP8, or FP4, running on Tensor Cores. If both ALU utilization and memory throughput are low, look for long-latency operations, synchronization overhead, low ILP, or too little parallel work. Low on both counts means the kernel is waiting, not working.

2.4 Comparing throughput with the hardware peaks​

The Roofline model puts this comparison in one picture. It plots a kernel's achieved FLOPS against its arithmetic intensity, which is FLOPS per byte moved. The roofline has a compute roof, the highest FLOPS the GPU can sustain, and a memory roof, the highest bandwidth it can deliver. A kernel that sits under the memory roof is limited by data movement, and a kernel that sits under the compute roof is limited by math.

If your kernel's FLOP per byte ratio is below the hardware's compute-to-memory ratio, you are memory bound. You cannot supply data fast enough. If the ratio is high but the FLOPS stay far below peak, the kernel is likely latency bound or short on ILP. Each new GPU generation raises bandwidth modestly while compute grows much faster. Kernels therefore tend to become more memory bound over time. The compute-to-memory ratio of the hardware is the point where the two roofs meet, and it moves with each generation.

Compare two numbers in every review. Put your kernel's memory throughput next to the peak memory bandwidth. Then put its compute throughput next to the peak FLOPS. Those two comparisons show whether the next change should target memory access, compute work, or parallelism. Write both numbers down in the same place, so the comparison stays honest across runs.

Nsight Compute reports the achieved GB/s of a kernel. If the kernel reaches near-peak memory bandwidth, more arithmetic will not help. You must raise arithmetic intensity by moving less data per operation. Reduced precision with Tensor Cores, concurrency that hides more latency, and kernel fusion all cut the size of the intermediate data that moves through global memory. A kernel that reaches about 80 percent or more of peak bandwidth is likely memory bound, because little headroom is left. Adding math to such a kernel does not change how long the data takes to arrive.

Blackwell changes this picture. It has a large 126 MB L2 cache. Its two dies connect through a 10 TB/s NV-HBI link, so they act as one for memory access. Many kernels that were memory bound on older GPUs may use the cache well on Blackwell. Use the memory chart in Nsight Compute to compare L2 traffic with DRAM traffic. A high L2 hit rate can ease a global memory bottleneck, which can leave the kernel limited by compute. On Blackwell, you can also control L2 data persistence to keep a critical working set resident. A working set is the data a kernel keeps coming back to, and persistence keeps that data in the cache instead of letting it be evicted.

Low achieved FLOPS often come from low occupancy or from stalls inside instructions. If only 30 percent of warps are active, the kernel sits far below the compute roof. Check the Occupancy section and Source Counters in Nsight Compute. Launch enough threads to fill the GPU, up to the resident warp limit per SM, which is 64 warps on many data-center parts. Achieved occupancy is measured per SM, because only warps on the same SM share resources and hide each other's latency. Think of each SM as one kitchen. Cooks in another kitchen cannot cover for a stall here.

Also check instruction issue efficiency. Blackwell has many SMs, so a small shortfall in each kernel adds up to a large loss across the device. The dual-die packaging does not, by itself, raise the per-SM issue rate. Packaging decides how the chip is built, while issue rate decides how fast each SM can start instructions. The two are separate questions.

If FLOPS are moderate to high and memory throughput is low, the kernel is mostly compute focused but held back by instruction dependencies. Check the Exec Dependency stall share to confirm. If compute throughput is near peak, the kernel is truly compute bound. At that point the memory access pattern is already tuned, or the kernel already uses lower-precision Tensor Cores. Confirm with the stall breakdown before you commit to a change.

Sustained near-peak compute can also hit the power limits of the GPU. The card then lowers its clocks to stay healthy, which can look like a kernel regression. Monitor the enforced power limit and any HW Slowdown flags during a run with the nvidia-smi query in Section 5. For scripts, NVML provides nvmlDeviceGetPowerUsage() and nvmlDeviceGetEnforcedPowerLimit() in CUDA C++, with equivalent Python APIs. NVML is the NVIDIA Management Library, the interface that nvidia-smi itself uses. A slower run on a hot card is a clock problem, not a code problem.

Here is one way a reading can go. The occupancy bar is low, the Eligible Warps per Cycle count sits below the scheduler count, and the top stall is Long Scoreboard. Memory throughput is also low. That combination says the warps have too little work in flight to hide DRAM latency. The next step is to raise occupancy or expose more ILP, then measure again. A different reading, with occupancy already healthy and the top stall reported as Math Pipe Throttle, points the other way. There the kernel needs lower precision or Tensor Cores, not more warps. The same counters can lead to opposite fixes, which is why you read them as a set.

Use all of these signals together. Look at occupancy, warp stall reasons, memory throughput, and compute throughput at the same time. A healthy kernel shows high occupancy, high warp efficiency, and balanced use of the execution units, including Tensor Cores. One signal alone can mislead you, so read them as a set.

2.5 Block size, register pressure, and the launch configuration​

Block size can limit occupancy on its own. A very large block, such as 1,024 threads, can use so many registers or so much shared memory that only one block fits on an SM. A moderate block of 128 to 256 threads lets several blocks reside on the same SM at once. Smaller blocks use fewer resources each, so more of them can run in parallel. Block size works like team size, and a team that is too big may leave no room for a second team.

Use the Nsight Compute occupancy calculator and the CUDA Occupancy API to test different launch shapes. The calculator suggests configurations for the highest theoretical occupancy. In practice, the fastest setting can sit a little below that theoretical peak. A lower occupancy can run faster when it means less register spilling or better memory coalescing. Always time the suggested bestBlockSize before you adopt it. The suggestion is a starting point, not an answer.

Some kernels need more threads simply because they launch too little work. If you launch only 20 warps per SM and the GPU supports 64, a larger grid or more threads per block can raise occupancy. Launch at least as many blocks as there are SMs, and usually many more, because blocks run in parallel on each SM. If SM Active Cycles stay low, scale up the workload or the batch size. A kitchen with only a few orders on the ticket rail will look idle no matter how fast the cooks are.

Register pressure is the next limit to watch. Each thread holds registers, and a kernel with too many live values forces the compiler to cut the number of resident warps. Unrolling too far makes this worse. When Nsight Compute shows Limited by Registers, dial back the unrolling, reduce the number of independent accumulators, or relax the launch bounds. Lowering the minimum blocks per SM, or raising the maximum threads per block, lets each block use more registers without spilling. A live value is one the kernel still needs later, and an accumulator is a running total that holds one such value.

Think of a launch bound as a budget that you write down in advance. The compiler reads the budget, works out how many registers each thread may use, and then shapes the code to fit. The budget is only as good as the numbers you put in. If you ask for a crew size that the kernel's register needs cannot fit, the compiler spills rather than fails. That is why the spill counters belong in your check after every change, not only the speed number.

The compiler usually makes good choices, so start there. Reach for __launch_bounds__ and the occupancy API when you know the kernel can trade per-thread resources for more active warps. Those tools help when heavy threads leave the SMs underoccupied. Start with the default, measure, and only then override it.

Occupancy has diminishing returns. Moving from 10 percent to 50 percent achieved occupancy on a memory-bound kernel can give a large boost, because the warps now cover the latency. Moving from 50 percent to 100 percent often adds little, since cache misses or bandwidth saturation take over. Around 60 to 70 percent, it usually pays more to improve memory locality, raise ILP, and use shared memory and registers as caches. Diminishing returns means each extra step buys less than the step before it.

3. Improving Warp Execution Efficiency: Branch Divergence and Predication​

A developer writes a thresholding or activation kernel using a standard conditional statement. Half of the elements in each warp are above the threshold and half are below. Even though every thread performs only one assignment in C++, the GPU takes twice as long to finish. Hardware counters show that the kernel executes twice as many dynamic instructions as expected. The code looks simple, yet the warps are doing double the work.

3.1 How SIMT branch divergence serializes warps​

In Nsight Compute, Warp Execution Efficiency measures the average percentage of the 32 lanes in an active warp that are predicated on and performing useful work per executed instruction. A lane is predicated on when its per-thread flag allows it to run the current instruction. Because all threads in a warp share a single hardware instruction pointer under SIMT execution, a warp can only fetch and issue one instruction at a time across all lanes. The lanes move together, so a lane that does not need an instruction still sits through it.

The before code is the familiar form. Each thread reads one value, compares it with the threshold, and writes either the value or zero. The if and else branches make the warp take two paths. Nothing in the code looks wrong, which is why the problem hides so well. The profile is the only place where the doubled instruction count shows up.

// BEFORE: Divergent branch (threshold_naive.cu, ASP Ch 8 p. 278)
if (X[i] > threshold) {
    Y[i] = X[i]; // Pass 1: active only for lanes where X[i] > threshold
} else {
    Y[i] = 0.0f; // Pass 2: active only for lanes where X[i] <= threshold
}

When a data-dependent condition splits a warp evenly, so 16 lanes take the first branch and 16 lanes take the second branch, the hardware serializes execution into two passes. In the first pass, the first 16 lanes execute while the remaining 16 lanes are masked off. In the second pass, the roles reverse. Dynamic instruction count doubles and Warp Execution Efficiency drops to 50 percent. In kitchen terms, half the crew plates fish while the other half waits, then the roles swap, so the whole batch takes twice as long.

A single-lane branch split is even more skewed during the divergent pass. If a single outlier thread takes an expensive branch while 31 lanes take the alternative branch, 31 of the 32 lanes sit completely idle for the entire duration of the first pass. One outlier can stall a whole crew, which is why sorting work by type helps so much.

3.2 Five techniques to eliminate warp divergence and Nsight Compute Table 8-3​

Five practical programming patterns eliminate or reduce intra-warp branch divergence. Intra-warp means inside one warp. Each pattern below changes either the code or the data, so that the lanes of a warp agree on the path they take.

First, replace short conditional branches with predication using the C++ ternary operator or PyTorch elementwise primitives such as torch.maximum and torch.where wrapped in torch.compile. The ternary select compiles to PTX conditional select instructions with zero branches. All 32 lanes execute a single uniform instruction stream without serial passes or branch-resolving stalls. The price is that every lane computes both values, so the trick works best when each side is short.

// AFTER: Predicated select (threshold_predicated.cu, compiles to PTX @p selp / mov with 0 branches)
float x = X[i];
Y[i] = (x > threshold) ? x : 0.0f;

Second, align branch boundaries to 32-thread warp boundaries so conditions are warp-unanimous. Divergence only occurs when threads inside the same warp disagree. Two different warps taking different branches incur zero divergence penalty. Dividing threadIdx.x by 32 computes a warp identifier that guarantees all lanes in any given warp take the exact same path at full warp execution efficiency. Think of it as splitting the kitchen into whole crews, so each crew does one job from start to finish.

Third, use warp-vote intrinsics such as __ballot_sync, __any_sync, and __all_sync to evaluate predicates across all active lanes in a single register operation. If all lanes or no lanes satisfy the condition, the warp can skip the second path entirely. Calling __ballot_sync builds a 32-bit bitmask of active lanes for work compaction. Work compaction means packing the lanes that need extra work into a list, so the rest of the warp can move on. A vote is a quick yes or no check by the whole crew.

Fourth, sort or partition heterogeneous data on the host or in a preprocessing pass before launching the compute kernel, so each warp receives uniform inputs. Heterogeneous data is a mix of different kinds of items. Partitioning sorts the items into groups before the kernel runs, so each warp sees a group of similar items. Fifth, when both conditional bodies contain hundreds of instructions, avoid predication, because predication forces every thread to compute both heavy paths. Instead, compact indices and launch two separate specialized kernels. Compacting indices means building a list of the positions each kernel should process.

3.3 Warp intrinsics for work inside one warp​

Sometimes the threads of one warp must share data, for example to add up a reduction. You can exchange values directly through registers with warp shuffle intrinsics, __shfl_sync and __shfl_down_sync. The other option is to stage the values in shared memory and call __syncthreads(). That path adds extra L1 and L2 traffic and needs a full-block barrier, so it slows the kernel down. A barrier makes every thread in the block wait for the others, even the ones that have nothing to contribute.

A shuffle moves data only between registers. It also synchronizes the 32 lanes of a warp at each instruction, and it adds only a few clock cycles of latency. For purely intrawarp work, shuffles are almost always the fastest choice. The warp basics earlier in Part 10 show full reduction and prefix-sum examples. A prefix sum is a running total across the lanes, where each lane gets the sum of all the lanes before it.

If the cooperation spans several warps, shuffles are not enough. You still need a block-level or grid-level barrier, such as __syncthreads(), or cooperative groups. Cooperative groups are a CUDA API for defining and synchronizing groups of threads at different sizes. In short, reach for __shfl_sync and its relatives when threads in the same warp must coordinate. Use block-level shared memory and __syncthreads() only when the cooperation truly crosses warp boundaries.

3.4 Measuring divergence and the payoff from fixing it​

Nsight Compute's Source Counters and Warp State statistics show divergent warps. Look for a high Branch Divergence metric. Poorly coalesced loads also show up, with many replay events or L2 cache misses. The profiler can flag shared-memory bank conflicts and Tensor Core pipeline stalls too. A high share of memory_throttle stalls can mean the kernel lacks memory-level parallelism. Try more independent memory accesses in flight, or asynchronous copies such as cp.async and the CUDA Pipeline API, to hide latency. Memory-level parallelism means many memory requests in flight at once, the way a kitchen that orders several ingredients together waits less.

Low warp execution efficiency is the main symptom of divergence. This metric is the average percentage of active threads in a warp. An efficiency of 30 percent means that, on average, only 30 percent of the threads do useful work at any moment. The rest sit idle because of divergence.

A divergent kernel also shows a high share of predicated-off instructions. These are instructions the hardware fetches and issues, but they do no work because their lane is masked off. The dynamic instruction count also looks inflated compared with the data you processed. Together, these two numbers show that each warp walks down every side of a conditional, one after another.

Divergence is easy to spot in source code. Any per-thread condition, such as a threshold check, a sparse-data loop, or a data-dependent filter, can trigger this serial pattern. To reclaim the lost time, eliminate or flatten the branch. You can make the condition uniform across the warp, pull it out of a tight loop, or replace it with arithmetic or a lookup table. A lookup table replaces the branch with a read from a small precomputed array.

Divergence often gives a modest gain. Warp-level fixes like these commonly deliver speedups of about 5 to 30 percent, which is small next to a change in the algorithm. They still matter in highly tuned code, where every cycle counts. A speedup of 1.1 to 1.3 times is common in a tight kernel. These fixes also work well with occupancy and memory-access tuning. Set expectations before you start, so a small gain is not mistaken for a failed fix.

When a kernel contains several divergence points, or each divergent branch carries heavy work, removing those branches can compound the gain. In the ideal 50/50 split, removing the divergent branch can nearly double throughput, up to about 2 times. Each eliminated heavy branch can add its own gain. Compounding here means the gains build on one another across the branches you remove.

Warp Execution Efficiency is easiest to read as a fraction of lanes doing useful work. When the number is high, almost every lane in the crew is busy on each instruction, and the remaining question is whether those instructions are needed at all. When the number is low, the crew is walking through each branch in single file, and the fix is to restructure the data or the condition. Check the number against the predicated-off share too. The two should move in opposite directions. If efficiency rises while predicated-off threads fall, the change did what you wanted.

Predication is not free, though. Some threads still compute values whose results are never used. If each branch does substantial work, computing both sides for every thread can cost more than mild divergence. Benchmark the branch version and the predicated version, and compare their warp execution efficiency in Nsight Compute. If efficiency is low and each branch is light, predication usually wins. If one branch is heavy, a little divergence or a separate kernel may be the better choice. Measure both, since the answer depends on the work inside each side.

3.5 Restructuring conditions and splitting kernels​

The best fix is to reorganize the data so each warp follows one path. Move the divergent condition outside the inner loop when you can, or into a separate kernel launch. You can also sort or group the data, so each warp handles similar cases. Divergence only affects threads within one warp, so threads in different warps never stall each other on a branch. The crew analogy holds here too. Different crews can take different orders without slowing one another down.

Take an array where negative values need different work than nonnegative values. A naive kernel puts an if (x < 0) check inside the loop, and every warp that mixes the two signs diverges. A better approach partitions the data first. One kernel handles all the negatives, and another handles the nonnegatives. Aligning the data with warp boundaries keeps most warps on a single path. The partition costs some time up front, and then each kernel reads a clean list.

Another option is to split the work into separate kernel launches, one for the if case and one for the else case. A prefix sum or stream compaction can distribute the threads to the right kernel. This removes the divergence, but it adds launches and extra logic that moves the data around. The trade is worth it only when divergence is a major cost and both sides are large in instruction count.

You can also rewrite a condition so it is warp-unanimous, meaning all 32 threads of a warp agree on it. A common trick uses the warp index. Compute int warpId = threadIdx.x / 32;, and then let half the warps run task A and the other half run task B. Every warp still evaluates the check, but all its lanes agree, so no warp splits. This works well when you can divide the work into coarse blocks of 32 threads. Coarse blocks here means whole warps taking the same task.

Warp-vote tools help too. Intrinsics such as __ballot_sync, __any_sync, and __all_sync let a warp decide together which lanes need special work. Cooperative groups offer the same votes through warp ballot, any, and all calls. The warp can then compact that work into one or a few lanes, instead of branching all 32. This can shift load imbalance onto a few lanes, so profile the result before you keep it. Load imbalance means some lanes now carry most of the work while the others wait.

3.6 Divergence in PyTorch code and fused kernels​

PyTorch does not expose warp intrinsics, so you cannot steer warp execution from Python directly. You still benefit, because PyTorch's own CUDA kernels use warp-level tricks. For example, torch.sum(x, dim=0) often uses warp reductions when the reduced dimension is small, within about 32 elements. Each warp then adds up its values with shuffles, without divergence or shared memory. The library does this for you. Your job is to hand it a tensor layout it can handle well.

If you write a custom CUDA kernel as a PyTorch extension, use the same warp-level ideas in device code. For a warp-wide sum or an exchange between threads, prefer __shfl_sync over a shared-memory approach. Watch for per-element if statements as well. Express the condition as a tensor operation, such as torch.where on the whole tensor, so the library can handle it in a vectorized, warp-friendly way. A tensor operation runs the same expression across all elements, which is the shape the GPU likes.

Fusion helps as well. When several elementwise operations run in one fused kernel, each warp does more useful work in a single pass. Fusion does not remove a divergence that is part of the algorithm. It does spread that overhead over more computation. For example, a ReLU followed by an abs() can run in one fused kernel, so the branch cost is shared across both operations. ReLU is a function that keeps positive values and sets negative values to zero.

The PyTorch version is short on purpose. The torch.maximum call against a zeros tensor computes the same threshold as the CUDA ternary. The decorator on the function lets the compiler build a fused kernel the first time the function runs. The synchronize call at the end waits for the GPU, which matters when you time the call, because launches return before the work is finished.

# threshold_op.py
import torch

@torch.compile()
def threshold_op(X):
    return torch.maximum(X, torch.zeros_like(X))

X = torch.randn(N, device='cuda')
Y = threshold_op(X)
torch.cuda.synchronize()

The compiler fuses these pointwise operations into kernels that behave much like the hand-written predicated version. It does not guarantee the best occupancy or ILP, so profile the result. In general, use built-in tensor operations instead of explicit Python loops with per-element conditionals. Pointwise means each output depends on one input position.

4. Exposing Instruction-Level Parallelism and Blackwell Dual-Issue Rules​

Suppose a kernel uses a large shared-memory tile and high register counts per thread, capping SM occupancy at a quarter or three-eighths of peak. With only 16 to 24 resident warps on the SM, each warp must keep multiple independent instructions in flight at the same time. Otherwise, the warp schedulers will stall on Execution Dependency and Long Scoreboard every time an instruction waits on the previous line's result. A warp with a single dish in flight leaves the scheduler with nothing to do while the oven runs.

4.1 How ILP hides latency within a single warp and cuts required occupancy​

Occupancy hides latency across different warps through Thread-Level Parallelism. Thread-level parallelism means many warps take turns, so while one waits, another runs. Instruction-Level Parallelism hides latency within a single warp by issuing multiple independent loads and math instructions back-to-back before consuming their outputs. Adding ILP does not change a kernel's arithmetic intensity, and it yields no speedup if execution units or HBM bandwidth are already completely saturated. Instead, ILP fills empty pipeline slots when warps are latency bound. Think of the two as two ways to keep the stove busy: more cooks, or one cook with more pans going.

Read the two blocks side by side. In the first block, the add needs the first multiply, and the second multiply waits behind that add. In the second block, the two multiplies are independent, so the second one can start while the first is still in flight. The add comes last, when both inputs are ready. The rearranged code is the same arithmetic in a different order, and that order is what lets the hardware keep busy while a result is on its way.

// BAD (Serial Dependency Chain -> Stall: Exec Dependency, ASP Ch 8 p. 285):
float u = x * x;
float temp = u + 1.0f; // Stalls waiting for u = x * x to finish BEFORE v = y * y can even issue
float v = y * y;

// GOOD (Reordered Independent Ops -> 2-Way ILP):
float u = x * x;       // Issues on cycle t
float v = y * y;       // Independent of u; issues immediately on cycle t+1 while u is in flight
float temp = u + 1.0f; // By the time temp issues, u has already progressed through the pipeline

Loop unrolling with #pragma unroll and multiple independent accumulators applies the same principle to memory loads and reductions. Loop unrolling copies the loop body several times in the code, so the compiler can see independent work side by side. Instead of loading one value, waiting hundreds of cycles for it to arrive, multiplying, and only then loading the next value, an unrolled four-way loop issues four independent loads back-to-back. All four HBM requests travel in parallel before the first multiply consumes the first value. An accumulator is the running total that a loop adds into, and several accumulators let the adds run side by side.

4.2 Blackwell's Unified INT32/FP32 Core Dual-Issue Rule and Register Pressure​

Two hardware rules govern how far you can push ILP and dual-issue on Blackwell GPUs. Dual-issue means one scheduler sends two instructions in one cycle. The rules below set the limits, so you know when extra ILP stops paying off.

First, understand Blackwell's unified integer and floating-point core design. On Ampere and Hopper, separate integer and floating-point datapaths allowed a single lane to execute an integer pointer-arithmetic instruction alongside a floating-point math instruction. A datapath is the set of circuits that carries one kind of operation. On Blackwell, the floating-point and integer units were merged into unified CUDA cores. Each unified core executes either floating-point math or integer math in a given clock cycle, never both on the same core in the same cycle. Instead, each of the SM's four warp schedulers can dual-issue one arithmetic instruction paired with one memory load or store instruction from the same warp. Think of the arithmetic and the memory instruction as two different jobs for two different tools, so they can go out together.

Second, balance loop unrolling against register pressure. When #pragma unroll and ILP restructuring succeed, Nsight Compute shows Execution Dependency stalls dropping and per-scheduler Instructions Per Cycle rising from 1.0 to 1.8 instructions per cycle. However, keeping four or eight independent loads and accumulators live at the same time consumes extra registers per thread. Pushing ILP beyond four-way rarely improves speed, and it can drop occupancy or trigger Local Memory spills, so always verify in Nsight Compute that register limits were not exceeded. The unroll that helps today can hurt after the next code change, so check it each time.

Expose two-to-four-way ILP per thread by issuing independent loads and math operations back-to-back. Pair arithmetic instructions with memory load and store instructions to exploit dual-issue on Blackwell warp schedulers. Start at two independent operations, then measure before you go further.

4.3 Writing code that exposes ILP​

Most ILP comes from the way you write the loop. The goal is to issue several independent operations per thread before you need any one of their results. Two patterns cover most cases. The first is unrolling a small loop with separate accumulators. The second is interleaving operations on different data. Both patterns give the scheduler something to do while a load is pending.

Consider a loop that multiplies four values and adds them into one sum. Each step depends on the sum from the step before, and each iteration finishes its load and its multiply before the next one begins. Unrolling the loop changes that. The four loads are issued first, and each multiply can start as soon as its load returns. The overlap hides the memory latency. The first block below is the reference, and the second block is what the rewrite looks like.

float sum = 0.0f;
for (int k = 0; k < 4; ++k) {
    float a = A[idx * 4 + k];
    sum += a * w[k];   // dependent on load a
}
float a0 = A[idx * 4 + 0];
float a1 = A[idx * 4 + 1];
float a2 = A[idx * 4 + 2];
float a3 = A[idx * 4 + 3];
float sum0 = a0 * w[0];
float sum1 = a1 * w[1];
float sum2 = a2 * w[2];
float sum3 = a3 * w[3];
float sum = sum0 + sum1 + sum2 + sum3;

Interleaving works the same way. When two results do not depend on each other, write them as separate statements. The first multiply can start as soon as its input is ready, and the second can overlap with it. Keep the execution units busy by not letting one dependent instruction block the next independent one.

float x = A[idx];
float y = B[idx];
float u = x * c;   // can start as soon as x is ready
float v = y * d;   // can start as soon as y is ready, overlapping with u

Compiler hints help the compiler build these chains. #pragma unroll on a short loop gives it more independent work to schedule. If the unrolled code needs more registers, you can raise the limit with -maxrregcount. More registers per thread means more ILP and fewer threads, so occupancy trades against ILP.

Be careful with very large unrolls. Excessive unrolling can bloat the code size, which saturates instruction fetch and decode. Instruction fetch and decode are the front end that reads and sorts the instructions for the scheduler. Watch the instruction-fetch and issue stall reasons in Nsight Compute after each change.

A common misunderstanding is that more ILP means more work. It does not. ILP does not add operations. It keeps the existing operations busy while others wait on memory or on earlier results. ILP only helps when the issue slots sit idle because of latency. If a tight loop already uses every execution unit on every cycle, more ILP will not speed it up. ILP and occupancy also work together. Occupancy gives the scheduler many warps to switch to, and ILP lets one warp issue several independent instructions. A CPU with out-of-order execution follows the same idea, but here the compiler sets the schedule.

Blackwell schedulers can issue more than one instruction per cycle. Each SM has four warp schedulers, and each scheduler can dispatch up to two independent instructions in a cycle. This is called dual issue. Two instructions do not need to fire in the same cycle to overlap, though. While one long load is pending, the warp can issue a different independent instruction on the next cycle. By the time the data returns, the arithmetic has already made progress.

The register file is large enough to support this. Each SM has 256 KB of registers, which is 64K 32-bit registers. That capacity lets ILP run without spilling, as long as the unrolled code does not exceed the per-thread limit. Keep the count in mind when you add accumulators, because each one takes registers from the same pool.

Not every ILP change pays off. If the kernel is already limited by DRAM bandwidth, the extra loads queue behind a bus that is already full. If the loop is short and the compiler already scheduled the independent work, the source change does nothing. In both cases the counters look the same before and after. The right response is to go back to the regime classification in Section 1.3 and pick a different fix. An ILP change that leaves the stall mix untouched is a signal to stop, not a signal to add more unrolling.

Check the result in Nsight Compute. A successful ILP change lowers the Exec Dependency stall share. It also raises the instructions per cycle per warp scheduler. On this path, the metric can rise from 1.0 to about 1.8 instructions per cycle. The exact value depends on the instruction mix and the scheduler limits, so compare before and after on your own kernel.

Checkpoint questions (20)​

1. How do Nsight Systems, Nsight Compute, and torch.profiler divide profiling responsibilities, and why must you be careful with FLOP estimation in torch.profiler?

Nsight Systems (nsys) captures the system-wide CPU and GPU timeline, dataloader gaps, NVTX ranges, and stream overlap. Nsight Compute (ncu) collects hardware PMU counters for individual kernels including Roofline metrics, warp stall reasons, and occupancy limiters. The torch.profiler tool correlates Python operators with GPU kernels, but its FLOP estimation flag computes formula-based estimates for known operators rather than reading hardware counters.

2. Contrast Long Scoreboard stalls against Short Scoreboard stalls in Nsight Compute's Warp State Statistics.

A Long Scoreboard stall means the warp is waiting for a long-latency off-chip global memory load or a spilled Local Memory access to return to a register. That round trip takes roughly 800 cycles. A Short Scoreboard stall means the warp is waiting for a shorter, variable-latency on-chip Shared Memory load of roughly 20 to 30 cycles or a Special Function Unit result.

3. What does a high percentage of Execution Dependency stalls indicate in Nsight Compute, and what two code transformations fix it?

Execution Dependency stalls mean warps are waiting on the register output of a prior arithmetic or ALU instruction inside the same thread due to low Instruction-Level Parallelism. Fix it by reordering independent instructions before dependent consumers and unrolling small loops with #pragma unroll using multiple independent accumulators.

4. Why is seeing a high percentage of Not Selected stalls in Nsight Compute usually a good sign rather than a bug?

Not Selected means the warp was completely ready and eligible to issue an instruction, but the SM's warp scheduler chose another eligible warp in that scheduling partition on that clock cycle. It proves that occupancy is high enough to keep multiple ready warps available so the scheduler can hide latency every cycle.

5. Contrast the four kernel execution regimes from Table 8-2 of AI Systems Performance Engineering Chapter 8.

An underutilized kernel shows both low DRAM bandwidth and low FLOPs with No Eligible stalls because too few blocks were launched. A latency-bound kernel has resident work but low DRAM and FLOP utilization because warps stall on scoreboard or execution dependencies with fewer than four eligible warps per cycle. A memory-bound kernel saturates DRAM bandwidth while ALUs wait for data, and a compute-bound kernel saturates ALU or Tensor Core pipelines with Math Pipe Throttle stalls.

6. What is the maximum number of resident warps and threads per SM on Ampere, Hopper, and Blackwell B200 versus workstation Blackwell GPUs?

Data-center Ampere, Hopper, and Blackwell B200 GPUs support up to 64 warps or 2,048 threads per SM, so 30 percent achieved occupancy equals roughly 19 active warps per SM. Workstation and desktop Blackwell GPUs such as the NVIDIA RTX PRO 6000 and Spark DGX GB10 Superchip support up to 48 warps or 1,536 threads per SM.

7. How do Eligible Warps per Cycle and Active Warps per Scheduler in Nsight Compute tell you whether raising occupancy will actually speed up your kernel?

Each Hopper or Blackwell SM has four warp schedulers. If Eligible Warps per Cycle is below four, the schedulers frequently have no ready warp to switch to when a warp stalls, so raising occupancy or ILP will directly increase throughput. If Eligible Warps per Cycle is four or higher, the schedulers already have ready warps every cycle, and adding more occupancy yields diminishing returns.

8. What are the three occupancy limiters reported by Nsight Compute, and what happens if a 256-thread block uses 80 registers per thread on a Blackwell SM?

The three limiters are Registers per Thread, Shared Memory per Block, and Thread or Block Count Slots. At 256 threads per block and 80 registers per thread, each block consumes 20,480 registers, so a 65,536-register SM can host at most three blocks. That caps residency at 24 warps or 37.5 percent theoretical occupancy and flags Registers per Thread as the limiter.

9. What do the two parameters in __launch_bounds__(256, 8) specify, and how many registers per thread does that annotation allow on a Blackwell SM?

The first parameter promises the kernel will never launch with more than 256 threads per block. The second parameter requests that the compiler cap registers so at least eight blocks fit on each SM. Dividing 65,536 registers by 2,048 threads caps the kernel at 32 registers per thread.

10. How do you query the optimal block size for a kernel programmatically at runtime in CUDA C++, and why must you still benchmark the suggested configuration?

Call cudaOccupancyMaxPotentialBlockSize along with cudaOccupancyMaxActiveBlocksPerMultiprocessor. You must still benchmark because full theoretical occupancy is sometimes slower than moderate occupancy if smaller blocks reduce shared-memory tile reuse or per-thread ILP.

11. What PyTorch compiler modes and optimizer flags does AI Systems Performance Engineering Chapter 8 recommend to improve kernel occupancy and launch efficiency automatically?

Use torch.compile in max-autotune mode for long-running training and inference with stable shapes, reduce-overhead for small-batch loops, or max-autotune-no-cudagraphs when CUDA Graphs are undesirable. Pair compilation with torch.optim.AdamW using fused=True and Automatic Mixed Precision to fuse dozens of tiny optimizer launches into a single high-occupancy kernel.

12. Why does an even divergent branch inside a warp drop Warp Execution Efficiency to 50 percent and double dynamic instruction count?

All 32 threads in a warp share a single hardware instruction counter under SIMT execution. When 16 threads take the first branch and 16 take the second branch, the hardware executes the first path with the other 16 lanes masked off and then serially executes the second path. That serialization doubles dynamic instructions while keeping only half the warp active on each pass.

13. How does predication eliminate warp divergence, and when can predication actually hurt performance?

Predication compiles short conditionals into a uniform instruction stream using a per-lane predicate mask in PTX with zero branch instructions and zero warp serialization. However, because every thread executes the instructions for both sides of the expression before selecting the result, predication hurts performance if the branch bodies are long and compute-heavy.

Kernel execution time dropped from 30 ms to 15 ms, dynamic instruction count fell by half, and average warp branch-resolving stall latency fell from 200 cycles to 100 cycles. At the same time, Warp Execution Efficiency rose from 50 percent to 99 percent and Predicated-Off Threads dropped to zero percent. See Table 8-3 in Section 3.2 for the exact table.

15. What is a warp-unanimous branch, and what do the warp-vote intrinsics __ballot_sync, __any_sync, and __all_sync do?

Because integer division of threadIdx.x by 32 produces the exact same value for all 32 lanes inside a warp, branching on the warp identifier guarantees that all lanes take the same path with zero SIMT divergence. Warp-vote intrinsics evaluate a predicate across active lanes in one register instruction. Calling __any_sync returns true if any lane is true, __all_sync returns true if all lanes are true, and __ballot_sync returns a 32-bit bitmask of which lanes evaluated true.

16. Does increasing Instruction-Level Parallelism change a kernel's Arithmetic Intensity, and when does adding ILP yield zero speedup?

No, ILP does not change total FLOPs or bytes moved, so arithmetic intensity stays constant. ILP overlaps independent instructions in flight within each thread to hide latency and fill idle issue slots. If a kernel is already saturating all execution units or HBM bandwidth every cycle with no latency stalls, adding more ILP yields zero speedup.

17. How do required threads per SM, warps per SM, and SM occupancy percentage change across ILP levels one through four in Table 8-4 of AI Systems Performance Engineering Chapter 8?

With single-instruction ILP, saturation requires roughly 1,536 threads or 48 warps at 75 percent occupancy. Increasing ILP to two, three, and four independent operations per thread progressively lowers the required active warps down to 16 warps or 25 percent occupancy. See Table 8-4 in Section 4.1 for all four rows.

18. Why does pushing per-thread ILP beyond four-way typically hurt or stop improving performance on Blackwell?

Once two-to-four-way ILP saturates the SM's warp schedulers and instruction issue slots, unrolling further consumes extra registers per thread, risking occupancy drops or local-memory register spills. Excessive unrolling can also bloat binary size and exceed the SM's instruction-fetch and decode bandwidth.

19. Why can a single Blackwell CUDA core not dual-issue an integer instruction and a floating-point instruction in the same clock cycle, and how does dual-issue work on Blackwell instead?

On Blackwell, the integer and floating-point execution units were unified into a single core per lane that must choose either floating-point or integer math each clock cycle. Instead, each of the SM's four warp schedulers can dual-issue one arithmetic instruction paired with one memory load or store instruction from the same warp in a single cycle.

20. How do you verify in Nsight Compute that loop unrolling (#pragma unroll) and ILP restructuring succeeded without causing excessive register pressure?

Check three counters together in Nsight Compute. First, verify that Execution Dependency stalls drop significantly. Second, confirm that issued Instructions Per Cycle per warp scheduler rises toward 1.8. Third, check that the Occupancy section does not show a severe drop from register limits or non-zero Local Memory spills.
