Why this matters for AI infrastructure​

User-reported error messages in production GPU clusters almost never name the actual failing hardware or software layer. A user writes "the GPU is broken" and attaches a stack trace. The message names the place where the failure became visible, which is rarely the place where it started. When engineers react to surface symptoms without a structured triage order, they replace healthy motherboards, swap network switches or raise collective timeouts while the true root cause remains untouched. Mastering cross-layer troubleshooting lets on-call teams isolate the exact broken subsystem in minutes. The habit that makes this work is simple. Before you touch any hardware, you collect the evidence that separates the layers from one another.

Consider three classic misdiagnoses. First, a researcher reports an out-of-memory error on an idle A100 where nvidia-smi shows zero total memory. Unracking the server wastes days when the real cause is MIG mode enabled with zero GPU instances created, a container shipping a stale NVML library against a newer host kernel, or a dead OS process holding memory inside a zombie CUDA context. Each of those three causes is a software or configuration state, and each one is cheap to check. None of them requires a repair technician.

Second, a distributed training run crashes with an NCCL operation timeout. Blaming the network fabric misses the fact that three ranks reached collective operation 4821 while Rank 3 is stuck at operation 4820 with almost zero GPU utilization. A rank is one process in the job, and every rank has to reach the same collective before any of them can move on. Rank 3 is stalled because its local disk is full and its dataset shard is more than four times larger than Rank 0's shard. The network was waiting on Rank 3, not broken.

Third, a Grafana dashboard reports 100% GPU utilization and normal power draw while training throughput drops by fivefold, or attaching a profiler cuts throughput in half. Those dashboards are not lying on purpose. They are answering a narrower question than the one the team is asking. This final chapter of Part 10 walks through the 12 end-to-end GPU troubleshooting runbooks. It also covers the four incident postmortem labs and the production incident playbooks, and it follows each runbook from the first symptom to a decision.

1. Runbook Family 1: Missing GPU Memory, Zombie Contexts, DKMS, and Container Visibility​

1.1 The four causes of missing or unavailable GPU memory​

Picture the scene. A researcher starts a job on a node that worked yesterday. The script dies on its first allocation with CUDA_ERROR_OUT_OF_MEMORY, and when you run nvidia-smi the card shows no memory at all. The instinct is to suspect dead HBM stacks and open an RMA ticket. When a training script crashes immediately with CUDA_ERROR_OUT_OF_MEMORY or cudaGetDeviceProperties returns zero total memory on an A100-SXM4-80GB, operators can waste hours suspecting dead HBM stacks. In practice, missing or unavailable GPU memory almost always stems from one of four software or configuration states on the host. HBM is the high-bandwidth memory stacked next to the GPU die, and a real hardware fault there is rare compared with a configuration change. Comparing the failing GPU against a healthy peer GPU on the same node narrows the root cause in seconds. The healthy peer is your control, so any difference between the two is a clue.

First, check for the MIG zero-instance trap. MIG stands for Multi-Instance GPU, a mode that splits one card into hardware partitions. When MIG mode is enabled on a GPU, CUDA applications cannot allocate memory on the parent physical device. Instead, they can only allocate through instantiated GPU Instances, which are the partitions themselves. If an admin enabled MIG mode without creating any instances, nvidia-smi reports 0 MiB total memory on that GPU while adjacent GPUs report their full 81,920 MiB capacity. The fix is either to create the instances you meant to create or to turn MIG off. Also verify that CUDA_VISIBLE_DEVICES uses the full MIG UUID rather than bare device index 0, because a bare index can point at the parent device, which has no memory to give.

Second, check for a userspace versus kernel driver version mismatch. Userspace is the set of libraries a program loads, and the kernel module is the driver that runs in the operating system. They must agree on a version. If a container image bakes in a stale NVML library or a host upgrade leaves old symlinks behind, NVML fails to initialize when talking to the newer nvidia.ko kernel module. NVML is the management library that the monitoring tools call. Updating the symlink with ldconfig or injecting host libraries via the NVIDIA Container Toolkit resolves the mismatch immediately, because the library the program loads finally matches the driver underneath it.

Third, check for an orphaned zombie CUDA context. When a training process crashes ungracefully, the kernel driver can keep its GPU memory allocation pinned to a dead OS PID that no longer appears in ps. A CUDA context is the per-process state the driver keeps for the GPU. Killing open file descriptors on /dev/nvidia0 with fuser -k or resetting the GPU reclaims the memory. Fourth, check whether legacy ECC Page Retirement has blacklisted enough pages to drop total memory below your pre-flight capacity gate. A pre-flight gate is a check that runs before a job is allowed to start on a node. Read the four causes in that order, because the first two are answered by a single command each.

1.2 Kernel patch DKMS breaks, missing Enroot hooks, and systemd boot races​

Even when GPU hardware and MIG settings are healthy, OS patching pipelines and container runtime updates can sever the link between workloads and the GPU driver. A patch is a small update that the operating system applies on a schedule, and it can rebuild or replace pieces the GPU stack depends on. Fleet operators frequently see an entire maintenance batch fail nvidia-smi after a routine kernel upgrade. The batch looks like a fleet-wide hardware problem, but it is a sequencing problem. Similarly, Slurm containers can lose GPU visibility while Kubernetes pods on the same host run fine, or node health agents can fail permanently at boot. Two things on the same host can disagree about the GPU, and the disagreement is the clue.

The table below details the diagnostic evidence and atomic fixes for these three lifecycle incidents.

Walk through the three incidents as small stories. The DKMS story starts with a patch wave that stops at the first reboot. The module was built for the old kernel, so the new kernel boots without a driver for the GPU. The Enroot story starts with a golden image update that quietly removed a hook file, so containers started through Slurm never receive the device. The boot race starts with a health agent that tries to talk to the driver before the persistence service has prepared it, hits its restart limit and stays failed. In each story the first check is about order. Which component should have run first, and did it? The fix is to restore the missing step and then make the order explicit in the install or the unit file, so the next reboot does not depend on luck.

2. Runbook Family 2: Thermal Throttling, Fan Rise Rates, PSU Brownouts, and DVFS Clock Instability​

2.1 Separating thermal throttling from power limiting​

Picture a run that was steady for an hour and then slowed down. The graph shows the clock sliding while the job keeps going, and every rank waits at each collective for the one slowed GPU. When a GPU's clock frequency drops in the middle of a training run, throughput can fall by 15% to 40% while every rank in the collective waits on the slowed device. Operators who only inspect temperature, clock speed and power draw often guess the wrong cause and order a larger power supply for a cooling problem. Lowering clock frequency automatically reduces dynamic power draw, so the power reading falls as a consequence of the slowdown, not as its cause. Observing a lower power reading alongside a lower clock never proves that a power limit caused the slowdown.

To separate thermal throttling from software power caps and hardware PSU brake events, always inspect the hardware throttle reason bitmask in nvidia-smi -i 0 -q -d PERFORMANCE and DCGM_FI_DEV_CLOCK_THROTTLE_REASONS. A bitmask is a set of flags, one per reason, and each reason shows as Active or Not Active. The reasons are the question. Read them before you read the power or the clock, because the reason tells you which fix to order. Thermal slowdown needs airflow or a cooling repair. A software power cap needs a limit change. A hardware power brake points at the power supply.

dcgm-exporter 4.9.0 version note. dcgm-exporter 4.9.0 (2026-11-06) renamed many default metrics and changed some units. For example DCGM_FI_DEV_GPU_UTIL (percent) became DCGM_FI_DEV_GPU_UTIL_RATIO (0 to 1), and DCGM_FI_DEV_FB_USED (MiB) became DCGM_FI_DEV_FB_USED_BYTES. The metric names in this chapter are the 4.8.x names. On a 4.9.0 exporter use the full mapping in 17.4, and change thresholds together with the unit.

Keep an important hardware caveat in mind when triaging data-center servers. HGX and DGX SXM modules such as H100 SXM5 and B200, as well as passively cooled PCIe cards such as H100 PCIe and L40S, have no on-board GPU fan. As a result, nvidia-smi reports N/A for fan speed. Their airflow comes from server chassis fans managed by the BMC via ipmitool sdr type Fan or from direct-to-chip liquid cooling loops. Degraded thermal interfaces require a vendor RMA rather than opening a sealed GPU module in the rack.

2.2 Fan degradation, temperature rise rate, and the 2h 35m postmortem​

Imagine a cooling fan that is failing slowly. Nothing alarms during the day, because the GPU never gets hot enough to trip a static threshold while it is idle. The first sign appears only when a heavy job starts, and the temperature climbs faster than it used to. Relying solely on a static 85°C temperature alert catches cooling failures only after a GPU is already throttling in the middle of a production job. A degrading chassis fan bearing or failing liquid-cooling pump reveals itself weeks earlier through an abnormally steep temperature rise rate during the first 30 to 60 seconds of load. The rate of change, which is the derivative, is the early signal that the static number misses. Measuring the temperature derivative in Prometheus turns reactive thermal outages into scheduled maintenance.

In the fan-failure postmortem, a training job started at 06:00 on a node with a degrading fan bearing and did not trip the static 85°C alert until 08:15. Swapping the fan module took 20 minutes and wasted 2 hours and 35 minutes of cluster time. Adding a Prometheus derivative alert and a weekly 30-second burn test catches degrading fans two weeks before hard failure.

2.3 Power supply brownouts, 12V voltage sag, and PSU capacity sizing​

Picture a node that runs cool and still slows down in short, sharp dips. The temperatures are fine, the fans are fine, and the drops line up with the moments when all the GPUs start heavy work together. When all eight GPUs in a server transition simultaneously from an idle network barrier to heavy Tensor Core matrix multiplication, node power demand spikes by several kilowatts in milliseconds. A barrier here means the point where every GPU waits for the others before the next phase. If the power supplies are undersized or a 12V auxiliary rail sags under the transient load, the GPU asserts a hardware power brake slowdown or drops its enforced power limit. A rail is one of the DC voltage lines the power supply feeds to the board. That action cuts clock speeds across one or more GPUs while temperatures remain completely cool, which is the sign that power, not heat, is the cause.

You diagnose a PSU brownout by checking BMC voltage sensors with ipmitool sensor list and ipmitool sel list. Verify that total PSU wattage includes at least 30% headroom above peak GPU power draw. If a node's PSU is undersized, cap total GPU power to 80% of PSU capacity using nvidia-smi -pl until higher-wattage PSUs are installed.

The three power rows answer three questions in order. The first asks whether a GPU is being held back by a limit or a brake, and the reading of each GPU tells you whether one card behaves differently from its neighbours. The second asks whether the voltage at the board stayed inside its band during the spike, and a reading below the warning line is the direct evidence. The third asks whether the node was ever sized for its load at all. A sizing calculation is cheap, and it is the only row that tells you whether the fix is a setting or a new power supply. Keep the three rows in that order so you do not reach for a bigger supply when a cap would have solved the problem.

2.4 DVFS clock instability at flat 65°C temperature​

Imagine the clock trace on a dashboard that looks like a saw blade. The temperature is cool and no throttle reason is active, yet the frequency keeps dropping and recovering. Sometimes a GPU's graphics clock oscillates wildly every half-second even though temperature is a cool 65°C and every hardware throttle bit reads inactive. This clock jitter creates variable iteration times that slow down synchronous all-reduce steps across the entire cluster. Because every rank waits for the slowest step, a jittery card costs the whole job, not just its own share.

The root cause is firmware Dynamic Voltage and Frequency Scaling reacting to short 5-millisecond idle gaps between bursty DataLoader batches by downshifting from performance state P0 into power-saving states P2 or P3. An operator script can also leave a stale low clock lock behind. Data-center GPU DVFS is managed entirely in GPU firmware, so there is no host BIOS toggle that disables GPU DVFS. Lock the GPU graphics clock with nvidia-smi -lgc and set the host CPU governor to performance to eliminate the oscillation.

The DVFS row reads as a short story with a clear order. The clock and power trace show the oscillation, and the state column shows the card moving between its performance states. The fix is in three moves. Keep the driver in persistence mode so it does not drop its state between jobs. Remove a stale clock lock that an old script may have left behind. Then lock the clock to a steady value. The alert counts unique frequencies, which turns a visual jitter into a number you can watch. Check the lock after every change, because a lock that is not applied looks exactly like no lock at all.

3. Runbook Family 3: PCIe Down-Training, NCCL Stragglers, NVLink Degradation, and ECC Storms​

3.1 PCIe link down-training and DMA faults​

Picture a node where one GPU's data transfers take twice as long as its neighbours, and nothing in the logs says so loudly. The GPU works, the job runs, and the only symptom is a slow input path. A PCIe riser is the small board that carries the slot to the GPU, and a retimer is a chip that cleans up the signal on a long link. When a PCIe riser card loosens due to thermal cycling or a retimer experiences electrical noise, the PCIe link silently negotiates a slower generation speed or narrower lane width instead of crashing outright. Generation and lane width together set how much data the link can carry, so a link that falls back to a slower mode carries less data every second. Host-to-device batch transfers and checkpoint writes suddenly stall, dragging down training throughput across every GPU in the job. Checking the PCIe replay counter, benchmarking host-to-device copy speed, and inspecting negotiated link status in lspci isolates a down-trained PCIe slot in under a minute.

After draining the node, you can often recover full PCIe Gen4 x16 speed without rebooting the host by removing the PCIe device node in sysfs and triggering a bus rescan. Always re-verify the negotiated link state in lspci -vvv and bandwidthTest throughput before returning the node to scheduling.

3.2 Hunting the single straggler behind an NCCL timeout​

Picture a log wall. Every rank prints the same timeout trace at the same second, and the message looks like a network failure across the whole job. The reflex is to check cables and switches. When a distributed training job aborts with an NCCL operation timeout, almost every rank prints a timeout stack trace at the exact same moment. Operators who react by swapping network cables or raising the collective timeout to six hours waste time because an NCCL timeout almost never means all network switches died simultaneously. Instead, one rank failed to arrive at a synchronous collective barrier while all healthy ranks waited for it. The healthy ranks are the ones that report the timeout. The rank that never arrived is the one to find, and the job's own counters can show you which one it is.

To find the straggler, inspect NCCL_DEBUG=INFO with NCCL_DEBUG_SUBSYS=COLL or query the RAS subsystem in NCCL 2.24 and newer. If ranks freeze at completely different, non-converging operation count values, the Python script has a divergent conditional branch calling different collectives on different ranks. If all ranks except one reach operation 4821 while Rank 3 lags at operation 4820, Rank 3 is the straggler.

The mermaid flow above is the order to follow. Each question has one of two answers, and each answer points to one next check, so you never need to guess. Pick the branch the counters point to, and only then open the next layer.

Next, check whether Rank 3 is starved upstream of the GPU or slowed inside the GPU or fabric. Upstream means the data pipeline before the GPU, such as storage and the loader. Fabric means the NVLink and network path between GPUs. Note that NCCL has no NCCL_TIMEOUT environment variable; collective timeouts are configured in PyTorch via dist.init_process_group. Also remember to place per-rank iteration timers after torch.cuda.synchronize() and before dist.all_reduce, because timing after the collective includes the time fast ranks spent waiting for the slow rank.

3.3 ECC storm escalation math and automated job-stop thresholds​

Because Single-Bit ECC errors are corrected in hardware, operators sometimes let a training job continue running while a GPU experiences an accelerating ECC storm of hundreds of errors per hour. The job still looks fine on the surface, because each error is fixed as it happens. The danger is the rate. A storm is a rate that keeps climbing, and each step up makes the next uncorrectable error more likely. Waiting for a fatal Double-Bit Error or waiting until model validation accuracy collapses wastes hours of cluster compute on a dying HBM stack. The better habit is to decide the threshold before the storm starts, and to let a rule act on the rate automatically.

In the ECC storm postmortems, a training run on GPU 0 saw its ECC rate jump from 1 error per hour at 15:00 to 100 errors per hour by 15:30. By 16:15 the rate reached 400 errors per hour and validation accuracy dropped from 92% to 85% before a human stopped the job at 16:20. Enforcing an automated rate-based stop policy halts the job and drains the GPU at 15:30, saving 45 minutes of wasted training. Also remember that user applications cannot carve out specific bad physical HBM addresses in software. If the Hardware Row Remapper does not absorb the errors, the GPU must be RMA'd.

The accuracy drop is the last thing to change, so waiting for it means the cluster has already spent the time and the model has already been affected. Automate the stop at the escalation tier, and keep the human review for the decision about the GPU afterward.

4. Runbook Family 4: Cross-Layer Diagnosis — When Metrics Lie​

4.1 Multi-failure evidence priority and the 7-stage synchronous breakdown​

Picture the incident channel at its busiest. One node reports an ECC warning, a thermal alert and a collective timeout, all within the same few minutes, and every person in the channel picks a different signal to chase. The noise is the problem. During a complex production incident, a single node can simultaneously report ECC or Xid errors, thermal throttling, and NCCL collective timeouts. Investigating those signals in the wrong order wastes hours chasing downstream symptoms or saving a checkpoint whose weights are already corrupted. Always evaluate multi-failure evidence in strict priority order: Data Integrity first, Hardware Performance Cause second, and Downstream Communication Symptom third.

Priority RankFailure Domain & SignalsWhy It Ranks Here
Priority 1: Data IntegrityUncorrectable ECC / Xid 48, 95, 64 & ECC storm countersMemory corruption invalidates model weights and checkpoints; the node must be drained regardless of thermal or network status.
Priority 2: Hardware Performance CausePERFORMANCE throttle bitmask (HW Thermal Slowdown, HW Power Brake) & TEMPPhysical throttling slows one rank's execution, which directly causes the collective delay.
Priority 3: Downstream Communication SymptomNCCL timeout & per-rank opCount lagThe collective hang is the downstream consequence of the slow or dead rank identified in Priorities 1 and 2.

When GPU utilization, power, and temperature all look healthy yet end-to-end training is slow, aggregate dashboards cannot tell you which layer is stalling the step. Insert torch.cuda.synchronize() barriers around all seven stages of a single training iteration. That instrumentation measures the exact millisecond share of CPU data loading, PCIe transfer, GPU forward, backward, loss, and optimizer math, and network all-reduce.

Read the seven stages as a budget for one iteration. Each row is a slice of the step, and the shares add up to the whole. In the breakdown below, all four GPU compute stages combined consume only 14.4% of the 750.00 ms step. That measurement proves that rewriting CUDA kernels would save almost nothing while 60.0% sits in CPU data loading. The lesson is about where to spend effort. A team that starts with kernel tuning would be polishing the smallest slice, while the largest slice waits for a data pipeline fix.

4.2 Five classic "lying metrics" scenarios and Profiler Heisenbugs​

Dashboards and profilers can actively deceive engineers when a metric measures the wrong hardware concept, when a dead exporter is masked by a fleet average, or when the profiler itself slows down the workload. Attaching a heavyweight tracer or running nvidia-smi in a tight shell loop introduces a Profiler Heisenbug that alters CPU and GPU scheduling and cuts throughput by 10% to 50%. A heisenbug is a problem that changes when you observe it, and the observer here is the profiler itself. The fix is to measure with the cheapest tool that answers your question, and to measure the overhead of that tool before you trust its numbers.

The table below catalogs the five classic "lying metric" scenarios, along with the cross-layer evidence that exposes the truth. Checkpoint questions (20)​

1. When nvidia-smi reports 0 MiB total memory on GPU 0 and 81,920 MiB on GPU 1 of the same node, what does the peer comparison immediately rule out, and what is the primary root cause?

Because GPU 1 on the same host reports its full 81,920 MiB capacity, a node-wide kernel driver installation failure is ruled out immediately. The primary root cause on GPU 0 is MIG mode enabled with zero GPU Instances created. When nvidia-smi mig -lgi returns empty, no memory can be allocated on the parent device.

2. How do you identify and clear a zombie CUDA context that holds 71,234 MiB of GPU memory with no visible OS process?

Query compute applications with nvidia-smi to find the PID holding 71,234 MiB, and check ps to confirm the OS process exited without releasing its GPU context. Reclaim the memory with sudo fuser -k /dev/nvidia0 or sudo nvidia-smi --gpu-reset -i 0.

3. Why does a routine kernel patch cause nvidia-smi to fail across an entire maintenance batch, and how do you fix it without another reboot?

The patching pipeline updated the Linux kernel package and rebooted before DKMS rebuilt nvidia.ko against the new kernel headers. Checking dkms status shows the module registered only for the previous kernel. Running dkms autoinstall builds and loads the module for the running kernel immediately without requiring a second reboot.

4. Why can Kubernetes GPU pods work normally on a node while Slurm container jobs report no devices found?

Kubernetes uses the NVIDIA Container Toolkit or CDI path, whereas Slurm Pyxis and Enroot rely on /etc/enroot/hooks.d/*nvidia* to bind-mount driver libraries and device nodes into the rootless container. If that hook file is missing after a node image update, GPU visibility variables are unset inside Enroot containers.

5. Why can't temperature, clock, and power readings distinguish thermal throttling from power limiting on their own?

Lowering clock frequency automatically reduces dynamic power draw regardless of why the clock dropped. To prove whether heat or power triggered the reduction, inspect the hardware throttle reason bitmask via nvidia-smi -i 0 -q -d PERFORMANCE and DCGM_FI_DEV_CLOCK_THROTTLE_REASONS.

6. Why does fan speed query return N/A on H100 SXM5, H100 PCIe, and L40S GPUs, and how do you inspect their cooling fans?

Data-center HGX and DGX SXM modules and passively cooled server PCIe cards do not have GPU-mounted fans. Their airflow is provided by server chassis fans controlled by the Baseboard Management Controller. Query chassis fan RPMs via IPMI or Redfish using ipmitool sdr type Fan to spot a stuck 0 RPM fan.

7. Contrast a healthy GPU temperature rise rate under load against a stuck-fan rise rate, and state the Prometheus alert rule from the fan postmortem.

A healthy GPU rises at roughly 0.05°C/sec and plateaus below 80°C. A GPU with a failed fan or degraded thermal interface rises at 0.20 to 0.30°C/sec over 60 seconds, or 0.93°C/sec during a 30-second burn test. Alert proactively when deriv(gpu_temp[1m]) > 0.15 holds for 10 minutes.

8. How do you size PSU capacity for four 300 W A100 GPUs, and what auxiliary voltage reading confirms a PSU brownout sag?

Include 30% PSU headroom so four 300 W GPUs require at least 1,560 W of PSU capacity, and cap total node GPU power at 80% of PSU capacity. On the 12V auxiliary rail, a sensor reading below 11.4 V such as 10.8 V confirms voltage sag under peak Tensor Core load.

9. When GPU clocks oscillate between 1,980 MHz and 800 MHz at a cool 65°C with zero active throttle reasons, what is happening and how do you fix it?

Short idle gaps between bursty data loader batches allow firmware DVFS to downshift from state P0 into lower power states P2 or P3. Enable persistence mode, set the host CPU governor to performance, and lock graphics clocks with sudo nvidia-smi -i 0 -lgc 1800.

10. What throughput and lspci fields indicate PCIe Gen4 x16 down-training, and how do you retrain the link without rebooting?

Healthy PCIe Gen4 x16 delivers 20 to 26 GB/s in bandwidthTest, with a weekly gate of 17.6 GB/s. Measuring 2.3 GB/s with 127 PCIe replays while lspci -vvv shows Gen3 x8 in LnkSta confirms link degradation. Remove the PCIe device node and trigger a sysfs bus rescan to retrain the link without rebooting.

11. How do you use NCCL debug logs or RAS in NCCL 2.24+ to distinguish a starved straggler rank from an application-level collective deadlock?

In a starved straggler scenario, most ranks converge on the latest operation count such as 4821 while one rank lags behind at 4820. In an application code deadlock from a divergent conditional branch, ranks freeze permanently at different, non-converging operation counts because different ranks called different sequences of collectives.

12. In the NCCL timeout incident, why was Rank 3 stuck at operation 4820 with 2% GPU utilization, and what was the underlying storage cause?

Rank 3's GPU was healthy with zero Xids and 78.3 W power draw, but it starved waiting 47.31 seconds for the data loader. Its local /data volume was 96% full due to uneven dataset sharding. Specifically, Rank 3's shard was 187 GB versus 41 GB on Rank 0, or 4.56x larger.

13. Why must per-rank iteration timers be placed before dist.all_reduce, and how do you localize a slow GPU using nccl-tests?

Because dist.all_reduce synchronizes all ranks, post-collective timers include the time fast ranks spent waiting for the straggler, making every rank look equally slow. Synchronizing and timing before the collective exposes the 10.02x straggler ratio on GPU 2. Because all_reduce_perf prints one summary row per size, run 2-GPU subsets and check nvidia-smi nvlink --status to spot degraded or failed links.

14. In the ECC storm postmortem, at what timestamp and error rate should automated monitoring have stopped the job before accuracy dropped from 92% to 85%?

Monitoring should have stopped the job at 15:30, when 50 errors accumulated in 30 minutes for a rate of 100 errors per hour. That threshold fired 45 minutes before validation accuracy dropped from 92% to 85% at 16:15. The automated policy logs fewer than 1 error per hour as normal, schedules maintenance at 1 to 10 per hour, and immediately drains the GPU above 10 per hour.

15. When a GPU simultaneously exhibits ECC/Xid errors, thermal throttling, and NCCL hangs, in what priority order must you evaluate the evidence and why?

First, evaluate Data Integrity across uncorrectable ECC and Tier 3 Xids, because memory corruption invalidates outputs and mandates an immediate node drain regardless of other findings. Second, evaluate Hardware Performance Cause using the throttle bitmask and temperature, which explains why one rank slowed down physically. Third, evaluate Downstream Symptom in NCCL operation lag, which is the consequence of the slow or dead rank.

16. Walk through the 7-stage synchronous iteration breakdown (750.00 ms total), and explain why optimizing GPU kernels would be wasted effort on that workload.

In the 750.00 ms iteration, CPU data loading takes 450.00 ms or 60.0%, and network all-reduce takes 150.00 ms or 20.0%. All four GPU compute stages combined take only 108.00 ms or 14.4%, plus 10.00 ms for PCIe copy. Even a 2x faster GPU kernel would save less than 8% of step time while 60% sits in CPU data loading.

17. How can nvidia-smi report 100% GPU utilization while actual throughput is only 200 samples/sec instead of 1,000 samples/sec?

Both nvidia-smi and PyTorch utilization queries report the percentage of sampling intervals during which any context was active on the GPU. That metric stays near 100% even when the GPU is idle 90% of the time waiting between slow CPU kernel launches at 50 kernels/sec instead of 1,000+ kernels/sec. Capturing CUDA Graphs eliminates the CPU launch gap.

18. What is a Profiler Heisenbug, what overheads did nvidia-smi polling and nsys introduce in the Chapter 12 benchmark, and how do you order tools by overhead?

A Profiler Heisenbug occurs when measurement overhead alters application behavior, dropping throughput from 500 samples/sec unprofiled to 450 samples/sec (-10%) with a 1-second nvidia-smi loop and 250 samples/sec (-50%) under nsys. Order tools from lowest to highest overhead: Python time.perf_counter(), DCGM, nvidia-smi polling, Nsight Systems, and heavyweight CPU instrumentation.

19. How do stale green Grafana dashboards and masked fleet averages deceive operators into thinking a broken GPU fleet is healthy?

In a stale green panel, when Prometheus stops scraping a dead target, Grafana continues rendering the last scraped value inside the panel window. That behavior looks like a steady green plateau unless you alert on sample age and target up status. In a masked fleet average, a panel plotting average GPU utilization across the fleet silently drops any node whose exporter is down. You must alert on the count of down targets so dead nodes are not hidden.

20. How do a broken Slurm NHC virtualenv and an SELinux device block silently disable GPU health monitoring?

In the false-green Slurm NHC case, a package update breaks a Python import inside the healthcheck virtualenv. A catch-all wrapper then exits 0 on exceptions and marks nodes with active Xid faults as healthy. In the SELinux block case, an OS hardening baseline lacks an SELinux type mapping for a GPU device node. Enforcing mode silently denies exporter reads without logging an application error, requiring ausearch -m avc -ts recent and audit2why to diagnose.
